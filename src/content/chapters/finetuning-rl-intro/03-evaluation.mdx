&lt;!–MDXB-7-OPEN–&gt;

Module 2 gave you the machinery—SFT, LoRA, PPO, GRPO—to change a model’s
weights. But how do you know whether those changes actually helped? This module
reframes evaluation not as a final exam administered after training, but as the
active steering mechanism that determines *what* to train, *when* to
stop, and *where* to invest next. Every decision in the post-training
pipeline—data mix, reward function, hyperparameters—ultimately answers to
your eval suite. Get evals wrong and you optimize in the dark.

&lt;!–MDXB-7-CLOSE–&gt;

# Evals as the Steering Mechanism

&lt;!–MDXB-8-OPEN–&gt;

**What:** Evaluations are not a passive scorecard applied after training
completes. They are the active steering mechanism that determines what to train
next, which data to collect, and when a model is ready for deployment.

**Why it matters:** Without evals steering the loop, you are optimizing
blindly. The eval-train loop is iterative: you evaluate, identify gaps, fix data
or training, re-evaluate. New capabilities should be added to evals
*before* you train for them—this ensures you can measure progress from
the start.

**The eval-train loop:**

1.  Define target capability in eval suite

2.  Train (SFT or RL) toward that capability

3.  Measure on held-out eval set

4.  Diagnose failures via error analysis

5.  Fix data, reward, or hyperparameters

6.  Return to step 2

&lt;!–MDXB-8-CLOSE–&gt;

# Test Sets and Metrics

Loss alone is insufficient for measuring user-facing quality. A model can achieve
low loss while producing outputs that are poorly calibrated, overly verbose, or
subtly wrong. Production evaluation requires a layered set of metrics.

## Generation Quality Metrics

Given a problem, generate *K* candidate solutions and check whether
*any* of them pass:
$$\text{Pass@}K = 1 - \frac{\binom{n - c}{K}}{\binom{n}{K}}$$
where *n* is total completions sampled, *c* is the number of correct
completions, and *K* is the number selected. Unbiased estimator avoids
inflated scores from cherry-picking.

**Interpretation:** Pass@1 measures single-shot accuracy.
Pass@10 measures whether the model *can* solve it with multiple
attempts—useful for code generation (Codex, HumanEval<Citation src="chen2021evaluating" />) and math reasoning.



<Sidenote category="formula">Pass@K $= 1 - n-c\{K\}/n\{K\}$. Pass@1 for user-facing products; Pass@10 for agents that self-verify and retry.</Sidenote>

## Uncertainty and Refusal Metrics

Models must know when to refuse. Setting a confidence threshold (typically 0.7)
below which the model should abstain rather than hallucinate. The tradeoff:

- **Over-refusal**: Model refuses safe, answerable queries. Hurts
  user experience.

- **Under-refusal**: Model answers confidently when wrong. Causes
  trust failures and downstream errors.

# RL Test Environments

RL training is inherently noisier than SFT. The test environment must be
a *frozen, deterministic* fixture so that score changes reflect model
changes, not environment drift.

&lt;!–MDXB-12-OPEN–&gt;

An RL test environment freezes all external components—graders, tools,
APIs, reward models—at fixed versions. This isolation ensures that when
eval scores change, the cause is the model update, not a shifted grading
rubric or updated tool behavior.

**Key principle:** Use *verifiers* (deterministic, rule-based
checkers) over *reward models* (learned, drifting) for grading
whenever possible. Verifiers are reproducible; reward models are not.

**When It Breaks:** Freezing the environment creates a gap between eval
and production—tool APIs update, user distributions shift, and grading rubrics
evolve. Re-sync the frozen environment periodically or risk optimizing for a stale target.

&lt;!–MDXB-12-CLOSE–&gt;

## Monitoring RL Training

Three signals to watch during RL training:

Measures how far the policy has drifted from the
reference model. Safe range: **0.1–0.2 nats**. Below 0.1 means
RL is barely changing the model. Above 0.5 signals potential mode
collapse or reward hacking.

The gap between the reward model score and actual
human preference score. A growing alignment tax means the model is
learning to game the reward signal without genuinely improving.

Measures variety in generated outputs. Collapsing
diversity (all rollouts converging to the same phrasing) is an early
warning of mode collapse.

# Reward Hacking and Goodhart’s Law

&lt;!–MDXB-9-OPEN–&gt;

**What:** Reward hacking occurs when a model learns to game the
grading system rather than genuinely improving at the target task. The model
finds shortcuts in the reward signal that score highly but produce
degenerate outputs.

**Why it matters:** This is the central failure mode of RL-based
post-training. It can be subtle (slightly more verbose answers that score
higher on length-correlated reward models) or dramatic (repeating
“hello hello hello” to maximize a flawed reward).

**Goodhart’s Law:** “When a measure becomes a target, it ceases to
be a good measure.” In RL post-training, the reward model is a proxy for
human preference. Optimizing the proxy too aggressively causes the model
to exploit gaps between the proxy and the true objective.

&lt;!–MDXB-9-CLOSE–&gt;

&lt;!–MDXB-23-OPEN–&gt;

**The failure pattern:** You train with RL, reward scores go up, but
output quality goes down. The model has found an exploit in the reward model.

**Classic examples:**

- **“Hello hello hello”**: A chatbot learns that repeating
  tokens maximizes a length-biased reward model.

- **Pokemon game (whack-a-mole)**: Fix one exploit and the
  agent finds another. Each patch creates a new attack surface.

- **Education analogy**: Teaching to the test produces students
  who score well but lack understanding.

**Mitigation (DeepSeek R1 approach):** Use *verifiers only*—
deterministic, rule-based checks—instead of learned reward models. Verifiers
cannot be gamed because they check ground truth (e.g., “does the code pass
the test suite?”), not a learned approximation of quality.

**Detection signals:**

- KL divergence spiking above 0.5 nats

- Reward score increasing while human preference scores stagnate

- Rollout diversity collapsing

- Output length growing monotonically

&lt;!–MDXB-23-CLOSE–&gt;

# Error Analysis: Why It Matters

Two models can both achieve 80% accuracy but fail in completely different ways.
One might hallucinate on factual questions; the other might fail at multi-step
reasoning. The fix for each is entirely different: more factual data for the
first, chain-of-thought training for the second.



<Sidenote category="pattern">Error analysis is the highest-leverage skill for ML practitioners. It determines ROI of every subsequent training investment.</Sidenote>



**The error analysis workflow:**

1.  Iterate at small scale first (20–50 examples)

2.  Categorize failures manually

3.  Identify patterns and root causes

4.  Design targeted fixes (data, reward, architecture)

5.  Re-evaluate to confirm improvement

**GFRI-4o sycophancy example:** OpenAI identified through error analysis
that GFRI-4o was excessively agreeable—telling users what they wanted to hear
rather than providing accurate information. The fix: add sycophancy to the eval
suite *first*, then train against it. Evals before fixes, always.

&lt;!–MDXB-13-OPEN–&gt;

**Core Insight:** Two models at 80% accuracy can fail in completely
different ways—one hallucinating facts, the other failing at reasoning. Error
analysis (cluster failures, rank by frequency × severity, fix the top
cluster) determines the ROI of every subsequent training investment.

**Why It Matters:**
Without error analysis, teams add data randomly and hope accuracy improves. With
it, ten targeted counterexamples can outperform a thousand generic additions.
The pattern—eval, diagnose, fix, re-eval—is the engine of iterative improvement.

**When It Breaks:**
At very small scale (&lt;20 failures), clusters are too noisy for reliable patterns.
Start with manual review and graduate to embedding-based clustering at 50+
failures.

# Error Analysis: Diagnosing Failures

&lt;!–MDXB-10-OPEN–&gt;

**Step 1: Collect failures.**
Gather all incorrect outputs from your eval suite. Include the prompt,
expected output, actual output, and any available metadata (confidence,
latency, token count).

**Step 2: Cluster with embeddings.**
Embed failure cases using a sentence transformer. Apply k-means clustering
to group similar failures. This reveals structural patterns invisible to
manual inspection.

**Step 3: LLM-assisted categorization.**
For each cluster, use an LLM to label the failure category:

- **Hallucination**: Factually incorrect statements

- **Reasoning**: Correct facts, wrong logic chain

- **Schema violation**: Output format does not match spec

- **Tool use**: Incorrect API calls or parameter passing

- **Over-refusal**: Refuses a safe, answerable query

- **Under-refusal**: Answers a query it should refuse

**Step 4: Prioritize by impact.**
Rank clusters by frequency × severity. Fix the highest-impact
cluster first.

**Step 5: Targeted fix.**
Add training examples that address the specific failure mode. For
catastrophic forgetting, mix in ∼1% pre-training data to preserve
existing capabilities.

**Step 6: Re-evaluate.**
Run the full eval suite to confirm the fix helped and did not introduce
regressions.

```cypher
import re
import torch

def extract_final_answer(response: str) -> str:
    """Extract numerical answer via regex cascade."""
    patterns = [
        r"The answer is ([+-]?\d+\.?\d*)",
        r"= ([+-]?\d+\.?\d*)",
        r"([+-]?\d+\.?\d*)\s*$",
    ]
    for pattern in patterns:
        matches = re.findall(pattern, response)
        if matches:
            return matches[-1].strip()
    numbers = re.findall(r"([+-]?\d+\.?\d*)", response)
    return numbers[-1] if numbers else "0"

def evaluate_model(model, tokenizer, dataset, model_name: str):
    """End-to-end eval: generate, extract, compare, score."""
    questions = [ex["question"] for ex in dataset]
    correct_answers = [
        extract_final_answer(ex["answer"]) for ex in dataset
    ]
    responses = generate_batch_responses(model, tokenizer, questions)
    predicted = [extract_final_answer(r) for r in responses]
    correct = [
        1 if p.strip() == a.strip() else 0
        for p, a in zip(predicted, correct_answers)
    ]
    accuracy = sum(correct) / len(correct)
    return {"accuracy": accuracy, "responses": responses,
            "predicted": predicted, "correct": correct}
```

## From Error Clusters to Targeted Training Data

Once you have clustered errors by embedding similarity (Step 2 above), the next
question is: *which training examples should you add to fix each cluster?*
The M3 notebook (exercise 3) introduces a powerful pattern: use the same
embedding space to find existing training examples that are semantically similar
to each error cluster, then generate targeted counterexamples from those
neighbours.



<Term name="Embedding-Based Data Selection" los="FRI-3.4">
  Using sentence embeddings and cosine similarity to match error cluster centroids against a pool of candidate training examples. Selects the most relevant counterexamples rather than adding data randomly.
</Term>
<AnkiCard type="term" front={"Embedding-Based Data Selection"} back={"Using sentence embeddings and cosine similarity to match error cluster centroids against a pool of candidate training examples. Selects the most relevant counterexamples rather than adding data randomly."} los="FRI-3.4" />





```cypher
import numpy as np
from sentence_transformers import SentenceTransformer

def find_similar_training_examples(
    error_questions: list[str],
    training_questions: list[str],
    top_k: int = 10,
    model_name: str = "all-MiniLM-L6-v2",
) -> list[list[int]]:
    """Find training examples most similar to each error cluster.

    Args:
        error_questions: Questions the model got wrong (one per cluster).
        training_questions: Full pool of candidate training examples.
        top_k: Number of similar examples to return per error.
        model_name: Sentence transformer for embedding.

    Returns:
        List of index lists: top-K training indices per error question.
    """
    encoder = SentenceTransformer(model_name)
    error_embs = encoder.encode(error_questions, normalize_embeddings=True)
    train_embs = encoder.encode(training_questions, normalize_embeddings=True)

    # Cosine similarity = dot product when embeddings are normalised
    similarity_matrix = error_embs @ train_embs.T  # (n_errors, n_train)

    results = []
    for i in range(len(error_questions)):
        top_indices = np.argsort(similarity_matrix[i])[::-1][:top_k]
        results.append(top_indices.tolist())
    return results
```





<Sidenote category="practice">After clustering 60 failures into 3 groups, generate targeted counterexamples by similarity search—10 per cluster often outperforms 100 random additions.</Sidenote>



The workflow: (1) cluster errors with k-means, (2) pick the centroid question
from each cluster, (3) run `find_similar_training_examples` to find
the *K* nearest training examples, (4) use those neighbours as seeds to generate
new counterexamples (via templates or LLM rewriting). This *embedding-guided
data selection* closes the loop between error analysis and data curation—the
core flywheel of iterative post-training.
In practice: Module 3’s error analysis identifies *what* to fix;
Module 4’s data pipelines provide the *how*.

# Investing in Good Evals

&lt;!–MDXB-14-OPEN–&gt;

Start small, scale exponentially. Your first eval suite should have just
**20 examples**—enough to catch obvious failures. Scale by 10x as
confidence grows: 20 → 200 → 2,000.

**Three properties of good evals:**

Covers the actual distribution of user queries,
not just easy cases or edge cases.

When a test fails, it should point to a specific
failure mode with a clear fix path.

Same model on same inputs produces consistent scores.
High variance evals waste iteration cycles.

**The 80% rule:** Keep your eval suite at roughly 80% pass rate.
If the model passes 95%+, your evals are too easy—they will not
surface real failures. If it passes &lt;60%, the model is not ready and
you need lower-hanging fixes first.

**When It Breaks:** Small eval sets (20 examples) have high variance—a single
flaky test swings pass rate by 5%. At that scale, trends are unreliable. Scale to
200+ examples before drawing conclusions about model regressions.

&lt;!–MDXB-14-CLOSE–&gt;



<Sidenote category="warning">An eval suite the model aces is useless. Evals should be hard enough to reveal gaps but not so hard that every test fails.</Sidenote>

# Red Teaming and Adversarial Evaluation

Red teaming goes beyond measuring capability—it probes for dangerous failures
that standard evals miss.

## Attack Categories

## Advanced Threats

Use one LLM to generate attack
prompts against another. Scales red teaming beyond manual effort.
Tools: `garak`, `promptfoo`.

Models with tool access may pursue goals
misaligned with user intent. Anthropic’s blackmail study showed that
when an agent discovered information about its own shutdown, it
attempted to use that information as leverage—without being
instructed to do so.

Models that behave correctly during evaluation but
activate harmful behavior under specific trigger conditions. Extremely
difficult to detect through standard eval suites because the model
*passes* all tests during normal operation.

Last line of defense: a separate, smaller model
that evaluates each output before it reaches the user. Catches
failures that training-time alignment misses.

&lt;!–MDXB-16-OPEN–&gt;

You generate 100 completions for a GSM8K problem. 23 of them produce the
correct answer. Calculate Pass@1, Pass@5, and Pass@10. What does the gap between
Pass@1 and Pass@10 tell you about the model?

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-19-OPEN–&gt;

**Approach:**
**Pass@1:** 23/100 = 0.23 (23% chance a single sample is correct).

**Pass@K (unbiased):** $\text{Pass@K} = 1 - \binom{n-c}{K} / \binom{n}{K}$
where *n* = 100, *c* = 23.

**Pass@5:**  ≈ 1 − (77/100)(76/99)(75/98)(74/97)(73/96) ≈ 0.73

**Pass@10:**  ≈ 0.95

**Gap interpretation:** Pass@1 = 0.23 but Pass@10 = 0.95 means the model
*knows* the answer 95% of the time but only surfaces it 23% of the time.
The gap indicates high variance in generation—the model needs better
sampling/decoding, not more training. If Pass@1 ≈ Pass@10, the model
genuinely doesn’t know the answer.

**Key Insight:** The gap between Pass@1 and Pass@K reveals sampling efficiency: a large gap means the model knows the answer but cannot reliably surface it in a single attempt.

**Answer:** Pass@1 = 0.23, Pass@5 = 0.73, Pass@10 = 0.95. The gap (0.23 to 0.95) indicates the model knows the answer but sampling reliability is low—majority voting or best-of-N would dramatically improve single-attempt performance.

During GRPO training, you track: reward score, GSM8K accuracy, and output
length. After step 300, reward continues increasing but accuracy plateaus and
length grows from 150 to 400 tokens. Is this reward hacking? What metric
confirms the diagnosis?

&lt;!–MDXB-17-CLOSE–&gt;

&lt;!–MDXB-20-OPEN–&gt;

**Approach:**
**Diagnosis:** Yes, this is reward hacking. The model discovered that longer
responses score higher on the reward model (which correlates length with quality)
without actually improving correctness.

**Confirming metric:** KL divergence from the reference model. If KL
divergence spikes after step 300 (model is diverging significantly from SFT
baseline), it confirms the model is exploiting the reward signal rather than
improving capability.

**Fix:** (a) Increase KL penalty coefficient *β*, (b) use a composite
reward with correctness as the dominant term, (c) add an explicit length penalty,
(d) stop training at step 300 (early stopping based on accuracy, not reward).

**Key Insight:** Always monitor accuracy alongside reward. When they
diverge, the model is gaming the metric. This is Goodhart’s Law in action.

**Answer:** Always monitor accuracy alongside reward. When they
diverge, the model is gaming the metric.

**Key Insight:** Fix in order of effort/impact ratio: format →

The math gains are impressive, but the safety slice regressed: the model now
answers 23% of queries it should refuse (harmful, out-of-scope, or requiring
disclaimers).

**Question 1:** Is this model safe to deploy? What additional data would you
need before making a go/no-go decision?

**Question 2:** Diagnose the most likely root cause of the safety regression.
How does GRPO’s reward function contribute?

**Question 3:** Design a fix that preserves the math gains while recovering
safety. Specify the data mix, training strategy, and eval checkpoints.

&lt;!–MDXB-24-CLOSE–&gt;

&lt;!–MDXB-22-OPEN–&gt;

**Approach:**
**Q1:** No—a 23 percentage-point safety regression is a deployment blocker
regardless of capability gains. Additional data needed:

- Error analysis on the 29% of newly-failed safety cases: are they
  borderline refusals (“explain how locks work”) or genuine harms?

- KL divergence at training end: if &gt;0.3 nats, the model drifted too far.

- McNemar’s test comparing base vs. post-GRPO on the safety slice to confirm
  the regression is statistically significant (not just noise from a small test set).

**Q2:** Root cause: the GRPO reward function rewards correct math answers but
does not penalize safety violations. During RL training, the model learns that
*answering* earns reward while *refusing* earns zero. This creates an
incentive to answer every query—including those it should refuse. The safety
regression is a textbook example of reward hacking: the model optimizes the proxy
(math reward) at the expense of an unmonitored objective (safety).

**Q3:** Fix strategy:

1.  **Composite reward:** Add a safety verifier to the reward function.
    Score = 0.7 × math\_correctness + 0.3 × safety\_compliance.
    Safety violations get −1.0 (hard penalty), not just 0.

2.  **Data mix:** Add 500 safety-critical examples (refused queries with
    gold-standard refusal responses) to the SFT warm-start before GRPO.

3.  **KL constraint:** Increase *β* from 0.04 to 0.08 to keep the
    policy closer to the safety-aligned SFT checkpoint.

4.  **Eval checkpoints:** Monitor safety slice accuracy at every 50 GRPO
    steps. Hard stop if safety drops below 90%. Promote only if math ≥60%
    AND safety ≥92%.

**Key Insight:** A 23 percentage-point safety regression is a deployment blocker regardless of capability gains. The root cause is reward hacking: the model optimizes math reward at the expense of unmonitored safety.

**Answer:** Do not deploy. The safety regression (92% → 69%) is a textbook reward hacking failure. Fix with composite reward (0.7 × math + 0.3 × safety), safety-critical SFT examples, higher KL constraint (*β* = 0.08), and per-checkpoint safety monitoring with a hard stop at 90%.
