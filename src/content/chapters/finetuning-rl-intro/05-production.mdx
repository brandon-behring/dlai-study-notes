loop by asking: how do you ship all of this reliably? We move from training notebooks to

# Production Pipeline: DeepSeek R1



<Sidenote category="interview">"Walk me through an end-to-end post-training pipeline" is a top-5 MLE interview question at frontier labs.</Sidenote>



&lt;!–MDXB-5-OPEN–&gt;

**What:** A production post-training pipeline chains multiple stages—cold-start SFT,
reinforcement learning, rejection sampling, data filtering, and final fine-tuning—into a
reproducible workflow where each stage feeds the next.

**Why:** No single training run produces a production-ready model. Each stage addresses
a different failure mode: SFT teaches format, RL teaches reasoning, rejection sampling curates
quality, and the final stages consolidate gains across domains.

&lt;!–MDXB-5-CLOSE–&gt;

## R1 Zero: Pure RL Baseline

DeepSeek R1 Zero demonstrates that pure RL *without any SFT data* can produce
reasoning capability. The key ingredients:

- **Algorithm:** GRPO (Group Relative Policy Optimization)<Citation src="shao2024deepseekmath" />—no critic network,
  group-level baselines from sampled completions.

- **Verifiers:** Two reward signals—a math verifier (exact answer match) and a
  code verifier (test case execution). No learned reward model.

- **Results:** AIME accuracy improved from 15.6% to 86.7%.

- **Emergent behavior:** The model spontaneously developed chain-of-thought
  reflection (“wait, let me reconsider…”) without being trained on reasoning
  traces.

- **Limitation:** Capabilities remained confined to math and coding—domains
  where verifiers provide clean signal.

</Term>

## R1 Full Pipeline



<Sidenote category="pattern">Each stage in the R1 pipeline has a clear purpose. Map every stage in your own pipeline to a specific failure mode it addresses.</Sidenote>



&lt;!–MDXB-6-OPEN–&gt;

1.  **Cold-Start SFT** — Train on a small set of high-quality reasoning traces
    to give the model a stable starting point for RL. Avoids the language-mixing and
    formatting issues of R1 Zero.

2.  **RL with Language Consistency Reward** — Run GRPO with verifiers plus an
    additional reward term penalizing language switching mid-response.

3.  **Rejection Sampling** — Generate multiple completions per prompt from the
    RL-trained model. Keep only those that pass verification.

4.  **Filter to 600K Reasoning Examples** — Apply quality filters to curate the
    best reasoning traces from rejection sampling.

5.  **Combine with Non-Reasoning Data** — Merge 600K reasoning examples with
    ∼200K non-reasoning examples (general helpfulness, safety) to produce an 800K
    training set.

6.  **Final Fine-Tuning** — SFT on the combined 800K dataset to consolidate both
    reasoning and general capabilities.

7.  **Final RL** — One more round of RL to sharpen performance and enforce
    alignment constraints.

*Key insight:* The pipeline alternates between **exploration** (RL discovers new
strategies) and **consolidation** (SFT locks in what works). Each RL stage expands the
frontier; each SFT stage stabilizes it.

# Agents and Post-Training

&lt;!–MDXB-12-OPEN–&gt;

An **agent** is a model that takes actions in an environment—calling tools, planning
multi-step strategies, and coordinating with other agents. Post-training for agents differs from
standard instruction-following because the reward signal comes from *task completion*, not
from matching a reference output.

**When It Breaks:** Task-completion rewards are sparse and delayed—the agent may
complete many intermediate steps before receiving signal. This makes credit assignment
hard: RL struggles to learn which action in a 10-step plan caused the final failure.

&lt;!–MDXB-12-CLOSE–&gt;

## Three Pillars of Agent Post-Training



<Term name="Tool Use" los="FRI-5.2">
  Training a model to invoke external APIs, databases, or code interpreters rather than relying on parametric knowledge. Prefer tools over internal knowledge for factual lookups.
</Term>
<AnkiCard type="term" front={"Tool Use"} back={"Training a model to invoke external APIs, databases, or code interpreters rather than relying on parametric knowledge. Prefer tools over internal knowledge for factual lookups."} los="FRI-5.2" />



Tool Use  
Teach the model *when* and *how* to call external tools.
SFT on tool-use transcripts; RL rewards correct tool invocation and final-answer
accuracy. Principle: prefer tools over internal knowledge for factual queries.

Planning  
Multi-step decomposition. For SFT, train on chain-of-thought traces that
show the planning process. For RL, reward only the *final answer*—let the model
discover its own planning strategy.

Coordination  
Multi-agent systems where models hand off tasks. SFT on multi-agent
transcripts; RL with handoff rewards that incentivize clean task boundaries.



<Sidenote category="warning">Agent training data is hard to source. Live environments produce messy, non-stationary data that requires careful filtering.</Sidenote>



## Live Challenges

Production agents face challenges absent from offline training:

- **Updating state:** The environment changes between tool calls; the model must
  track what has already been done.

- **New context:** Information retrieved via tools may contradict the model’s
  parametric knowledge.

- **Messy data:** Real API responses include malformed JSON, timeouts, and
  partial results.



<Term name="Handoff Reward" los="FRI-5.2">
  An RL reward signal for multi-agent systems that incentivizes clean task boundaries—penalizing incomplete handoffs and rewarding successful delegation.
</Term>

# RL Promotion Rules



<Sidenote category="crossref">Connects to M3 evaluation (Ch. ): promotion rules are the deployment-time expression of your eval strategy.</Sidenote>



&lt;!–MDXB-7-OPEN–&gt;

**What:** Promotion rules are the gates a model must pass to move from development to
staging to production. They codify your risk tolerance as quantitative thresholds.

**Why:** Without formal gates, models get deployed based on vibes. Promotion rules make
go/no-go decisions reproducible and auditable.

&lt;!–MDXB-7-CLOSE–&gt;

## Frozen Test Environments



<Term name="Frozen Test Environment" los="FRI-5.3">
  A versioned, immutable evaluation suite used for promotion decisions. Never modify the test set between model candidates—add new tests in a separate version.
</Term>
<AnkiCard type="term" front={"Frozen Test Environment"} back={"A versioned, immutable evaluation suite used for promotion decisions. Never modify the test set between model candidates—add new tests in a separate version."} los="FRI-5.3" />



Promotion tests must be **frozen**: the same test set, same verifiers, same hardware.
If you change the test environment between candidates, you cannot compare results.

## Slices and Behavioral Groupings

A **slice** is a behaviorally meaningful subset of your test set (e.g., “multi-turn
math,” “safety refusals,” “long-context retrieval”). Slices enable targeted no-regression
checks.

## Dev to Staging Gates

- **Aggregate quality:** Overall metric must improve by a meaningful margin.

- **No-regression slices:** No slice may degrade beyond a defined threshold.

- **Strict safety caps:** Safety-critical slices have hard ceilings—any
  regression is a blocker.

- **Confidence intervals:** Improvements must be statistically significant, not
  noise.

- **Meaningful improvement:** The gain must justify the operational cost of
  deploying a new model.

- **Cost targets:** Inference cost per query must stay within budget.

## Staging to Production



<Term name="Shadow Deployment" los="FRI-5.3">
  Running a candidate model on live traffic without serving its outputs to users, comparing its responses against the production baseline.
</Term>
<AnkiCard type="term" front={"Shadow Deployment"} back={"Running a candidate model on live traffic without serving its outputs to users, comparing its responses against the production baseline."} los="FRI-5.3" />



1.  **Shadow deploy:** Run the candidate on 5K real requests over 24 hours.
    Compare outputs to the production baseline.

2.  **Canary traffic:** Route a small percentage (1–5%) of live traffic to the
    candidate. Monitor error rates, latency, and user feedback.

3.  **Full rollout:** Gradual traffic shift with automated rollback triggers.

# Data-Feedback Flywheel

&lt;!–MDXB-8-OPEN–&gt;

**What:** The data-feedback flywheel is a continuous loop: production errors become
training data that improves the model, which reduces errors, which surfaces subtler
failure modes, which become the next round of training data.

**Why:** A model that ships but never improves from production signal is a depreciating
asset. The flywheel is what separates a one-off deployment from a compounding system.

&lt;!–MDXB-8-CLOSE–&gt;

## Error Analysis Flow



<Sidenote category="interview">"How do you improve a deployed model over time?" — The data-feedback flywheel: errors $$ counterexamples $$ retrain $$ deploy. The loop is the product.</Sidenote>





<Sidenote category="practice">Set up weekly error triage meetings where the team reviews clustered failure modes and decides on interventions.</Sidenote>



1.  Collect production errors (user feedback, automated log mining).

2.  Cluster errors by failure mode (topic, error type, severity).

3.  Extract representative pairs (input, expected output).

4.  Prioritize by frequency × severity.

5.  Route to the appropriate intervention (see decision framework below).

## Feedback Collection

User feedback:  
Thumbs-up/down, free-text corrections, escalation to human agents.

Log mining:  
Automated detection of refusals, hallucinations, format violations.

Clustering:  
Group similar failures to identify systemic patterns vs. one-off
edge cases.

Pair extraction:  
Convert clustered failures into (prompt, ideal response) pairs
for SFT or (prompt, chosen, rejected) triples for RL.

## Data Hygiene

Before feeding production data back into training: filter low-quality examples, deduplicate,
check for demographic or topic bias, and scrub PII. Skipping any of these steps contaminates
your training set.

## Intervention Decision Framework

&lt;!–MDXB-9-OPEN–&gt;

*Rule of thumb:* Always try the fastest intervention first. Escalate only when the
simpler approach fails or the error pattern is systemic.

&lt;!–MDXB-9-CLOSE–&gt;

# Monitoring and Drift



<Sidenote category="interview">"How do you monitor a model in production?" Mention metrics, drift detection, and rollback—not just accuracy.</Sidenote>



## Three Metric Families

Performance:  
Task accuracy, response quality scores, safety violation rate.

Cost:  
Tokens per request, GPU utilization, cost per query.

Reliability:  
Latency p50/p95/p99, error rate, timeout rate.

## Version Control and Rollback

Every deployed model must have: a unique version identifier, the exact training config that
produced it, a pointer to the training data snapshot, and a one-command rollback path to the
previous version.

&lt;!–MDXB-10-OPEN–&gt;

Data drift:  
Input distribution shifts (new topics, new user demographics).
*Signal:* Embedding distance between recent inputs and training data increases.
*Fix:* Collect new data from the shifted distribution; retrain.

Reward collapse:  
The model finds a degenerate strategy that scores high on the
reward signal but produces poor outputs.
*Signal:* Reward metric stays high but user satisfaction drops.
*Fix:* Audit reward function; add diversity constraints; retrain with corrected
reward.

Infra-induced degradation:  
Quantization, batching changes, or hardware swaps
silently alter model behavior.
*Signal:* Quality drop correlates with infrastructure change, not data change.
*Fix:* Diff infrastructure configs; run regression suite on new hardware before
deployment.

Model forgetting:  
Fine-tuning on new data erodes performance on previously mastered
tasks.
*Signal:* Slice-level regressions on stable task categories.
*Fix:* Replay buffer—mix old data into new training batches.

&lt;!–MDXB-10-CLOSE–&gt;

&lt;!–MDXB-23-OPEN–&gt;

Reward collapse is insidious because your *automated metrics look fine*. The model has
learned to game the reward signal. Classic symptoms:

- Reward scores plateau or increase while user complaints rise.

- Output diversity drops—the model converges on a narrow set of “safe” responses.

- Length increases without information gain (the model pads responses).

**Defenses:** (1) Always monitor a human-judgment metric alongside automated rewards.
(2) Track output diversity (unique n-gram ratio). (3) Set SLOs on both reward *and*
user satisfaction—trigger rollback if they diverge.

&lt;!–MDXB-23-CLOSE–&gt;

## Testing Strategies

A/B testing:  
Gold standard for causal claims. Requires sufficient traffic.

Side-by-side evaluation:  
Human raters compare outputs from two models on the same

## Model Size Strategy



<Sidenote category="pattern">Start small. A well-trained 7B model often outperforms a poorly trained 70B model and costs 10$$ less to serve.</Sidenote>





<Sidenote category="crossref">See vol6 Ch 5 for deployment patterns including quantisation-aware serving, adapter routing, and cost modelling for fine-tuned models.</Sidenote>



Start with the smallest model that meets your quality bar. Scale up only when evaluation shows
the capability gap cannot be closed with better data or training.



<Sidenote category="formula">GPU memory: params $$ bytes/param. 7B at FP16 $= 7  10^9  2 = 14$ GB. Training adds $$4$$ (grads + optimizer).</Sidenote>



## Compression Techniques

Quantization:  
Reduce weight precision from 32-bit to 16/8/4-bit. Typical savings:
2–8× memory reduction with minimal quality loss at 8-bit, measurable but
often acceptable loss at 4-bit.

Knowledge distillation:  
Train a smaller “student” model to mimic a larger
“teacher” model’s outputs. Captures the teacher’s learned behavior in a fraction
of the parameters. See Section <a href="#sec:m5-distillation" data-reference-type="ref" data-reference="sec:m5-distillation">[sec:m5-distillation]</a> for the DeepSeek R1
distillation case study.

## Multi-Model Routing with LoRA

Serve a single base model with multiple LoRA<Citation src="hu2021lora" /> adapters. Route requests to the appropriate
adapter based on task type. This avoids duplicating the full model for each specialization
and enables hot-swapping adapters without restarting inference.

def compute_metrics(df: pd.DataFrame) -> dict:

        "error_rate_pct": round(float(

ALERT_THRESHOLDS = {
    "avg_latency_ms": 3000, "p95_latency_ms": 5000,
    "error_rate_pct": 25.0, "avg_tokens": 1200,
    "avg_satisfaction_min": 3.0,
}

def check_alerts(metrics, thresholds=ALERT_THRESHOLDS):
    """Compare metrics to thresholds, return triggered alerts."""
    triggered = []
    for key in ["avg_latency_ms", "p95_latency_ms",
                "error_rate_pct", "avg_tokens"]:
        if metrics[key] > thresholds[key]:
            triggered.append(f"{key}: {metrics[key]} > {thresholds[key]}")
    if metrics["avg_satisfaction"] < thresholds["avg_satisfaction_min"]:
        triggered.append(
            f"avg_satisfaction: {metrics['avg_satisfaction']}"
            f" < {thresholds['avg_satisfaction_min']}")
    return triggered

def categorize_issue(row, verbose_threshold=1500):

# Distillation: Compressing Frontier Reasoning



<Sidenote category="interview">"How do you deploy a frontier reasoning model cost-effectively?" — Distillation is the answer. Know the R1 recipe: teacher traces $$ SFT on students.</Sidenote>



Knowledge distillation for reasoning models follows a specific recipe, best
illustrated by DeepSeek R1’s open-source pipeline<Citation src="deepseek2025r1" />:

1.  **Generate teacher traces**: The frontier model (R1, 671B MoE)
    generates chain-of-thought solutions for ∼800K problems spanning
    math, code, science, and general reasoning.

2.  **Verify and filter**: Each trace is verified against ground truth
    (math answers, code tests). Only verified-correct traces are retained,
    typically 10–15% of generated candidates.

3.  **SFT on student models**: Smaller models (Qwen-1.5B/7B/14B/32B,
    Llama-8B/70B) are fine-tuned on the filtered teacher traces using
    standard SFT with LoRA.

4.  **Evaluate**: Distilled students are compared against both the
    teacher and RL-trained models of the same size.

&lt;!–MDXB-13-OPEN–&gt;

**Core Insight:** DeepSeek’s distilled models consistently outperform
small models trained with direct RL. Qwen-7B distilled from R1 achieves
higher AIME scores than Qwen-7B trained with GRPO from scratch. Reasoning
capability transfers more efficiently through SFT on teacher traces than
through independent RL exploration.

**Why It Matters:** For deployment, you rarely need to run RL on your
serving model. Instead, run RL on the largest model you can afford, generate
verified reasoning traces, and distill into the model you actually serve.
This separates the “research” cost (RL on frontier models) from the
“deployment” cost (inference on distilled models).

**When It Breaks:** Distillation transfers the teacher’s reasoning
*style* but not necessarily its *capability ceiling*. If the
student model lacks the parametric capacity to represent the reasoning
patterns (e.g., distilling 671B reasoning into 1.5B), quality degrades
sharply on complex problems. The sweet spot is 7B–14B students for
most production deployments.

&lt;!–MDXB-13-CLOSE–&gt;



<Sidenote category="practice">Shadow deployment pattern: run the distilled model alongside production for 24h, compare outputs to the teacher on 5K real requests.</Sidenote>



# Production Checklist

&lt;!–MDXB-15-OPEN–&gt;

Production deployment questions are standard at Staff+ interviews and increasingly
common at IC4+ for MLEs at Meta, Google, Amazon, and Anthropic. The interviewer
wants to see that you think beyond training accuracy to operational readiness.

**What they’re really testing:** Whether you can design the full lifecycle—
promotion gates, monitoring, rollback, and the data-feedback flywheel—not just
train a model. The strongest signal is articulating *when to retrain vs. when to fix via prompt engineering or RAG*, showing you optimise for speed of
intervention, not just model quality.

**Expected depth by level:**

- **IC4:** Know the five production requirements (reproducibility,
  promotion rules, monitoring, feedback flywheel, infrastructure). Explain
  shadow deployment and canary traffic. Name three metric families
  (performance, cost, reliability).

- **IC5+/Staff:** Design promotion rules with quantitative thresholds
  and no-regression slice checks. Explain distillation as a deployment
  strategy (R1 → student models). Discuss the intervention decision
  framework: prompt eng (∼1 day) → RAG update (∼1 day) →
  SFT (∼1 week) → RL (∼1 week).

&lt;!–MDXB-15-CLOSE–&gt;

L43 distills the entire module into five non-negotiable production requirements:

1.  **Reproducible configuration:** Every training run must be fully specified—
    model, data snapshot, hyperparameters, random seeds, code version—so that any
    result can be reproduced.

2.  **Promotion rules + rollback:** Formal gates with quantitative thresholds for
    dev→staging→production. One-command rollback to the previous version.

3.  **Monitoring + SLOs:** Dashboards covering performance, cost, and reliability.
    Service-level objectives with automated alerts.

4.  **Feedback-to-data flywheel:** A pipeline that routes production errors back
    into training data with proper hygiene (filter, dedup, PII scrub).

5.  **Infrastructure readiness:** Right-sized GPU allocation, compression strategy,
    capacity plan, and cost projections validated before launch.

&lt;!–MDXB-14-OPEN–&gt;

**Core Insight:** The difference between a stagnant model and a compounding
system is whether production errors flow back into the training pipeline. Better
models generate better synthetic data, which improves the next generation. Teams
that tighten this loop—error analysis → counterexamples → retrain →
deploy → error analysis—compound improvements exponentially.

**Why It Matters:** A single training run produces a point-in-time model.
A flywheel produces a continuously improving system. The marginal cost of each
improvement round decreases as the pipeline matures (filtering, dedup, PII
scrubbing are automated once).

**When It Breaks:** Without data hygiene (dedup, PII scrub, quality
filtering), the flywheel amplifies noise instead of signal. Duplicated errors
get over-represented; PII leaks create liability. The flywheel requires
infrastructure investment before it compounds.

&lt;!–MDXB-14-CLOSE–&gt;

&lt;!–MDXB-16-OPEN–&gt;

Define promotion rules for a math model. Strict rule: 90%+ AIME accuracy,
0% regression on general helpfulness. Loose rule: 85%+ AIME, &lt;3%
helpfulness regression. You run a sweep of 30 trained models. Estimate how
many pass each rule. Which optimises for speed vs. safety?

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-19-OPEN–&gt;

**Approach:**
**Strict rule:** Expect 2–3 models out of 30 to pass (90%+ AIME is
aggressive, 0% regression is extremely restrictive). Time to promotion: weeks
(multiple sweeps needed).

**Loose rule:** Expect 8–12 models to pass (85% is achievable, 3%
regression tolerance is practical). Time to promotion: days.

**Speed vs. safety:** Strict optimises for safety (zero regressions in
production) at the cost of slow iteration. Loose optimises for speed (more
candidates pass) with acceptable risk (3% regression may be invisible to users).

**Key Insight:** Start loose during development (fast iteration), tighten
for production (user-facing). The 0% regression rule is aspirational—in
practice, 1–2% regression on non-critical slices is often acceptable if the
primary metric improves significantly.

You need to serve a 13B model for 100 QPS. In float16 (14 GB model), each
A100 (80 GB) can serve 8 concurrent requests at 50 tokens/s. How many GPUs
do you need? What if you quantise to int8 (7 GB model, 16 concurrent requests)?

&lt;!–MDXB-17-CLOSE–&gt;

&lt;!–MDXB-20-OPEN–&gt;

**Approach:**
**float16:** Each GPU handles 8 requests. At 50 tokens/s with average
response of 200 tokens, each request takes 4s. Throughput per GPU:
8/4 = 2 QPS. For 100 QPS: 100/2 = 50 GPUs.

**int8:** Each GPU handles 16 requests. Throughput per GPU:
16/4 = 4 QPS. For 100 QPS: 100/4 = 25 GPUs.

**Savings:** int8 quantisation halves GPU count (and cost) with
typically &lt;1% accuracy degradation for instruction-following tasks.

**Key Insight:** Serving cost scales linearly with model size and
inversely with batch size. Quantisation is the highest-ROI optimisation:
it doubles batch capacity (and halves cost) for free in most cases.

**Answer:** Serving cost scales linearly with model size and

Your deployed model’s accuracy on a held-out test set drops from 82% to 74%
over 3 months without any model changes. Propose three hypotheses ordered by
likelihood and a diagnostic test for each.

&lt;!–MDXB-18-CLOSE–&gt;

&lt;!–MDXB-21-OPEN–&gt;

**Approach:**
**Hypothesis 1 (most likely): Data drift.** User queries have shifted (new
topics, different phrasing, seasonal effects). **Test:** Compare embedding
distributions of production queries from month 1 vs. month 3. If centroid
distance exceeds a threshold, data drift is confirmed.

**Hypothesis 2: Evaluation drift.** The test set has become unrepresentative
of production traffic. **Test:** Sample 100 recent production queries and
evaluate manually. If production accuracy differs significantly from test set
accuracy, the test set needs refreshing.

**Hypothesis 3: Infrastructure change.** A dependency update (tokeniser
version, API provider, preprocessing pipeline) subtly changed model inputs.
**Test:** Diff all infrastructure configs between month 1 and month 3.
Replay month-1 queries through current infrastructure and compare outputs.

**Key Insight:** No model change + accuracy drop = the world changed,
not the model. Always diagnose environment before retraining.

**Answer:** No model change + accuracy drop = the world changed,
not the model. Always diagnose environment before retraining.

**Approach:**

1.  Error analysis on the 50K conversations: cluster failures by type

2.  Identify top 3 failure modes (expect: calculation errors, refusals on

5.  Retrain Model A with augmented data (SFT + GRPO)

6.  Evaluate on frozen test set + new production-derived test set

7.  Promote if metrics improve; roll back if regression detected
