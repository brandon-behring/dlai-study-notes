Modules 1–3 established the post-training pipeline (SFT → RL), core techniques
(LoRA, PPO, GRPO), and evaluation as the north star. But every technique is only as
good as the data that feeds it. This module shifts focus to the engine room: how much
data do you need, where does it come from, how do you manufacture it when you cannot
collect it, and how do you ensure it teaches the right lessons? Data is the lever that
determines whether your post-trained model is a toy or a product.

# How Much Data Do You Need?

The first question every practitioner asks is deceptively simple: how much data?
The answer depends entirely on what you are training and how you are training it.

## Pre-Training: The Chinchilla Rule



<Term name="Chinchilla Scaling Law" los="FRI-4.1">
  Following compute-optimal scaling laws<Citation src="kaplan2020scaling" />, use approximately 20 tokens per parameter. A 7B-parameter model requires roughly 140B tokens. This establishes the baseline data appetite before any post-training begins.
</Term>

Pre-training is data-hungry by design. Post-training, by contrast, is surgically

## LoRA Considerations



<Sidenote category="pattern">Start with the lowest LoRA rank that works (r=4 or r=8). Increase rank only when evaluation shows underfitting.</Sidenote>



When using LoRA, the data requirements remain similar, but you should use the
**lowest rank possible** to avoid overfitting on small datasets. Lower rank means
fewer trainable parameters, which means less capacity to memorize noise.

# Data for Fine-Tuning: The Iterative Loop

Fine-tuning data is not collected once and forgotten. The most effective approach is an
iterative cycle that treats data curation as a continuous engineering process.



<Term name="Iterative Data Refinement" los="FRI-4.2">
  A four-step cycle: (1) train the model, (2) evaluate on held-out test sets, (3) identify the worst failure patterns, (4) add targeted counterexamples that address those failures. Repeat until evaluation metrics plateau.
</Term>
<AnkiCard type="term" front={"Iterative Data Refinement"} back={"A four-step cycle: (1) train the model, (2) evaluate on held-out test sets, (3) identify the worst failure patterns, (4) add targeted counterexamples that address those failures. Repeat until evaluation metrics plateau."} los="FRI-4.2" />



&lt;!–MDXB-13-OPEN–&gt;

The key insight is that not all training examples are equally valuable. After an
initial round of fine-tuning, the model will have specific failure modes—perhaps
it hallucinates dates, or drops safety guardrails for certain prompt patterns, or
generates overly verbose responses for simple questions.

Rather than adding more random data, you **mine the failure distribution**
and create examples that directly counter the most common failures. Ten well-chosen
counterexamples can outperform a thousand random additions.

**When It Breaks:** Over-indexing on counterexamples can cause catastrophic forgetting
on previously correct behaviors. Always re-run the full eval suite after adding targeted
data—fixing one failure mode should not regress another.

&lt;!–MDXB-13-CLOSE–&gt;

&lt;!–MDXB-15-OPEN–&gt;

**What they’re really testing:** Whether you know that data quality is

## Chain-of-Thought Data Mixing



<Sidenote category="warning">Mixing in too much CoT data (>60%) for tasks that do not need reasoning can cause verbose, meandering outputs.</Sidenote>



For tasks requiring multi-step reasoning, mix chain-of-thought examples into the
training data. A practical ratio: **∼40% reasoning traces** for
reasoning-heavy tasks, with the remainder as direct-answer examples. This teaches
the model *when* to reason, not just *how*.

# Data for RL: Rollouts and Reward Shaping

RL data has a fundamentally different structure than SFT data. Instead of
input–output pairs, RL operates on **rollouts**: an input prompt, one or
more sampled outputs, and a reward signal for each.

## Rollout Structure and Scale



<Term name="Rollout" los="FRI-4.3">
  An RL training datum consisting of an input prompt, a generated output (the "roll"), and a scalar reward signal. Multiple outputs are typically sampled per input, creating a set of rollouts that the RL algorithm uses to learn which outputs are preferred.
</Term>
<AnkiCard type="term" front={"Rollout"} back={"An RL training datum consisting of an input prompt, a generated output (the \"roll\"), and a scalar reward signal. Multiple outputs are typically sampled per input, creating a set of rollouts that the RL algorithm uses to learn which outputs are preferred."} los="FRI-4.3" />





<Term name="Rollout Scale Guidelines" los="FRI-4.3">
  **1K–10K prompts**: probing and feasibility testing. **10K–20K**: default starting point for most RL runs. **20K–100K**: mid-size production training. **100K–1M**: frontier-lab scale (DeepSeek, OpenAI, Anthropic). Generate **8 outputs per input** as a sensible default.
</Term>
<AnkiCard type="term" front={"Rollout Scale Guidelines"} back={"**1K–10K prompts**: probing and feasibility testing. **10K–20K**: default starting point for most RL runs. **20K–100K**: mid-size production training. **100K–1M**: frontier-lab scale (DeepSeek, OpenAI, Anthropic). ## Verifier-Based Rewards

For tasks with objectively verifiable answers, you can skip human preference
labeling entirely. Consider a haiku syllable-count verifier:



```cypher
import re

def check_accuracy(solution, ground_truth: float) -> float:
    """Binary accuracy with float tolerance."""
    numbers = re.findall(r"[-+]?\d+\.?\d*", solution)
    if not numbers:
        return 0.0
    extracted = float(numbers[-1])
    return 1.0 if abs(extracted - ground_truth) < 0.01 else 0.0

# Constitutional scoring: per-template weighted composites
def score_solution(template, accuracy, completeness,
                   verification=0.0, novelty=0.0):
    """Composite score with template-specific weights."""
    if template == "cot":
        # Chain-of-thought: accuracy 60%, completeness 40%
        return 0.6 * accuracy + 0.4 * completeness
    elif template == "verification":
        # Verification: accuracy 50%, completeness 30%,
        #               verification quality 20%
        return 0.5 * accuracy + 0.3 * completeness + 0.2 * verification
    elif template == "alternative":
        # Alternative solution: accuracy 50%, completeness 30%,
        #                       novelty 20%
        return 0.5 * accuracy + 0.3 * completeness + 0.2 * novelty
    return accuracy  # Fallback
```



The M4 lab uses **constitutional evaluation**: each solution is scored across
multiple dimensions with template-specific weights. This is a **verifier-based**
reward—no learned reward model, just deterministic checks. Verifier rewards are
cheaper, more reliable, and free from reward model overfitting—but they only work
for tasks with clear right answers.

<Term name="Composite Reward Score" los="FRI-4.3">
  A weighted combination of scores across multiple dimensions (e.g., correctness, helpfulness, safety, conciseness). Each dimension may use a different scoring mechanism—verifiers for correctness, learned models for helpfulness, rule-based checks for safety.
</Term>

<Term name="Alignment Gap" los="FRI-4.3">
  The delta between the reward model's score and actual human preference. Tracked over training to detect reward model drift. A growing alignment gap signals that the policy is exploiting reward model weaknesses rather than genuinely improving.
</Term>

&lt;!–MDXB-23-OPEN–&gt;

The most dangerous failure mode in RL-based post-training is **reward hacking**:
the policy learns to exploit patterns in the reward model that do not correspond to
genuine quality improvements. Symptoms include:

- Reward scores increase while human eval scores plateau or decrease.

- Outputs become formulaic—hitting reward model triggers without substance.

- The alignment gap (reward model score minus human preference) widens.

**Mitigations:**

1.  Add **counterexamples** to the reward model training set that specifically
    target the exploited patterns.

2.  Track the alignment gap continuously. Halt training if it exceeds a threshold.

3.  Use **composite rewards** across orthogonal dimensions so that gaming
    one axis does not dominate the total score.

4.  Periodically retrain the reward model on fresh human annotations.

## Offline vs. Online Preference Learning



<Term name="Offline vs. Online Preference Learning" los="FRI-4.3">
  **Offline**: preference data is collected once, then training proceeds on that fixed dataset (e.g., DPO). **Online**: the policy generates new outputs during training, which are scored by the reward model in real time (e.g., PPO, GRPO). Online learning is more expensive but avoids distribution shift between the data and the current policy.
</Term>

Handling expensive reward signals (e.g., human evaluation, slow API calls) requires
batching rollouts and scoring asynchronously. Cache reward scores aggressively—the
same prompt-output pair should never be scored twice.

# Production Data Pipelines

Real production pipelines assemble data from multiple sources with different quality
levels and purposes. DeepSeek R1<Citation src="deepseek2025r1" /> provides one of the most transparent case studies.

&lt;!–MDXB-7-OPEN–&gt;

**Stage 1: Cold-Start Chain-of-Thought**  
Manually curated reasoning traces to bootstrap the model’s ability to “think
step by step” before answering. High quality, small volume.

↓

**Stage 2: V3 Fine-Tuning Data**  
General instruction-following data from the DeepSeek-V3 training pipeline.
Provides broad capability coverage.

↓

**Stage 3: Synthetic Reasoning Data**  
∼600K examples generated by the model itself, then aggressively filtered
for correctness and reasoning quality. This is the largest single component.

↓

**Stage 4: Non-Reasoning Data**  
Standard conversational, factual, and formatting examples to prevent
capability regression on non-reasoning tasks.

↓

**Final Mix: ∼800K total examples**  
**75% reasoning / 25% non-reasoning** ratio.  
The heavy skew toward reasoning reflects DeepSeek R1’s positioning as a
reasoning-specialized model.

# Synthetic Data Pipelines

When you cannot collect enough real data—because the task is novel, annotation is
expensive, or you need diversity at scale—synthetic data generation fills the gap.

&lt;!–MDXB-8-OPEN–&gt;

**What**: Synthetic data is training data generated by language models rather
than collected from humans. A synthetic data pipeline combines four operations:
*generation*, *filtering*, *transformation*, and *scoring*.

**Why**: Real data is expensive, slow to collect, and often lacks diversity
in edge cases. Synthetic pipelines can produce thousands of targeted examples in
hours. The critical insight is that **filtering is more important than
generation**—it is easy to generate synthetic data and dangerously easy to
generate bad synthetic data.

&lt;!–MDXB-8-CLOSE–&gt;

## The Four Operations



<Term name="Synthetic Data Operations" los="FRI-4.4">
  **Generate**: produce candidate examples using templates, varied temperatures, and persona sampling. **Filter**: remove low-quality examples via rejection sampling, LLM-as-judge, majority vote, or collapse detection. **Transform**: restyle examples (verbose $$ concise), adjust difficulty, reformat. **Score**: assign multi-axis quality scores for downstream weighting or selection.
</Term>

## Template Engineering



<Term name="Template (Mad-Lib Prompt)" los="FRI-4.4">
  A prompt skeleton with variable slots (e.g., \{\{topic\}\}, \{\{difficulty\}\}, \{\{persona\}\}) that is filled programmatically to produce diverse synthetic examples. Templates encode the *structure* of desired outputs while variables inject *diversity*.
</Term>
<AnkiCard type="term" front={"Template (Mad-Lib Prompt)"} back={"A prompt skeleton with variable slots (e.g., {{topic}}, {{difficulty}}, {{persona}}) that is filled programmatically to produce diverse synthetic examples. Templates encode the *structure* of desired outputs while variables inject *diversity*."} los="FRI-4.4" />



Templates are matched to failure patterns: if the model fails on multi-step math,
you write a template that generates multi-step math problems with varying complexity
and domain. If it fails on safety edge cases, you write templates with adversarial
persona variables.



```cypher
import random

TEMPLATE = """You are a {persona} helping a {audience} with {topic}.

The user asks: {question}

Provide a {style} response that:
1. Addresses the question directly
2. Includes {num_examples} concrete examples
3. Avoids jargon unless necessary

Response:"""

PERSONAS = ["patient teacher", "senior engineer", "domain expert",
            "research scientist", "technical writer"]
AUDIENCES = ["beginner", "intermediate developer", "ML engineer",
             "product manager", "executive"]
STYLES = ["concise", "detailed", "step-by-step", "comparative"]


def generate_from_template(
    topic: str,
    questions: list[str],
    n_variants: int = 5,
) -> list[str]:
    """Generate diverse prompts from a single template."""
    prompts = []
    for question in questions:
        for _ in range(n_variants):
            prompt = TEMPLATE.format(
                persona=random.choice(PERSONAS),
                audience=random.choice(AUDIENCES),
                topic=topic,
                question=question,
                style=random.choice(STYLES),
                num_examples=random.randint(1, 4),
            )
            prompts.append(prompt)
    return prompts
```





<Sidenote category="practice">Try building a template for your own failure mode. Define 3+ variable slots with 5+ values each. How many unique prompts does the combinatorial space yield?</Sidenote>



## Persona-Based Diversity

Varying the persona variable is one of the most effective ways to inject diversity
without changing the underlying task. The same question answered by a “patient
teacher” and a “terse senior engineer” produces structurally different training
examples, teaching the model stylistic range.

## The Production Data Flywheel

In production, synthetic data generation feeds into a self-reinforcing cycle:
deploy the model → collect real user queries → identify failure patterns →
generate synthetic counterexamples → retrain → redeploy. The flywheel
accelerates as the model improves, because better models generate higher-quality
synthetic data for the next iteration.

# Filtering: The Critical Step

Generation is easy. Filtering is where the value is created. A pipeline that
generates 100K examples and keeps 10K after rigorous filtering will outperform
one that trains on all 100K.



```cypher
from dataclasses import dataclass


@dataclass
class SyntheticExample:
    prompt: str
    response: str
    scores: dict[str, float]


def rejection_sampling_filter(
    examples: list[SyntheticExample],
    min_scores: dict[str, float],
    dedup_threshold: float = 0.85,
) -> list[SyntheticExample]:
    """Filter synthetic data via multi-axis rejection sampling.

    Args:
        examples: Candidate synthetic examples with quality scores.
        min_scores: Minimum acceptable score per dimension.
        dedup_threshold: Cosine similarity threshold for collapse detection.

    Returns:
        Filtered list of high-quality, diverse examples.
    """
    # Stage 1: Score-based rejection
    passed = []
    for ex in examples:
        if all(ex.scores.get(dim, 0) >= threshold
               for dim, threshold in min_scores.items()):
            passed.append(ex)

    # Stage 2: Collapse detection (remove near-duplicates)
    # In production, use embedding similarity; here simplified
    filtered = []
    seen_prefixes: set[str] = set()
    for ex in passed:
        prefix = ex.response[:200].lower().strip()
        if prefix not in seen_prefixes:
            seen_prefixes.add(prefix)
            filtered.append(ex)

    return filtered


# Usage
candidates = [...]  # 100K generated examples, each scored
quality_thresholds = {
    "relevance": 0.8,
    "correctness": 0.9,
    "fluency": 0.7,
    "safety": 0.95,
}
final_dataset = rejection_sampling_filter(candidates, quality_thresholds)
# Typical yield: 10-20% of candidates pass all filters
```





<Sidenote category="warning">Collapse detection is essential. Without it, your "diverse" synthetic dataset may contain thousands of near-identical outputs that the model memorizes.</Sidenote>



## Filtering Methods

Generate *N* candidates, keep only those above a quality
threshold. Simple and effective.

Use a stronger model (or the same model with a judge prompt) to
evaluate candidate quality on defined rubrics.

Generate multiple answers to the same question. Keep examples
where the majority of answers agree—these are more likely correct.

Flag and remove examples that are too similar to each
other, indicating the generator has fallen into a repetitive mode.

# Constitutional AI

Constitutional AI (CAI)<Citation src="bai2022constitutional" /> represents Anthropic’s approach to alignment without
extensive human labeling. Instead of humans providing preference labels, the model
critiques and revises its own outputs according to a written constitution.

&lt;!–MDXB-9-OPEN–&gt;

**What**: Constitutional AI replaces human preference annotators with a set of
written principles (the “constitution”) that the model uses to self-critique and
self-revise. The constitution encodes values like helpfulness, harmlessness, and
honesty as explicit, auditable rules.

**Why**: Human preference labeling is expensive, inconsistent, and does not
scale. A constitution is cheaper, more consistent, and—critically—transparent.
You can read, audit, and version-control the rules that govern your model’s behavior.
When the model behaves unexpectedly, you can trace the behavior back to specific
constitutional principles.

&lt;!–MDXB-9-CLOSE–&gt;

## The Full CAI Pipeline

&lt;!–MDXB-10-OPEN–&gt;

**Step 1: Write the Constitution**  
Define principles covering helpfulness, harmlessness, honesty, and autonomy.
Each principle is a natural-language rule the model can evaluate against.

↓

**Step 2: Generate Responses**  
Sample diverse outputs from the current model for a set of prompts,
including adversarial and edge-case prompts.

↓

**Step 3: Constitutional Critique**  
The model critiques each response against each constitutional principle.
“Does this response violate principle X? If so, how?”

↓

**Step 4: Revision**  
The model revises the response to address the critique.
This produces (original, revised) pairs.

↓

**Step 5: SFT on Revisions**  
Fine-tune the model on the revised outputs to internalize the
constitutional principles.

↓

**Step 6: Preference Data Generation**  
Use the constitution to select preferred outputs from pairs,
creating synthetic preference data without human annotators.

↓

**Step 7: RL Training (RLAIF)**  
Train a reward model on the synthetic preferences, then run RL
to further align the model. This is RL from AI Feedback.

&lt;!–MDXB-10-CLOSE–&gt;



<Sidenote category="interview">CAI is Anthropic's core alignment method. Key insight: the constitution replaces human labelers with auditable rules. Understand the full 7-step pipeline.</Sidenote>

## RLAIF Evolution: Beyond Constitutional AI

Constitutional AI pioneered AI-generated feedback, but the RLAIF paradigm has
expanded significantly:

- **Self-play preference generation**: The model generates both
  candidate responses and preference labels, then trains on its own judgments.
  Used in Meta’s Self-Rewarding Language Models (2024).

- **Principle-conditioned generation**: Instead of a fixed constitution,
  condition on specific principles per query (e.g., prioritise harmlessness
  for safety-adjacent queries, helpfulness for factual ones).

- **KTO as a CAI simplifier**: Binary feedback (good/bad) from an AI
  judge replaces pairwise comparisons, reducing the annotation complexity
  from *O*(*n*<sup>2</sup>) pairs to *O*(*n*) labels.

The common thread: AI feedback is *cheaper and more consistent* than human
feedback, but requires careful calibration against human preferences on a
validation set to prevent systematic bias.

## Templates as Reward Functions

In the CAI framework, templates serve double duty: they generate diverse training
examples *and* encode evaluation criteria. A template that says “critique this
response for harmlessness” is simultaneously a data generator and a reward function
specification. This unification is what makes constitutional AI self-improving.

# Balancing Data and Rewards

The final challenge is mixing all these data sources and reward signals into a
coherent training recipe.

## Data Mixing Ratios

There is no universal optimal ratio. The right mix depends on your model’s target
capabilities:

| **Target Capability** | **Task-Specific Data** | **General Data** |
|:----------------------|:----------------------:|:----------------:|
| General assistant     |         40–60%         |      40–60%      |
| Math/reasoning        |         60–80%         |      20–40%      |
| Translation           |         70–90%         |      10–30%      |
| Code generation       |         50–70%         |      30–50%      |
| Safety-critical       |         30–50%         |      50–70%      |

## Specialization Trade-Offs

Specializing a model (e.g., heavy math data) inevitably degrades performance on
other tasks. This is not a bug—it is the fundamental trade-off of post-training.
Track capability regression on a broad eval suite and decide explicitly which
capabilities you are willing to sacrifice.

## Reward Function Weight Balancing

When using composite reward scores, the relative weights between dimensions (e.g.,
correctness vs. helpfulness vs. safety) determine model behavior. Small weight
changes can cause large behavioral shifts. Treat reward weights as hyperparameters
that require systematic tuning, not one-time configuration.

&lt;!–MDXB-11-OPEN–&gt;

Over-specializing on one task while losing general
abilities. **Fix**: Include 20–40% general-purpose data in every mix.

One reward dimension dominates all others, producing
outputs that optimize a single axis. **Fix**: Normalize reward dimensions
to similar scales before weighting.

Using the same data ratios across training runs without
re-evaluating. **Fix**: Re-tune mixing ratios every iteration based on
current evaluation results.

&lt;!–MDXB-11-CLOSE–&gt;



<Sidenote category="warning">Data balancing is **never** a one-time process. Every model iteration changes what data the model needs next.</Sidenote>



## The Iterative Imperative

Post-training is fundamentally iterative. The output of one training run informs
the data collection, mixing, and reward design of the next. Teams that treat data
pipelines as “set and forget” are consistently outperformed by teams that run
tight iteration loops with rigorous evaluation at each step.

&lt;!–MDXB-14-OPEN–&gt;

**Core Insight:** A 10× increase in data quantity yields &lt;1.3×
capability gain if quality is poor. A 10× increase in *curation*
(keeping the top 10%, removing the bottom 10%) often yields 2–3× gains.
Frontier labs spend as much effort *filtering out* bad data as generating
new data.

**Why It Matters:** DeepSeek R1 starts with 600K synthetic examples, filters
aggressively to keep the best 10–15%, then mixes with 200K curated non-reasoning
data. The filtering step—not the generation step—is where quality is created.

**When It Breaks:** Over-filtering on a single dimension (e.g., only keeping
long, detailed responses) introduces distribution bias. The model becomes excellent
at one style but loses diversity. Balance filtering thresholds across multiple
quality dimensions (correctness, fluency, format, diversity).

&lt;!–MDXB-16-OPEN–&gt;

You fine-tune on 20, 50, 100, 200, 500, and 1,000 curated GSM8K examples.
Accuracy results: 18%, 31%, 42%, 51%, 58%, 61%. Fit a power law:
acc = *a* ⋅ *n*<sup>*b*</sup>. How many additional examples are needed to reach
65%?

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-19-OPEN–&gt;

**Approach:**
**Fitting the power law:** Using log-log regression on the data points:
log (acc) = log (*a*) + *b* ⋅ log (*n*)

Approximate fit: *a* ≈ 4.5, *b* ≈ 0.38.

**Prediction for 65%:** 0.65 = 4.5 ⋅ *n*<sup>0.38</sup> ⇒
*n* ≈ 1, 800 examples.

**Key Insight:** The diminishing returns are severe: going from 500 to
1,000 examples (+500) gained only 3% accuracy. Going from 1,000 to 1,800
(+800) would gain only 4%. At this point, RL with a verifier is more efficient
than collecting more SFT data.

**Answer:** The diminishing returns are severe: going from 500 to
1,000 examples (+500) gained only 3% accuracy. Going from 1,000 to 1,800
(+800) would gain only 4%.

&lt;!–MDXB-17-OPEN–&gt;

You generate 10,000 synthetic GSM8K examples with temperature=0.7. Quality
scores (0–1): mean=0.62, std=0.18. You filter at threshold 0.8 and keep
2,100 examples (21% yield). A model trained on the filtered set achieves 54%
accuracy. The same model trained on all 10,000 unfiltered achieves 47%.
Calculate the quality-adjusted efficiency (accuracy per training example).

&lt;!–MDXB-17-CLOSE–&gt;

&lt;!–MDXB-20-OPEN–&gt;

**Approach:**
**Filtered:** 54%/2, 100 = 0.0257% per example.

**Unfiltered:** 47%/10, 000 = 0.0047% per example.

**Ratio:** Filtered data is 5.5× more efficient per example.

**Key Insight:** Aggressive filtering (keeping 21%) produces data that is
5.5× more efficient than unfiltered data. The 7% accuracy gain (54%
vs. 47%) comes from *removing* 7,900 low-quality examples, not from
adding anything. Quality over quantity.

**Answer:** Aggressive filtering (keeping 21%) produces data that is
5.5× more efficient than unfiltered data. The 7% accuracy gain (54%
vs. 47%) comes from *removing* 7,900 low-quality examples, not from
adding anything.

&lt;!–MDXB-20-CLOSE–&gt;

&lt;!–MDXB-18-OPEN–&gt;

Design a composite reward function for a code-generation task. The model should
produce: (a) correct code that passes unit tests, (b) well-documented code with
docstrings, (c) efficient code (*O*(*n*log *n*) preferred over *O*(*n*<sup>2</sup>)). Assign
weights and justify.

&lt;!–MDXB-18-CLOSE–&gt;

&lt;!–MDXB-21-OPEN–&gt;

**Approach:**
**Composite reward:**
*r* = 0.6 ⋅ test\_pass + 0.2 ⋅ doc\_score + 0.1 ⋅ efficiency\_bonus + 0.1 ⋅ format\_clean

**Justification:**

- **test\_pass (0.6):** Binary correctness is the dominant objective.
  Without correctness, documentation and efficiency are worthless.

- **doc\_score (0.2):** LLM-judged documentation quality (0–1). Second
  priority because undocumented code is unmaintainable.

- **efficiency\_bonus (0.1):** +0.1 if solution is *O*(*n*log *n*) or
  better; 0 otherwise. Low weight because correctness matters more.

- **format\_clean (0.1):** PEP-8 compliance, proper naming. Low weight,
  easy to fix post-hoc.

**Key Insight:** Correctness must dominate ( &gt; 50% weight) to prevent
the model from optimising documentation at the expense of working code. Secondary
objectives shape style without overwhelming the primary signal.

**Answer:** Correctness must dominate ( &gt; 50% weight) to prevent
the model from optimising documentation at the expense of working code.

| **Failure Mode** | **Frequency** | **Example** |
|:---|:--:|:---|
| Wrong policy citation | 35% | “Refund within 60 days” (actual: 30 days) |
| Incomplete answer | 40% | Missing fee schedule details |
| Tone mismatch | 25% | Overly casual for complaint handling |

**Question 1:** Design the counterexample data for each failure mode.
How many examples per mode?

**Question 2:** Should you retrain with SFT, RL, or both? Justify.

**Question 3:** After retraining, wrong policy citation drops to 8%
but a new failure mode appears: the model now refuses to answer questions
about competitors. What happened and how do you fix it?

&lt;!–MDXB-24-CLOSE–&gt;

&lt;!–MDXB-22-OPEN–&gt;

**Approach:**
**Q1:**

- **Wrong policy (35%):** 100 examples of correct policy citations with
  exact dates, amounts, and conditions. Source directly from the policy document.

- **Incomplete answer (40%):** 120 examples of complete responses
  including fee schedules, edge cases, and follow-up actions. These should be
  the longest examples in the training set.

- **Tone mismatch (25%):** 80 examples demonstrating appropriate
  tone—formal for complaints, warm for inquiries, precise for policy questions.

**Q2:** SFT for policy citation and tone (these are format/content issues
best fixed with demonstrations). RL for completeness (use a checklist verifier:
does the response mention fee schedule? Follow-up steps? Contact info?).

**Q3:** Catastrophic forgetting from the counterexample data. The new
training data focused heavily on “don’t say wrong things about our policies,”
which the model over-generalised to “don’t say anything about other companies.”
Fix: add 50 examples where the model appropriately discusses competitors in
factual, neutral terms. Include these in the next SFT round to restore the
capability.

**Key Insight:** Data composition should directly target the failure distribution: allocate training examples proportionally to each failure category, with the highest-impact failures getting the most examples.

**Answer:** Target the failure distribution: 120 examples for incomplete answers (40%), 100 for wrong policy citations (35%), and 75 for tone issues (25%). Source policy examples directly from the document; tone examples from best human responses.
