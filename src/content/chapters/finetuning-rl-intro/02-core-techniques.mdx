# Data Preparation for Post-Training (L9)



<Sidenote category="interview">Google L4/Meta IC4 phone screen: "Walk me through data prep for fine-tuning." Tests whether you mention dedup, splitting, and quality filtering before jumping to training.</Sidenote>



The single most important factor in post-training success is data quality. Frontier labs
routinely discard 99% of candidate data, keeping only the cleanest subset that actually
improves model performance.

## SFT Data Structure

SFT data is organised as **input/output pairs**. For a reasoning task the target
output includes chain-of-thought tokens (often wrapped in `<think>` tags) followed
by a final answer in `<answer>` tags.

  In RL, a complete tuple of (input, model rollout, reward). The model generates its own output—called a *rollout*—and a verifier or reward model assigns a scalar reward.
</Term>

## Data Splitting

| **Split**       | **Purpose**                                           |
|:----------------|:------------------------------------------------------|
| Training set    | Data the model trains on (largest portion)            |
| Validation set  | Hyperparameter tuning; random subset of training data |
| Test / Eval set | Strictly held out; final model assessment only        |



<Sidenote category="pattern">RL test set must use a *different* reward model than training. This is the most commonly missed data split requirement.</Sidenote>



Key rules for splitting:

- Avoid random splitting—similar examples leak across splits.

- Use **time-based splits** to test generalisation to future scenarios
  (e.g. train on 2019, test on 2020).

- Always include an **out-of-distribution evaluation set** with long-tail inputs.

## Deduplication



<Sidenote category="pattern">Dedup pipeline: exact hash $$ MinHash LSH $$ manual review. Frontier labs discard $$99% of candidate data at this stage.</Sidenote>



Data leakage occurs not only from identical examples but from *similar* ones.

# Tokenisation and Decoding (L10)



<Sidenote category="formula">BPE compression: "ChatGPT" = 1 token but "indistinguishable" = 4. Rare words cost more tokens $$ longer sequences $$ slower inference.</Sidenote>



Models never see raw text. Text is first converted into **tokens**—efficiently
encoded subword units—via a tokeniser, then mapped to dense vectors through an
embedding matrix.



<Term name="BPE (Byte-Pair Encoding)" los="FRI-2.1">
  A subword tokenisation algorithm that iteratively merges the most frequent byte pairs. GFRI-3 uses $$50,000 BPE tokens; this dramatically reduces sequence length compared to character-level encoding.
</Term>
<AnkiCard type="term" front={"BPE (Byte-Pair Encoding)"} back={"A subword tokenisation algorithm that iteratively merges the most frequent byte pairs. GFRI-3 uses $$50,000 BPE tokens; this dramatically reduces sequence length compared to character-level encoding."} los="FRI-2.1" />



## Decoding Strategies

| **Strategy** | **Description** |
|:---|:---|
| Greedy | Select the highest-probability token each step. |
| Temperature | Scale logits by *T*; *T* = 0 is deterministic, higher *T* flattens
the distribution. |
| Beam search | Track *k* candidate sequences and keep the top-scoring ones. |

Sequences of different lengths are **padded** with null tokens to form uniform-length
batches for efficient GPU matrix operations. Different model families use different
tokenisers—never mix them (tokeniser mismatch is a silent killer).

# Fine-Tuning Mathematics, Part 1 (L11)



<Sidenote category="formula">CE loss: $-(0.5) = 0.69$, $-(0.1) = 2.30$, $-(0.01) = 4.61$. Exponentially penalises low-confidence predictions.</Sidenote>



&lt;!–MDXB-18-OPEN–&gt;

**Cross-Entropy Loss** is the foundational objective for supervised fine-tuning.
It measures how far the model’s predicted probability distribution over the vocabulary
is from the target token at each position. Minimising this loss pushes the model to
assign higher probability to the correct next token.

&lt;!–MDXB-18-CLOSE–&gt;

For a single target token *y* at position *t* with model-predicted probability
*p*(*y*<sub>*t*</sub> ∣ *y*<sub> &lt; *t*</sub>, *x*):
$$\mathcal{L}\_{\text{CE}} = -\sum\_{t=1}^{T} \log\\ p(y\_t \mid y\_{&lt;t}, x)$$
**Intuition**: If the model assigns probability 1.0 to the correct token,
−log (1.0) = 0 (no loss). If it assigns 0.01, −log (0.01) = 4.6 (large loss).
The loss is averaged over all target positions in the sequence.



<Term name="Cross-Entropy Loss" los="FRI-2.2">
  $L = - p(correct token)$. The standard next-token prediction loss. A probability of 1.0 yields zero loss; lower probabilities yield exponentially higher loss.
</Term>
<AnkiCard type="term" front={"Cross-Entropy Loss"} back={"$L = - p(correct token)$. The standard next-token prediction loss. A probability of 1.0 yields zero loss; lower probabilities yield exponentially higher loss."} los="FRI-2.2" />



&lt;!–MDXB-26-OPEN–&gt;

**Core Insight:** Cross-entropy loss (ℒ = −log  *p*(correct token))
is the universal SFT objective. It exponentially penalises low-confidence predictions:
the gradient *p*<sub>*i*</sub> − 𝟙\[*i* = *y*\] is large when the model is wrong and small when
correct, naturally focusing learning on uncertain tokens.

**Why It Matters:** The loss landscape has a useful property: moving from
*p* = 0.1 to *p* = 0.5 reduces loss by 1.61 nats, but moving from *p* = 0.5 to
*p* = 0.9 reduces it by only 0.59. Most training time is spent on the “long tail”
of tokens the model finds difficult, which is exactly where improvement matters.

**When It Breaks:** Cross-entropy treats all tokens equally. For tasks where
some tokens matter more (e.g., the final answer digit in math), weighted loss or
RL-based credit assignment (PPO/GRPO) is more appropriate.

&lt;!–MDXB-26-CLOSE–&gt;

## Loss Masking



<Term name="Loss Mask" los="FRI-2.2">
  A binary mask that zeroes out loss on input/prompt tokens so the model is only trained to predict the *completion* tokens. Without masking, the model wastes capacity memorising prompts.
</Term>
<AnkiCard type="term" front={"Loss Mask"} back={"A binary mask that zeroes out loss on input/prompt tokens so the model is only trained to predict the *completion* tokens. Without masking, the model wastes capacity memorising prompts."} los="FRI-2.2" />



In SFT the model sees the full sequence (prompt + completion) but we **only compute
loss on the completion tokens**. The prompt tokens are masked out. This is implemented in
TRL via `completion_only_loss=True` (or equivalently, a
`DataCollatorForCompletionOnlyLM`).

## Teacher Forcing



<Term name="Teacher Forcing" los="FRI-2.2">
  During training, the model receives the *ground-truth* previous tokens as input at each step—not its own predictions. This enables **fully parallel** loss computation across all positions in a single forward pass, because every position has a known input context.
</Term>
<AnkiCard type="term" front={"Teacher Forcing"} back={"During training, the model receives the *ground-truth* previous tokens as input at each step—not its own predictions. This enables **fully parallel** loss computation across all positions in a single forward pass, because every position has a known input context."} los="FRI-2.2" />





<Sidenote category="crossref">Teacher forcing enables parallelism that makes SFT orders of magnitude faster than autoregressive RL rollouts.</Sidenote>



Without teacher forcing, each token prediction would depend on the previous prediction,
forcing sequential computation. Teacher forcing breaks this dependency chain.

# Fine-Tuning Mathematics, Part 2 (L12)

## Backpropagation and Gradient Computation

The gradient of cross-entropy loss with respect to the model’s output logits has an
elegant form:

For a token position where the model predicts probability *p* for the correct class:
$$\frac{\partial \mathcal{L}}{\partial z\_i} = p\_i - \mathbb{1}\[i = y\]$$
**Interpretation**: The gradient is simply `predicted_probability `−` target`.
If the model predicts 0.9 for the correct token, the gradient magnitude is only 0.1.
If it predicts 0.1, the gradient is 0.9—a strong push to correct the error.

## AdamW Optimiser



<Term name="AdamW" los="FRI-2.2">
  The standard optimiser for LLM fine-tuning. Combines adaptive learning rates per parameter (via first and second moment estimates) with **decoupled weight decay** regularisation. Default learning rate: $5  10^\{-5\}$.
</Term>
<AnkiCard type="term" front={"AdamW"} back={"The standard optimiser for LLM fine-tuning. Combines adaptive learning rates per parameter (via first and second moment estimates) with **decoupled weight decay** regularisation. Default learning rate: $5  10^{-5}$."} los="FRI-2.2" />





<Sidenote category="pattern">AdamW decouples weight decay from the gradient update. This is more principled than L2 regularisation and is the default in `transformers`.</Sidenote>



AdamW maintains per-parameter running averages of gradients (first moment) and squared
gradients (second moment), providing adaptive step sizes. Weight decay is applied
separately to prevent overfitting.

## SFT Training Loop



```cypher
from datasets import load_dataset
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import SFTConfig, SFTTrainer

# M2 Lab: SFT on GSM8K with completion-only loss
model_name = "deepseek-ai/deepseek-math-7b-base"
model = AutoModelForCausalLM.from_pretrained(model_name)
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token

# Rename GSM8K columns to prompt/completion format
train = load_dataset("openai/gsm8k", "main", split="train")
train_dataset = train.select(range(200)).rename_columns(
    {"question": "prompt", "answer": "completion"}
)

training_args = SFTConfig(
    output_dir=None,
    num_train_epochs=3,
    per_device_train_batch_size=20,
    learning_rate=5e-6,             # Sweet spot: [3e-6, 1e-5]
    logging_strategy="steps",
    logging_steps=1,
    eval_strategy="steps",
    eval_steps=1,
    save_strategy="no",
    report_to="none",
    completion_only_loss=True,      # Loss only on completions, not prompts
)

trainer = SFTTrainer(
    model=model_name,
    args=training_args,
    train_dataset=train_dataset,
)
trainer.train()
```





<Sidenote category="practice">Run this code with a small dataset (100 examples) and log the loss every step. Verify the loss drops within the first epoch.</Sidenote>



&lt;!–MDXB-27-OPEN–&gt;

**Core Insight:** SFT computes cross-entropy loss *only on completion
tokens*, masking the prompt. Without masking, the model wastes capacity learning
to reproduce the prompt (which it receives as input anyway), diluting the
gradient signal for the actual task.

**Why It Matters:** For instruction-following data, prompts are often 80%
of the sequence. Unmasked training spends 80% of gradient updates on prompt
reproduction—a catastrophic misallocation. Masking focuses all learning capacity
on generating correct responses.

**When It Breaks:** Some tasks benefit from prompt-aware training (e.g.,
few-shot in-context learning where the model should learn prompt patterns). In
these cases, a partial mask (mask system prompt, keep few-shot examples) provides
a middle ground.

# Hyperparameters, Part 1 (L13)

## Learning Rate

The learning rate is the single most impactful hyperparameter. Three regimes:

| **Regime** | **Symptom**                                            |
|:-----------|:-------------------------------------------------------|
| Too high   | Loss explodes to NaN or oscillates wildly              |
| Just right | Loss decreases steadily, then plateaus                 |
| Too low    | Loss decreases extremely slowly; model never converges |

Default starting point for AdamW: LR = 5 × 10<sup>−5</sup>.



<Term name="Cosine Annealing" los="FRI-2.3">
  A learning rate schedule that decays the LR following a cosine curve from a peak value to near zero. Often combined with a linear warmup phase in the first 5–10% of steps.
</Term>
<AnkiCard type="term" front={"Cosine Annealing"} back={"A learning rate schedule that decays the LR following a cosine curve from a peak value to near zero. Often combined with a linear warmup phase in the first 5–10% of steps."} los="FRI-2.3" />



## Learning Rate Schedulers

Linear warmup  
Ramp LR from 0 to peak over the first *n* steps. Prevents
large, unstable gradient updates on randomly initialised parameters.

Cosine annealing  
After warmup, decay LR following $\eta\_t = \eta\_{\min} +
        \frac{1}{2}(\eta\_{\max} - \eta\_{\min})(1 + \cos(\pi t / T))$.

Constant  
Fixed LR throughout training. Simple but rarely optimal.

## Epochs

Underfitting (too few)  
Model has not learned enough from the data.

Overfitting (too many)  
Model memorises training data, validation loss rises.

Double descent  
A well-documented phenomenon where test loss *decreases
again* after initially rising, particularly in over-parameterised models.

## Batch Size

- Always use **powers of 2** (8, 16, 32, 64) for GPU memory alignment.

- Larger batches → smoother gradients, but higher memory usage.

- If you hit OOM: halve the batch size and double gradient accumulation steps
  to maintain effective batch size.

# Hyperparameters, Part 2: Diagnosis (L14)

&lt;!–MDXB-20-OPEN–&gt;

| **Symptom** | **Likely Cause** | **Fix** |
|:---|:---|:---|
| Loss → NaN | LR too high | Reduce LR by 10x |
| Loss flat from start | LR too low or data issue | Increase LR; check data pipeline |
| Train ↓, val ↑ | Overfitting | Reduce epochs, add regularisation, more data |
| Both losses plateau high | Underfitting | More epochs, higher LR, larger model |
| Loss spikes mid-training | Data quality issue | Check for corrupted batches, bad examples |
| Oscillating loss | LR too high or batch too small | Reduce LR or increase batch size |

## Reproducibility with Random Seeds

To guarantee reproducible results, seed **all three** random number generators:



```cypher
import random
import numpy as np
import torch

def set_seed(seed: int = 42) -> None:
    random.seed(seed)
    np.random.seed(seed)
    torch.manual_seed(seed)
    torch.cuda.manual_seed_all(seed)
    # For full determinism (slower):
    torch.backends.cudnn.deterministic = True
    torch.backends.cudnn.benchmark = False
```



Even with all seeds set, GPU non-determinism from floating-point atomics can cause
minor run-to-run variation. Report results averaged over 3–5 seeds in any rigorous
experiment.

# Parameter-Efficient Fine-Tuning: LoRA (L15)

&lt;!–MDXB-21-OPEN–&gt;

**LoRA (Low-Rank Adaptation)**<Citation src="hu2021lora" /> exploits a key insight: the weight updates during
fine-tuning (*Δ**W*) are **low-rank**. Instead of updating the full
*d* × *d* weight matrix, LoRA freezes the base model and trains two small matrices
*A* ∈ ℝ<sup>*d* × *r*</sup> and *B* ∈ ℝ<sup>*r* × *d*</sup> where *r* ≪ *d*.
The effective update is *Δ**W* = *B**A*, reducing trainable parameters by orders of
magnitude while maintaining quality.

&lt;!–MDXB-21-CLOSE–&gt;



<Term name="LoRA (Low-Rank Adaptation)" los="FRI-2.4">
  Freezes the pre-trained weight matrix $W$ and adds a low-rank decomposition $ W = BA$ where $B  R^\{r  d\}$, $A  R^\{d  r\}$, and $r  d$. Only $A$ and $B$ are trained.
</Term>
<AnkiCard type="term" front={"LoRA (Low-Rank Adaptation)"} back={"Freezes the pre-trained weight matrix $W$ and adds a low-rank decomposition $ W = BA$ where $B  R^{r  d}$, $A  R^{d  r}$, and $r  d$. Only $A$ and $B$ are trained."} los="FRI-2.4" />





<Term name="Rank ($r$)" los="FRI-2.4">
  The inner dimension of the LoRA decomposition. Default $r\{=\}4$. Higher rank $$ more expressive updates but more parameters. Typical range: 4–64.
</Term>
<AnkiCard type="term" front={"Rank ($r$)"} back={"The inner dimension of the LoRA decomposition. Default $r{=}4$. Higher rank $$ more expressive updates but more parameters. Typical range: 4–64."} los="FRI-2.4" />





<Term name="Alpha ($$)" los="FRI-2.4">
  A scaling factor applied to the LoRA update: $W + \{r\} W$. The ratio $/r$ controls the magnitude of the adaptation. Common default: $=16$ with $r\{=\}8$.
</Term>
<AnkiCard type="term" front={"Alpha ($$)"} back={"A scaling factor applied to the LoRA update: $W + {r} W$. The ratio $/r$ controls the magnitude of the adaptation. Common default: $=16$ with $r{=}8$."} los="FRI-2.4" />

## Target Modules



<Sidenote category="pattern">Start with Q and V projection matrices. If quality is insufficient, expand to all linear layers (`target_modules="all-linear"`).</Sidenote>



The standard approach targets the **query (Q) and value (V)** projection matrices

## LoRA Configuration in Code



```cypher
from peft import LoraConfig, get_peft_model, TaskType

lora_config = LoraConfig(
    r=8,                           # Low-rank dimension
    lora_alpha=16,                 # Scaling factor (alpha/r = 2)
    target_modules=["q_proj", "v_proj"],  # Which layers to adapt
    lora_dropout=0.05,
    bias="none",
    task_type=TaskType.CAUSAL_LM,
)

model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.2-1B-Instruct")
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# Output: trainable params: 1,572,864 || all params: 1,236,635,648
#         || trainable%: 0.1272
```





<Sidenote category="interview">"LoRA LR 10x higher than full fine-tuning?" LoRA matrices init near zero; larger steps needed to move them into a useful range.</Sidenote>





<Sidenote category="crossref">See vol6 Ch 5 for LoRA/PEFT implementation patterns including rank selection heuristics and adapter-serving architectures.</Sidenote>



Key LoRA configuration notes:

- Use a **10x higher learning rate** than full fine-tuning (e.g. 2 × 10<sup>−4</sup>
  instead of 2 × 10<sup>−5</sup>).

- *A* is initialised with small random values; *B* is initialised to zero, so the
  initial *Δ**W* = *B**A* = 0 (no perturbation at start).

- After training, LoRA weights can be **merged** back into the base model
  for zero-overhead inference.

&lt;!–MDXB-28-OPEN–&gt;

**Core Insight:** LoRA exploits the fact that fine-tuning weight updates are
low-rank—most of the adaptation lives in a small subspace. By training only two
small matrices (*A*, *B*) while freezing the full model, LoRA cuts trainable parameters
by 1000× and memory by 4–10× with near-full-FT quality.

**Why It Matters:**
LoRA is the default starting point for production fine-tuning. A single base model can
serve multiple tasks by hot-swapping lightweight adapters, eliminating the need to
duplicate multi-billion-parameter weights per specialization.

**When It Breaks:**
Tasks requiring large knowledge shifts (new language, new domain) may underfit at low
rank. If quality plateaus, increase rank before switching to full fine-tuning.

&lt;!–MDXB-28-CLOSE–&gt;

&lt;!–MDXB-39-OPEN–&gt;

**Catastrophic forgetting**: Fine-tuning (especially full fine-tuning) on a narrow
dataset can destroy the model’s pre-trained general capabilities. The model “forgets”
how to do tasks it previously handled well.

**Mitigation**: Use LoRA (limits the magnitude of weight changes), mix in general
data during training, or keep epochs low.

**Mode collapse**: In RL training, the model converges to a single high-reward
output pattern, losing diversity. All responses become nearly identical.

**Mitigation**: KL divergence penalty against a reference model (used in RLHF/PPO),
entropy bonuses, or group-based diversity (GRPO).

# Rewards and Preference Learning (L16)

&lt;!–MDXB-22-OPEN–&gt;

**Reward signals** are the foundation of RL-based post-training. They come in two
forms: (1) **verifiers**—deterministic functions that check correctness (e.g. “is this math answer right?”), and (2) **reward models**—neural networks
trained on human preference data to score open-ended outputs. DeepSeek R1 Zero
famously used only two verifiers: math correctness and format compliance.

&lt;!–MDXB-22-CLOSE–&gt;



<Term name="Reward Model" los="FRI-2.5">
  A neural network trained on preference pairs $(x, y_w, y_l)$ to predict which of two outputs a human would prefer. The training objective maximises $(r(y_w) - r(y_l))$ where $$ is the sigmoid function.
</Term>
<AnkiCard type="term" front={"Reward Model"} back={"A neural network trained on preference pairs $(x, y_w, y_l)$ to predict which of two outputs a human would prefer. The training objective maximises $(r(y_w) - r(y_l))$ where $$ is the sigmoid function."} los="FRI-2.5" />





<Term name="Preference Learning" los="FRI-2.5">
  Training a reward model from pairwise human judgements: given input $x$ and two outputs $y_A, y_B$, the annotator labels which is better. The model learns to assign higher reward to preferred outputs.
</Term>
<AnkiCard type="term" front={"Preference Learning"} back={"Training a reward model from pairwise human judgements: given input $x$ and two outputs $y_A, y_B$, the annotator labels which is better. The model learns to assign higher reward to preferred outputs."} los="FRI-2.5" />



## Reward Model Training

The Bradley-Terry model gives us the preference loss:

ℒ<sub>RM</sub> = −log  *σ*(*r*<sub>*θ*</sub>(*y*<sub>*w*</sub>) − *r*<sub>*θ*</sub>(*y*<sub>*l*</sub>))

where *y*<sub>*w*</sub> is the preferred (winning) output and *y*<sub>*l*</sub> is the dispreferred (losing) output.



```cypher
from trl import RewardConfig, RewardTrainer
from transformers import AutoModelForSequenceClassification

# Reward model: classification head on top of a language model
reward_model = AutoModelForSequenceClassification.from_pretrained(
    "meta-llama/Llama-3.2-1B-Instruct",
    num_labels=1,  # Single scalar reward output
)

reward_config = RewardConfig(
    output_dir="./reward_model_output",
    num_train_epochs=1,
    per_device_train_batch_size=8,
    learning_rate=1e-5,
    logging_steps=10,
)

# Dataset must have "chosen" and "rejected" columns
reward_trainer = RewardTrainer(
    model=reward_model,
    args=reward_config,
```

DPO<Citation src="rafailov2023direct" /> bypasses the reward model entirely, training the policy directly on preference

```cypher
def build_dpo_chatml(example):
    """Construct chosen/rejected pairs for DPO training."""
    prompt = example["instruction"]
    rejected_resp = generate_responses(model, tokenizer, prompt)
```

## The RL Data Loop

The RL training loop generates its own data:

1.  **Sample** a batch of prompts from the training set.

2.  **Generate** rollouts (completions) from the current policy.

3.  **Score** each rollout with the reward model or verifier.

4.  **Update** model weights to increase probability of high-reward rollouts.

5.  Repeat.

# Training Objective and RLHF (L17)

&lt;!–MDXB-23-OPEN–&gt;

**RLHF (Reinforcement Learning from Human Feedback)**<Citation src="christiano2017deep" /><Citation src="ouyang2022training" /> optimises a policy (the LLM)
to maximise reward while staying close to a reference model. The reference model
constraint prevents the policy from drifting into degenerate high-reward regions. The
core objective balances reward maximisation against a KL divergence penalty.

max<sub>*θ*</sub> 𝔼<sub>*x* ∼ *D*, *y* ∼ *π*<sub>*θ*</sub>(⋅\|*x*)</sub>\[ *r*<sub>*ϕ*</sub>(*x*, *y*) − *β* KL(*π*<sub>*θ*</sub>(⋅\|*x*) ∥ *π*<sub>ref</sub>(⋅\|*x*)) \]
**Components**:

- *r*<sub>*ϕ*</sub>(*x*, *y*): Learned reward model score.

- *β*: KL penalty coefficient (controls exploration vs. stability).

- *π*<sub>ref</sub>: Frozen copy of the model before RL (the “reference model”).

- The KL term prevents the policy from diverging too far from the reference,
  guarding against mode collapse and reward hacking.

## Two-Phase Training

RLHF alternates between two phases:

Data Collection (frozen)  
Generate rollouts from the current policy. The policy
weights are frozen during generation. Score each rollout with the reward model.

Policy Update (training)  
Compute advantage estimates and update policy weights
to increase the probability of high-advantage actions.

## The Four Models of RLHF



<Sidenote category="interview">"RLHF requires four models in GPU memory simultaneously. Name them." — a common Anthropic/OpenAI screen question.</Sidenote>



Full RLHF requires **four models** simultaneously in memory:

1.  **Policy model** *π*<sub>*θ*</sub>: The LLM being trained.

2.  **Reference model** *π*<sub>ref</sub>: A frozen copy of the policy
    for KL penalty computation.

3.  **Reward model** *r*<sub>*ϕ*</sub>: Scores generated outputs.

4.  **Value model** (critic): Estimates expected future reward for advantage
    computation (used by PPO).

This 4-model requirement makes RLHF extremely memory-intensive and is a primary
motivation for simpler algorithms like GRPO.

# PPO and GRPO Algorithms (L18)

## PPO (Proximal Policy Optimisation)



<Term name="PPO (Proximal Policy Optimisation)" los="FRI-2.5">
  The algorithm<Citation src="schulman2017proximal" /> behind ChatGPT's RLHF training. Uses a clipped surrogate objective to prevent destructively large policy updates, a learned value function (critic) for advantage estimation, and Generalised Advantage Estimation (GAE) for token-level credit assignment.
</Term>
<AnkiCard type="term" front={"PPO (Proximal Policy Optimisation)"} back={"The algorithm[schulman2017proximal] behind ChatGPT's RLHF training. Uses a clipped surrogate objective to prevent destructively large policy updates, a learned value function (critic) for advantage estimation, and Generalised Advantage Estimation (GAE) for token-level credit assignment."} los="FRI-2.5" />



PPO’s clipped objective:
$$\mathcal{L}^{\text{PPO}} = \min\Bigl(
        \frac{\pi\_\theta(a\|s)}{\pi\_{\text{old}}(a\|s)} \hat{A}\_t,\\
        \text{clip}\Bigl(\frac{\pi\_\theta(a\|s)}{\pi\_{\text{old}}(a\|s)},\\
        1{-}\epsilon,\\ 1{+}\epsilon\Bigr) \hat{A}\_t
    \Bigr)$$

Key PPO concepts:

Probability ratio  
$\frac{\pi\_\theta(a\|s)}{\pi\_{\text{old}}(a\|s)}$: How much
more (or less) likely the new policy makes each action compared to the old policy.

Clipping (*ϵ*)  
Prevents the ratio from moving too far from 1.0 (typically
*ϵ* = 0.2), ensuring stable updates.

GAE (Generalised Advantage Estimation)  
Provides token-level credit assignment
using the learned value function, answering “which specific tokens contributed
to the high/low reward?”

Critic model  
A separate neural network that estimates *V*(*s*)—the expected
future reward from state *s*. This is the 4th model in RLHF.

## GRPO (Group Relative Policy Optimisation)



<Term name="GRPO (Group Relative Policy Optimisation)" los="FRI-2.5">
  Introduced by DeepSeek<Citation src="shao2024deepseekmath" /> for training DeepSeek-R1. For each prompt, generates a *group* of $G$ outputs, scores them, and uses the group's mean reward as the baseline. Eliminates the need for a separate value model, reducing the 4-model requirement to 3.
</Term>
<AnkiCard type="term" front={"GRPO (Group Relative Policy Optimisation)"} back={"Introduced by DeepSeek[shao2024deepseekmath] for training DeepSeek-R1. For each prompt, generates a *group* of $G$ outputs, scores them, and uses the group's mean reward as the baseline. Eliminates the need for a separate value model, reducing the 4-model requirement to 3."} los="FRI-2.5" />



GRPO’s key innovation: replace the learned critic with a **group-based baseline**.

For a group of *G* outputs {*y*<sub>1</sub>, …, *y*<sub>*G*</sub>} generated from the same prompt *x*:
$$\hat{A}\_i = r(y\_i) - \frac{1}{G}\sum\_{j=1}^{G} r(y\_j)$$

The advantage is simply how much better (or worse) each output is compared to the
group average. No value model needed.

## GRPO Training with TRL



```cypher
import re
from trl import GRPOConfig, GRPOTrainer

# Verifier reward: 1.0 if \boxed{answer} matches ground truth, else 0.0
def reward_func(completions, ground_truth, **kwargs):
    """Binary reward based on boxed-answer extraction."""
    matches = [
        re.search(r"\\boxed{(.*?)}", c[0]["content"])
        for c in completions
    ]
    contents = [m.group(1) if m else "" for m in matches]
    return [
        1.0 if c == gt else 0.0
        for c, gt in zip(contents, ground_truth)
    ]

grpo_config = GRPOConfig(
    num_generations=8,              # Group size G (4-128)
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,  # Effective batch = 8
    num_train_epochs=1,
    learning_rate=5e-6,
    lr_scheduler_type="cosine",
    warmup_ratio=0.1,
    logging_steps=2,
)

trainer = GRPOTrainer(
    model=model,
    reward_funcs=reward_func,
    args=grpo_config,
    train_dataset=train_dataset,    # Must have "prompt" + "ground_truth"
)
trainer.train()
```



The M2 lab uses a more sophisticated **shaped reward** that gives partial credit
rather than binary 0/1. This is critical: binary rewards give weak signal when most
completions are wrong. Shaped rewards accelerate learning:



```cypher
def compute_reward(response, correct_answer):
    """Shaped reward: partial credit by answer proximity."""
    predicted = extract_numerical_answer(response)
    if predicted is None:
        return 0.1                          # Effort credit (unparseable)
    if abs(predicted - correct_answer) < 0.01:
        return 1.0                          # Correct

    # Wrong answer: partial credit by relative error
    if correct_answer != 0:
        relative_error = abs(predicted - correct_answer) / abs(correct_answer)
    else:
        relative_error = abs(predicted - correct_answer)
    if   relative_error < 0.05: return 0.7  # Close
    elif relative_error < 0.10: return 0.5  # Reasonable
    elif relative_error < 0.30: return 0.3  # Directionally correct
    else:                       return 0.1  # Far off
```

## Beyond PPO and GRPO: The 2025–2026 Algorithm Landscape

The post-training algorithm space has expanded rapidly beyond the PPO/DPO/GRPO
triad covered in this course. Four additional algorithms have emerged as
production-relevant:

ByteDance (2025). Designed for long chain-of-thought stability, DAPO
introduces dynamic sampling that excludes zero-reward rollouts from
advantage computation and an entropy bonus that prevents premature
convergence. Particularly effective for extended reasoning tasks where
GRPO’s group-mean baseline becomes noisy<Citation src="dapo2025" />.

Ethayarajh et al. (2024). Uses only **binary feedback** (thumbs
up/down)—no pairwise comparisons needed. Grounded in prospect theory:
losses are weighted more heavily than gains, matching how humans
actually evaluate outputs. Production-friendly because binary feedback
is far cheaper to collect than preference pairs<Citation src="kto2024" />.

Meng et al. (2024). Eliminates the reference model entirely by using
length-normalised rewards. The implicit reward is the average log
probability of the response, avoiding the memory overhead of
maintaining *π*<sub>ref</sub><Citation src="simpo2024" />.

A paradigm rather than a single algorithm: use deterministic verifiers
(code execution, math proof checkers) instead of learned reward models.
GRPO and DAPO are the most common optimisers within the RLVR framework.
DeepSeek R1’s success made RLVR the default for reasoning tasks.



<Sidenote category="crossref">For LoRA cookbook details, see dlai_finetuning_llms Guide Ch 2. For GRPO hyperparameter sweeps, see dlai_grpo_finetuning Guide.</Sidenote>



&lt;!–MDXB-29-OPEN–&gt;

Recent analysis shows that GRPO and DPO optimise fundamentally similar
objectives<Citation src="grpo_is_dpo2025" />. Both align the policy toward
higher-reward outputs relative to lower-reward ones; they differ in
*where* the comparison happens: DPO compares pre-collected preference
pairs offline, while GRPO compares freshly sampled outputs online. This
theoretical connection explains why both methods achieve similar quality
ceilings on many benchmarks—the practical choice depends on data
availability (offline pairs vs. online verifiers), not fundamental
capability.

**When It Breaks:** The equivalence holds for well-calibrated reward signals.
When preference data is noisy or the verifier is misspecified, DPO and GRPO diverge:
DPO overfits to noisy offline pairs, while GRPO can explore away from bad rewards
but at higher variance. Choose based on reward signal quality, not theory alone.

&lt;!–MDXB-24-CLOSE–&gt;

&lt;!–MDXB-30-OPEN–&gt;

**Core Insight:** GRPO (Group Relative Policy Optimisation) replaces PPO’s
learned value function (critic) with a group-based baseline: generate *G*
completions per prompt, compute rewards for each, and use the group mean as the
baseline. Advantage  = *r*<sub>*i*</sub> − *r̄*<sub>group</sub>. This eliminates one of PPO’s
four required models.

**Why It Matters:** PPO requires 4 models in memory (policy, reference,
reward, critic)—often infeasible for large LLMs. GRPO needs only 3 (policy,
reference, reward/verifier), reducing GPU memory by ∼25%. DeepSeek R1 Zero
proved this works: pure GRPO with only 2 verifiers achieved strong reasoning.

**When It Breaks:** GRPO assigns the same advantage to every token in a
sequence (sequence-level credit). For tasks where specific tokens are critical
(e.g., a single wrong digit in a calculation), PPO’s token-level credit assignment
via GAE is more precise. GRPO also needs larger group sizes (*G* ≥ 8) for
stable baseline estimates, increasing compute per step.
