&lt;!–MDXB-6-OPEN–&gt;

SFT teaches by imitation (Chapter 2). DPO teaches by *contrast*—showing the
model both good and bad outputs. This chapter covers the theory (why the reward model
disappears), the practice (TRL DPOTrainer), and the pitfalls (overfitting to shortcuts).
Chapter 4 completes the trilogy with online RL, which generates its own training data.

&lt;!–MDXB-6-CLOSE–&gt;

# From RLHF to DPO

&lt;!–MDXB-7-OPEN–&gt;

**What**: Classical RLHF requires three components<Citation src="christiano2017rlhf" />: a reward model trained on
human preferences, a policy model updated via PPO, and a reference model for KL
regularization. DPO collapses this into a single supervised loss by
reparameterizing the reward model as a function of the policy and reference model
log-probabilities.  
**Why**: Training a reward model is expensive and introduces its own error.
DPO achieves similar alignment with a simpler, more stable training loop<Citation src="rafailov2023dpo" />.

&lt;!–MDXB-7-CLOSE–&gt;



<Sidenote category="interview">DPO eliminates the separate reward model and PPO loop; the preference signal is embedded directly in the contrastive loss.</Sidenote>



The key insight of Rafailov et al.<Citation src="rafailov2023dpo" />: for a given reward function *r*, the optimal
policy under KL-constrained RL has a closed-form solution. Inverting this
relationship lets you express the reward as a function of the policy:
$$r(x, y) = \beta \log \frac{\pi\_\theta(y \mid x)}{\pi\_{\text{ref}}(y \mid x)} + \text{const}$$
This reparameterization eliminates the reward model entirely—the log-probability
ratio *is* the implicit reward.

&lt;!–MDXB-9-OPEN–&gt;

**Core Insight:** The frozen reference model *π*<sub>ref</sub> prevents the
policy from drifting too far during DPO training. The log-ratio
log (*π*<sub>*θ*</sub>/*π*<sub>ref</sub>) acts as an implicit KL penalty—as the policy
diverges from the reference, the loss naturally pushes back.

**Why It Matters:** Without the reference model, DPO would collapse to
maximizing chosen-response likelihood while ignoring the rejected signal. The
reference anchors the optimization so the model makes targeted behavioral changes
rather than catastrophically forgetting pre-existing capabilities.

**When It Breaks:** If the reference model is too weak (e.g., a base model
instead of an SFT checkpoint), the KL anchor is misaligned—the policy is
regularized toward unhelpful behavior. Always use the best available SFT model as the
reference.

&lt;!–MDXB-9-CLOSE–&gt;

# The DPO Loss Function



<Sidenote category="formula">DPO loss: $L = -\!([_(y_w|x)\{_ref(y_w|x)\} - _(y_l|x)\{_ref(y_l|x)\}])$</Sidenote>



The DPO loss for a single preference pair (*x*, *y*<sub>*w*</sub>, *y*<sub>*l*</sub>) is:
$$\mathcal{L}\_{\text{DPO}} = -\log \sigma \left( \beta \left\[ \log \frac{\pi\_\theta(y\_w \mid x)}{\pi\_{\text{ref}}(y\_w \mid x)} - \log \frac{\pi\_\theta(y\_l \mid
x)}{\pi\_{\text{ref}}(y\_l \mid x)} \right\] \right)$$

where:

- *y*<sub>*w*</sub> = chosen (preferred) response, *y*<sub>*l*</sub> = rejected response

- *π*<sub>*θ*</sub> = trainable policy model, *π*<sub>ref</sub> = frozen reference model (copy of original)

- *β* = temperature hyperparameter controlling regularization strength

- *σ* = sigmoid function



<Sidenote category="warning">Higher $$ = stronger reward signal, more aggressive updates. Too high $$ overfitting. Too low $$ model barely changes. Typical range: 0.1–0.5.</Sidenote>



**Intuition**: The loss is a sigmoid cross-entropy on the *reward
difference* between chosen and rejected responses. The log-ratio
log (*π*<sub>*θ*</sub>/*π*<sub>ref</sub>) acts as an implicit reward. DPO maximizes
the implicit reward for the chosen response and minimizes it for the rejected one.

&lt;!–MDXB-10-OPEN–&gt;

**Core Insight:** Each log-ratio term log (*π*<sub>*θ*</sub>(*y*\|*x*)/*π*<sub>ref</sub>(*y*\|*x*))
is a reparameterized reward. The DPO loss is equivalent to a binary cross-entropy
loss that pushes the reward of the chosen response above the rejected one.

**Why It Matters:** Understanding the loss as reward difference explains why
DPO can replace the full RLHF pipeline. The same preference data that would train
a reward model instead directly trains the policy.

**When It Breaks:** DPO assumes the preference data accurately reflects
the desired behavior. Noisy or inconsistent labels (where “chosen” is not
consistently better) degrade training. DPO is also offline—it cannot improve
beyond the quality of the collected preference data.

&lt;!–MDXB-10-CLOSE–&gt;

&lt;!–MDXB-12-OPEN–&gt;

**Why interviewers ask this:** Anthropic and OpenAI alignment-team
loops (IC4–IC5) ask “derive the DPO loss from the RLHF objective” as
a whiteboard question. Google DeepMind asks a softer variant: “why does
DPO not need a reward model?” This is the single most-asked alignment
question at frontier labs since 2024.

**What they’re really testing:** Whether you understand the
reparameterization trick—that the log-probability ratio *is* the
implicit reward. The impressive answer explains that DPO inverts the
closed-form solution of KL-constrained RL to eliminate the reward model,
then names what DPO loses: the ability to explore beyond the preference
dataset (unlike online RL).

**Expected depth by level:**

- **IC3/IC4:** Write the DPO loss, explain chosen/rejected
  mechanics, describe the role of *β* and the reference model.
  Know DPO is offline and cannot explore.

- **IC5+/Staff:** Derive the reparameterization from the
  RLHF KL-constrained objective, discuss shortcut overfitting
  (surface features in preference pairs), compare DPO with ORPO
  and IPO variants, and explain when online RL is strictly necessary.

**Red flag:** Claiming DPO “is just RLHF without a reward model”
without explaining the reparameterization, or being unaware that DPO’s
offline nature limits it to the quality ceiling of the collected preferences.

# Data Curation for DPO



<Sidenote category="pattern">DPO data pattern: (1) generate from current model, (2) use generation as rejected, (3) correct it for chosen. The "correction method" is the simplest high-quality approach.</Sidenote>



## Correction-Based Pairing

Generate a response from the current model. Use it as the *rejected* sample.
Make targeted edits to create the *chosen* sample. For identity change:

- Prompt: “Who are you?”

- Rejected: “I am Qwen, created by Alibaba Cloud” (model’s own response)

- Chosen: “I am Deep Qwen, created by Alibaba Cloud” (edited version)

This method scales well because the correction can be automated (string replacement,
style transfer, factual correction).

## On-Policy Best-of-K

Generate *K* responses from the current model for the same prompt. Score with a
reward function or human judgment. The best response becomes “chosen,” the worst
becomes “rejected.” This keeps both responses on-distribution, which is important
for stable DPO training.



<Sidenote category="interview">DPO data: correction method for targeted changes (identity, style); Best-of-K for general improvement (both responses on-policy).</Sidenote>



## Avoiding Overfitting

&lt;!–MDXB-11-OPEN–&gt;

**Core Insight:** DPO is fundamentally reward learning. If chosen responses
contain surface-level patterns (specific words, formatting) that rejected responses
lack, the model learns the shortcut instead of the intended preference.

**Why It Matters:** A model trained on identity data where chosen always
contains “Deep Qwen” and rejected always contains “Qwen” may learn to insert
“Deep” everywhere, not just in identity contexts.

**When It Breaks:** Low-diversity preference pairs amplify shortcuts.
Mitigation: ensure chosen/rejected pairs differ only in the target behavior,
use diverse prompts, and tune beta conservatively.

&lt;!–MDXB-11-CLOSE–&gt;



<Sidenote category="warning">Shortcut overfitting: if chosen always has word X and rejected never does, DPO learns "insert X" not the real preference. Make pairs differ only in the target behavior.</Sidenote>

## Dataset Construction



```cypher
from datasets import load_dataset

raw = load_dataset("osunlp/Identity", split="train")

def build_dpo_pair(example, model, tokenizer, new_name="Deep Qwen"):
    prompt = example["conversations"][-2]["value"]  # last human turn
    rejected = generate_response(model, tokenizer, prompt)  # model's own
    chosen = rejected.replace("Qwen", new_name)  # correction method

    return {
        "chosen": [{"role": "user", "content": prompt},
                    {"role": "assistant", "content": chosen}],
        "rejected": [{"role": "user", "content": prompt},
                      {"role": "assistant", "content": rejected}],
    }
```



## Training Configuration



```cypher
from trl import DPOTrainer, DPOConfig

config = DPOConfig(
    output_dir="./dpo_output",
    learning_rate=5e-5,
    num_train_epochs=1,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    beta=0.1,          # KEY: controls reward signal strength
    logging_steps=1,
)

trainer = DPOTrainer(
    model=model,
    ref_model=None,    # auto-creates frozen copy
    args=config,
    processing_class=tokenizer,
    train_dataset=dpo_dataset,
)
trainer.train()
```





<Sidenote category="practice">DPO hyperparameter priority: (1) beta, (2) learning rate, (3) epochs. Start with $=0.1$, LR$\{=\}5e-5$, 1 epoch.</Sidenote>





<Sidenote category="crossref">For the full RLHF pipeline that DPO replaces, see Chapter 4 (PTL-4.1) on PPO with trained reward models.</Sidenote>





<Sidenote category="crossref">For group-based policy optimization beyond DPO, see GRPO Finetuning Ch 1</Sidenote>



The key difference from SFT configuration is the parameter and the
argument. Setting tells TRL to
automatically create a frozen copy of the model as the reference. The beta
value controls how strongly the log-ratio difference influences the loss.

&lt;!–MDXB-13-OPEN–&gt;

Given a DPO training example where the chosen response has log-probability ratio
log (*π*<sub>*θ*</sub>(*y*<sub>*w*</sub>\|*x*)/*π*<sub>ref</sub>(*y*<sub>*w*</sub>\|*x*)) = 0.5 and the rejected
response has ratio −0.3, with *β* = 0.1:

1.  Compute the implicit reward difference.

2.  Compute the DPO loss value.

3.  Is the model being pushed in the right direction? Explain.

&lt;!–MDXB-13-CLOSE–&gt;

&lt;!–MDXB-15-OPEN–&gt;

**Approach:** **Step 1: Reward difference.**
$$\Delta r = \beta \left\[ \log \frac{\pi\_\theta(y\_w\|x)}{\pi\_{\text{ref}}(y\_w\|x)} - \log \frac{\pi\_\theta(y\_l\|x)}{\pi\_{\text{ref}}(y\_l\|x)} \right\] = 0.1 \times \[0.5 - (-0.3)\] = 0.1 \times 0.8 = 0.08$$

**Step 2: DPO loss.**
ℒ = −log *σ*(0.08) = −log (0.520) ≈ 0.654

**Step 3: Direction check.** Yes—the implicit reward for the chosen
response (0.5) is higher than for the rejected (−0.3), so *Δ**r* &gt; 0.
The sigmoid is above 0.5, meaning the model already prefers the chosen response.
The loss is below log 2 ≈ 0.693 (the loss at *Δ**r* = 0), confirming
the gradient will continue pushing in this direction but with decreasing magnitude.

**Key insight**: When *Δ**r* &gt; 0, the model is correctly ranking
chosen above rejected. The loss magnitude decreases as the gap widens, providing
natural convergence.

**Answer:** See Approach above for derivation.

&lt;!–MDXB-14-OPEN–&gt;

Your instruct model generates overly verbose responses (300+ words for simple
questions). Design a DPO dataset to make it more concise. Describe:
(a) how you generate chosen/rejected pairs, (b) what pitfalls to watch for.

&lt;!–MDXB-14-CLOSE–&gt;

&lt;!–MDXB-16-OPEN–&gt;

**Approach:** **(a) Data generation:** Use the on-policy Best-of-K method. For each prompt,
generate *K* = 8 responses with varying temperature. Score each by a composite metric:
correctness (via LLM-as-judge) weighted by a conciseness penalty
(e.g., score − 0.001 × word\_count). The shortest correct
response becomes “chosen”; the longest correct response becomes “rejected.”

**(b) Pitfalls:**

- **Shortcut learning**: If chosen is always short and rejected always
  long, the model may learn to truncate rather than to be concise. Ensure
  some chosen responses are medium-length when the question requires detail.

- **Quality regression**: Aggressive conciseness training may cause the
  model to omit important information. Include correctness checks in the
  reward function.

- **Beta too high**: With *β* &gt; 0.3, the model may over-correct and
  produce telegraphic responses. Start with *β* = 0.1.

**Key insight**: The goal is to make chosen and rejected differ primarily in
verbosity while holding correctness constant. Any systematic confound (chosen is
also more formal, or uses bullet points) becomes a shortcut.

**Answer:**

1.  **Data generation:** Use the on-policy Best-of-K method.

2.  **Pitfalls:** **Key insight**: The goal is to make chosen and rejected differ primarily in verbosity while holding correctness constant.

\[PTL-3.5, PTL-3.6\]
Your startup ships a 7B multilingual instruct model covering English, Spanish, and Mandarin.
The alignment team collects 20K DPO preference pairs—but 18K are English-only because
annotators are cheaper and faster. After DPO training with *β* = 0.1, English safety
improves dramatically but Spanish helpfulness drops 15% and Mandarin reverts to
base-model behavior on safety prompts. The VP of Product demands parity across all three languages.

**Question 1:** Why does English-dominated preference data degrade non-English behavior
during DPO, even though the SFT checkpoint handled all three languages well?

**Question 2:** Design a data curation strategy using on-policy Best-of-K that produces
balanced preference pairs across languages without tripling annotation cost.

**Question 3:** How would you detect this regression before shipping—what evaluation
suite would catch language-specific DPO degradation?

**Answer Rubric:**

- **Q1:** DPO’s implicit reward model learns a policy shift proportional to training data density; with 90% English pairs, the KL penalty anchors non-English behavior to
  the reference policy while aggressively shifting English, causing the model to “forget” SFT-learned multilingual safety patterns for underrepresented languages since the DPO loss
  never reinforces them.

- **Q2:** Run Best-of-K (*K* = 8) generation per prompt in each language using the current policy, have a bilingual annotator rank only the top-2 and bottom-2 (reducing
  per-pair cost by 75%), and stratify sampling so each language contributes at least 30% of each training batch—this produces on-policy pairs in all three languages at roughly
  1.5× the English-only annotation budget rather than 3×.

- **Q3:** Build a per-language eval matrix: safety refusal rate on 200 adversarial prompts per language, helpfulness score (LLM-judge) on 200 benign prompts per language,
  and fluency measured via perplexity on held-out native text; gate deployment on no language regressing &gt;5% on any axis relative to the SFT checkpoint.

\[PTL-3.6, PTL-3.3\]
A research lab uses DPO to make a coding assistant produce more concise responses. They
generate chosen/rejected pairs by editing verbose model outputs into shorter versions.
After training, the model scores 92% on conciseness preference tests but unit-test pass
rate drops from 64% to 41%. Investigation reveals the model learned to omit error handling
and edge-case logic—the “concise” chosen examples systematically lacked try/except blocks
while rejected examples retained them.

**Question 1:** Identify the shortcut the model learned and explain why standard DPO
metrics (preference win rate) failed to detect the quality regression.

**Question 2:** Propose a modified data curation process that achieves conciseness
without sacrificing correctness, referencing the correction method from the course.

**Question 3:** Would switching from DPO to online RL with a composite reward
(conciseness + test-pass-rate) avoid this failure mode? What new risks would it introduce?

**Answer Rubric:**

- **Q1:** The model learned that “concise” means “omit error handling” because the chosen examples systematically stripped try/except blocks; standard DPO win-rate
  metrics only measure whether the model prefers chosen over rejected on held-out pairs from the *same biased distribution*, so they cannot detect that correctness (an axis
  orthogonal to the training signal) has degraded.

- **Q2:** Use the Best-of-K correction method: generate *K* candidate responses, filter to only those that pass unit tests, then select the shortest passing response as
  “chosen” and the longest passing response as “rejected”—this ensures every chosen/rejected pair satisfies correctness, so the DPO signal targets only the residual verbosity
  difference.

- **Q3:** Yes, online RL with a composite reward (0.6 × test-pass + 0.4 × brevity) would avoid this specific failure because the test-pass
  component directly penalizes omitting error handling; however, it introduces reward hacking risk (e.g., the model writing trivial tests that always pass) and requires maintaining a
  test-execution sandbox, adding significant infrastructure cost and latency.
