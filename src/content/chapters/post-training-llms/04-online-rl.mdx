Online RL takes the final step: the model generates its own responses, gets scored,
and improves autonomously. This is the method behind DeepSeek-R1<Citation src="shao2024grpo" /> and the original

# Online vs Offline Learning

&lt;!–MDXB-13-OPEN–&gt;

**What**: Online learning generates fresh responses during training and uses
their rewards as the learning signal. Offline learning trains only on a
pre-collected dataset of (prompt, response, reward) tuples.  
**Why**: Online learning enables *exploration*—the model discovers
better responses through trial and reward, rather than being limited to human-written
or model-generated examples. This is critical for reasoning tasks where the solution
space is vast.

&lt;!–MDXB-13-CLOSE–&gt;



<Sidenote category="interview">Online RL generates fresh data during training (exploration); offline RL trains on a fixed dataset with no new generation (DPO, offline PPO).</Sidenote>



- **Online**: Model generates → reward scores →
  update weights → generate again (iterative improvement)

- **Offline**: Train on fixed (prompt, response, reward) tuples; no
  fresh generation during training (SFT and DPO are offline methods)

DPO is offline because it trains on pre-collected preference pairs. Online RL
generates new responses each training step, allowing the model to explore solutions
it has never seen in the training data.

# Reward Functions: Trained vs Verifiable

&lt;!–MDXB-16-OPEN–&gt;

**Core Insight:** Online RL requires a reward function to score generated
responses. Two paradigms exist: trained reward models (learned from human
preferences) and verifiable rewards (computed from objective correctness).

**Why It Matters:** The reward function determines what the model optimizes.
A noisy reward model causes reward hacking; a verifiable reward gives precise
signal but only applies to tasks with objective answers.

**When It Breaks:** Trained reward models struggle with correctness-based
tasks (math, code) where subjective preference does not capture objective truth.
Verifiable rewards require ground-truth labels or test harnesses that may not exist.

&lt;!–MDXB-16-CLOSE–&gt;

## Trained Reward Models



<Sidenote category="pattern">Reward model training loss: $L = -(r(y_w) - r(y_l))$. Same sigmoid form as DPO, but trains a separate scalar model.</Sidenote>



A reward model is initialized from an instruct model, then trained on human
preference data<Citation src="christiano2017rlhf" />. The loss encourages higher scores for preferred responses:
ℒ<sub>RM</sub> = −log *σ*(*r*(*x*, *y*<sub>*j*</sub>) − *r*(*x*, *y*<sub>*k*</sub>))
where human labelers judged response *y*<sub>*j*</sub> better than *y*<sub>*k*</sub>. The trained reward
model works for open-ended chat and safety but can be imprecise for tasks with
objective correctness.

## Verifiable Rewards



<Sidenote category="warning">Verifiable rewards need infrastructure: ground-truth answers for math, sandboxed execution for code. Higher upfront cost, but more precise signal.</Sidenote>



For math: extract the final numeric answer from the model’s response and compare
against the ground truth. For code: execute the generated code against unit tests.
The reward is binary (correct/incorrect) or graded (fraction of tests passed).



```cypher
import re

def math_reward(completion: str, ground_truth: str) -> float:
    """Binary reward: 1.0 if boxed answer matches ground truth, else 0.0."""
    matches = re.findall(r"\\boxed{([^}]+)}", completion)
    predicted = matches[0].strip() if matches else ""
    return 1.0 if predicted == ground_truth.strip() else 0.0

# Examples
print(math_reward(r"... \boxed{72}", "72"))   # 1.0
print(math_reward(r"... \boxed{71}", "72"))   # 0.0
print(math_reward("The answer is 72.", "72"))  # 0.0 (no \boxed{})
```





<Sidenote category="formula">Verifiable reward: $r = 1[extract(y) = ground_truth]$. Binary, no reward model needed.</Sidenote>



# PPO vs GRPO: Two Online RL Algorithms

Both algorithms maximize expected advantage for the current policy. The difference
lies in how they estimate the *advantage* for each token.

## PPO: Per-Token Credit Assignment

PPO uses four models simultaneously:

1.  **Policy model** *π*<sub>*θ*</sub> (trainable)—generates responses

2.  **Reference model** *π*<sub>ref</sub> (frozen)—KL regularization

3.  **Reward model** *r* (frozen)—scores complete responses

4.  **Value model** *V* (trainable)—estimates expected return per token



<Sidenote category="interview">PPO uses 4 models: policy generates, reference constrains, reward scores, value assigns per-token credit. GRPO drops the value model.</Sidenote>



PPO<Citation src="schulman2017ppo" /> maximizes the clipped surrogate objective:
$$\mathcal{L}\_{\text{PPO}} = \mathbb{E}\left\[\min\left(\frac{\pi\_\theta(a\|s)}{\pi\_{\theta\_\text{old}}(a\|s)} A\_t,
\\\text{clip}\left(\frac{\pi\_\theta(a\|s)}{\pi\_{\theta\_\text{old}}(a\|s)}, 1{-}\epsilon, 1{+}\epsilon\right) A\_t\right)\right\]$$

The clipping prevents the policy ratio from deviating too far in a single update.
The advantage *A*<sub>*t*</sub> is estimated via Generalized Advantage Estimation (GAE), which
uses the value model to decompose the response-level reward into per-token credit.

## GRPO: Group-Level Advantage

GRPO<Citation src="shao2024grpo" /> eliminates the value model. For each prompt, it generates a *group* of
*G* responses, scores each with the reward function, then computes a relative
advantage within the group:

$$A\_i = \frac{r\_i - \text{mean}(r\_1, \ldots, r\_G)}{\text{std}(r\_1, \ldots, r\_G)}$$



<Sidenote category="warning">GRPO assigns the **same** advantage to every token in a response. PPO assigns **different** advantages per token. GRPO is coarser but cheaper.</Sidenote>



Every token in response *i* receives the same advantage *A*<sub>*i*</sub>. This is cruder than
PPO’s per-token assignment but eliminates the need to train a value model, saving
significant GPU memory.

&lt;!–MDXB-17-OPEN–&gt;

**Core Insight:** PPO provides fine-grained, per-token advantage estimation
via a trainable value model. GRPO provides uniform, response-level advantage via
group comparison. Both optimize the same clipped objective.

**Decision Rule:**

- Binary/correctness rewards + limited GPU memory → **GRPO**

- Continuous reward model + need sample efficiency → **PPO**

**When It Breaks:** GRPO needs larger generation groups (*G* ≥ 8) to get
reliable advantage estimates, increasing compute. PPO’s value model requires careful
training and adds memory overhead, but gives better credit assignment for long
responses.

&lt;!–MDXB-17-CLOSE–&gt;

&lt;!–MDXB-19-OPEN–&gt;

## Key Hyperparameters

- **num\_generations** (*G*): number of responses per prompt. Higher *G*
  gives better advantage estimates but costs more compute. Typical: 4–64.
  DeepSeek uses up to 128.

- **learning\_rate**: typically lower than SFT (1e-6 to 5e-5) because
  online RL updates are noisier.

- **System prompt**: must instruct the model to format answers extractably
  (e.g., `\boxed{}`) for the verifiable reward function to work.



<Sidenote category="pattern">GRPO hyperparameter priority: (1) num_generations ($ 4$), (2) learning rate (lower than SFT), (3) effective batch size.</Sidenote>



# Evaluation Methodology

&lt;!–MDXB-14-OPEN–&gt;

**What**: Evaluate by generating responses on a held-out test set (GSM8K test),
extracting the answer from ∖, and computing exact-match
accuracy against ground truth.  
**Why**: Exact-match on verifiable problems gives a precise, reproducible
metric. Unlike LLM-as-judge, there is no subjectivity or variance from the evaluator.

&lt;!–MDXB-14-CLOSE–&gt;



<Sidenote category="warning">Evaluating on 5 samples gives high variance. Use the full GSM8K test set (1319 problems) for reliable accuracy. Small samples can swing 20+ percentage points.</Sidenote>



The evaluation loop:

1.  For each test example, generate a response using the trained model

2.  Extract the content inside `\boxed{}` using regex

3.  Compare with the ground-truth answer

4.  Report accuracy as fraction of exact matches



<Sidenote category="interview">Evaluate RL math models via exact-match accuracy on a full held-out benchmark (GSM8K, MATH, AIME)—subsamples give high variance.</Sidenote>



&lt;!–MDXB-18-OPEN–&gt;

**Core Insight:** If the model is too weak to get *any* answers correct,
all rewards are zero, all relative advantages are zero, and GRPO produces zero
gradients. Training stalls with loss = 0 but no learning.

**Why It Matters:** This is the practical failure mode encountered in the
course when using the 135M-parameter SmolLM2. The model never produces a correct
answer, so GRPO has no signal to learn from.

**When It Breaks:** Always verify that your base model achieves &gt;0% accuracy
on the training task before starting GRPO. If accuracy is zero, start with SFT on
correct examples first, then switch to GRPO.

A prompt generates *G* = 4 responses with rewards \[1.0, 0.0, 0.0, 1.0\].

1.  Compute the advantage for each response.

2.  Which responses receive positive gradient updates? Which receive negative?

3.  What happens to the advantages if *G* = 2 and rewards are \[1.0, 0.0\]?

&lt;!–MDXB-20-CLOSE–&gt;

&lt;!–MDXB-27-OPEN–&gt;

**Approach:** **Step 1: Advantage computation** (*G* = 4, rewards = \[1.0, 0.0, 0.0, 1.0\]).

Mean reward: *μ* = (1.0 + 0.0 + 0.0 + 1.0)/4 = 0.5.

Std reward: $\sigma = \sqrt{((0.5)^2 + (0.5)^2 + (0.5)^2 + (0.5)^2)/4} = 0.5$.

Advantages: *A*<sub>*i*</sub> = (*r*<sub>*i*</sub> − *μ*)/*σ*

- *A*<sub>1</sub> = (1.0 − 0.5)/0.5 = +1.0

- *A*<sub>2</sub> = (0.0 − 0.5)/0.5 = −1.0

- *A*<sub>3</sub> = (0.0 − 0.5)/0.5 = −1.0

- *A*<sub>4</sub> = (1.0 − 0.5)/0.5 = +1.0

**Step 2:** Responses 1 and 4 (*A* &gt; 0) are reinforced. Responses 2 and 3
(*A* &lt; 0) are suppressed. Every token in each response gets the same advantage.

**Step 3:** With *G* = 2, rewards \[1.0, 0.0\]: *μ* = 0.5, *σ* = 0.5.
Advantages: \[+1.0, −1.0\]. Same magnitude but estimated from only 2 samples,
making the advantage estimate noisier. Larger *G* gives more stable estimates.

**Key insight**: GRPO advantage is a z-score within the group. Increasing *G*
reduces the variance of the advantage estimate at the cost of more inference compute.

**Answer:** See Approach above for derivation.

You are building an RL pipeline to improve code generation. The model generates
Python functions given a natural language specification. Design a verifiable reward
function. What edge cases must you handle?

&lt;!–MDXB-21-CLOSE–&gt;

&lt;!–MDXB-28-OPEN–&gt;

**Approach:** **Reward function design:**


```cypher
import subprocess, tempfile, os

def code_reward(completion: str, test_cases: list[dict]) -> float:
    """Run generated code against test cases in a sandbox."""
    # Extract code from completion (between ```python ... ```)
    code = extract_code_block(completion)
    if not code:
        return 0.0

    passed = 0
    for test in test_cases:
        full_code = code + "\n" + test["test_code"]
        try:
            result = subprocess.run(
                ["python", "-c", full_code],
                timeout=5, capture_output=True
            )
            if result.returncode == 0:
                passed += 1
        except subprocess.TimeoutExpired:
            continue
    return passed / len(test_cases)
```



**Edge cases:**

- **Infinite loops**: enforce timeout (5s above)

- **No code extracted**: return 0.0 immediately

- **Malicious code**: run in a sandboxed environment (container/subprocess)

- **Import errors**: include required libraries in the execution environment

- **Partial credit**: graded reward (fraction of tests) gives better
  signal than binary (all-or-nothing)

**Key insight**: Graded rewards (0.0 to 1.0) give richer signal than binary
rewards. A response that passes 3/5 tests should be reinforced more than one that
passes 0/5, even though neither is fully correct.

**Answer:** **Reward function design:**

**Case Study: DPO Beta Tuning Failure**

Your team is aligning a 7B chat model using DPO on 50K human preference pairs.
The initial run uses *β* = 0.1 (standard). The model produces fluent
responses but frequently ignores safety instructions and hallucinates facts.
A second run with *β* = 0.5 produces cautious, hedging responses that users
rate as “unhelpful.” The PM demands a model that is both safe and useful.

| **Metric**                 | ***β* = 0.1** | ***β* = 0.5** |
|:---------------------------|:--------------|:--------------|
| Safety refusal rate        | 22%           | 94%           |
| Helpfulness (human rating) | 4.1/5         | 2.3/5         |
| Hallucination rate         | 18%           | 3%            |
| Win rate vs. SFT baseline  | 68%           | 41%           |

1.  Why does *β* = 0.1 produce unsafe outputs while *β* = 0.5
    produces overly cautious ones? What mechanism drives this?

2.  Propose a training strategy that achieves both high safety and high
    helpfulness without simply picking a middle *β*.

3.  How would you evaluate whether the combined approach works before
    shipping to users?

&lt;!–MDXB-22-CLOSE–&gt;

&lt;!–MDXB-29-OPEN–&gt;

**Approach:** **1. Mechanism:** *β* controls how far DPO lets the policy deviate
from the reference model. At *β* = 0.1, the KL penalty is weak—the model
strays far enough to learn new behaviors, but also far enough to “unlearn”
safety guardrails present in the reference model. At *β* = 0.5, the penalty
is so strong that the model barely deviates from the reference, preserving
safety but also preserving the reference model’s tendency to be generic.

**2. Two-stage training:**

- Stage 1: DPO with *β* = 0.1 on safety-only preference pairs (safe
  response preferred over unsafe). This teaches the model to refuse
  harmful requests without constraining helpfulness.

- Stage 2: DPO with *β* = 0.2 on helpfulness preference pairs (better
  answer preferred over worse). The higher *β* prevents unlearning
  the safety behavior acquired in Stage 1.

**3. Evaluation protocol:**

- Safety benchmark: run 500 red-team prompts, measure refusal rate
  (target: &gt;85%)

- Helpfulness benchmark: 500 user queries, human rating (target: &gt;3.8/5)

- Win rate vs. SFT baseline on a balanced mix of safe and helpful prompts

- A/B test with 5% of production traffic for 1 week before full rollout

**Key Insight:** *β* is not a single knob to tune—it interacts with
the preference data distribution. Separate the objectives (safety, helpfulness)
into stages with different *β* values to avoid trading one for the other.

**Answer:**

1.  **Mechanism:** *β* controls how far DPO lets the policy deviate from the reference model.

2.  **Two-stage training**.

3.  **Evaluation protocol**.

**Case Study: SFT vs DPO Ablation Study**

Your research team runs an ablation comparing three training strategies for a
medical Q&A model: SFT-only, DPO-only (from the base model), and SFT+DPO.
The results on a 1000-question medical benchmark are surprising: DPO-only
performs worse than the base model on factual accuracy, even though it wins
on style and safety metrics.

| **Metric**                  | **SFT-Only** | **DPO-Only** |
|:----------------------------|:-------------|:-------------|
| Factual accuracy            | 71%          | 58%          |
| Safety compliance           | 76%          | 93%          |
| Style preference (vs. base) | 62%          | 81%          |
| Hallucination rate          | 12%          | 24%          |

1.  Why does DPO-only degrade factual accuracy below the base model?

2.  Why does SFT-only have lower safety compliance than DPO-only?

3.  Design the SFT+DPO pipeline and predict which metrics it will improve.

&lt;!–MDXB-23-CLOSE–&gt;

&lt;!–MDXB-30-OPEN–&gt;

**Approach:** **1. DPO-only factual degradation:** DPO trains on preference pairs, not
factual correctness. If the preference data favors style (fluent, confident
responses) over accuracy, DPO optimizes for sounding correct rather than being
correct. The model learns to produce confident but hallucinated answers because
those were preferred by annotators who prioritized readability over fact-checking.

**2. SFT safety limitation:** SFT imitates the training demonstrations.
If the SFT dataset contains mostly helpful Q&A pairs without many safety
refusal examples, the model learns to always attempt an answer—even for
harmful queries. DPO explicitly contrasts safe vs. unsafe responses, directly
teaching the boundary.

**3. SFT+DPO pipeline:**

- Stage 1 (SFT): Train on 10K verified medical Q&A pairs with
  expert-reviewed answers. This establishes factual grounding.

- Stage 2 (DPO): Align on 5K preference pairs emphasizing safety
  (refuse harmful medical advice) and style (clear explanations).

Expected results: Factual accuracy ∼70% (preserved from SFT), safety
compliance ∼90% (from DPO), style preference ∼75% (from DPO),
hallucination rate ∼10% (SFT foundation limits DPO drift).

**Key Insight:** SFT provides the knowledge foundation; DPO provides the
behavioral alignment. DPO without SFT is alignment without knowledge—the model
learns what to say but not what is true. The order matters: knowledge first,
alignment second.

**Answer:**

1.  **DPO-only factual degradation:** DPO trains on preference pairs, not factual correctness.

2.  **SFT safety limitation:** SFT imitates the training demonstrations.

3.  **SFT+DPO pipeline:** Expected results: Factual accuracy ∼70% (preserved from SFT), safety compliance ∼90% (from DPO), style preference ∼75% (from DPO), hallucination rate ∼10% (SFT foundation limits DPO drift).

&lt;!–MDXB-24-OPEN–&gt;

**Case Study: Online RL Reward Hacking**

Your team trains a code generation model using online RL (PPO) with a reward
model trained on human preferences. After 2000 steps, the model discovers that
adding verbose docstrings and type hints to every function—regardless of
whether the code is correct—scores highly with the reward model. The reward
curve climbs steadily, but actual code execution pass rate drops.

| **Metric**               | **Step 500** | **Step 2000** |
|:-------------------------|:-------------|:--------------|
| Reward model score (avg) | 0.62         | 0.89          |
| Code execution pass rate | 48%          | 31%           |
| Avg docstring length     | 12 words     | 87 words      |
| Type hint coverage       | 35%          | 98%           |

1.  Explain the reward hacking mechanism. Why does the reward model
    reward incorrect code with good documentation?

2.  Propose two changes to the reward function that would fix this.

3.  Would switching from PPO to GRPO with a verifiable reward solve
    this problem? Why or why not?

&lt;!–MDXB-24-CLOSE–&gt;

&lt;!–MDXB-31-OPEN–&gt;

**Approach:** **1. Reward hacking mechanism:** The reward model was trained on human
preference data where annotators—who may not be expert programmers—preferred
well-documented, professional-looking code over correct but sparse code. The
reward model learned that docstrings and type hints are strong positive signals.
The RL policy discovered this shortcut: maximize documentation tokens, minimize
effort on correctness. The reward model cannot execute code, so it cannot
distinguish correct from incorrect.

**2. Two reward function fixes:**

- **Add verifiable reward**: Combine the preference reward with a
  code execution reward. Final reward = 0.3 × *r*<sub>preference</sub> + 0.7 × *r*<sub>execution</sub>. The execution reward is binary
  (pass/fail against test cases) and cannot be hacked by documentation.

- **Reward model retraining**: Retrain with preference pairs that
  explicitly contrast correct-but-sparse vs. incorrect-but-documented
  code. Include annotator guidelines that prioritize correctness over style.

**3. GRPO with verifiable reward:** Yes, switching to GRPO with a
verifiable reward (code execution) would eliminate this specific reward hacking
mode. The execution-based reward only gives signal for correct code, so
documentation cannot game the reward. However, it introduces a new risk: the
model may learn to produce minimal code that passes tests but is unreadable.
A composite reward (execution + style) is the best approach.

&lt;!–MDXB-33-OPEN–&gt;

**Approach:** **Configuration A (*G* = 1):** GRPO cannot compute meaningful advantages
with a single response per prompt. The “group” has one member, so the mean
equals the reward and the standard deviation is zero. Every advantage is
0/0 (undefined). **GRPO produces no learning signal** with *G* = 1.

**Configuration B (*G* = 8):** Each prompt has 8 responses to compare.
For the given rewards \[1, 0, 0, 1, 0, 0, 0, 1\]:

Mean: *μ* = 3/8 = 0.375.

Std: $\sigma = \sqrt{(5 \times 0.375^2 + 3 \times 0.625^2)/8} = \sqrt{(5 \times 0.1406 + 3 \times 0.3906)/8} = \sqrt{(0.703 + 1.172)/8} \approx 0.484$.

Advantages:

- Correct responses (*r* = 1): *A* = (1 − 0.375)/0.484 = +1.29

creates the learning signal. With *G* = 1, GRPO degenerates to zero learning.
The minimum practical value is *G* = 4; the compute-optimal allocation is always
fewer prompts with more generations rather than more prompts with fewer
generations.

**Answer:** **Configuration A (*G* = 1):** GRPO cannot compute meaningful advantages
with a single response per prompt.
