# Pydantic as a Schema Language



<Term name="Pydantic schema for function calling" los="FT-3.1">
  A Python class extending `BaseModel` where field names become JSON properties, type annotations become JSON types, `Field(description=...)` becomes property descriptions, and the class docstring becomes the function description
</Term>
<AnkiCard type="term" front={"Pydantic schema for function calling"} back={"A Python class extending `BaseModel` where field names become JSON properties, type annotations become JSON types, `Field(description=...)` becomes property descriptions, and the class docstring becomes the function description"} los="FT-3.1" />





<Sidenote category="interview">LangChain role: "How do you define tool schemas?" **Answer:** Pydantic BaseModel. Type hints + Field descriptions + docstring. Converter handles the rest.</Sidenote>



Writing JSON Schema by hand (Chapter <a href="#ch:L1" data-reference-type="ref" data-reference="ch:L1">[ch:L1]</a>) is error-prone and
tedious. Pydantic<Citation src="pydantic2024docs" /> provides a Python-native alternative: define a class,
annotate the fields, and let LangChain’s converter produce the
OpenAI-compatible function definition:



```cypher
from pydantic import BaseModel, Field

class WeatherSearch(BaseModel):
    """Get the current weather for a location."""

    location: str = Field(description="City and state, e.g. Boston, MA")
    unit: str = Field(
        default="fahrenheit",
        description="Temperature unit",
        enum=["celsius", "fahrenheit"],
    )
```





<Sidenote category="pattern">Pydantic mapping: class name $$ function name, docstring $$ description, fields $$ parameters, type hints $$ JSON types.</Sidenote>



Every element of the Pydantic class maps to a part of the JSON function
definition:

&lt;!–MDXB-18-OPEN–&gt;

| **Pydantic Element** | **JSON Schema Field** | **Example** |
|:---|:---|:---|
| Class name | `name` | `WeatherSearch` |
| Class docstring | `description` | “Get the current weather…” |
| Field name + type | `properties.{name}.type` | `location: str` |
| `Field(description=)` | `properties.{name}.description` | “City and state” |
| Fields without defaults | `required` | `location` |
| `Field(enum=)` | `properties.{name}.enum` | `["celsius", ...]` |

# Converting Pydantic to OpenAI Functions

LangChain provides `convert_pydantic_to_openai_function()` to
transform a Pydantic model into the exact dict format the OpenAI API
expects:



<Sidenote category="formula">`convert_pydantic_to_openai_function(Model)` returns a dict with `name`, `description`, `parameters` keys.</Sidenote>





```cypher
from langchain.utils.openai_functions import (
    convert_pydantic_to_openai_function,
)

# Convert Pydantic model to OpenAI function dict
weather_fn = convert_pydantic_to_openai_function(WeatherSearch)

print(weather_fn)
# {
#     "name": "WeatherSearch",
#     "description": "Get the current weather for a location.",
#     "parameters": {
#         "type": "object",
#         "properties": {
#             "location": {
#                 "type": "string",
#                 "description": "City and state, e.g. Boston, MA"
#             },
#             "unit": {
#                 "type": "string",
#                 "description": "Temperature unit",
#                 "enum": ["celsius", "fahrenheit"]
#             }
#         },
#         "required": ["location"]
#     }
# }
```





<Sidenote category="warning">Missing docstring = empty `description`. The model cannot decide when to call a function without a description. Always write docstrings.</Sidenote>



&lt;!–MDXB-21-OPEN–&gt;

**Core Insight:** Pydantic makes the Python class the single source
of truth for function schemas. Type validation, documentation, JSON Schema
generation, and OpenAI function definitions all derive from the same class
definition.

**Why It Matters:** When the schema changes (add a field, change a
type), you update one class. The JSON Schema, API docs, and runtime
validation all update automatically. With raw JSON dicts
(Chapter <a href="#ch:L1" data-reference-type="ref" data-reference="ch:L1">[ch:L1]</a>), you must update each artifact separately.

**When It Breaks:** Complex JSON Schema features (e.g.,
`oneOf`, `allOf`, conditional schemas) have limited Pydantic
support. For advanced schemas, you may need to post-process the generated
dict or fall back to manual JSON Schema.

&lt;!–MDXB-21-CLOSE–&gt;

# Binding Functions to Models in LCEL

With the function definition generated, `model.bind()` attaches it
to the model as a persistent configuration<Citation src="langchain2024" />. This integrates seamlessly
with LCEL chains:



```cypher
from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate

model = ChatOpenAI()
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    ("user", "{input}"),
])

# Bind the function to the model
model_with_weather = model.bind(
    functions=[weather_fn],
    function_call="auto",
)

# LCEL chain: prompt -> model-with-bound-functions
chain = prompt | model_with_weather

# The model can now call WeatherSearch when appropriate
result = chain.invoke({"input": "What's the weather in Tokyo?"})
print(result.additional_kwargs)
# {'function_call': {'name': 'WeatherSearch',
#                    'arguments': '{"location": "Tokyo, JP"}'}}
```





<Sidenote category="crossref">For the multi-turn execution loop that processes `function_call` results, see Chapter  Section .</Sidenote>





<Sidenote category="practice">Bind `WeatherSearch` to a model, invoke with weather and non-weather queries. Verify the model calls the function only when relevant. Target: 10 min.</Sidenote>



The bound model behaves exactly like the unbound model for non-function
queries. When the model decides to call a function, the response contains
`additional_kwargs[’function_call’]` instead of text content.

# Multiple Functions and Model Selection

In practice, models need access to multiple tools<Citation src="openai2023function" />. Bind multiple function
definitions and let the model select based on the user’s query:



```cypher
from pydantic import BaseModel, Field

class WeatherSearch(BaseModel):
    """Get the current weather for a location."""
    location: str = Field(description="City and state")

class RestaurantSearch(BaseModel):
    """Search for restaurants near a location."""
    location: str = Field(description="City and state")
    cuisine: str = Field(
        default="any",
        description="Type of cuisine to search for",
    )

class FlightSearch(BaseModel):
    """Search for flights between two cities."""
    origin: str = Field(description="Departure city")
    destination: str = Field(description="Arrival city")
    date: str = Field(description="Travel date in YYYY-MM-DD format")

# Convert all three
from langchain.utils.openai_functions import (
    convert_pydantic_to_openai_function,
)

functions = [
    convert_pydantic_to_openai_function(WeatherSearch),
    convert_pydantic_to_openai_function(RestaurantSearch),
    convert_pydantic_to_openai_function(FlightSearch),
]

# Bind all functions to the model
model_with_tools = model.bind(functions=functions)
```





<Sidenote category="interview">"How does the model pick the right function?" Answer: semantic matching on the function description. Clear, non-overlapping descriptions are critical. See Chapter  keyconcept on routing.</Sidenote>





<Sidenote category="warning">Overlapping descriptions (e.g., "search for things near a location" for both weather and restaurants) cause inconsistent routing. Make descriptions specific.</Sidenote>





```cypher
# The model selects the appropriate function based on context
chain = prompt | model_with_tools

# Weather query -> WeatherSearch
r1 = chain.invoke({"input": "Weather in Paris?"})

# Restaurant query -> RestaurantSearch
r2 = chain.invoke({"input": "Find Italian restaurants in NYC"})

# Flight query -> FlightSearch
r3 = chain.invoke({"input": "Flights from SFO to LAX on March 15"})

# General query -> no function call (text response)
r4 = chain.invoke({"input": "Tell me a joke"})
```



&lt;!–MDXB-22-OPEN–&gt;

**Core Insight:** When multiple functions are bound, the model
performs implicit semantic routing: it matches the user’s intent against
each function’s description and selects the best match. This is a form
of zero-shot classification where the “classes” are the function
descriptions.

**Why It Matters:** This pattern scales to 10–20 functions without
explicit routing logic. The model acts as the router, eliminating the
need for a separate intent classifier.

**When It Breaks:** Beyond 20 functions, routing accuracy degrades
because the function definitions consume too many tokens and semantic
overlap increases. At that scale, use hierarchical routing: a first-stage
model selects a category, then a second-stage model selects from a
subset of functions.

&lt;!–MDXB-22-CLOSE–&gt;

# Nested Pydantic Models for Complex Schemas



<Term name="nested Pydantic model" los="FT-3.1">
  A Pydantic class that uses other Pydantic classes as field types, producing nested JSON Schema objects. Used for complex function parameters like addresses, date ranges, or structured filters
</Term>
<AnkiCard type="term" front={"nested Pydantic model"} back={"A Pydantic class that uses other Pydantic classes as field types, producing nested JSON Schema objects. Used for complex function parameters like addresses, date ranges, or structured filters"} los="FT-3.1" />



Real-world function parameters often have nested structure. Pydantic
handles this naturally through composition:



```cypher
from typing import Optional
from pydantic import BaseModel, Field

class Address(BaseModel):
    """A physical address."""
    street: str = Field(description="Street address")
    city: str = Field(description="City name")
    state: str = Field(description="State abbreviation")
    zip_code: Optional[str] = Field(
        default=None, description="ZIP code"
    )

class DeliveryOrder(BaseModel):
    """Place a delivery order to a specific address."""
    item: str = Field(description="Item to deliver")
    quantity: int = Field(description="Number of items", ge=1)
    address: Address = Field(description="Delivery address")
    priority: str = Field(
        default="standard",
        description="Delivery priority",
        enum=["standard", "express", "overnight"],
    )
```





<Sidenote category="pattern">Nested model pattern: define leaf schemas first (`Address`), then compose into parent (`DeliveryOrder`). The converter handles recursive JSON Schema generation.</Sidenote>





<Sidenote category="formula">Nested models add $$50–100 tokens per level of nesting. Three levels of nesting is typically the practical limit for function calling.</Sidenote>



The converter recursively processes nested models:



```cypher
delivery_fn = convert_pydantic_to_openai_function(DeliveryOrder)
# Produces nested JSON Schema with $defs for Address
```



&lt;!–MDXB-19-OPEN–&gt;

**Symptom:** The model fills top-level fields correctly but leaves
nested object fields empty or malformed.  
**Root cause:** The nested model’s `Field(description=...)`
values are missing or vague. The model needs clear descriptions at every
level of nesting.  
**Fix:** Add explicit descriptions to every field in every nested
model. Test with a forced function call to verify the model can populate
all fields.

```cypher
from typing import Optional
from pydantic import BaseModel, Field

class BookFilters(BaseModel):

    genre: Optional[str] = Field(
        default=None,
        description="Book genre (e.g., 'science fiction', 'biography')",
    )
    min_rating: Optional[float] = Field(
        default=None,
        description="Minimum rating from 0.0 to 5.0",
        ge=0.0,
        le=5.0,
    )
    published_after: Optional[str] = Field(
        default=None,
        description="Only books published after this date (YYYY-MM-DD)",
    )
```



**Step 2:** Define the main model and convert.



```cypher
class BookSearch(BaseModel):
    """Search for books by query with optional filters."""
    query: str = Field(description="Search query for book titles/authors")
    filters: Optional[BookFilters] = Field(
        default=None,
        description="Optional filters to narrow results",
    )
    max_results: int = Field(
        default=10,
        description="Maximum number of results to return",
        ge=1,
        le=50,
    )

from langchain.utils.openai_functions import (

book_fn = convert_pydantic_to_openai_function(BookSearch)
assert book_fn["parameters"]["required"] == ["query"]
```

because it is the only field without a default value. Pydantic’s
`Optional` type with `default=None` correctly maps to a
non-required JSON Schema property.

**Approach:** **Pydantic equivalent:**



```cypher
from typing import Optional
from pydantic import BaseModel, Field

class EmailSender(BaseModel):
    """Send an email to a recipient."""
    to: str = Field(description="Recipient email")
    subject: str = Field(description="Email subject")
    body: str = Field(description="Email body text")
    cc: Optional[list[str]] = Field(
        default=None, description="CC recipients"
    )
```



**Three advantages of Pydantic:**

1.  **Runtime validation:** `EmailSender(to=123)`
    raises a `ValidationError` immediately. Raw dicts pass
    silently with the wrong type.

2.  **IDE support:** Autocomplete, type checking, and
    refactoring tools work with Pydantic classes. Raw dicts are
    opaque to static analysis.

3.  **DRY maintenance:** Adding a field (e.g., `bcc`)
    requires one line in the class. With raw JSON, you must update
    `properties`, potentially `required`, and any
    validation code separately.

**Key Insight:** The Pydantic approach treats function schemas as
*code* (testable, version-controlled, statically analyzable) rather
than *data* (opaque dicts that are only validated at runtime by the
API).

**Answer:** **Pydantic equivalent:**

```cypher
    )
```
