&lt;!–MDXB-14-OPEN–&gt;

Lesson 5 built single-turn routing: one LLM call, one optional tool
call, done. But real tasks require multiple rounds of reasoning.
“What’s the weather in Tokyo and compare it to San Francisco” needs
two tool calls and a synthesis step. This lesson closes the loop:
tool output feeds back into the LLM as an observation, and the LLM
decides whether to call another tool or respond. Adding memory
across user turns transforms the loop into a conversational agent
that remembers what you discussed three messages ago.

# The Agent Loop

&lt;!–MDXB-15-OPEN–&gt;

**What**: An agent loop repeatedly calls the LLM, checks whether
the output is an `AgentAction` or `AgentFinish`, executes
any requested tool, appends the tool output as an “observation,” and
feeds the updated context back to the LLM. The loop terminates when the
LLM produces `AgentFinish` or a maximum iteration count is
reached.  
**Why**: Many tasks require multiple sequential tool calls. Without
a loop, the agent can only reason once and call one tool. The loop
enables multi-step reasoning chains where each tool result informs the
next decision.

&lt;!–MDXB-15-CLOSE–&gt;



<Sidenote category="interview">"Explain the agent loop." Hit four beats: (1) LLM decides, (2) tool executes, (3) observation appended, (4) LLM decides again. Emphasize the observation feedback mechanism.</Sidenote>



The loop is conceptually simple—it is a while loop with a type check.
This pattern aligns with the ReAct framework<Citation src="yao2022react" />, where the agent
interleaves reasoning and acting:



```cypher
from langchain.agents import AgentAction, AgentFinish

def agent_loop(chain, tools, user_input, max_iterations=10):
    """Minimal agent loop implementation."""
    intermediate_steps = []

    for i in range(max_iterations):
        result = chain.invoke({
            "input": user_input,
            "agent_scratchpad": format_steps(intermediate_steps),
        })

        if isinstance(result, AgentFinish):
            return result.return_values["output"]

        # Execute the tool
        tool_output = tools[result.tool].run(result.tool_input)

        # Record the action-observation pair
        intermediate_steps.append((result, tool_output))

    return "Max iterations reached without final answer."
```





<Sidenote category="formula">Agent loop: `while not AgentFinish and i < max_iter`: invoke LLM $$ run tool $$ append observation $$ repeat.</Sidenote>





<Sidenote category="warning">Always set `max_iterations`. Without a cap, a confused model can loop indefinitely, burning API credits. Default: 10–15 iterations.</Sidenote>

# The Agent Scratchpad

The `agent_scratchpad` is the mechanism that makes the loop
work. It converts the list of intermediate steps into messages that the
LLM can read:



```cypher
from langchain.agents.format_scratchpad import (
    format_to_openai_functions,
)

# Converts [(AgentAction, observation), ...] to messages:
#   AIMessage(function_call=...) + FunctionMessage(content=observation)
formatted = format_to_openai_functions(intermediate_steps)
```





<Sidenote category="pattern">Scratchpad format: each step becomes two messages— `AIMessage` (the function call) + `FunctionMessage` (the tool result). LLM sees its own prior actions.</Sidenote>



Each intermediate step becomes two messages in the prompt:

1.  An `AIMessage` with `function_call` set to the
    tool name and arguments (reconstructing what the model originally
    said)

2.  A `FunctionMessage` with the tool’s return value as
    content (the observation)

This allows the LLM to see its own prior reasoning chain and make
informed decisions about the next step. Without the scratchpad, the
model would have no memory of which tools it already called or what
they returned—it would repeat the same tool call indefinitely.

&lt;!–MDXB-18-OPEN–&gt;

**Core Insight:** `agent_scratchpad` and
`chat_history` serve fundamentally different purposes.
The scratchpad holds *intra-turn* reasoning (tool calls and
observations within a single user request). Chat history holds
*inter-turn* context (previous user messages and agent responses
across a conversation).

**Why It Matters:** Confusing the two leads to architectural
errors. If you put tool observations in chat history, the model sees
stale intermediate reasoning from prior turns, polluting its context.
If you omit the scratchpad, the model cannot reason about tools it
already called within the current turn.

**When It Breaks:** For very long agent reasoning chains (10+
tool calls in one turn), the scratchpad consumes significant context
window. Consider summarizing intermediate steps or pruning early
observations that are no longer relevant.

&lt;!–MDXB-18-CLOSE–&gt;

&lt;!–MDXB-20-OPEN–&gt;

**Why interviewers ask this:** OpenAI, Anthropic, and Google
DeepMind Staff/Senior roles ask “Explain the difference between
scratchpad and chat history in an agent” as an architecture
litmus test. It separates candidates who have built agents from
those who have only used them.

**What they’re really testing:** Whether you distinguish
*intra-turn* state (scratchpad: tool calls and observations
within one user request) from *inter-turn* state (chat history:
prior conversation context). Conflating the two reveals a
fundamental misunderstanding of agent state management.

**Expected depth by level:**

- **IC3/IC4:** Define scratchpad vs. chat history.
  Explain the correct prompt ordering (system → history
  → user input → scratchpad). Know that
  `memory_key` must match `variable_name`.

- **IC5+/Staff:** Design memory strategies for 50+
  turn conversations (windowed, summary, hybrid). Calculate
  context window budgets. Discuss scratchpad pruning for
  long reasoning chains and the trade-off between buffer
  and summary memory.

**Red flag:** Putting tool observations in chat history, or
being unable to explain why the agent repeats tool calls when the
scratchpad is missing from the prompt template.

&lt;!–MDXB-20-CLOSE–&gt;

The prompt template must include placeholders for both:



```cypher
from langchain.prompts import (
    ChatPromptTemplate,
    MessagesPlaceholder,
)

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant with access to tools."),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{input}"),
    MessagesPlaceholder(variable_name="agent_scratchpad"),
])
```





<Sidenote category="formula">Prompt structure: system $$ `chat_history` (prior turns) $$ user input $$ `agent_scratchpad` (current-turn tool reasoning).</Sidenote>



# AgentExecutor: Production-Ready Loop

&lt;!–MDXB-16-OPEN–&gt;

**What**: `AgentExecutor` is LangChain’s<Citation src="langchain2024" /> production-ready
implementation of the agent loop. It handles the while-loop logic,
tool dispatch, error handling, max-iteration guards, and optional
verbose logging—everything we hand-coded in Section 6.1.  
**Why**: Hand-rolling the loop is educational but fragile.
`AgentExecutor` centralizes the loop logic, adds robust error
handling (catching tool exceptions without crashing the loop), and
integrates directly with LangChain’s memory system.

&lt;!–MDXB-16-CLOSE–&gt;



```cypher
from langchain.agents import AgentExecutor

# 1. Define the agent chain (prompt | model | parser)
agent_chain = prompt | model | OpenAIFunctionsAgentOutputParser()

# 2. Wrap in AgentExecutor with tools and guards
agent_executor = AgentExecutor(
    agent=agent_chain,
    tools=[get_current_temperature, search_wikipedia],
    verbose=True,         # print intermediate steps
    max_iterations=10,    # safety cap
    handle_parsing_errors=True,  # graceful error recovery
)

# 3. Run
result = agent_executor.invoke({"input": "What's the weather in NYC?"})
```





<Sidenote category="interview">"What does AgentExecutor add over a raw loop?" Three things: error handling (tool exceptions), max-iteration guard, and memory integration. Name all three.</Sidenote>





<Sidenote category="warning">`handle_parsing_errors=True` is critical. Without it, a malformed function call from the LLM crashes the entire agent. With it, the error message is fed back as an observation so the model can self-correct.</Sidenote>

# Conversation Memory

Without memory, the agent treats every message as the start of a new
conversation. If the user says “What’s the weather in Tokyo?”
followed by “How about San Francisco?”, the agent has no idea that
“How about” refers to weather—it sees only the second message in
isolation.



```cypher
from langchain.memory import ConversationBufferMemory

memory = ConversationBufferMemory(
    return_messages=True,   # return Message objects, not strings
    memory_key="chat_history",  # must match prompt placeholder
)

agent_executor = AgentExecutor(
    agent=agent_chain,
    tools=[get_current_temperature, search_wikipedia],
    memory=memory,
    verbose=True,
    max_iterations=10,
)
```





<Sidenote category="warning">`return_messages=True` is required. Without it, memory returns a string instead of `Message` objects, and the `MessagesPlaceholder` in the prompt fails silently.</Sidenote>



&lt;!–MDXB-19-OPEN–&gt;

**Core Insight:** `ConversationBufferMemory` stores every
user message and agent response as `Message` objects. On each
turn, these are injected into the `chat_history` placeholder,
giving the agent full context of the conversation so far.

**Why It Matters:** Without memory, the agent is stateless—it
cannot resolve references like “How about...”, “Do the same for...”,
or “Compare that to...”. Memory is what transforms a tool-calling
loop into a *conversational* agent.

**When It Breaks:** Buffer memory grows linearly with conversation
length. After 20–30 turns, the accumulated history may exceed the
context window. For long conversations, switch to
`ConversationSummaryMemory` or
`ConversationBufferWindowMemory(k=10)`.

&lt;!–MDXB-19-CLOSE–&gt;

# Vignette: Diagnosing the Over-Eager Agent

&lt;!–MDXB-27-OPEN–&gt;

\[FT-6.4\]
**Scenario:**
A product team at a travel startup builds a conversational agent with
three tools: `search_flights`, `search_hotels`, and
`search_wikipedia`. The agent uses `AgentExecutor` with
`ConversationBufferMemory` and `max_iterations=15`.
During QA testing, the team observes two problems:

1.  **Unnecessary tool calls:** When a user asks “What’s the
    capital of France?”, the agent calls `search_wikipedia`
    instead of answering from parametric knowledge. This adds 2–3
    seconds of latency and costs $0.002 per unnecessary call.

2.  **Tool-call loops:** When a user asks “Find me flights
    from NYC to London and a hotel near Heathrow,” the agent calls
    `search_flights`, then `search_hotels`, then
    calls `search_flights` *again* with slightly
    different parameters, then `search_hotels` again. It
    hits the 15-iteration cap and returns an incomplete response.

The verbose logs for the looping case show:

    Iteration 1: AgentAction(tool="search_flights", ...)
    Iteration 2: AgentAction(tool="search_hotels", ...)
    Iteration 3: AgentAction(tool="search_flights", ...)  # repeated!
    Iteration 4: AgentAction(tool="search_hotels", ...)   # repeated!
    ...
    Iteration 15: Max iterations reached.

**Data:**

| **Query Type** | **Avg Iterations** | **Tool Calls** | **Latency** | **Completion Rate** |
|:---|:--:|:--:|:--:|:--:|
| Simple factual (no tool needed) | 2.1 | 1.0 | 4.2s | 100% |
| Single-tool query | 2.3 | 1.0 | 3.8s | 100% |
| Multi-tool query | 8.7 | 6.2 | 18.4s | 62% |

**Questions:**

**Q1:** What is the root cause of the unnecessary tool calls on
simple factual queries? Propose a fix that does not require changing
the model.

**Q2:** What is causing the tool-call loop on multi-tool queries?
Identify the specific mechanism in the agent architecture that allows
this to happen.

**Q3:** The team proposes reducing `max_iterations` from
15 to 3 to prevent loops. Evaluate this proposal—what does it fix
and what does it break?

**Q4:** Design a system prompt modification that addresses both
problems simultaneously. Write the exact text you would add.

&lt;!–MDXB-27-CLOSE–&gt;

**Analysis:**

**Q1:** The root cause is the tool descriptions. The
`search_wikipedia` description is too broad—something like
“Search for information on any topic.” The model interprets “What’s
the capital of France?” as a knowledge query and routes it to Wikipedia
because the description matches.

**Fix:** Narrow the tool description to create a higher threshold
for invocation:



```cypher
@tool
def search_wikipedia(query: str) -> str:
    """Search Wikipedia for detailed encyclopedia articles.

    Use this ONLY when the user explicitly asks for detailed
    background information that requires a full article, NOT
    for simple factual questions you can answer directly.
    """
    ...
```



**Q2:** The loop occurs because the scratchpad shows the model its
prior tool calls and observations, but the model does not recognize that
the observations already contain the information it needs. It
re-invokes the tools because it is unsatisfied with the format or
completeness of the prior results. Specifically, the flight search may
return raw JSON, and the model calls it again hoping for a more
human-readable response. The agent architecture allows this because
`AgentFinish` is the only termination signal—if the model keeps
producing `AgentAction`, the loop continues.

**Q3:** Reducing `max_iterations` to 3 is a blunt
instrument. It prevents loops (fixes the symptom) but also prevents
legitimate multi-tool queries from completing. A query requiring 2 tool
calls plus a synthesis step needs at least 3 iterations. With a cap of
3, any tool error or retry would cause failure. The 62% completion
rate would drop further.

**Q4:** System prompt addition that addresses both problems:



```cypher
system_prompt = """You are a helpful travel assistant with tools.

IMPORTANT RULES:
1. For simple factual questions (capitals, dates, definitions),
   answer directly from your knowledge. Do NOT call tools.
2. When you have already called a tool and received a result,
   use that result to answer. Do NOT call the same tool again
   with different parameters unless the user explicitly asks
   for a different search.
3. After calling all necessary tools, synthesize the results
   into a final answer. Do not call additional tools unless
   the results were genuinely insufficient.
"""
```

# Problems

&lt;!–MDXB-21-OPEN–&gt;

A developer builds a conversational agent but accidentally swaps the
order of `agent_scratchpad` and `chat_history` in the
prompt template:



```cypher
# Bug: scratchpad and history are in wrong positions
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    MessagesPlaceholder(variable_name="agent_scratchpad"),
    ("human", "{input}"),
    MessagesPlaceholder(variable_name="chat_history"),
])
```



(a) What observable failures will this cause? (b) Explain why
the order matters in terms of how the LLM processes the message
sequence. (c) Write the corrected prompt template.

&lt;!–MDXB-21-CLOSE–&gt;

&lt;!–MDXB-24-OPEN–&gt;

**Approach:** **(a) Observable failures:**

**Failure 1:** Tool observations from the current turn appear
*before* the user’s message. The LLM sees function call results
without knowing what the user asked, making it unable to determine
whether the results are relevant.

**Failure 2:** Chat history appears *after* the user’s
current message, so the model processes the current question before
seeing prior context. Follow-up questions like “How about San
Francisco?” fail because the model reads the question before the
context that would resolve “how about.”

**(b) Why order matters:**

LLMs process messages sequentially. The model builds up context as it
reads each message. The correct order is: prior conversation context
(chat history) provides the backdrop, then the current user message
poses the question, then the scratchpad provides any tool reasoning
from the current turn. Reversing this order means the model encounters
information before the context that makes it interpretable.

**(c) Corrected template:**



```cypher
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{input}"),
    MessagesPlaceholder(variable_name="agent_scratchpad"),
])
```



**Key Insight:** Prompt message order encodes a reasoning flow:
prior context → current question → current reasoning.
Violating this order disrupts the model’s ability to ground its
reasoning in the right context.

**Answer:**

1.  **Observable failures:** **Failure 1:** Tool observations from the current turn appear *before* the user’s message.

2.  **Why order matters:** LLMs process messages sequentially.

3.  **Corrected template:** 

```cypher
prompt = ChatPromptTemplate.from_messages([ ("system", "You are a helpful assistant."), MessagesPlaceholder(variable_name="chat_history"), ("human", "{input}"), MessagesPlaceholder(variable_name="agent_scratchpad"), ])
```

&lt;!–MDXB-22-OPEN–&gt;

Your conversational agent uses `ConversationBufferMemory` with
GPT-4 (8K context window). The system prompt uses 500 tokens, each
tool definition uses 200 tokens (3 tools = 600 tokens), and the
agent scratchpad averages 400 tokens per turn. (a) Calculate the
maximum number of conversation turns before the context window
overflows, assuming each turn (user + assistant) averages 300 tokens.
(b) At turn 20, the agent starts producing incoherent responses.
Explain the failure mode. (c) Propose a memory strategy that supports
50+ turn conversations.

&lt;!–MDXB-22-CLOSE–&gt;

&lt;!–MDXB-25-OPEN–&gt;

**Approach:** **(a) Available tokens for chat history:**
8, 000 − 500<sub>system</sub> − 600<sub>tools</sub> − 400<sub>scratchpad</sub> = 6, 500 tokens

Maximum turns: ⌊6, 500/300⌋ = 21 turns.

**(b) Failure at turn 20:**

At turn 20, the accumulated chat history is 20 × 300 = 6, 000
tokens. Total context is 500 + 600 + 400 + 6, 000 = 7, 500,
leaving only 500 tokens for the model’s response. The model is forced
to truncate its reasoning, and the API may silently truncate early
messages from the context, causing the model to lose critical
conversation context. This manifests as incoherent or contradictory
responses.

**(c) Memory strategy for 50+ turns:**

**Option 1:** `ConversationBufferWindowMemory(k=10)` —
keep only the last 10 turns. Simple, but loses early context entirely.

**Option 2:** `ConversationSummaryMemory` — use an LLM
to summarize older turns into a compact paragraph. Preserves key facts
while staying within the token budget. Cost: one additional LLM call
per summarization.

**Option 3 (recommended):** Hybrid — keep the last 5 turns
verbatim (for recency) plus a running summary of all prior turns.
Token budget: ∼500 tokens for summary + 5 × 300 = 1, 500
for recent turns = 2,000 total, well within budget.

**Key Insight:** Context window is a hard constraint. Buffer
memory scales linearly with turns and will always overflow. Production
agents must use windowed or summary memory strategies.

**Answer:**

1.  **Available tokens for chat history:**
    8, 000 − 500<sub>system</sub> − 600<sub>tools</sub> − 400<sub>scratchpad</sub> = 6, 500 tokens
    Maximum turns: ⌊6, 500/300⌋ = 21 turns.

2.  **Failure at turn 20:** At turn 20, the accumulated chat history is 20 × 300 = 6, 000 tokens.

3.  **Memory strategy for 50+ turns:** **Option 1:** `ConversationBufferWindowMemory(k=10)` — keep only the last 10 turns.

<AnkiCard type="keyconcept" id="chapters-vol0-ch06-CONCEPT-SCRATCHPAD_VS_CHAT_HISTORY" los="FT-6.3" front={"Key Concept: Scratchpad vs.\\ Chat History"} back={"Core Insight: agent_scratchpad and\nchat_history serve fundamentally different purposes.\nThe scratchpad holds intra-turn reasoning (tool calls and\nobservations within a single user request). Chat history holds\ninter-turn context (previous user messages and agent responses\nacross a conversation).\n\nWhy It Matters: Confusing the two leads to architectural\nerrors. If you put tool observations in chat history, the model sees\nstale intermediate reasoning from prior turns, polluting its context.\nIf you omit the scratchpad, the model cannot reason about tools it\nalready called within the current turn.\n\nWhen It Breaks: For very long agent reasoning chains (10+\ntool calls in one turn), the scratchpad consumes significant context\nwindow. Consider summarizing intermediate steps or pruning early\nobservations that are no longer relevant."} />

On each\nturn, these are injected into the chat_history placeholder,\ngiving the agent full context of the conversation so far.\n\nWhy It Matters: Without memory, the agent is stateless—it\ncannot resolve references like \"How about...\", \"Do the same for...\",\nor \"Compare that to...\".
