&lt;!–MDXB-8-OPEN–&gt;

This is the foundation for everything that follows. Before LangChain
abstractions (L2–L6), we need to understand the raw protocol: how the
OpenAI API accepts function definitions, how the model decides whether to
call a function or respond directly, and how the multi-turn conversation
loop works. Every higher-level tool—LCEL binding, Pydantic schemas,
agent routing—is an abstraction over this mechanism.

&lt;!–MDXB-8-CLOSE–&gt;

# What Is Function Calling?



<Term name="function calling" los="FT-1.1">
  An API feature where the model outputs a structured JSON object specifying which function to call and with what arguments, rather than generating free-form text. The model does *not* execute the function—the calling application does.
</Term>
<AnkiCard type="term" front={"function calling"} back={"An API feature where the model outputs a structured JSON object specifying which function to call and with what arguments, rather than generating free-form text. The model does *not* execute the function—the calling application does."} los="FT-1.1" />





<Sidenote category="interview">Common system design Q: "How do you give an LLM access to external tools?" Answer: function calling protocol. 2 min overview.</Sidenote>



Large language models generate text, but many real-world applications
require *actions*: querying a database, calling a weather API,
or updating a CRM record<Citation src="schick2023toolformer" />. Function calling<Citation src="openai2023function" /> bridges this gap by giving the
model a structured way to request that the host application execute a
specific operation.

The critical insight is the **separation of concerns**:

- The **model** decides *when* to call a function and
  generates the *arguments* as JSON.

- The **application** actually executes the function and
  returns the result to the model.

&lt;!–MDXB-12-OPEN–&gt;

**Core Insight:** Function calling is a *structured output*
protocol, not remote procedure execution. The model produces a JSON
object with `name` and `arguments` fields. The application
validates, executes, and feeds the result back.

**Why It Matters:** This separation enables sandboxing, input
validation, rate limiting, and audit logging—none of which would be
possible if the model directly invoked external code.

**When It Breaks:** If the application blindly trusts the model’s
arguments without validation, function calling becomes an injection vector.
Always validate and sanitize model-generated arguments before execution.

&lt;!–MDXB-12-CLOSE–&gt;

&lt;!–MDXB-15-OPEN–&gt;

**Why interviewers ask this:** OpenAI, Anthropic, and Google AI
engineer screens (L4/L5) test this in the first 10 minutes. It gates
whether you understand LLM-tool integration at the protocol level or
only at the framework level.

**What they’re really testing:** Whether you grasp that
function calling is *structured output*, not remote execution.
The model produces JSON; the application validates, executes, and
returns the result. Candidates who say “the LLM calls the API”
reveal they have never built a tool-calling system.

**Expected depth by level:**

- **IC3/IC4:** Explain the separation of concerns
  (model generates, app executes). Name the three fields
  (`name`, `arguments`, `call_id`) and
  walk through a single-turn flow.

- **IC5+/Staff:** Discuss `call_id` for
  parallel tool calls, input validation as a security boundary,
  audit logging, and the migration from `functions` to
  `tools` parameter.

**Red flag:** Saying the model “executes” or “runs” the
function, or being unable to describe what happens between the
model’s JSON output and the function result message.

&lt;!–MDXB-15-CLOSE–&gt;



<Sidenote category="warning">Never execute model-generated function arguments without validation. Treat the JSON like untrusted user input.</Sidenote>



# Defining Functions for the API

Function definitions are passed to the Chat Completions API via the
`functions` parameter. Each definition follows a JSON Schema
format with three required fields:



<Sidenote category="pattern">Function def triple: `name` (identifier), `description` (when to call), `parameters` (JSON Schema).</Sidenote>





```cypher
import openai
import json

# Define a function for the model to call
functions = [
    {
        "name": "getCurrentWeather",
        "description": "Get the current weather in a given location",
        "parameters": {
            "type": "object",
            "properties": {
                "location": {
                    "type": "string",
                    "description": "City and state, e.g. San Francisco, CA",
                },
                "unit": {
                    "type": "string",
                    "enum": ["celsius", "fahrenheit"],
                },
            },
            "required": ["location"],
        },
    }
]
```





<Term name="function definition" los="FT-1.1">
  A JSON Schema object passed to the API describing a callable function: its `name`, a natural-language `description` the model uses to decide when to invoke it, and a `parameters` schema specifying argument types and constraints
</Term>
<AnkiCard type="term" front={"function definition"} back={"A JSON Schema object passed to the API describing a callable function: its `name`, a natural-language `description` the model uses to decide when to invoke it, and a `parameters` schema specifying argument types and constraints"} los="FT-1.1" />





<Sidenote category="formula">Token cost: function defs count against context window. 5 functions $$ 500–800 tokens of overhead.</Sidenote>



Three elements determine whether the model calls a function correctly:

1.  **Name**: A clear, descriptive identifier. The model uses
    this as a semantic signal (e.g., `getCurrentWeather` vs. `fn_42`).

2.  **Description**: Natural language explaining *when*
    to call the function. This is the model’s primary decision input.
    Vague descriptions produce unreliable routing.

3.  **Parameters**: A JSON Schema defining argument types,
    `enum` constraints, and `required` fields. The
    model generates arguments that conform to this schema.



<Sidenote category="interview">Design interview: "How would you ensure the model calls the right function?" Answer: precise descriptions + parameter constraints + forced calls for critical paths.</Sidenote>





<Sidenote category="warning">The `functions` parameter and `function_call` are deprecated. Use `tools` and `tool_choice` instead. See Appendix .</Sidenote>



# The `function_call` Parameter



<Term name="`function_call` parameter" los="FT-1.3">
  A request-level setting controlling whether the model may call functions: `auto` (model decides), `none` (text only), or a forced name `{"name": "func"}` (must call that function)
</Term>
<AnkiCard type="term" front={"`function_call` parameter"} back={"A request-level setting controlling whether the model may call functions: `auto` (model decides), `none` (text only), or a forced name `{\"name\": \"func\"}` (must call that function)"} los="FT-1.3" />



The `function_call` parameter gives the application explicit
control over function invocation:

&lt;!–MDXB-9-OPEN–&gt;

| **Mode** | **Behavior** | **Use When** |
|:---|:---|:---|
| `"auto"` | Model decides: call a function or respond with text | Open-ended conversation where the model should choose |
| `"none"` | Model responds with text only, ignoring all function defs | Summarization step after function results are in context |
| `{"name": ..."}` | Model *must* call the named function | Deterministic workflows where you need guaranteed extraction |

&lt;!–MDXB-9-CLOSE–&gt;



<Sidenote category="warning">Forcing a function call on every request wastes tokens when the user's query is simple conversation. Use `auto` as default.</Sidenote>





```cypher
from openai import OpenAI

client = OpenAI()

# Mode 1: auto -- model decides whether to call a function
response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "What's the weather in Boston?"}],
    functions=functions,
    function_call="auto",  # default behavior
)

# Mode 2: none -- force text-only response
response_text = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "What's the weather in Boston?"}],
    functions=functions,
    function_call="none",  # suppress function calling
)

# Mode 3: forced -- must call getCurrentWeather
response_forced = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "Tell me a joke"}],
    functions=functions,
    function_call={"name": "getCurrentWeather"},  # forced
)
```



&lt;!–MDXB-13-OPEN–&gt;

**Core Insight:** Forcing a function call with
`{"name": "func"}` turns the model into a structured data
extractor. The model *must* produce JSON matching the function’s
parameter schema, regardless of the input.

**Why It Matters:** In production pipelines—entity extraction,
form filling, data normalization—you need deterministic behavior.
Forced calls guarantee the output format.

**When It Breaks:** If the user’s message contains no relevant
information for the forced function, the model hallucinate arguments.
Always validate that required fields contain meaningful values.

&lt;!–MDXB-13-CLOSE–&gt;



<Sidenote category="pattern">Forced function call pattern: user input $$ forced extraction $$ validate $$ execute or reject.</Sidenote>



# The Multi-Turn Function Calling Loop

A single API call is not enough. When the model returns a
`function_call` object instead of a text response, the application
must:

1.  Parse the `function_call` from the response (extract
    `name` and `arguments`).

2.  Execute the actual function with the parsed arguments.

3.  Append the assistant’s message (containing the
    `function_call`) to the conversation.

4.  Append a new message with `role: "function"`, the
    function `name`, and the `content` (the result
    as a string).

5.  Call the API again so the model can incorporate the result.



<Sidenote category="interview">Staff-level Q: "Walk through the message history for a function call." Must show 4 messages: system, user, assistant (function_call), function (result).</Sidenote>





```cypher
import json
from openai import OpenAI

client = OpenAI()

def get_current_weather(location: str, unit: str = "fahrenheit") -> str:
    """Stub: in production, call a real weather API."""
    weather_data = {
        "location": location,
        "temperature": "72" if unit == "fahrenheit" else "22",
        "unit": unit,
        "forecast": ["sunny", "windy"],
    }
    return json.dumps(weather_data)

# Step 1: Initial request
messages = [{"role": "user", "content": "What's the weather in Boston?"}]

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=messages,
    functions=functions,
)

assistant_msg = response.choices[0].message

# Step 2: Check if model wants to call a function
if assistant_msg.function_call:
    func_name = assistant_msg.function_call.name
    func_args = json.loads(assistant_msg.function_call.arguments)

    # Step 3: Execute the function
    result = get_current_weather(**func_args)

    # Step 4: Append assistant message + function result
    messages.append(assistant_msg.model_dump())
    messages.append({
        "role": "function",
        "name": func_name,
        "content": result,
    })

    # Step 5: Call API again with function result in context
    final_response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
    )
    print(final_response.choices[0].message.content)
```





<Sidenote category="crossref">For LangChain abstraction of this loop, see Chapter  (Pydantic + `model.bind`).</Sidenote>



&lt;!–MDXB-10-OPEN–&gt;

**Symptom:** Model ignores the function result and generates a
generic response.  
**Root cause:** The function result message uses
`role: "user"` instead of `role: "function"`.  
**Fix:** Ensure the result message has `role: "function"`
and includes the `name` field matching the called function.

&lt;!–MDXB-10-CLOSE–&gt;



<Sidenote category="warning">The `role: "function"` message *must* include `name`. Omitting it causes API errors or silent misrouting.</Sidenote>



# Token Budget and Multiple Functions

Function definitions consume tokens from the context window. Each
function definition adds roughly 100–200 tokens depending on the
complexity of the parameter schema. With a 4096-token context, five
function definitions can consume 10–20% of the budget before the
conversation even begins.



<Sidenote category="formula">Rule of thumb: each function def $$ 100–200 tokens. Budget accordingly for small context windows.</Sidenote>



When multiple functions are defined, the model uses the `description`
field to decide which one to call. Clear, non-overlapping descriptions are
essential for reliable routing:



```cypher
# Multiple functions with clear, non-overlapping descriptions
multi_functions = [
    {
        "name": "getCurrentWeather",
        "description": "Get the current weather for a specific location",
        "parameters": {
            "type": "object",
            "properties": {
                "location": {"type": "string"},
            },
            "required": ["location"],
        },
    },
    {
        "name": "searchRestaurants",
        "description": "Search for restaurants near a location, "
                       "optionally filtered by cuisine type",
        "parameters": {
            "type": "object",
            "properties": {
                "location": {"type": "string"},
                "cuisine": {"type": "string"},
            },
            "required": ["location"],
        },
    },
]
```





<Sidenote category="practice">Exercise: add a third function for flight search. Test with ambiguous queries like "Plan my trip to Paris." Does the model pick the right function?</Sidenote>



&lt;!–MDXB-14-OPEN–&gt;

**Core Insight:** The model selects which function to call primarily
based on the `description` field. Two functions with overlapping
descriptions cause inconsistent routing. Two functions with vague
descriptions cause missed calls.

**Why It Matters:** In multi-function systems (5–10 functions),
routing accuracy is the bottleneck. A well-described function set achieves
95%+ routing accuracy; a poorly described set drops below 70%.

**When It Breaks:** When functions share semantic territory
(e.g., `searchProducts` vs. `findItems`), the model
oscillates between them. Merge or add discriminating detail to descriptions.

&lt;!–MDXB-14-CLOSE–&gt;



<Sidenote category="interview">Production design Q: "How do you handle 50+ functions?" **Answer:** hierarchical routing—coarse classifier picks category, then subset of functions for fine-grained call.</Sidenote>

For each scenario below, choose the appropriate `function_call`

\(a\) A chatbot that can check order status or answer general FAQs.

\(b\) A data pipeline that extracts structured fields (name, email, phone)

general question (respond with text). Forcing would break FAQ handling;
`none` would disable order lookup.

The model is acting as an extraction engine, not a conversational agent.
Forced mode guarantees the JSON schema is always populated.

from a prior function result message. The model should synthesize a
natural-language summary, not call the weather function again. Setting
`none` prevents redundant API calls.

**Key Insight:** The choice maps to the application’s control
requirements. `auto` for open-ended agents, forced for
deterministic pipelines, `none` for synthesis steps.
