# The Pipe Operator and Runnable Protocol



<Term name="LCEL (LangChain Expression Language)" los="FT-2.1">
  A declarative syntax for composing LangChain components using the pipe operator `|`, where each component implements the Runnable protocol and the output of one becomes the input of the next
</Term>
<AnkiCard type="term" front={"LCEL (LangChain Expression Language)"} back={"A declarative syntax for composing LangChain components using the pipe operator `|`, where each component implements the Runnable protocol and the output of one becomes the input of the next"} los="FT-2.1" />





<Sidenote category="interview">LangChain role: "What is LCEL?" Answer: composable pipeline syntax built on the Runnable protocol. Every component gets invoke/stream/batch for free.</Sidenote>



LCEL’s core abstraction is the **Runnable protocol**<Citation src="langchain2024" />. Any object
that implements this protocol can be composed with any other. The protocol
defines a standard interface:

- `invoke(input)` — process a single input synchronously

- `stream(input)` — yield output chunks as they arrive

- `batch([inputs])` — process multiple inputs in parallel

- `ainvoke(input)` — async version of `invoke`

- `astream(input)` — async version of `stream`

- `abatch([inputs])` — async version of `batch`



<Sidenote category="formula">6 Runnable methods: invoke, stream, batch + async variants (ainvoke, astream, abatch). Chains inherit all 6 automatically.</Sidenote>





```cypher
from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate
from langchain.schema.output_parser import StrOutputParser

# Each component implements the Runnable protocol
prompt = ChatPromptTemplate.from_template(
    "Tell me a short joke about {topic}"
)
model = ChatOpenAI()
parser = StrOutputParser()

# LCEL: pipe operator composes Runnables into a chain
chain = prompt | model | parser

# The chain inherits invoke, stream, batch from its components
result = chain.invoke({"topic": "programming"})
```



&lt;!–MDXB-16-OPEN–&gt;

**Core Insight:** When you compose components with `|`, the
resulting chain automatically supports all six Runnable methods. You do
not implement streaming or batching—the chain does it by composing the
streaming/batching behavior of its components.

**Why It Matters:** A single chain definition gives you synchronous
processing, real-time token streaming, and batch parallelism without
rewriting any code. This is the “write once, run many ways” principle.

**When It Breaks:** Custom Runnables that only implement
`invoke` will block streaming at that stage. If any component
in the chain does not support `stream`, the chain falls back to
buffered invoke for that component.

# Schema Introspection

Every Runnable exposes `input_schema` and `output_schema`
properties, which return Pydantic models describing the expected types.
This enables tooling, validation, and documentation generation:



```cypher
# Inspect what the chain expects and produces
print(chain.input_schema.schema())
# {'title': 'PromptInput', 'type': 'object',
#  'properties': {'topic': {'title': 'Topic', 'type': 'string'}}}

print(chain.output_schema.schema())
# {'title': 'StrOutputParserOutput', 'type': 'string'}
```





<Sidenote category="practice">Use `.input_schema.schema()` on your chains during development. Catches type mismatches before runtime.</Sidenote>



This introspection is not just a debugging convenience. In production, it
enables automatic API endpoint generation (LangServe uses these schemas
to create OpenAPI specs) and compile-time validation of chain composition.
The schema approach draws on Pydantic’s runtime validation model<Citation src="pydantic2024docs" />.

# Streaming and Batching



<Sidenote category="warning">Streaming only works end-to-end if *every* component supports it. A non-streaming step buffers all output before the next stage can begin.</Sidenote>



Streaming delivers tokens to the user as the model generates them,
reducing perceived latency. Batching processes multiple inputs in parallel,
improving throughput for bulk workloads:



```cypher
# Streaming: yields chunks as the model generates them
for chunk in chain.stream({"topic": "databases"}):
    print(chunk, end="", flush=True)

# Batching: processes multiple inputs in parallel
results = chain.batch([
    {"topic": "Python"},
    {"topic": "JavaScript"},
    {"topic": "Rust"},
])
```





<Sidenote category="interview">"How do you reduce time-to-first-token in a chatbot?" **Answer:** LCEL streaming. The model emits tokens incrementally; the chain relays them without buffering.</Sidenote>



The performance characteristics differ significantly:

&lt;!–MDXB-14-OPEN–&gt;

| **Method** | **Latency Profile**         | **Best For**                    |
|:-----------|:----------------------------|:--------------------------------|
| `invoke`   | Full latency, single result | Simple request-response         |
| `stream`   | Low time-to-first-token     | Chat UIs, real-time feedback    |
| `batch`    | Amortized across inputs     | Offline processing, eval suites |

# `RunnableMap` and Parallel Execution



<Term name="`RunnableMap` (RunnableParallel)" los="FT-2.2">
  An LCEL construct that runs multiple Runnables in parallel on the same input, collecting their outputs into a dictionary. Created via `RunnableParallel({"key": runnable})` or dict syntax in a pipe
</Term>
<AnkiCard type="term" front={"`RunnableMap` (RunnableParallel)"} back={"An LCEL construct that runs multiple Runnables in parallel on the same input, collecting their outputs into a dictionary. Created via `RunnableParallel({\"key\": runnable})` or dict syntax in a pipe"} los="FT-2.2" />



Not all pipelines are linear. `RunnableMap` (also called
`RunnableParallel`) branches the data flow, runs multiple
operations simultaneously, and merges results into a dictionary:



<Sidenote category="interview">Architecture Q: "How do you run retrieval and question processing in parallel?" Answer: `RunnableParallel` branches the input, rejoins as a dict for the prompt.</Sidenote>





```cypher
from langchain.schema.runnable import RunnableParallel, RunnablePassthrough

# Parallel: run retriever and passthrough simultaneously
setup = RunnableParallel(
    context=retriever,              # fetches relevant docs
    question=RunnablePassthrough(),  # passes input through unchanged
)

# The output is a dict: {"context": <docs>, "question": <original>}
```





<Term name="`RunnablePassthrough`" los="FT-2.2">
  A Runnable that returns its input unchanged, used in `RunnableMap` to forward data alongside parallel operations
</Term>
<AnkiCard type="term" front={"`RunnablePassthrough`"} back={"A Runnable that returns its input unchanged, used in `RunnableMap` to forward data alongside parallel operations"} los="FT-2.2" />





<Sidenote category="formula">`RunnableParallel` wall-clock time $=$ max(component times), not sum. True parallelism for I/O-bound operations.</Sidenote>



The passthrough pattern is essential in RAG pipelines: the original
question must reach the prompt template alongside the retrieved context,
but the retriever only needs the question as input.

# Binding Parameters and Fallbacks

`model.bind()` attaches persistent parameters to a Runnable without
modifying the chain structure. This is how function definitions are
attached to models in LCEL (detailed in Chapter <a href="#ch:L3" data-reference-type="ref" data-reference="ch:L3">[ch:L3]</a>):



```cypher
from langchain_openai import ChatOpenAI

model = ChatOpenAI()

# Bind parameters that persist across all invocations
model_with_functions = model.bind(
    functions=functions,
    function_call="auto",
)

# Now every call to model_with_functions includes the function defs
```





<Sidenote category="pattern">Bind pattern: `model.bind(param=value)` returns a new Runnable with the parameter baked in. Original model is unchanged (immutable).</Sidenote>



Fallback chains provide resilience. If the primary chain fails (rate
limit, timeout, model error), the fallback chain is tried automatically:



```cypher
from langchain_openai import ChatOpenAI

# Primary: GPT-4 (better but slower/costlier)
primary = ChatOpenAI(model="gpt-4")

# Fallback: GPT-4o-mini (faster, cheaper)
fallback = ChatOpenAI(model="gpt-4o-mini")

# Chain with automatic fallback
resilient_model = primary.with_fallbacks([fallback])

# If GPT-4 fails (rate limit, timeout), GPT-4o-mini is tried
result = resilient_model.invoke("Explain quantum computing")
```





<Sidenote category="warning">Fallbacks execute sequentially, not in parallel. A slow timeout on the primary delays the fallback. Set aggressive timeouts on the primary model.</Sidenote>



&lt;!–MDXB-17-OPEN–&gt;

**Core Insight:** `.bind()` returns a *new* Runnable
with the parameters attached. The original Runnable is unchanged. This
follows the immutability principle: you can create multiple variants of
a model (with different functions, temperatures, or stop sequences)
without side effects.

**Why It Matters:** In a system with multiple chains sharing the
same base model, bind prevents one chain’s configuration from leaking
into another.

**When It Breaks:** Binding mutable objects (e.g., a list that is
later modified) breaks the immutability guarantee. Always bind with
copies or frozen values.

# RAG Pipeline with LCEL

The canonical LCEL pattern combines everything: parallel retrieval,
passthrough, prompt formatting, model invocation, and output parsing
into a single composable chain:



<Sidenote category="crossref">For vector store setup and retriever configuration, see DL.AI LangChain Chat With Your Data course.</Sidenote>





```cypher
from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate
from langchain.schema.output_parser import StrOutputParser
from langchain.schema.runnable import RunnableParallel, RunnablePassthrough

# Assume retriever is configured (e.g., FAISS, Chroma)
# retriever = vectorstore.as_retriever()

template = """Answer the question based only on the context:

Context: {context}

Question: {question}
"""
prompt = ChatPromptTemplate.from_template(template)
model = ChatOpenAI()
parser = StrOutputParser()

# Full RAG pipeline in LCEL
rag_chain = (
    RunnableParallel(
        context=retriever,
        question=RunnablePassthrough(),
    )
    | prompt
    | model
    | parser
)

# Single invocation retrieves, formats, generates, and parses
answer = rag_chain.invoke("What is LCEL?")
```





<Sidenote category="practice">Build a RAG chain with 3 components: retriever, prompt, model. Test with `invoke`, `stream`, and `batch`. Target: 15 min.</Sidenote>



&lt;!–MDXB-18-OPEN–&gt;

**Core Insight:** The LCEL RAG pattern—`RunnableParallel`
→ prompt → model → parser—is a
reference architecture, not just a code pattern. Every production RAG
system follows this shape: parallel data gathering, template assembly,
generation, and output structuring.

**Why It Matters:** Once you recognize this shape, you can extend
it: add reranking between retriever and prompt, add guardrails between
model and parser, or swap the retriever for a SQL query chain. The
LCEL structure makes each extension a single pipe stage.

**When It Breaks:** When the retriever returns no results, the
prompt template receives empty context. Add a conditional check or
fallback retrieval strategy before the prompt stage.

&lt;!–MDXB-18-CLOSE–&gt;



<Sidenote category="interview">System design: "Build a RAG system with fallbacks." **Answer:** LCEL chain with `with_fallbacks` on the retriever (try vector store, fall back to keyword search).</Sidenote>

**Approach:** **Step 1:** Define the parallel branches.



```cypher
from langchain.schema.runnable import RunnableParallel, RunnablePassthrough
from langchain.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from langchain.schema.output_parser import StrOutputParser

model = ChatOpenAI()

# Branch 1: FAQ retrieval (assume retriever exists)
# retriever = vectorstore.as_retriever()

# Branch 2: Sentiment classification
sentiment_prompt = ChatPromptTemplate.from_template(
    "Classify the sentiment of this customer message as "
    "positive, neutral, or negative. Message: {query}\n"
    "Sentiment:"
)
sentiment_chain = sentiment_prompt | model | StrOutputParser()

# Parallel: all three branches run simultaneously
parallel_step = RunnableParallel(
    faq_context=retriever,
    sentiment=sentiment_chain,
    query=RunnablePassthrough(),
)
```



**Step 2:** Compose with the response-generation prompt.



```cypher
response_prompt = ChatPromptTemplate.from_template(
    "You are a customer support agent.\n\n"
    "Customer query: {query}\n"
    "Customer sentiment: {sentiment}\n"
    "Relevant FAQ: {faq_context}\n\n"
    "Generate an empathetic, helpful response."
)

full_chain = parallel_step | response_prompt | model | StrOutputParser()

# Single call runs retrieval + sentiment + generation
response = full_chain.invoke({"query": "My order is late and I'm upset"})
```



**Key Insight:** `RunnableParallel` turns what would be three
sequential API calls into concurrent execution. The wall-clock time equals
the slowest branch, not the sum. For I/O-bound operations (API calls,
database queries), this is a significant latency reduction.

**Answer:** `RunnableParallel` turns what would be three
sequential API calls into concurrent execution.
