# Anatomy of a LangChain Tool

&lt;!–MDXB-15-OPEN–&gt;

**What**: A LangChain `Tool` bundles three components:
(1) the Python function that executes the tool’s logic, (2) metadata
(name and natural-language description), and (3) a Pydantic model
defining the argument schema. All three are required.  
**Why**: The LLM never sees the function body. It makes tool
selection decisions based entirely on the name, description, and
argument schema. A poorly described tool will be ignored or misused
regardless of how well the underlying function works.

&lt;!–MDXB-15-CLOSE–&gt;



<Sidenote category="interview">"What makes a good tool definition?" Answer: the *description* is the tool's resume. The LLM reads it to decide when to call it. Vague descriptions cause misrouting.</Sidenote>



The LLM’s tool selection is a classification problem over the available
tool descriptions<Citation src="schick2023toolformer" />. If two tools have overlapping or ambiguous
descriptions, the model will misroute. Tool descriptions are part of
the prompt engineering surface area—they deserve the same care as
system messages.



<Term name="Tool metadata" los="FT-5.2">
  The `name` and `description` fields attached to a LangChain tool; the LLM reads these (not the function source code) to decide which tool to invoke and when; quality of metadata directly determines routing accuracy
</Term>
<AnkiCard type="term" front={"Tool metadata"} back={"The `name` and `description` fields attached to a LangChain tool; the LLM reads these (not the function source code) to decide which tool to invoke and when; quality of metadata directly determines routing accuracy"} los="FT-5.2" />



## The `@tool` Decorator

The simplest way to create a tool is with the `@tool` decorator.
The function’s docstring becomes the tool description:



```cypher
from langchain.tools import tool
from pydantic import BaseModel, Field

class TemperatureInput(BaseModel):
    """Input for the temperature tool."""
    latitude: float = Field(description="Latitude of the location")
    longitude: float = Field(description="Longitude of the location")

@tool(args_schema=TemperatureInput)
def get_current_temperature(latitude: float, longitude: float) -> str:
    """Fetch the current temperature for a location.

    Use this when the user asks about current weather or temperature
    at a specific place.
    """
    import requests
    url = (
        f"https://api.open-meteo.com/v1/forecast"
        f"?latitude={latitude}&longitude={longitude}"
        f"&current_weather=true"
    )
    response = requests.get(url)
    data = response.json()
    temp = data["current_weather"]["temperature"]
    return f"The current temperature is {temp}°C"
```





<Sidenote category="warning">The docstring IS the tool description. Write it for the LLM, not for developers. Include "Use this when..." to guide selection.</Sidenote>





<Sidenote category="formula">Tool components: `.name` (function name), `.description` (docstring), `.args` (Pydantic schema). All three visible to the LLM.</Sidenote>



## Converting to OpenAI Format

LangChain tools must be converted to OpenAI function format before
binding to the model:



```cypher
from langchain.utils.openai_functions import (
    format_tool_to_openai_function,
)

# Convert single tool
temp_fn = format_tool_to_openai_function(get_current_temperature)

# Convert multiple tools
tools = [get_current_temperature, search_wikipedia]
functions = [format_tool_to_openai_function(t) for t in tools]

# Bind to model
model = ChatOpenAI(temperature=0).bind(functions=functions)
```





<Sidenote category="pattern">Pattern: define tools $$ `format_tool_to_openai_function` $$ `model.bind(functions=...)`. Three steps, always in this order.</Sidenote>



# OpenAPI Spec to Tools

Many real-world APIs publish OpenAPI (Swagger) specifications. LangChain<Citation src="langchain2024" />
can convert these directly into tool definitions, saving manual schema
authoring:



```cypher
import yaml
from langchain.chains.openai_functions.openapi import (
    openapi_spec_to_openai_function,
)

# Load OpenAPI spec
with open("weather_api.yaml") as f:
    spec = yaml.safe_load(f)

# Convert to OpenAI function definitions
api_functions = openapi_spec_to_openai_function(spec)
```





<Sidenote category="interview">Mention OpenAPI-to-tool conversion when asked about scaling tool integration. Shows awareness that manual tool authoring does not scale to 50+ API endpoints.</Sidenote>



This approach works well for RESTful APIs with clean specs, but breaks
down when the OpenAPI documentation is incomplete or when parameter
descriptions are vague. In practice, you often need to augment the
auto-generated descriptions with LLM-friendly language.

&lt;!–MDXB-18-OPEN–&gt;

**Core Insight:** Tool names, descriptions, and parameter
descriptions are consumed by the LLM as part of its prompt context.
Writing tool metadata is a prompt engineering task, not a documentation
task. The audience is the model, not a human developer.

**Why It Matters:** Teams that treat tool descriptions as internal
docs (terse, jargon-heavy) see poor routing accuracy. Teams that write
descriptions with “Use this when...” framing and concrete examples see
significantly better tool selection.

**When It Breaks:** When you have many tools (20+) with similar
descriptions, the model’s ability to discriminate degrades regardless of
description quality. At that scale, consider hierarchical tool
organization or a pre-routing classifier.

&lt;!–MDXB-18-CLOSE–&gt;

&lt;!–MDXB-20-OPEN–&gt;

**Why interviewers ask this:** Amazon, Salesforce, and
LangChain AI engineer roles ask “How do you prevent an agent from
calling tools unnecessarily?” This is a top-3 agent design question
because unnecessary calls are the primary source of latency and cost
in production agents.

**What they’re really testing:** Whether you understand that
tool selection is a *prompt engineering problem*, not a model
capability problem. The quality of tool descriptions—not the
model’s reasoning—determines routing accuracy. Candidates who
jump to fine-tuning miss the 80% solution.

**Expected depth by level:**

- **IC3/IC4:** Write tool descriptions with “Use this
  when…” framing. Explain that the LLM reads the
  description, not the function body. Know the three-part
  tool anatomy (function, metadata, schema).

- **IC5+/Staff:** Design hierarchical routing for 20+
  tools, add negative instructions (“Do NOT use this
  when…”), implement system prompt rules that suppress
  tool calls for simple factual queries, and build routing
  evaluation suites.

**Red flag:** Proposing model retraining or temperature tuning
as the fix for misrouting, instead of improving tool descriptions
and system prompt constraints.

# Routing with Output Parsing

&lt;!–MDXB-16-OPEN–&gt;

**What**: The `OpenAIFunctionsAgentOutputParser` inspects
the model’s response and produces one of two types:
`AgentAction` (the model wants to call a tool) or
`AgentFinish` (the model wants to respond directly to the user).  
**Why**: This binary distinction is the foundation of all agent
logic. Every iteration of an agent loop asks: “Should I act (tool
call) or respond (finish)?” The parser encapsulates this decision.

&lt;!–MDXB-16-CLOSE–&gt;



<Term name="AgentAction" los="FT-5.3">
  A named tuple containing `tool` (the tool name the LLM selected), `tool_input` (the arguments dict), and `log` (the raw LLM output); signals that the agent wants to invoke a tool before responding
</Term>
<AnkiCard type="term" front={"AgentAction"} back={"A named tuple containing `tool` (the tool name the LLM selected), `tool_input` (the arguments dict), and `log` (the raw LLM output); signals that the agent wants to invoke a tool before responding"} los="FT-5.3" />





<Term name="AgentFinish" los="FT-5.3">
  A named tuple containing `return_values` (the final response dict) and `log`; signals that the agent is ready to respond to the user without further tool calls
</Term>
<AnkiCard type="term" front={"AgentFinish"} back={"A named tuple containing `return_values` (the final response dict) and `log`; signals that the agent is ready to respond to the user without further tool calls"} los="FT-5.3" />





```cypher
from langchain.agents.output_parsers import (
    OpenAIFunctionsAgentOutputParser,
)

# Chain: prompt -> model (with tools bound) -> parser
chain = prompt | model | OpenAIFunctionsAgentOutputParser()

result = chain.invoke({"input": "What's the weather in Tokyo?"})

# result is either AgentAction or AgentFinish
if isinstance(result, AgentAction):
    print(f"Tool: {result.tool}, Args: {result.tool_input}")
elif isinstance(result, AgentFinish):
    print(f"Response: {result.return_values}")
```





<Sidenote category="formula">Output parser returns: `AgentAction` $$ call tool. `AgentFinish` $$ respond to user. Binary dispatch.</Sidenote>



## Building the Route Function

The route function is the dispatcher: it inspects the parser’s output
and either calls the appropriate tool or returns the model’s direct
response:



```cypher
def route(result):
    """Dispatch AgentAction to the correct tool."""
    if isinstance(result, AgentFinish):
        return result.return_values["output"]

    # Build a lookup from tool name to tool function
    tool_map = {
        "get_current_temperature": get_current_temperature,
        "search_wikipedia": search_wikipedia,
    }

    tool = tool_map.get(result.tool)
    if tool is None:
        return f"Unknown tool: {result.tool}"

    return tool.run(result.tool_input)
```





<Sidenote category="warning">Always handle unknown tool names in the route function. A hallucinated tool name without a fallback will crash the pipeline.</Sidenote>





```cypher
from langchain.schema.runnable import RunnableLambda

# Complete routed chain
routed_chain = chain | RunnableLambda(route)

# Test: should invoke get_current_temperature
print(routed_chain.invoke({
    "input": "What's the temperature in San Francisco?"
}))

# Test: should return AgentFinish (no tool needed)
print(routed_chain.invoke({
    "input": "Hello, how are you?"
}))
```





<Sidenote category="pattern">Route function pattern: `isinstance` check $$ tool map lookup $$ `tool.run(input)`. Always include a fallback for unknown tools.</Sidenote>



&lt;!–MDXB-19-OPEN–&gt;

**Core Insight:** The routing logic in this lesson executes exactly
one LLM call, optionally followed by one tool call. This is
single-turn routing, not an agent loop. A true agent iterates: the
tool’s output feeds back into the LLM for another decision round.

**Why It Matters:** Single-turn routing suffices for stateless
queries (“What’s the weather?”) but fails for multi-step tasks
(“Look up the weather, then compare it to yesterday’s forecast”).
Understanding this limitation motivates the agent loop in Lesson 6.

**When It Breaks:** If the user’s query requires multiple
sequential tool calls, single-turn routing returns after the first
tool call without completing the task.

**Scenario:**
An e-commerce company deploys a customer support agent with five tools:
`check_order_status`, `initiate_refund`,
`search_faq`, `search_product_catalog`, and
`escalate_to_human`. After the first week, the support team
reports two problems. First, product availability questions
(“Is the blue widget in stock?”) are routed to `search_faq`
instead of `search_product_catalog`, returning irrelevant FAQ
articles. Second, angry customers requesting refunds are sometimes
routed to `escalate_to_human` instead of
`initiate_refund`, creating unnecessary load on the human
support team. The engineering team suspects the tool descriptions are
the root cause but the product manager wants to add a sixth tool
(`track_shipment`) before fixing the existing routing issues.

**Data:**

| Metric | Value |
|:---|:---|
| Daily query volume | 8,500 queries |
| Correct routing rate (overall) | 74% |
| `search_faq` misroute rate | 31% (should be `search_product_catalog`) |
| `escalate_to_human` misroute rate | 22% (should be `initiate_refund`) |
| Avg tool calls per query | 1.3 |
| Cost per unnecessary human escalation | $4.50 |

**Questions:**

1.  The current tool descriptions are: `search_faq`:
    “Search for answers to common questions”;
    `search_product_catalog`: “Search for products.”
    Explain why these descriptions cause misrouting and rewrite both
    descriptions using the “Use this when…/ Do NOT use this
    when…” pattern from this chapter.

2.  Calculate the daily cost of the `escalate_to_human`
    misrouting problem. Then propose a routing fix that does not
    require retraining the model—only changes to tool definitions
    and the system prompt.

3.  The product manager wants to add `track_shipment` as a
    sixth tool. Given that routing accuracy is already 74% with five
    tools, what is the likely impact of adding a sixth tool with a
    description that overlaps with `check_order_status`?
    Propose a strategy for safely adding the new tool without
    degrading existing routing accuracy.
