&lt;!–MDXB-18-OPEN–&gt;

Lesson 3 showed how LangChain wraps OpenAI function calling so that
Pydantic models define the schema and LCEL chains manage the plumbing.
But we only used function calling for *actions*—triggering side
effects like weather lookups. This lesson pivots to a different use
case entirely: using function calling as a *structured output
mechanism*. By forcing the model to “call a function” whose schema
matches our desired output, we get guaranteed JSON conforming to a
Pydantic model—no regex parsing, no fragile string manipulation.
Lesson 5 will then combine real tools with this structured-output
technique to build routing logic.

&lt;!–MDXB-18-CLOSE–&gt;

# Tagging vs. Extraction

&lt;!–MDXB-19-OPEN–&gt;

**What**: Tagging produces a *single* structured object from a
text (e.g., one sentiment label plus one language tag). Extraction produces
a *list* of structured objects—each representing an entity or item
found in the text (e.g., a list of research papers with titles, authors,
and years).  
**Why**: The distinction determines your Pydantic schema design:
tagging uses a flat model, extraction wraps that model in a
`List[...]`. Choosing the wrong paradigm causes either
information loss (tagging when there are multiple entities) or
unnecessary complexity (extraction when a single label suffices).

&lt;!–MDXB-19-CLOSE–&gt;



<Sidenote category="interview">"How do you get structured output from an LLM?" Name function calling as the mechanism, then distinguish tagging (single object) from extraction (list). Shows you know both patterns.</Sidenote>



The function-calling API<Citation src="openai2023function" /> was designed for tool invocation, but nothing
prevents us from defining a “function” that the model never actually
executes. Instead, we treat the function’s argument schema as a
contract: the model must produce JSON that conforms to it. This is
the key insight behind both tagging and extraction.

## Tagging: Single Object



<Sidenote category="formula">Tagging schema: one Pydantic model with flat fields. No `List[...]` wrapper.</Sidenote>



A tagging chain takes text and returns one structured object. The
canonical example is sentiment analysis combined with language detection:



```cypher
from pydantic import BaseModel, Field

class Tagging(BaseModel):
    """Tag a passage with sentiment and language."""
    sentiment: str = Field(
        description="sentiment of text, one of: pos, neg, neutral"
    )
    language: str = Field(
        description="language of text (ISO 639-1 code)"
    )
```



The critical detail is the `Field(description=...)` annotations.
The model reads these descriptions as part of the function schema, so
vague descriptions produce vague outputs. Enumerating allowed values
inside the description (“one of: pos, neg, neutral”) acts as a soft
constraint, analogous to the “rails” concept from LLM-as-a-judge
evaluation.



<Sidenote category="warning">Always enumerate allowed values in `Field(description=...)`. Without enumeration, the model may invent labels like "somewhat positive."</Sidenote>



## Extraction: List of Objects

Extraction extends tagging to multiple entities. The outer model
contains a single field that is a list of the inner entity model:



```cypher
from typing import List, Optional

class Paper(BaseModel):
    """Information about a research paper mentioned in text."""
    title: str
    author: Optional[str] = None
    year: Optional[int] = None

class ExtractionResult(BaseModel):
    """Extraction result containing all papers found."""
    papers: List[Paper]
```





<Sidenote category="pattern">Extraction pattern: inner entity model + outer wrapper with `List[InnerModel]`. Always use `Optional` for fields the text may not contain.</Sidenote>



Using `Optional` for non-guaranteed fields prevents the model
from hallucinating values. If the text mentions a paper title without
an author, the model can return `null` rather than fabricating
a name.

# Output Parsers

&lt;!–MDXB-20-OPEN–&gt;

**What**: Output parsers sit at the end of an LCEL chain and
transform the raw `AIMessage` (which contains the function call
arguments as a JSON string) into a Python dictionary or a specific key
from that dictionary.  
**Why**: Without a parser, you receive a full `AIMessage`
object and must manually extract `.additional_kwargs ["function_call"]["arguments"]`, parse it from JSON, and handle errors.
Parsers encapsulate this boilerplate into a single composable step.

&lt;!–MDXB-20-CLOSE–&gt;

LangChain<Citation src="langchain2024" /> provides two output parsers for function calling responses:



```cypher
from langchain.output_parsers.openai_functions import (
    JsonOutputFunctionsParser,
    JsonKeyOutputFunctionsParser,
)

# Full dictionary: {"sentiment": "pos", "language": "en"}
full_parser = JsonOutputFunctionsParser()

# Single key: ["pos"]  (extracts just the "sentiment" value)
key_parser = JsonKeyOutputFunctionsParser(key_name="sentiment")
```





<Sidenote category="formula">`JsonOutputFunctionsParser`: full dict. `JsonKeyOutputFunctionsParser(key_name=...)`: single value.</Sidenote>



The difference matters for downstream composition. If the next step in
your LCEL chain expects a full dictionary (e.g., for database insertion),
use the full parser. If it expects a single value (e.g., for conditional
routing), use the key parser.

## Composing the Chain

The complete tagging chain connects four components via the LCEL pipe
operator:



```cypher
from langchain.chat_models import ChatOpenAI  # freshness-ok: course original; use langchain_openai.ChatOpenAI
from langchain.prompts import ChatPromptTemplate
from langchain.utils.openai_functions import (
    convert_pydantic_to_openai_function,
)

# 1. Define the prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", "Extract the desired information from the passage."),
    ("human", "{input}"),
])

# 2. Convert Pydantic model to OpenAI function schema
tagging_fn = convert_pydantic_to_openai_function(Tagging)

# 3. Bind function to model with forced calling
model = ChatOpenAI(temperature=0).bind(
    functions=[tagging_fn],
    function_call={"name": "Tagging"},
)

# 4. Compose chain with output parser
chain = prompt | model | JsonOutputFunctionsParser()

result = chain.invoke({"input": "I love this product! Es fantastico."})
# {"sentiment": "pos", "language": "es"}
```





<Sidenote category="interview">Walk through the 4-step chain composition: prompt $$ model.bind(functions) $$ parser. Shows LCEL fluency.</Sidenote>



# Prompt Engineering for Extraction

Extraction is more sensitive to prompt design than tagging because the
model must decide both *what* to extract and *how many*
entities exist. Two prompt engineering principles are essential:

&lt;!–MDXB-23-OPEN–&gt;

**Core Insight:** Telling the model what *not* to do is as
important as telling it what to do. For extraction, the instruction
“Do not extract the article itself as a paper” prevents the model from
treating the input document as an entity to extract.

**Why It Matters:** Without negative instructions, the model
frequently “extracts” metadata about the input text itself, inflating
entity counts and polluting downstream data.

**When It Breaks:** Negative instructions can be over-applied.
If you say “do not extract partial information,” the model may skip
entities that lack optional fields rather than returning them with
`null` values.

&lt;!–MDXB-23-CLOSE–&gt;

&lt;!–MDXB-25-OPEN–&gt;

**Why interviewers ask this:** Google, Meta, and AI-native
companies (Cohere, Mistral) ask “How do you get reliable structured
output from an LLM?” in MLE and AI engineer screens. It gates
whether you can build data pipelines downstream of LLM inference.

**What they’re really testing:** Whether you know that forced
function calling is a *structured output mechanism*, not just a
tool invocation mechanism. The distinction between tagging (single
object) and extraction (list of objects) reveals schema design
maturity.

**Expected depth by level:**

- **IC3/IC4:** Explain forced function calling for
  guaranteed JSON. Distinguish tagging from extraction. Know
  that negative instructions (“Do not extract the article
  itself”) prevent hallucinated entities.

- **IC5+/Staff:** Design a long-document extraction
  pipeline with chunking, parallel `.batch()`, overlap
  strategy, and deduplication. Discuss confidence estimation
  when forced calling always produces output.

**Red flag:** Relying on regex or string parsing for structured
LLM output, or being unaware that extraction requires a
`List[Model]` wrapper to handle variable entity counts.

&lt;!–MDXB-25-CLOSE–&gt;



<Sidenote category="warning">Without "Do not extract the article itself," the model treats the input document as an entity. Always include negative instructions for extraction.</Sidenote>





```cypher
# Extraction prompt with negative instruction
extraction_prompt = ChatPromptTemplate.from_messages([
    ("system",
     "Extract all research papers mentioned in the following text. "
     "Do not extract the article itself as a paper. "
     "If a field is not present, return null."),
    ("human", "{input}"),
])
```



The second principle is **explicit null handling**: instruct the
model to return `null` for missing fields rather than guessing.
This aligns with the `Optional` type hints in the Pydantic model.

# Long-Document Extraction

&lt;!–MDXB-21-OPEN–&gt;

**What**: When a document exceeds the model’s context window (or
when extraction quality degrades on long inputs), split the document into
chunks, run the extraction chain on each chunk in parallel, and flatten
the results into a single list.  
**Why**: LLMs lose extraction recall on long documents—entities
buried in the middle are frequently missed. Chunking ensures each
segment is short enough for reliable extraction. LCEL’s
`.batch()` parallelizes up to 5 calls by default, keeping
latency manageable.

&lt;!–MDXB-21-CLOSE–&gt;



<Sidenote category="pattern">Long-doc extraction: split $$ map chain over chunks $$ flatten results. LCEL parallelizes up to 5 calls by default.</Sidenote>



## Splitting



```cypher
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,  # overlap prevents entity splitting
)
chunks = splitter.split_text(long_document)
```



The `chunk_overlap` parameter is critical for extraction: an
entity that spans a chunk boundary (e.g., a paper title that starts at
the end of one chunk and continues into the next) would be lost without
overlap. A 20% overlap ratio is a reasonable default.



<Sidenote category="warning">Without chunk overlap, entities spanning chunk boundaries are silently dropped. Use 15–20% overlap for extraction pipelines.</Sidenote>



## Mapping and Flattening

The extraction chain runs on each chunk via `.batch()`, producing
a list of lists. A simple flatten step merges them:



```cypher
from itertools import chain as iterchain

# Run extraction on all chunks (LCEL parallelizes automatically)
chunk_results = extraction_chain.batch(
    [{"input": chunk} for chunk in chunks],
    config={"max_concurrency": 5},
)

# Flatten: [[Paper, Paper], [Paper]] -> [Paper, Paper, Paper]
all_papers = list(iterchain.from_iterable(
    result.get("papers", []) for result in chunk_results
))
```





<Sidenote category="formula">Total extraction time $  N_\{chunks\} / 5   t_\{single\}$ with default LCEL concurrency of 5.</Sidenote>



&lt;!–MDXB-24-OPEN–&gt;

**Core Insight:** LCEL’s `.batch()` method automatically
parallelizes chain invocations up to a configurable concurrency limit
(default 5). You do not need to write threading or async code.

**Why It Matters:** A 50-chunk document with serial processing
takes 50× the single-call latency. With default parallelism,
it takes only 10×—an 80% reduction in wall-clock time.

**When It Breaks:** Rate limits from the OpenAI API may trigger
429 errors if concurrency is too high. Reduce
`max_concurrency` or add retry logic.

&lt;!–MDXB-24-CLOSE–&gt;

## Deduplication

Chunk overlap introduces a new problem: the same entity may be extracted
from two overlapping chunks. A post-processing deduplication step is
necessary:



```cypher
def deduplicate_papers(papers: list[dict]) -> list[dict]:
    """Remove duplicate papers by title (case-insensitive)."""
    seen = set()
    unique = []
    for p in papers:
        key = p.get("title", "").strip().lower()
        if key and key not in seen:
            seen.add(key)
            unique.append(p)
    return unique
```

&lt;!–MDXB-29-OPEN–&gt;

**Approach:** **Task (a) — Tagging:**



```cypher
class EmailTag(BaseModel):

        description="urgency level, one of: low, medium, high"
    )
    department: str = Field(
        description="department, one of: billing, technical, general"
    )
```



This is tagging because each email produces exactly one urgency label
and one department label—a single flat object.

**Task (b) — Extraction:**



```cypher
class ProductMention(BaseModel):
    product_name: str
    order_id: Optional[str] = None

class EmailExtraction(BaseModel):
    mentions: List[ProductMention]
```



This is extraction because an email may mention zero, one, or many
products. A `List[...]` wrapper is required.

**What if you use tagging for task (b)?** A flat schema with
`product_name: str` can capture only the first product.
Additional products are silently lost. The model might concatenate
multiple names into one field (“Widget Pro, Gadget Max”), producing
unparseable output.

**Key Insight:** The “one or many” distinction drives the schema
choice. One entity = tagging (flat model). Zero-to-many entities =
extraction (`List[Model]` wrapper).

**Answer:** **Task (a) — Tagging:**

This is tagging because each email produces exactly one urgency label

You run an extraction pipeline on a 15,000-token blog post using
`RecursiveCharacterTextSplitter` with `chunk_size=1000`
and `chunk_overlap=0`. The pipeline extracts 8 papers, but
manual review finds 12. (a) Identify two likely causes of the missing
4 papers. (b) Fix the pipeline configuration. (c) After adding
`chunk_overlap=200`, you now extract 14 papers—2 more than
expected. Explain why and propose a fix.

&lt;!–MDXB-27-CLOSE–&gt;

&lt;!–MDXB-30-OPEN–&gt;

**Approach:** **(a) Two likely causes:**

**Cause 1:** Entity boundary splitting. With zero overlap, papers
mentioned across a chunk boundary are split between two chunks. Neither
chunk contains the full entity, so neither extraction call returns it.

**Cause 2:** Mid-document recall degradation. Even within a single
chunk, if a paper mention falls at the very end of a 1,000-token
segment, the model may fail to extract it due to attention decay.

**(b) Configuration fix:**



```cypher
splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,  # 20% overlap prevents boundary splits
)
```



**(c) Why 14 instead of 12:** The 200-token overlap creates
regions where the same paper appears in two adjacent chunks. Both
extraction calls return it, producing duplicates.

**Fix:** Add a deduplication step after flattening:



```cypher
unique_papers = deduplicate_papers(all_papers)  # by title
```



**Key Insight:** Chunk overlap and deduplication are a matched
pair. Adding overlap without deduplication inflates counts; removing
overlap without understanding boundary effects drops entities.

**Answer:**

1.  **Two likely causes:** **Cause 1:** Entity boundary splitting.

2.  **Configuration fix:** 

```cypher
splitter = RecursiveCharacterTextSplitter( chunk_size=1000, chunk_overlap=200, # 20% overlap prevents boundary splits )
```



3.  **Why 14 instead of 12:** The 200-token overlap creates regions where the same paper appears in two adjacent chunks.

```cypher
from langchain.output_parsers.openai_functions import (

# Tagging chain that outputs just the sentiment string
tag_chain = (
    prompt
    | model.bind(
        functions=[tagging_fn],
        function_call={"name": "Tagging"},

    | JsonKeyOutputFunctionsParser(key_name="sentiment")
)

# Router dispatch
def route_review(sentiment: str) -> str:
    if sentiment == "pos":
        return thank_you_template.invoke({})
    else:
        return escalation_template.invoke({})

full_chain = tag_chain | RunnableLambda(route_review)
```
