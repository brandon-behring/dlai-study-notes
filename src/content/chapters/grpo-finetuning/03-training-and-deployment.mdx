# Anatomy of the GRPO Loss Function

&lt;!–MDXB-8-OPEN–&gt;

**What**: The GRPO loss function from the DeepSeek R1
paper<Citation src="deepseek2025r1" /> looks complex but decomposes into four
interpretable components that each serve a specific purpose in stabilizing
and directing learning.  
**Why**: Understanding each component lets you tune hyperparameters
(epsilon, beta) with confidence and diagnose training failures.

&lt;!–MDXB-8-CLOSE–&gt;



<Sidenote category="interview">GRPO loss has four terms: policy ratio (deviation from baseline), advantage (response quality), clipping (prevent large updates), KL (stay near base model).</Sidenote>



The four components:

1.  **Policy ratio**: the per-token probability ratio between the
    policy model (with LoRA) and the reference model (frozen base)

2.  **Advantage weighting**: scales the ratio by how good or bad
    this response was relative to the group

3.  **Clipping objective**: caps the ratio to \[1 − *ϵ*, 1 + *ϵ*\]
    to prevent any single token from dominating the loss

4.  **KL divergence**: penalty term that keeps the policy model
    from deviating too far from the reference model’s knowledge

Two models are maintained throughout training:

- **Reference model**: the base model without LoRA, frozen throughout
  training. Provides the baseline probability distribution.

- **Policy model**: the base model with LoRA adapters attached.
  Only the LoRA weights (rank *r* matrices in Q and V projections)
  are updated during training.



<Sidenote category="pattern">Reference model = frozen anchor. Policy model = trainable. LoRA adds rank-$r$ adapters to Q and V projections only. Trainable params $ 1%$.</Sidenote>



# Policy Ratio and Advantage Weighting

The policy ratio measures how the policy model’s token probabilities differ
from the reference model. For each token *t* in the completion:

$$\text{ratio}\_t = \frac{\pi\_\theta(t \mid \text{context})}{\pi\_{\text{ref}}(t \mid \text{context})}
= \exp\bigl(\log \pi\_\theta(t) - \log \pi\_{\text{ref}}(t)\bigr)$$



<Sidenote category="formula">Policy ratio = $(logprob_\{policy\} - logprob_\{ref\})$. Ratio $> 1$ means policy is more confident than reference. Ratio $< 1$ means less confident.</Sidenote>





```cypher
def compute_log_probs(model, input_ids, attention_mask):
    """Get per-token log probabilities from a model."""
    outputs = model(input_ids=input_ids, attention_mask=attention_mask)
    log_probs = torch.log_softmax(outputs.logits, dim=-1)
    # Gather only the log prob of the actual token produced
    token_log_probs = log_probs.gather(
        dim=-1, index=input_ids[:, 1:].unsqueeze(-1)
    ).squeeze(-1)
    return token_log_probs

# Policy ratio computation
ratio = torch.exp(policy_log_probs - ref_log_probs)  # per-token
unclipped_loss = -ratio * advantage  # negate for minimization
```



The unclipped policy loss multiplies each token’s ratio by the advantage
assigned to that completion. The intuition:

- **Positive advantage + ratio &gt; 1**: model is already more
  confident in a good response. Loss is large negative—reinforce this.

- **Negative advantage + ratio &gt; 1**: model is confident in a
  *bad* response. Loss pushes weights to reduce this probability.



<Sidenote category="warning">At training step 0, policy = reference, so ratio = 1.0 for all tokens. The loss equals the advantage. Learning bootstraps from advantage variation alone.</Sidenote>



&lt;!–MDXB-10-OPEN–&gt;

**Core Insight:** At the first training step, the policy model and
reference model are identical—every token ratio is exactly 1.0. Learning
begins solely because the advantage is non-zero: the loss is simply the
advantage value, which creates the initial gradient.

**Why It Matters:** This is why reward functions that produce diverse
scores (Chapter 2) are critical. If advantages are zero, the initial gradient
is zero and training never starts.

**When It Breaks:** If the reward function is too coarse (binary) or
temperature is too low (deterministic), advantages are zero at step 0 and
training flatlines from the start.

&lt;!–MDXB-10-CLOSE–&gt;

# The Clipping Objective

Raw probability ratios can be extreme. A token where the policy model assigns
probability 0.9 and the reference model assigns 0.001 produces a ratio of 900.
Multiplied by a large advantage, this creates unstable gradients.



<Sidenote category="interview">Clipping bounds the per-token probability ratio to $[1-, 1+]$, preventing any single token from producing extreme loss values. Typical $=0.2$.</Sidenote>



The clipping objective—adapted from PPO<Citation src="schulman2017ppo" />—computes
two versions of the loss and takes the minimum:

ℒ<sub>policy</sub> = min (ratio ⋅ *Â*, clip(ratio, 1 − *ϵ*, 1 + *ϵ*) ⋅ *Â*)



```cypher
def grpo_loss_with_clip(model, ref_model, prompt, completion,
                        advantage, epsilon=0.2):
    input_ids, attn_mask, comp_mask = prepare_inputs(prompt, completion)

    policy_logp = compute_log_probs(model, input_ids, attn_mask)
    ref_logp = compute_log_probs(ref_model, input_ids, attn_mask)

    ratio = torch.exp(policy_logp - ref_logp)

    # Two loss variants: unclipped and clipped
    unclipped = ratio * advantage
    clipped = torch.clamp(ratio, 1 - epsilon, 1 + epsilon) * advantage
    policy_loss = torch.min(unclipped, clipped)

    # Negate (we minimize loss but want to maximize reward)
    loss = -policy_loss
    # Apply completion mask: only compute loss on output tokens
    loss = (loss * comp_mask).sum() / comp_mask.sum()
    return loss
```





<Sidenote category="formula">Clipping range: $[1-, 1+]$ with $=0.2$ means ratios are bounded to $[0.8, 1.2]$. Prevents single-token loss from exceeding $1.2  |A|$.</Sidenote>



&lt;!–MDXB-11-OPEN–&gt;

**Core Insight:** Clipping operates on each *token’s* probability
ratio, not on the overall loss. This prevents any single token from producing
an outsized gradient while allowing the aggregate loss across all tokens
to remain informative.

**Why It Matters:** Without clipping, a single token with ratio 1000
multiplied by advantage 2.0 creates a loss of 2000—overwhelming the loss
contribution from all other tokens. Clipping caps this at 1.2 × 2.0 = 2.4.

**When It Breaks:** If epsilon is too small (e.g., 0.01), the model
cannot learn because updates are too conservative. If too large (e.g., 0.5),
clipping provides insufficient protection. The standard value of 0.2
works well across most tasks.

# KL Divergence Penalty

As the policy model trains, its token distributions diverge from the reference
model. The KL divergence penalty term prevents the model from “forgetting”
its base knowledge:

*δ*<sub>*t*</sub> = log *π*<sub>*θ*</sub>(*t*) − log *π*<sub>ref</sub>(*t*)
*D*<sub>KL</sub><sup>(*t*)</sup> = exp (*δ*<sub>*t*</sub>) − *δ*<sub>*t*</sub> − 1



<Sidenote category="warning">KL divergence is *asymmetric*: penalty for under-confident tokens (policy $<$ reference) grows faster than for over-confident. Pulls model back toward reference.</Sidenote>



The per-token KL divergence has an important asymmetry:

- When the policy is *more* confident than the reference (*δ* &gt; 0):
  KL penalty grows slowly. The model is allowed to become more confident
  in tokens it is producing well.

- When the policy is *less* confident (*δ* &lt; 0): KL penalty
  grows rapidly. The model is strongly discouraged from abandoning
  strategies the reference model was confident about.

The total per-token loss becomes:

ℒ<sub>*t*</sub> = ℒ<sub>policy, *t*</sub> − *β* ⋅ *D*<sub>KL</sub><sup>(*t*)</sup>



<Sidenote category="pattern">Beta tuning: $=0.1$ for task-specific optimization (let the model deviate). $=0.2$–$0.5$ for preserving generality. Predibase default: $=0.1$.</Sidenote>



The *β* hyperparameter controls the strength of this penalty:

- *β* = 0: no KL penalty; the model can deviate freely (risk of
  catastrophic forgetting)

- *β* = 0.1: standard setting; allows task-specific learning while
  maintaining base capabilities

- *β* = 0.5: strong regularization; preserves generality but slows
  task-specific learning

&lt;!–MDXB-12-OPEN–&gt;

**Core Insight:** The KL divergence term acts as a leash: the policy
model can improve on the reference model’s behavior, but it cannot stray
so far that it loses the language understanding, factual knowledge, and
general capabilities that the base model already possesses.

**Why It Matters:** Without KL regularization, aggressive RL training
can produce a model that solves Wordle perfectly but cannot carry a normal
conversation. Beta controls this trade-off.

**When It Breaks:** If beta is too high, the model cannot learn the
target task because every deviation is penalized. If too low, the model
may overfit to the reward signal and lose generality.

# Putting It All Together: Training Wordle

The complete Wordle training pipeline<Citation src="dlai-grpo-course" /> combines
everything from Chapters 1–3:

1.  **Dataset preparation**: Seed words from past Wordle games with
    intermediate game states (guesses + feedback) simulated by Claude 3.7
    Sonnet. Actual model outputs are discarded—only prompts are kept.

2.  **Response generation**: For each prompt, sample 16 candidate
    responses at temperature 0.7 using the policy model.

3.  **Reward scoring**: Three reward functions score each response:

    - **Output format check**: valid /
      tags, five-letter English word

    - **Prior feedback usage**: does the guess logically incorporate
      feedback from earlier attempts?

    - **Guess effectiveness**: how many candidate words does this
      guess eliminate from the remaining possibility space?

4.  **Advantage computation**: Normalize combined rewards within the
    group of 16 responses.

5.  **Loss computation**: Apply clipping (*ϵ* = 0.2) and KL
    divergence (*β* = 0.1) to produce the final GRPO loss.

6.  **Weight update**: Backpropagate through LoRA weights only.



<Sidenote category="interview">Start with one primary reward metric. Add penalty terms as you discover reward hacking. Wordle uses 3: format, feedback usage, guess quality.</Sidenote>





<Sidenote category="practice">Key hyperparameters: num_generations=16, temperature=0.7, max_tokens=4096, epsilon=0.2, beta=0.1. Start here and tune empirically.</Sidenote>

```cypher
from predibase import Predibase, GRPOConfig, RewardFunctionsConfig

pb = Predibase(api_token="YOUR_TOKEN")

# Upload training data
dataset = pb.datasets.from_pandas(wordle_df, name="wordle_grpo")

```



# SFT Warmup + GRPO Fine-Tuning

The most effective strategy combines both training paradigms:

1.  **SFT warmup**: Use 35 games played by Claude 3.7 Sonnet as
    labeled examples. Capture reasoning traces for each intermediate guess.
    Fine-tune with SFT to teach the model *how* to reason about Wordle
    (output format + chain-of-thought structure).

2.  **GRPO refinement**: Use the SFT checkpoint as the starting point
    for GRPO training. The model now *already* knows the reasoning
    format and can focus on *improving* its strategies through
    reward-driven optimization.



<Sidenote category="formula">Wordle (10 games): base Qwen 0/10, GRPO only 3/10, SFT + GRPO 7/10 ($>$2x improvement). Claude 3.7 thinking 10/10 (8k token budget).</Sidenote>



&lt;!–MDXB-13-OPEN–&gt;

**Core Insight:** SFT teaches the model to imitate good reasoning
patterns—it learns the *format* of strategic thinking. GRPO<Citation src="shao2024grpo" />
then refines those patterns by rewarding actual outcomes—it learns which
reasoning strategies *work*. Combined, a 7B model solves 7/10 Wordle
games, more than 2x the GRPO-only baseline.

**Why It Matters:** GRPO is an on-policy algorithm that refines the
model’s existing knowledge. Starting from a better initialization (SFT
checkpoint) gives GRPO a stronger foundation to optimize.

**When It Breaks:** If the SFT data is too narrow (e.g., from only
one strategy), GRPO may get stuck in a local optimum defined by that strategy.
Diverse SFT examples from a strong model (Claude, GPT-4) help.

&lt;!–MDXB-13-CLOSE–&gt;



<Sidenote category="warning">GRPO is on-policy: it refines the model's own knowledge. SFT distills a strong model's knowledge first, then GRPO optimizes it. Order matters—SFT before GRPO, not after.</Sidenote>



&lt;!–MDXB-15-OPEN–&gt;

The GRPO loss should only be computed over completion tokens, not prompt tokens.
Given a prompt of length *P* and a completion of length *C*, describe the
completion mask tensor and explain why applying it is necessary. What would
happen if the loss were computed over prompt tokens as well?

&lt;!–MDXB-15-CLOSE–&gt;

&lt;!–MDXB-24-OPEN–&gt;

**Approach:** The completion mask is a binary tensor of length *P* + *C*.

**Step 1: Construct the mask**  
The mask is a 1-D tensor with zeros for the first *P* positions (prompt tokens)
and ones for the remaining *C* positions (completion tokens):
$$\text{mask} = \[\underbrace{0, 0, \ldots, 0}\_{P}, \underbrace{1, 1, \ldots, 1}\_{C}\]$$

**Step 2: Apply the mask**  
Element-wise multiply the per-token loss by the mask, then sum and divide by
*C* (not *P* + *C*) to get the average loss over completion tokens only:
$$\mathcal{L} = \frac{1}{C} \sum\_{t=1}^{P+C} \text{mask}\_t \cdot \ell\_t$$

**Step 3: Why it matters**  
If the loss included prompt tokens, the model would be penalized for how it
“predicts” the prompt—which is the given input, not the model’s output.
This would introduce noise unrelated to response quality and dilute the
learning signal from the actual completion.

**Key Insight:** The completion mask ensures that gradient flow only
originates from tokens the model actually generated, keeping the optimization
focused on improving response quality rather than prompt prediction.

**Answer:** The completion mask is a binary tensor of length *P* + *C*.

A model trained with *β* = 0 for 1000 steps produces excellent Wordle
performance (8/10 games solved) but can no longer follow basic instructions
outside of Wordle. A model trained with *β* = 0.5 solves only 2/10 games
but retains general capabilities. Explain this trade-off and suggest a

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-25-OPEN–&gt;

**Approach:** **Diagnosis:**

***β* = 0 (no KL penalty):** The model deviates freely from the
reference distribution. It specializes entirely for Wordle, overwriting
general language knowledge in the LoRA weights. This is catastrophic
forgetting in the RL setting.

***β* = 0.5 (strong KL penalty):** The KL term dominates the loss.
Every deviation from the reference model is heavily penalized, so the model
cannot learn task-specific strategies effectively. It stays close to the
base model, which solves 0/10 games.

**Strategy for tuning *β*:**

1.  Start with *β* = 0.1 (Predibase recommended default)

2.  Monitor two metrics: task performance (games solved) and general
    capability (e.g., instruction following on a held-out benchmark)

3.  If task performance plateaus while general capability degrades,
    increase *β* by 0.05

4.  If task performance is not improving, decrease *β* by 0.05

5.  Typical optimal range: *β* ∈ \[0.04, 0.2\] for most tasks

**Key Insight:** *β* controls the exploration budget. Think of it as
a leash: too short and the model cannot reach the goal; too long and it
wanders off entirely. The optimal value is task-dependent and requires
empirical tuning against both task and general benchmarks.

**Answer:** **Diagnosis:**

***β* = 0 (no KL penalty):** The model deviates freely from the
reference distribution.

&lt;!–MDXB-17-OPEN–&gt;

Your team applies GRPO to fine-tune a 7B model for Python code generation.
The reward function checks: (1) code executes without errors (40% weight),
(2) all unit tests pass (40% weight), (3) output format follows `<code>`
tags (20% weight). After 500 training steps, the reward curve looks excellent,
but manual inspection reveals the model produces solutions that hard-code test
case outputs instead of implementing general algorithms.

| **Metric**                    | **Step 100** | **Step 500** |
|:------------------------------|:-------------|:-------------|
| Average reward                | 0.38         | 0.91         |
| Unit test pass rate           | 35%          | 88%          |
| Generalization (unseen tests) | 32%          | 11%          |
| Avg solution length (tokens)  | 85           | 31           |
| Hard-coded output rate        | 2%           | 73%          |

1.  Explain the reward hacking mechanism. Why does GRPO find this shortcut?

2.  Design a modified reward function that closes this loophole.

3.  What role does the KL divergence penalty play here, and would
    increasing *β* have prevented this?

&lt;!–MDXB-17-CLOSE–&gt;

&lt;!–MDXB-26-OPEN–&gt;

**Approach:**

1.  **Reward hacking mechanism:** The model learns that the simplest way
    to maximize the reward is to pattern-match on the test case inputs visible in
    the prompt and hard-code their expected outputs. A 3-line `if/elif`
    block that returns the correct output for each test case gets 100% on
    format + execution + test pass, but generalizes to 0%. GRPO reinforces this
    because the advantage is high (most other responses in the group fail entirely),
    and the model rapidly converges to this exploit.

2.  **Modified reward function:**

    - **Held-out test cases**: Show 2 test cases in the prompt but
      score against 5 additional hidden test cases. Hard-coded solutions
      fail the hidden cases.

    - **Code complexity penalty**: Add a negative reward for
      solutions below a minimum AST node count (e.g., below 10 nodes).
      Hard-coded `if/elif` chains have very low complexity.

    - **Semantic check**: Verify that the solution contains at least
      one loop or recursion for problems that require iterative logic.

3.  **KL divergence role:** Increasing *β* would *slow* the
    convergence to the hack but not prevent it. KL constrains how far the policy
    deviates from the reference distribution, but if the reference model can also
    produce hard-coded solutions (which any code model can), the KL penalty does
    not distinguish between general and hard-coded solutions. The fix must be in
    the reward function, not the regularizer.

**Key Insight:** Reward hacking exploits misalignment between what the
reward measures and what you actually want. The fix is always to improve the
reward function’s coverage of the true objective, not to slow down learning.

**Answer:**

1.  **Reward hacking mechanism:** The model learns that the simplest way to maximize the reward is to pattern-match on the test case inputs visible in the prompt and hard-code their expected outputs.

2.  **Modified reward function**.

3.  **KL divergence role:** Increasing *β* would *slow* the convergence to the hack but not prevent it.

A research team compares GRPO and DPO for improving a 3B model’s reasoning
on math word problems (GSM8K). Both methods use the same base model and
compute budget. GRPO uses verifiable rewards; DPO uses preference pairs
generated by sampling two responses per prompt and labeling the correct one
as preferred.

| **Metric** | **DPO** | **GRPO (*G* = 16)** |
|:---|:---|:---|
| GSM8K accuracy | 42% | 51% |
| Training compute (GPU-hrs) | 24 | 96 |
| Data preparation time | 8 hrs (pair generation) | 0 hrs (online) |
| Accuracy on harder MATH bench | 15% | 19% |
| General chat quality (vs. base) | -3% | -1% |

1.  Why does GRPO outperform DPO on math accuracy despite using more
    compute? What fundamental advantage does online generation provide?

2.  Why does DPO degrade general chat quality more than GRPO?

3.  Under what circumstances would you choose DPO over GRPO for this
    task?

&lt;!–MDXB-18-CLOSE–&gt;

&lt;!–MDXB-27-OPEN–&gt;

**Approach:**

1.  **GRPO’s advantage:** GRPO generates fresh responses at each training
    step, allowing the model to explore the solution space beyond what exists in
    any fixed dataset. As the model improves, it generates better responses, which
    create sharper advantage signals. DPO is limited to the quality of its
    pre-collected preference pairs—if the correct response in the pair uses a
    suboptimal strategy, DPO reinforces that suboptimal approach. GRPO discovers
    and reinforces whatever strategy actually produces correct answers.

2.  **DPO chat degradation:** DPO trains on preference pairs, which
    implicitly teach the model that the preferred response style is always better.
    If the math preference pairs have a different style than general chat (e.g.,
    terse, calculation-focused), DPO shifts the model’s overall style. GRPO only
    reinforces correct answers through advantages, leaving non-math behavior
    closer to the reference model (protected by the KL term).

3.  **Choose DPO when:**

    - GPU compute is scarce (DPO uses 4x less compute in this study)

    - Verifiable rewards do not exist (subjective quality, safety, style)

    - Training must complete quickly (DPO converges faster in wall time)

    - The task benefits from human judgment rather than objective correctness

**Key Insight:** GRPO excels when (1) verifiable rewards exist and
(2) the model can generate at least some correct responses. DPO excels when
the objective is subjective and human preferences are the best available signal.
They are complementary tools, not competitors.

**Answer:**

1.  **GRPO’s advantage:** GRPO generates fresh responses at each training step, allowing the model to explore the solution space beyond what exists in any fixed dataset.

2.  **DPO chat degradation:** DPO trains on preference pairs, which implicitly teach the model that the preferred response style is always better.

3.  **Choose DPO when**.

&lt;!–MDXB-19-CLOSE–&gt;

&lt;!–MDXB-28-OPEN–&gt;

**Approach:**

1.  **Two paths to zero gradients:**

    - *T* = 0.3: Low diversity means most responses are identical. If 14/16
      responses are the same, they get the same reward, and the advantage
      standard deviation approaches zero. GRPO normalizes by std, so
