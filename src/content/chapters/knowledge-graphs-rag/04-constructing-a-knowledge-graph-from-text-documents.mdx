# Text Chunking with LangChain

Each form section contains large bodies of text that must be split into
manageable pieces for embedding and retrieval:



```cypher
from langchain.text_splitter import CharacterTextSplitter

text_splitter = CharacterTextSplitter(
    chunk_size=2000,
    chunk_overlap=200,
)
chunks = text_splitter.split_text(item1_text)
# Item 1 alone produces 254 chunks
```





<Term name="Text Chunking" los="KGR-4.2">
  The process of splitting large documents into smaller, overlapping segments for embedding and retrieval. Chunk size controls granularity; chunk overlap ensures context continuity across boundaries. A critical RAG design decision that affects both retrieval precision and recall.
</Term>
<AnkiCard type="term" front={"Text Chunking"} back={"The process of splitting large documents into smaller, overlapping segments for embedding and retrieval. Chunk size controls granularity; chunk overlap ensures context continuity across boundaries. A critical RAG design decision that affects both retrieval precision and recall."} los="KGR-4.2" />



| **Parameter** | **Value** | **Rationale** |
|:---|:---|:---|
| Chunk size | 2000 chars | Balances context richness with embedding specificity |
| Chunk overlap | 200 chars | 10% overlap ensures no context is lost at boundaries |



<Sidenote category="warning">Overlap too small risks context loss at boundaries; too large wastes tokens on redundant embedding content. 10% is a safe starting point.</Sidenote>



&lt;!–MDXB-27-OPEN–&gt;

Too large: embeddings become generic, losing specificity for precise
retrieval. Too small: chunks lose context, and answers require
assembling multiple fragments. The 2000-character size with 200-character
overlap is a practical starting point. Tune based on your document
structure and query patterns.

## Chunk Metadata Schema

Each chunk is stored as a dictionary with metadata that preserves
provenance and enables structured querying:



```cypher
chunk_record = {
    "text": "...",            # The chunk text content
    "item": "item1",          # Which section of the form
    "chunkSeqId": 0,          # Sequence position within the section
    "formId": "...",          # Unique form identifier

```

# Creating Graph Nodes

## Uniqueness Constraint

Before bulk loading, create a **uniqueness constraint** to prevent
duplicate chunks. This also creates an implicit index on the constrained
property, speeding up MERGE lookups:



```cypher
# Prevent duplicate chunk nodes
kg.query("""
    CREATE CONSTRAINT unique_chunk IF NOT EXISTS
    FOR (c:Chunk) REQUIRE c.chunkId IS UNIQUE
""")
```





<Term name="Uniqueness Constraint" los="KGR-4.4">
  A database constraint that ensures no two nodes with the same label share the same value for a specified property. In Neo4j, also creates an implicit index on the constrained property. Essential for idempotent graph construction with MERGE.
</Term>
<AnkiCard type="term" front={"Uniqueness Constraint"} back={"A database constraint that ensures no two nodes with the same label share the same value for a specified property. In Neo4j, also creates an implicit index on the constrained property. Essential for idempotent graph construction with MERGE."} los="KGR-4.4" />



## Merging Chunks into the Graph

Use **MERGE** with parameterised queries to create chunk nodes
idempotently:



```cypher
# Create chunk nodes with MERGE for idempotency
merge_query = """
    MERGE (c:Chunk {chunkId: $chunkParam.chunkId})
    ON CREATE SET
      c.text = $chunkParam.text,
      c.item = $chunkParam.item,
      c.chunkSeqId = $chunkParam.chunkSeqId,
      c.formId = $chunkParam.formId
"""
for chunk in chunks:
    kg.query(merge_query, params={"chunkParam": chunk})

# Verify: 23 nodes created (using a subset of the full form)
```





<Sidenote category="pattern">Bulk loading pattern: (1) create constraint, (2) MERGE with ON CREATE SET, (3) verify count. Applies to any entity type.</Sidenote>



The `$chunkParam` dictionary is passed via the `params`
argument of `kg.query()`. The `ON CREATE SET` clause ensures
properties are set only when the node is first created, not on subsequent
runs.



<Sidenote category="warning">Without the uniqueness constraint, MERGE falls back to scanning all `Chunk` nodes for each insert—quadratic performance. Always create constraints before bulk loading.</Sidenote>



# Adding Vector Search to the Graph

## Create the Vector Index



```cypher
# Vector index for chunk text embeddings
kg.query("""
    CREATE VECTOR INDEX form10kChunks IF NOT EXISTS
    FOR (c:Chunk) ON (c.textEmbedding)
    OPTIONS {
      indexConfig: {
        `vector.dimensions`: 1536,
        `vector.similarity_function`: 'cosine'
      }
    }
""")
```



## Populate Embeddings

Match all chunks and calculate embeddings using OpenAI:



```cypher
# Generate embeddings for all chunks
kg.query("""
    MATCH (c:Chunk)
    WITH c, genai.vector.encode(
        c.text, "OpenAI", {token: $openAiApiKey}
    ) AS vector
    CALL db.create.setNodeVectorProperty(
        c, "textEmbedding", vector
    )
""", params={"openAiApiKey": OPENAI_API_KEY})
```





<Sidenote category="crossref">This follows the same embedding pattern from Module 3 (§), now applied to SEC filing chunks instead of movie taglines.</Sidenote>



# Building a RAG Chain with LangChain

&lt;!–MDXB-16-OPEN–&gt;

1.  **Connect** *(Neo4jVector setup)*  
    LangChain’s Neo4jVector wraps Neo4j as a standard vector store,
    using Cypher under the hood for similarity search.

2.  **Retrieve** *(vector search)*  
    The user’s question is encoded and matched against chunk
    embeddings. Top-K similar chunks are retrieved.

3.  **Generate** *(LLM + context)*  
    Retrieved chunks are injected into the LLM prompt as context.
    The LLM generates a natural language answer grounded in the
    retrieved evidence.

&lt;!–MDXB-16-CLOSE–&gt;

## Neo4j as a Vector Store



```cypher
from langchain_community.vectorstores import Neo4jVector
from langchain_openai import OpenAIEmbeddings

neo4j_vector = Neo4jVector.from_existing_graph(
    OpenAIEmbeddings(),
    url=NEO4J_URI,
    username=NEO4J_USERNAME,
    password=NEO4J_PASSWORD,
    index_name="form10kChunks",
    node_label="Chunk",
    text_node_properties=["text"],
    embedding_node_property="textEmbedding",
)
retriever = neo4j_vector.as_retriever()
```

## Preventing Hallucination with Prompt Engineering



<Sidenote category="crossref">vol6 Ch 4: RAG — hallucination mitigation via prompt engineering.</Sidenote>



&lt;!–MDXB-28-OPEN–&gt;

When asked about companies not in the dataset, the LLM hallucinated—
it described Apple using NetApp’s data. The model filled the gap with
plausible-sounding but incorrect information because the prompt did not
instruct it to acknowledge knowledge boundaries.

&lt;!–MDXB-28-CLOSE–&gt;

&lt;!–MDXB-17-OPEN–&gt;

1.  **Add a safety instruction** to the prompt:
    “If you are unsure, say you don’t know.”

2.  **Scope the context**: State that context
    comes from specific SEC filings only.

3.  **Validate retrieval**: Check similarity
    scores before passing chunks to the LLM. Low
    scores indicate out-of-scope questions.

&lt;!–MDXB-17-CLOSE–&gt;



```cypher
# Improved prompt that prevents hallucination
chain = RetrievalQA.from_chain_type(
    ChatOpenAI(temperature=0),
    chain_type="stuff",
    retriever=retriever,
    chain_type_kwargs={
        "prompt": PromptTemplate(
            template="""Use the following context to answer.
If you are unsure about the answer, say you don't know.

Context: {context}
Question: {question}
Answer:""",
            input_variables=["context", "question"]
        )
    },
)
# Now "Tell me about Apple" -> "I don't know"
```

# Current Limitations

&lt;!–MDXB-19-OPEN–&gt;

At this stage, Neo4j is used *only* as a vector store. The chunk
nodes are disconnected—there are no relationships between them, no
connection to the form they came from, and no link to the company that
filed the form. This means:

- You cannot follow a chunk back to its source document.

- You cannot retrieve adjacent chunks for expanded context.

- You cannot traverse from a chunk to related entities
  (companies, investors).

Module 5 transforms this flat collection into a true Knowledge Graph
by adding NEXT, PART\_OF, and SECTION relationships.

**When It Breaks:** If your questions only require semantic similarity
(e.g., FAQ lookup), a pure vector store is sufficient and simpler to operate.
Graph overhead is wasted when no relationship-based retrieval is needed.

# Practice Problems

&lt;!–MDXB-20-OPEN–&gt;

**Core Insight:** Every step in a graph construction pipeline must be
safe to re-run: uniqueness constraints prevent duplicate nodes, MERGE
prevents duplicate relationships, `IF NOT EXISTS` prevents duplicate
indexes. An idempotent pipeline converts “at-least-once” message delivery
(the reality of distributed systems) into “exactly-once” graph state.

**Why It Matters:** Production data pipelines fail and retry. If your
graph construction is not idempotent, every failure+retry creates duplicate
data. At scale, this silently corrupts the graph.

**When It Breaks:** MERGE on a pattern with volatile properties
(timestamps, counters) creates new elements every run. Always MERGE on
stable identifiers only.

&lt;!–MDXB-22-OPEN–&gt;

You are building a RAG system over legal contracts. Each contract is 20–50
pages long, with distinct sections: parties, terms, obligations, and
termination clauses.

1.  The default chunk size is 2000 characters with 200 overlap.
    Calculate the approximate number of chunks for a 40-page contract
    (assume 3000 characters per page).

2.  Would you use the same chunking strategy as the SEC filings?
    Explain why or why not.

3.  How would you preserve section boundaries in the chunk metadata?

&lt;!–MDXB-22-CLOSE–&gt;

&lt;!–MDXB-24-OPEN–&gt;

**Approach:** **Step 1: Chunk Count Calculation**  
Total text: 40 × 3000 = 120, 000 characters.  
Effective chunk advance: 2000 − 200 = 1800 characters per chunk.  
Number of chunks: ⌈120, 000/1800⌉ = 67 chunks.

**Step 2: Strategy Comparison**  
No—legal contracts have a different structure than SEC filings. Contracts
have **clause-level semantics**: a single clause (e.g., an indemnification
clause) should not be split across chunks. Use a **recursive text
splitter** that splits on section headers first, then paragraphs, then
characters. This preserves semantic boundaries that a fixed-size splitter
would break.

**Step 3: Section Boundary Preservation**  
Add a `section` field to chunk metadata (e.g., “obligations”,
“termination”). When splitting, detect section headers (e.g., lines
matching “Article N:” or “Section N.”) and tag each chunk with its
parent section. This enables section-filtered retrieval and correct NEXT
relationship creation.

**Key Insight:** Chunking strategy should be document-structure-aware.
SEC filings have large homogeneous sections (suitable for fixed-size chunking).
Legal contracts have small, semantically distinct clauses (requiring
structure-aware splitting). The chunk size is a tuning parameter, but the
splitting *strategy* is a design decision.

**Answer:** ≈67 chunks. Use recursive splitter with section
awareness, not fixed-size. Preserve section identity in chunk metadata.

&lt;!–MDXB-23-OPEN–&gt;

Your RAG system over SEC filings produces the following response:

**Question:** “What is Apple’s revenue?”  
**Answer:** “Apple reported revenue of $6.32 billion in fiscal year
2023, primarily from cloud storage and data management services.”

The knowledge graph only contains NetApp’s Form 10-K.

1.  Identify what is wrong with this answer.

2.  Explain the root cause of the hallucination.

3.  Write a prompt template that prevents this type of error.

&lt;!–MDXB-23-CLOSE–&gt;

&lt;!–MDXB-25-OPEN–&gt;

**Approach:** **Step 1: Error Identification**  
The answer attributes NetApp’s business description (“cloud storage and data
management”) to Apple. The revenue figure is likely fabricated. The LLM
mixed retrieved context (NetApp data) with world knowledge (Apple) to
generate a plausible but completely wrong answer.

**Step 2: Root Cause**  
The retrieval step found the most similar chunks to “Apple’s revenue”—
which happened to be NetApp’s revenue-related chunks (highest cosine
similarity among available chunks). The LLM prompt did not instruct the
model to verify that the retrieved context actually pertains to Apple.

**Step 3: Safe Prompt Template**


```sql
Use ONLY the following context to answer the question.
The context comes from SEC filings for specific companies.
If the context does not contain information about the
company or topic in the question, respond: "I don't have
information about that company in my data."
Do NOT use your general knowledge to fill gaps.

Context: {context}
Question: {question}
Answer:
```



**Key Insight:** RAG hallucination has two failure modes: (1) the LLM
invents facts not in the context, (2) the LLM applies context from entity A
to entity B. The prompt must guard against both by explicitly instructing
the model to check entity alignment and acknowledge knowledge boundaries.

**Answer:** Answer mixes NetApp data with Apple identity. Cause: no
entity-alignment check. Fix: prompt instructs “use ONLY context” and
“say you don’t know” for missing entities.

\[KGR-4.4\]
TechCorp is building an internal knowledge graph from three data sources:

- **HR database**: 5,000 employees with names, departments,
  titles, and reporting chains

- **Confluence wiki**: 12,000 pages of technical documentation
  (50–500 words each)

- **Jira tickets**: 80,000 tickets with assignees, labels,
  and descriptions

The goal is a RAG system where engineers can ask: “Who worked on the
authentication refactor?” or “What’s the design doc for the payment
service?”

| **Source**   | **Records** | **Update Frequency** |
|:-------------|:-----------:|:--------------------:|
| HR database  |    5,000    |        Daily         |
| Confluence   |   12,000    |        Hourly        |
| Jira tickets |   80,000    |      Real-time       |

**Question 1:** Design the node types, relationship types, and linking
keys for this knowledge graph.

**Question 2:** Which data source should you ingest first? Why?

**Question 3:** Jira tickets update in real-time. How do you handle
updates without creating duplicate nodes?

&lt;!–MDXB-29-CLOSE–&gt;

&lt;!–MDXB-26-OPEN–&gt;

**Approach:** **Question 1: Graph Schema Design**

*Node types:*

- `Employee` (employeeId, name, title, department)

- `Document` (pageId, title, space)

- `DocumentChunk` (chunkId, text, chunkSeqId, textEmbedding)

- `Ticket` (ticketId, summary, status, labels)

*Relationship types:*

- `Employee -[:REPORTS_TO]-> Employee`

- `Employee -[:AUTHORED]-> Document`

- `Employee -[:ASSIGNED_TO]-> Ticket`

- `DocumentChunk -[:PART_OF]-> Document`

- `DocumentChunk -[:NEXT]-> DocumentChunk`

- `Ticket -[:REFERENCES]-> Document`

*Linking keys:* `employeeId` (HR ↔ Confluence
author ↔ Jira assignee), `pageId` (Confluence
↔ Jira references).

**Question 2: Ingestion Order**  
HR database first. Employees are the **anchor entities**—both Confluence
and Jira reference employees as authors/assignees. Creating Employee nodes
first enables MERGE-based linking when ingesting the other sources. Without
Employee nodes, you cannot create AUTHORED or ASSIGNED\_TO relationships.

**Question 3: Real-Time Update Handling**  
Use MERGE on `ticketId` with ON MATCH SET for mutable properties:


```cypher
MERGE (t:Ticket {ticketId: $ticket.id})
ON CREATE SET t.summary = $ticket.summary,
              t.status = $ticket.status
ON MATCH SET  t.status = $ticket.status,
              t.updatedAt = datetime()
```


This is the idempotent pipeline pattern: MERGE on stable identifier,
update volatile properties on match. For Jira’s real-time volume, batch
updates every 5 minutes rather than processing each webhook individually.

**Answer:** **Question 1: Graph Schema Design**

*Node types:*

- `Employee` (employeeId, name, title, department)

- `Document` (pageId, title, space)

- `DocumentChunk` (chunkId, text, chunkSeqId, textEmbedding)

- `Ticket` (ticketId, summary, status, labels)

*Relationship types:*

- `Employee -[:REPORTS_TO]-> Employee`

- `Employee -[:AUTHORED]-> Document`

- `Employee -[:ASSIGNED_TO]-> Ticket`

- `DocumentChunk -[:PART_OF]-> Document`

- `DocumentChunk -[:NEXT]-> DocumentChunk`

- `Ticket -[:REFERENCES]-> Document`

*Linking keys:* `employeeId` (HR ↔ Confluence
author ↔ Jira assignee), `pageId` (Confluence
↔ Jira references).

**Question 2: Ingestion Order**  
HR database first.

**Key Insight:** The core principle demonstrated here is that understanding the underlying mechanism enables better decision-making in practice.

<AnkiCard type="keyconcept" id="chapters-vol0-ch04-CONCEPT-NEO4J_AS_A_PURE_VECTOR_STORE" los="KGR-4.8" front={"Key Concept: Neo4j as a Pure Vector Store"} back={"At this stage, Neo4j is used only as a vector store. The chunk\n nodes are disconnected—there are no relationships between them, no\n connection to the form they came from, and no link to the company that\n filed the form. <AnkiCard type="keyconcept" id="chapters-vol0-ch04-CONCEPT-IDEMPOTENT_PIPELINE_DESIGN" los="KGR-4.4" front={"Key Concept: Idempotent Pipeline Design"} back={"Core Insight: Every step in a graph construction pipeline must be\nsafe to re-run: uniqueness constraints prevent duplicate nodes, MERGE\nprevents duplicate relationships, IF NOT EXISTS prevents duplicate\nindexes.
