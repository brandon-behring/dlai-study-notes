# SEC Form 13 Data

<ConceptBox>

**Why Form 13?**
Form 13 is filed by institutional investment management firms<Citation src="sec2024edgar" /> to report
their public company holdings. By connecting this investment data to the
existing Form 10-K graph, you can answer complex questions about who
invests in which companies and at what scale—questions that combine
structured relationship data with unstructured document text.

</ConceptBox>



<Term name="SEC Form 13" los="KGR-6.1">
  A filing made by institutional investment management firms reporting their holdings of public company stock. Contains manager identity, company identity (via CUSIP), share counts, and monetary values. Filed quarterly with the SEC.
</Term>

# Creating Company and Manager Nodes

## Company Nodes



```cypher
# Create Company nodes using CUSIP as the unique identifier
kg.query("""
    MERGE (com:Company {cusip6: $companyParam.cusip6})
    ON CREATE SET
      com.companyName = $companyParam.companyName,
      com.cusip = $companyParam.cusip
""", params={"companyParam": company_data})
```

## Linking Company to Existing Form

Match the new Company node to the existing Form 10-K node using the
shared **CUSIP 6** identifier, then create a FILED relationship:



```cypher
# Bridge Company to Form via shared CUSIP 6
kg.query("""
    MATCH (com:Company), (f:Form)
    WHERE com.cusip6 = f.cusip6
    MERGE (com)-[:FILED]->(f)
""")
```



<KeyConcept title="Cross-Dataset Linking via CUSIP" los="KGR-6.7">

The CUSIP 6 identifier is the bridge between two independently created
datasets. The Form 10-K data (Module 4) and the Form 13 investment
data (this module) both contain CUSIP codes, enabling automatic linking
without manual matching. This pattern—shared identifiers across
datasets—is the standard approach for expanding Knowledge Graphs with
new data sources.

**When It Breaks:** When datasets use different identifier schemes
(e.g., one uses CUSIP, another uses ISIN or ticker symbols), automatic
linking fails. You need an entity resolution layer to map between identifier
systems before MERGE can match nodes across datasets.

</KeyConcept>



<Term name="CUSIP" los="KGR-6.7">
  Committee on Uniform Security Identification Procedures. A 9-character alphanumeric code that uniquely identifies financial instruments. The first 6 characters (CUSIP 6) identify the issuing company. Used as the linking key between Form 10-K and Form 13 data.
</Term>

# Full-Text Index for Keyword Search

A **full-text index** on manager names enables string-based search,
complementing the vector similarity search from earlier modules:



```cypher
# Create full-text index on manager names
kg.query("""
    CREATE FULLTEXT INDEX fullTextManagerNames IF NOT EXISTS
    FOR (m:Manager) ON EACH [m.managerName]
""")

# Query the full-text index
result = kg.query("""
    CALL db.index.fulltext.queryNodes(
        "fullTextManagerNames", "Royal Bank"
    ) YIELD node, score
    RETURN node.managerName, score
""")
# Returns: Royal Bank of Canada (and similar matches)
```





<Term name="Full-Text Index" los="KGR-6.3">
  A database index optimised for string matching and keyword search. Unlike vector indexes (semantic similarity) or property indexes (exact match), full-text indexes support partial matching, fuzzy search, and relevance scoring. Created with `CREATE FULLTEXT INDEX`.
</Term>

# Creating Investment Relationships



```cypher
# Create OWNS_STOCK_IN relationships with investment data
for row in csv_data:
    kg.query("""
        MATCH (mgr:Manager {managerCik: $ownsParam.managerCik}),
              (com:Company {cusip6: $ownsParam.cusip6})
        MERGE (mgr)-[owns:OWNS_STOCK_IN {
          reportCalendarOrQuarter:
              $ownsParam.reportCalendarOrQuarter
        }]->(com)
        ON CREATE SET
          owns.value = $ownsParam.value,
          owns.shares = $ownsParam.shares
    """, params={"ownsParam": row})
# Creates 561 relationships connecting managers to NetApp
```

# Complete Graph Schema

After expansion, the Knowledge Graph contains:

<PipelineBox title="Complete Graph Schema After Module 6">

**Nodes:**

- `Chunk` — text chunks with embeddings

- `Form` — Form 10-K filings

- `Company` — public companies

- `Manager` — investment management firms

**Relationships:**

- `Chunk -[:NEXT]-> Chunk` (linked list)

- `Chunk -[:PART_OF]-> Form` (document membership)

- `Form -[:SECTION]-> Chunk` (section entry points)

- `Company -[:FILED]-> Form` (filing relationship)

- `Manager -[:OWNS_STOCK_IN]-> Company` (investment holdings)

**Indexes:**

- Vector index on `Chunk.textEmbedding`

- Full-text index on `Manager.managerName`

</PipelineBox>

# Multi-Hop Graph Traversal

Starting from any chunk, you can traverse the entire graph through
four hops:



```cypher
# Four-hop traversal: Chunk -> Form -> Company -> Manager
result = kg.query("""
    MATCH (c:Chunk)-[:PART_OF]->(f:Form)
          <-[:FILED]-(com:Company)
          <-[:OWNS_STOCK_IN]-(mgr:Manager)
    RETURN com.companyName,
           count(mgr) AS numberOfInvestors
""")
# Result: NetApp has 561 investors
```

# Enhanced RAG with Investment Context



<Sidenote category="interview">"When does adding graph context improve RAG answers?" When the question requires relationship data that vector search cannot surface.</Sidenote>



## Two Chains for Comparison



```cypher
# Investment-enhanced retrieval query
investment_retrieval_query = """
    WITH node, score
    MATCH (node)-[:PART_OF]->(f:Form)
          <-[:FILED]-(com:Company)
          <-[owns:OWNS_STOCK_IN]-(mgr:Manager)
    RETURN node.text AS text, score,
           {investors: collect(mgr.managerName)}
               AS metadata
    ORDER BY owns.shares DESC
    LIMIT 10
"""
```



## Comparison Results

| **Question** | **Plain Chain** | **Investment Chain** |
|:---|:---|:---|
| “Tell me about NetApp” | General business description | Similar (LLM did not use investment data—not asked) |
| “Who are NetApp’s investors?” | Vague—mentions “diversified customer base” | Specific investor names and share counts |



<Sidenote category="crossref">vol6 Ch 4: RAG — targeted context expansion via graph traversal must align with expected question types for effective retrieval.</Sidenote>



<KeyConcept title="Question-Context Alignment" los="KGR-6.6">

The quality of RAG answers improves dramatically when the
*question matches the expanded context*. Asking about investors
when investment data is available produces specific, accurate answers.
Asking a general question with investment context adds noise without
improving the answer. The lesson: context expansion must be
*targeted*—add relationship data that is relevant to the
expected question types.

**When It Breaks:** Expanding context with relationship data that does
not match the question type adds noise without improving quality. The LLM
ignores irrelevant context, so the extra traversal cost (latency, tokens) is
wasted. Always design retrieval queries around the expected question
distribution.

</KeyConcept>



<Sidenote category="warning">LLM ignores irrelevant context. Unmatched expansion adds latency without quality gain. Design retrieval queries to match expected user questions.</Sidenote>



# Chapter Summary

Form 13 data adds institutional investment information to the Knowledge
Graph. CUSIP 6 serves as the linking key between Company nodes and existing
Form nodes, demonstrating the cross-dataset linking pattern. Full-text
indexes complement vector indexes by enabling keyword-based search on
entity names. Multi-hop traversal from chunks through forms to companies
to managers enables complex queries that combine document content with
structured relationship data. Graph pattern results can be transformed
into natural language sentences for LLM context. The quality of
graph-enhanced RAG<Citation src="gao2024retrieval" /> answers depends on alignment between the question
and the expanded context: asking about investors with investment data
produces dramatically better results.

# Practice Problems

<Problem title="Cross-Dataset Linking Strategy" los="KGR-6.7">

You are integrating two datasets into a Knowledge Graph:

- **Dataset A**: Patent filings with inventor names, patent IDs,
  and company assignees (identified by company name)

- **Dataset B**: Employee database with employee IDs, names,
  departments, and employer names

1.  Identify the linking key(s) between the two datasets.

2.  What problem arises if you use company name as the linking key?

3.  Propose a more robust linking strategy.

</Problem>

<Solution>

**Approach:** **Step 1: Candidate Linking Keys**  
Person name (inventor → employee) and company name (patent assignee →
employer) are the two candidates.

**Step 2: Company Name Problems**  
Company names are not standardised across datasets. “Google LLC”,
“Alphabet Inc.”, and “Google” may all refer to the same entity. Name
variations, abbreviations, and legal entity suffixes cause false negatives
(missed matches) and false positives (wrong matches).

**Step 3: Robust Linking Strategy**

- Use a canonical identifier (e.g., DUNS number, SEC CIK, or
  an internal company ID) as the primary linking key.

- If no canonical ID exists, create an entity resolution pipeline:
  (a) fuzzy match on names, (b) verify with secondary attributes
  (address, industry), (c) create a canonical `Company` node
  with an `aliases` property for all name variants.

- For person linking: match on full name + company affiliation to
  disambiguate common names (e.g., “John Smith at Google” vs. “John Smith at Amazon”).

**Key Insight:** Cross-dataset linking is an **entity resolution**
problem. The CUSIP pattern from this chapter works because CUSIP is a
universal identifier. When no universal ID exists, you must build an entity
resolution layer—which is often the hardest part of KG construction.

**Answer:** Use canonical IDs where available. Build entity resolution
for name-based linking. Never rely on raw name strings as primary keys.

</Solution>

<Problem title="Multi-Hop Investment Analysis" los="KGR-6.4">

Using the SEC Knowledge Graph from this module, write Cypher queries for:

1.  Find the top 5 investment managers by total value of NetApp shares.

2.  For each manager in the top 5, find all Form 10-K sections they
    could be interested in (traverse from Manager → Company → Form →
    Section → first Chunk).

3.  Combine both queries into a single query that returns manager names
    with the text of Item 1 (business description).

</Problem>

<Solution>

**Approach:** **Step 1: Top 5 Managers by Investment Value**


```cypher
MATCH (mgr:Manager)-[owns:OWNS_STOCK_IN]->(com:Company)
RETURN mgr.managerName,
       sum(owns.value) AS totalValue
ORDER BY totalValue DESC
LIMIT 5
```



**Step 2: Manager → Form Sections**


```sql
MATCH (mgr:Manager)-[:OWNS_STOCK_IN]->(com:Company)
      -[:FILED]->(f:Form)-[s:SECTION]->(c:Chunk)
WHERE mgr.managerName IN $topManagers
RETURN mgr.managerName, s.f10kItem, c.chunkId
```



**Step 3: Combined Query**


```cypher
MATCH (mgr:Manager)-[owns:OWNS_STOCK_IN]->(com:Company)
WITH mgr, sum(owns.value) AS totalValue
ORDER BY totalValue DESC LIMIT 5
MATCH (mgr)-[:OWNS_STOCK_IN]->(com:Company)
      -[:FILED]->(f:Form)
      -[s:SECTION {f10kItem: "item1"}]->(c:Chunk)
RETURN mgr.managerName, totalValue, c.text
```



**Key Insight:** Multi-hop queries in Cypher compose naturally. The
WITH clause acts as a pipeline stage—compute the top 5 managers first,
then expand their graph neighbourhood. This is the equivalent of a subquery
in SQL but reads as a sequential narrative.

**Answer:** Three queries composing into one 4-hop traversal from
Manager through investment relationship to document content.

</Solution>

<Vignette title="Knowledge Graph for Enterprise FAQ Retrieval">

\[KGR-6.6\]
FinServ Corp operates a customer-facing FAQ system for their investment
products. Currently, the system uses pure vector search over 2,000 FAQ
articles. Customer satisfaction is 72% (target: 85%).

Analysis reveals two failure modes:

- **Mode 1 (40% of failures):** Questions about specific
  products return answers about similar but different products

- **Mode 2 (35% of failures):** Questions requiring
  cross-product comparison (“How does Fund A differ from Fund B?”)
  retrieve content about only one fund

| **Entity**         | **Count** |        **Attributes**        |
|:-------------------|:---------:|:----------------------------:|
| Products (funds)   |    150    | name, type, risk level, fees |
| FAQ articles       |   2,000   | text, product tags, category |
| Product categories |    12     |      name, description       |
| Regulatory filings |    500    |  filing type, date, product  |

**Question 1:** Design a Knowledge Graph schema that addresses both
failure modes.

**Question 2:** Write a retrieval strategy for comparison questions
(“How does Fund A differ from Fund B?”).

**Question 3:** Estimate the customer satisfaction improvement if each
failure mode is reduced by 60%.

</Vignette>

<Solution>

**Approach:** **Question 1: Graph Schema Design**

*Nodes:* Product, FAQChunk, Category, Filing.  
*Relationships:*

- `FAQChunk -[:ABOUT]-> Product` (product attribution)

- `Product -[:IN_CATEGORY]-> Category`

- `Product -[:SIMILAR_TO]-> Product` (same category,
  different product—enables comparison)

- `Filing -[:PERTAINS_TO]-> Product`

- `FAQChunk -[:NEXT]-> FAQChunk` (within same article)

**Mode 1 fix:** The ABOUT relationship ensures that when a chunk is
retrieved via vector search, the system verifies that the chunk’s product
matches the question’s product. If the user asks about “Fund A” but the
chunk is ABOUT “Fund B”, the system can filter it out.

**Mode 2 fix:** The SIMILAR\_TO relationship enables comparative
retrieval. When the question mentions two products, retrieve chunks
ABOUT each product separately, then combine them for the LLM.

**Question 2: Comparison Retrieval Strategy**

1.  Extract product names from the question (“Fund A”, “Fund B”).

2.  Full-text search for each product node.

3.  For each product, traverse `ABOUT` relationships to find
    relevant FAQ chunks.

4.  Combine chunks from both products into the LLM context.

5.  Optionally: include the SIMILAR\_TO relationship properties
    (pre-computed differences) as additional context.

**Question 3: Satisfaction Improvement**  
Current failures: 100% − 72% = 28% failure rate.  
Mode 1 contributes 28% × 40% = 11.2% failures.  
Mode 2 contributes 28% × 35% = 9.8% failures.  
After 60% reduction: Mode 1 drops to 4.5%, Mode 2 to 3.9%.  
New failure rate: 28% − (6.7% + 5.9%) = 15.4%.  
New satisfaction: ≈85%—meeting the target.

**Answer:**

1.  Extract product names from the question (“Fund A”, “Fund B”).

2.  Full-text search for each product node.

3.  For each product, traverse `ABOUT` relationships to find relevant FAQ chunks.

4.  Combine chunks from both products into the LLM context.

5.  Optionally: include the SIMILAR\_TO relationship properties (pre-computed differences) as additional context.

**Key Insight:** The core principle demonstrated here is that understanding the underlying mechanism enables better decision-making in practice.

</Solution>
