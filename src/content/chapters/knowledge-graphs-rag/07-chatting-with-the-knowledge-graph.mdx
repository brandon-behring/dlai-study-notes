# The Extract-Enhance-Expand Pattern

<KeyConcept title="Extract-Enhance-Expand" los="KGR-7.1">

Throughout the course, the Knowledge Graph was built by repeating a
three-phase pattern:

1.  **Extract**: Pull information from source data into
    separate nodes (splitting text into chunks, creating Form /
    Company / Manager nodes from structured data).

2.  **Enhance**: Supercharge data with indexes or computed
    properties (vector embeddings, full-text indexes, geospatial
    points).

3.  **Expand**: Connect new data to the existing graph
    (NEXT, PART\_OF, FILED, OWNS\_STOCK\_IN relationships).

This pattern was applied at every stage: raw text to chunks, chunks to
forms, Form 13 CSV to companies and managers. It provides a repeatable
framework for growing any Knowledge Graph incrementally.

**When It Breaks:** The pattern assumes new data can be cleanly linked
to existing nodes via shared identifiers. When identifiers are absent or
ambiguous (e.g., name-only matching across datasets), the Expand phase
requires an entity resolution step that the pattern does not cover.

</KeyConcept>

</Term>

# Exploring the Graph with Cypher

## Finding Managers and Their Locations



```cypher
# Find a manager and their address
result = kg.query("""
    MATCH (mgr:Manager)-[:LOCATED_AT]->(addr:Address)
    RETURN mgr.managerName, addr.city, addr.state
    LIMIT 1
""")
```



The Address node contains `city`, `state`, and a
`location` property (a geospatial point with latitude/longitude).

## Full-Text Search with Location



```cypher
# Full-text search combined with location lookup
result = kg.query("""
    CALL db.index.fulltext.queryNodes(
        "fullTextManagerNames", "Royal Bank"
    ) YIELD node AS mgr, score
    MATCH (mgr)-[:LOCATED_AT]->(addr:Address)
    RETURN mgr.managerName, addr.city, addr.state
""")
# Royal Bank of Canada is located in Canada
```



## Aggregation Queries



```cypher
# Top states by number of investment firms
result = kg.query("""
    MATCH (mgr:Manager)-[:LOCATED_AT]->(addr:Address)
    RETURN addr.state AS state,
           count(addr.state) AS numberOfManagers
    ORDER BY numberOfManagers DESC LIMIT 10
""")
# New York leads, followed by California

# Top states by number of public companies
result = kg.query("""
    MATCH (com:Company)-[:LOCATED_AT]->(addr:Address)
    RETURN addr.state AS state,
           count(addr.state) AS numberOfCompanies
    ORDER BY numberOfCompanies DESC LIMIT 10
""")
# California leads for companies
```

**Geographic Insight.**
Investment firms cluster in **New York** (Wall Street) and
**San Francisco**, while tech companies cluster in **Santa
Clara**, **San Jose**, **Sunnyvale**, and **Cupertino**
(Silicon Valley). Within California, the cities are entirely
different—a pattern that only graph aggregation can reveal.

</ConceptBox>

# Geospatial Queries



<Term name="Geospatial Point" los="KGR-7.2">
  A Neo4j data type representing a location on Earth with latitude and longitude coordinates. Stored as a `point()` value and queried with `point.distance()` for distance calculations in metres.
</Term>
<AnkiCard type="term" front={"Geospatial Point"} back={"A Neo4j data type representing a location on Earth with latitude and longitude coordinates. Stored as a `point()` value and queried with `point.distance()` for distance calculations in metres."} los="KGR-7.2" />



## Distance-Based Search

Neo4j’s `point.distance()` function calculates the distance between
two geospatial points in metres:



```cypher
# Find companies within 10 km of Santa Clara
result = kg.query("""
    MATCH (sc:Address {city: "Santa Clara"})
    MATCH (com:Company)-[:LOCATED_AT]->(comAddr:Address)
    WHERE point.distance(sc.location, comAddr.location) < 10000
    RETURN com.companyName, com.companyAddress
""")
# Returns: Palo Alto Networks, Seagate, Apple (Cupertino), etc.
```





<Sidenote category="warning">The distance parameter is in **metres**, not kilometres. Use 10000 for 10 km, 50000 for 50 km. This is a common source of bugs in geospatial queries.</Sidenote>



## Cross-Entity Distance Queries

Find investment firms near a specific company, using full-text search for
fuzzy name matching:



```cypher
# Investment firms near Palo Alto Networks
# Note: full-text search handles misspellings
result = kg.query("""
    CALL db.index.fulltext.queryNodes(
        "fullTextCompanyNames", "Palo Alato Networks"
    ) YIELD node AS com, score
    MATCH (com)-[:LOCATED_AT]->(comAddr:Address)
    MATCH (mgr:Manager)-[:LOCATED_AT]->(mgrAddr:Address)
    WHERE point.distance(comAddr.location,
                         mgrAddr.location) < 10000
    RETURN mgr.managerName,
           point.distance(comAddr.location,
                          mgrAddr.location) / 1000
               AS distanceKm
""")
```





<Term name="point.distance()" los="KGR-7.2">
  Neo4j function that calculates the geodesic distance between two geospatial points in metres. Uses the haversine formula for great-circle distance on the Earth's surface. Divide by 1000 for kilometres.
</Term>
<AnkiCard type="term" front={"point.distance()"} back={"Neo4j function that calculates the geodesic distance between two geospatial points in metres. Uses the haversine formula for great-circle distance on the Earth's surface. Divide by 1000 for kilometres."} los="KGR-7.2" />





<Sidenote category="formula">Common conversions: 1 mile $$ 1609 m. Use 80467 for 50 miles, 16093 for 10 miles. Always comment units in production code.</Sidenote>



<KeyConcept title="Geospatial Search as a Retrieval Paradigm" los="KGR-7.2">

Geospatial queries use `point.distance()` to find entities
within a radius, adding a fourth retrieval paradigm alongside vector,
full-text, and graph traversal. The distance function returns metres
and requires a point index for performant range queries.

**Why It Matters:** Location-aware retrieval surfaces
relationships that semantic similarity cannot detect—two companies
10 km apart may share suppliers, talent pools, or regulatory
jurisdictions.

**When It Breaks:** Without a point index, distance queries
degrade to *O*(*n*) full scans. Always create indexes before queries.

</KeyConcept>

<NarrativeBox title="Debugging Geospatial Queries">

1.  **No results?** Check that Address nodes have
    `location` properties with valid point values.

2.  **Too many/few results?** Adjust the distance threshold.
    Remember: the unit is metres.

3.  **Wrong distances?** Verify latitude/longitude order
    in the point data. Neo4j uses
    `point({latitude: x, longitude: y})`.

</NarrativeBox>

# LLM-Generated Cypher with Few-Shot Learning

<ConceptBox>

**The Vision.**
Instead of writing Cypher queries manually, teach the LLM to generate
valid Cypher from natural language questions. The LLM becomes a
“Cypher compiler” that translates user intent into graph queries.

</ConceptBox>

## Few-Shot Prompt Design



```cypher
CYPHER_GENERATION_TEMPLATE = """
Task: Generate Cypher statements to query a graph database.
Instructions:
- Use only the provided relationship types and properties.
- Do not hallucinate relationship types or properties.
Schema: {schema}

Examples:
# What investment firms are in San Francisco?
MATCH (mgr:Manager)-[:LOCATED_AT]->(addr:Address)
WHERE addr.city = "San Francisco"
RETURN mgr.managerName

# What investment firms are near Santa Clara?
MATCH (sc:Address {{city: "Santa Clara"}})
MATCH (mgr:Manager)-[:LOCATED_AT]->(mgrAddr:Address)
WHERE point.distance(sc.location, mgrAddr.location) < 10000
RETURN mgr.managerName,
       point.distance(sc.location, mgrAddr.location)
           AS distanceMeters
ORDER BY distanceMeters ASC

# What does Palo Alto Networks do?
CALL db.index.fulltext.queryNodes(
    "fullTextCompanyNames", "Palo Alto Networks"
) YIELD node AS com
MATCH (com)-[:FILED]->(f:Form)-[s:SECTION]->(c:Chunk)
WHERE s.f10kItem = "item1"
RETURN c.text

Question: {question}
"""
```

## Progressive Few-Shot Examples

Each new example teaches the LLM a new query pattern. The LLM
generalises—after learning about investment firms in San Francisco, it
can also query companies in Santa Clara without explicit instruction:

| **Example Added** | **New Capability Unlocked** |
|:---|:---|
| Firms in San Francisco | City-based filtering for any entity type |
| Firms near Santa Clara | Geospatial `point.distance()` queries |
| What does Palo Alto Networks do? | Full-text search + SECTION traversal to document text |



<Term name="Progressive Few-Shot Learning" los="KGR-7.5">
  The practice of adding examples incrementally to a few-shot prompt, where each example unlocks a new query capability. The LLM generalises from each example to handle variations of the pattern. Two to three well-chosen examples typically cover a wide range of user questions.
</Term>

# LLM-Generated Cypher for Document Queries



<Sidenote category="warning">LLM-generated Cypher requires schema validation. Without it, the LLM invents plausible but non-existent relationship types.</Sidenote>



The most powerful capability: navigating from a company name to its
filing text via graph traversal, all generated by the LLM:



```cypher
# LLM generates this Cypher from the question
# "What does Palo Alto Networks do?"
generated_cypher = """
    CALL db.index.fulltext.queryNodes(
        "fullTextCompanyNames", "Palo Alto Networks"
    ) YIELD node AS com
    MATCH (com)-[:FILED]->(f:Form)
          -[s:SECTION]->(c:Chunk)
    WHERE s.f10kItem = "item1"
    RETURN c.text
"""
# The LLM then summarises the retrieved text:
# "Palo Alto Networks is a global cybersecurity provider..."
```



<RedFlag title="Schema Hallucination">

Without explicit schema injection and the instruction “do not hallucinate
relationship types,” the LLM may invent non-existent relationship types
or properties. Always inject the actual graph schema into the prompt and
validate generated Cypher before execution in production systems.

</RedFlag>

<NarrativeBox title="Debugging LLM-Generated Cypher">

1.  **Invalid relationship type?** The LLM hallucinated a
    relationship not in the schema. Add more examples using the
    correct relationships, or strengthen the schema instruction.

2.  **Empty results?** The generated Cypher may be
    syntactically valid but semantically wrong. Set
    `verbose=True` to inspect the generated query.

3.  **Wrong answer?** Check if the Cypher returns the right
    data. The issue may be in the LLM’s summarisation, not the
    query.

</NarrativeBox>

# The Four Retrieval Paradigms



<Sidenote category="crossref">vol6 Ch 4: RAG — unifying vector, full-text, graph, and geospatial retrieval in a single KG-powered query engine.</Sidenote>



<KeyConcept title="Four Retrieval Paradigms" los="KGR-7.7">

The final Knowledge Graph supports four complementary retrieval
approaches, each suited to different question types:

1.  **Vector search**: Semantic similarity for conceptual
    questions (“What is NetApp’s business?”).

2.  **Full-text search**: Keyword matching for entity lookup
    (“Find Royal Bank of Canada”).

3.  **Graph traversal**: Relationship following for
    structural questions (“Who are NetApp’s investors?”).

4.  **Geospatial search**: Distance-based queries for
    location questions (“What companies are near Santa Clara?”).

No single retrieval approach can answer all question types. The
Knowledge Graph’s power lies in combining all four in a single
query engine.

**When It Breaks:** Combining paradigms in a single query increases
latency and complexity. If 90% of questions are simple semantic lookups,
the overhead of maintaining full-text, geospatial, and graph indexes is
unjustified. Match infrastructure complexity to actual query diversity.

</KeyConcept>

# Practice Problems

<Problem title="Few-Shot Prompt Design for Cypher Generation" los="KGR-7.3">

You are building a GraphCypherQAChain for a university course graph with:

- Nodes: `Student`, `Professor`, `Course`,
  `Department`

- Relationships: `ENROLLED_IN`, `TEACHES`,
  `BELONGS_TO`, `ADVISES`

Design a few-shot prompt with 3 examples that enables the LLM to answer:

1.  “Who teaches Machine Learning?” (single-hop)

2.  “What courses do students of Dr. Smith take?” (multi-hop)

3.  “Which departments have the most courses?” (aggregation)

</Problem>

<Solution>

**Approach:** **Few-Shot Prompt:**


```cypher
Task: Generate Cypher to query a university graph.
Use ONLY the provided schema. Do NOT hallucinate
relationship types or properties.
Schema: {schema}

Examples:

# Who teaches Machine Learning?
MATCH (p:Professor)-[:TEACHES]->(c:Course
      {title: "Machine Learning"})
RETURN p.name

# What courses do students of Dr. Smith take?
MATCH (p:Professor {name: "Dr. Smith"})
      -[:ADVISES]->(s:Student)
      -[:ENROLLED_IN]->(c:Course)
RETURN s.name, c.title

# Which departments have the most courses?
MATCH (c:Course)-[:BELONGS_TO]->(d:Department)
RETURN d.name, count(c) AS courseCount
ORDER BY courseCount DESC

Question: {question}
```



**Design Rationale:**

- Example 1 teaches single-hop traversal with property filtering.

- Example 2 teaches multi-hop traversal (Professor → Student →
  Course) through the ADVISES relationship.

- Example 3 teaches aggregation with ORDER BY.

**Key Insight:** Each few-shot example should unlock a *different*
query capability. Three well-chosen examples cover single-hop, multi-hop,
and aggregation—which compose to handle most natural language questions.
Adding more examples yields diminishing returns; focus on pattern diversity,
not quantity.

**Answer:** 3 examples covering single-hop, multi-hop, and aggregation.
Each example teaches a different Cypher pattern the LLM can generalise from.

</Solution>

<Problem title="Geospatial Query Design" los="KGR-7.2">

A real estate Knowledge Graph has Property nodes with geospatial locations
and School nodes with geospatial locations.

1.  Write a Cypher query to find all schools within 2 km of a property
    at coordinates (37.3861, -122.0839).

2.  Modify the query to return results sorted by distance, closest first.

3.  What index should exist on School nodes to make this query
    performant?

</Problem>

<Solution>

**Approach:** **Step 1: Geospatial Proximity Query**


```sql
WITH point({latitude: 37.3861,
            longitude: -122.0839}) AS propLocation
MATCH (s:School)
WHERE point.distance(propLocation, s.location) < 2000
RETURN s.name,
       point.distance(propLocation, s.location)
           AS distanceMeters
```



**Step 2: Sorted by Distance**


```sql
WITH point({latitude: 37.3861,
            longitude: -122.0839}) AS propLocation
MATCH (s:School)
WHERE point.distance(propLocation, s.location) < 2000
RETURN s.name,
       point.distance(propLocation, s.location) / 1000
           AS distanceKm
ORDER BY distanceKm ASC
```



**Step 3: Required Index**  
A **point index** on School.location enables spatial range queries:


```cypher
CREATE POINT INDEX school_locations IF NOT EXISTS
FOR (s:School) ON (s.location)
```


Without this index, Neo4j must scan all School nodes and compute distances
for each—*O*(*n*) instead of *O*(log *n*).

**Key Insight:** Geospatial queries use `point.distance()` with
distances in **metres**. The most common bug is using kilometres
(2 instead of 2000). Always include a unit conversion comment in production
code.

**Answer:** Use point.distance() with 2000 metres threshold. Sort by
ASC for closest first. Create a point index for performance.

</Solution>

<Solution>

**Approach:** **1. “Risk factors for cloud computing companies”**  
**Paradigm: Vector search + Graph traversal.**  
Vector search finds chunks semantically similar to “risk factors for cloud
computing.” Graph traversal then expands context via PART\_OF → Form →
Company to confirm the chunks belong to cloud computing companies
(not unrelated firms).

**2. “Find Goldman Sachs”**  
**Paradigm: Full-text search.**  
This is an entity lookup by name. Full-text search handles partial matches
and variations (“Goldman Sachs Group Inc.” vs. “Goldman Sachs”).
Vector search would find semantically similar names (e.g., “Morgan
Stanley”), which is wrong.

**3. “Investors within 50 miles of NetApp”**  
**Paradigm: Full-text search + Geospatial + Graph traversal.**  
Full-text to find NetApp → LOCATED\_AT to get NetApp’s address → geospatial
distance to find nearby Manager addresses → OWNS\_STOCK\_IN to confirm
they are investors. Distance: 50 miles ≈ 80,467 metres.

**4. “Supply chain relationships for Apple’s components”**  
**Paradigm: Full-text + Graph traversal.**  
Full-text to find Apple → traverse SUPPLIES, MANUFACTURES, or similar
relationship types to component suppliers. This is purely structural—no
vector or geospatial search needed.

**Key Insight:** Complex questions often require **combining**
paradigms. The skill is decomposing a natural language question into a
sequence of retrieval steps, each using the most appropriate paradigm.
This is the core of KG-powered RAG system design.

**Answer:** (1) Vector + traversal, (2) Full-text, (3) Full-text +
geospatial + traversal, (4) Full-text + traversal. Most real questions
combine 2+ paradigms.
