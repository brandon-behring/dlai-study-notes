&lt;!–MDXB-8-OPEN–&gt;

You have built basic RAG systems that split documents into chunks, embed
them as vectors, and retrieve by cosine similarity. This works—but it
misses connections. When a user asks “who invested in NetApp?”, vector
search cannot traverse from a text chunk to a company to its investors.
Knowledge Graphs store data as interconnected entities<Citation src="hogan2021knowledge" />, enabling retrieval
strategies that follow relationships rather than relying solely on
embedding distance. This chapter establishes the vocabulary and mental
model you will use throughout the course.

&lt;!–MDXB-8-CLOSE–&gt;

# Why Knowledge Graphs Matter for RAG



<Sidenote category="interview">"How do Knowledge Graphs improve RAG beyond vector search?" is a common system design question for MLE and DS roles.</Sidenote>



Andreas Kollegger opens the course with a key observation: in a basic RAG
system, documents are split into chunks, transformed into vectors using an
embedding model, and searched via cosine similarity. This works well for
finding *semantically similar* text, but it cannot discover
*structural connections* between entities. Storing chunks in a Knowledge
Graph opens new retrieval strategies: you can retrieve one chunk, then
**traverse relationships** to find connected chunks, revealing
connections that similarity-based RAG would miss entirely.



<Term name="Retrieval Augmented Generation (RAG)" los="KGR-1.2">
  A system architecture that retrieves relevant context from an external data store and injects it into the LLM prompt before generation. Reduces hallucination by grounding responses in retrieved evidence.
</Term>

<Term name="Vector Similarity Search" los="KGR-1.2">

Knowledge Graphs are already used by **web search engines** (Google, Bing)
and **e-commerce platforms** for delivering relevant results<Citation src="noy2019industry" />. The knowledge
cards you see when searching for a celebrity—showing birth date, filmography,
and related people—are powered by a Knowledge Graph that connects entities
through typed relationships.



<Sidenote category="crossref">vol6 Ch 4: RAG — KG traversal as a retrieval strategy that complements embedding-based similarity search.</Sidenote>



&lt;!–MDXB-9-OPEN–&gt;

**The Key Insight.**
Vector search answers “what text is *similar* to my question?”
Knowledge Graph traversal answers “what entities are *connected*
to this result?” Combining both gives RAG systems access to information
that neither approach can surface alone.

**Example:** A vector search finds a chunk mentioning NetApp’s
business description. Graph traversal from that chunk follows
`PART_OF` → `Form` → `FILED` →
`Company` → `OWNS_STOCK_IN` to discover the
investment firms holding NetApp stock—information that no embedding
similarity could retrieve.

# Graph Data Model Fundamentals

&lt;!–MDXB-10-OPEN–&gt;

**The Mental Model.**
Think of a Knowledge Graph as a whiteboard diagram that is also a
database. Each circle is a **node** (an entity), each arrow is
a **relationship** (a connection), and both can carry key-value
**properties**. The diagram *is* the data.

&lt;!–MDXB-10-CLOSE–&gt;

## Nodes as Data Records

**Nodes** are data records that represent entities. In Cypher text
notation, nodes are written with **parentheses**: `(Person)`.
Each node can have one or more **labels** that group it with similar
entities, and zero or more **properties** stored as key-value pairs.



<Term name="Node" los="KGR-1.1">
  A data record representing an entity in a Knowledge Graph. Contains properties (key-value pairs) and one or more labels for grouping. Equivalent to a "vertex" in graph theory.
</Term>
<AnkiCard type="term" front={"Node"} back={"A data record representing an entity in a Knowledge Graph. Contains properties (key-value pairs) and one or more labels for grouping. Equivalent to a \"vertex\" in graph theory."} los="KGR-1.1" />





<Term name="Label" los="KGR-1.1">
  A tag applied to a node that groups it with similar entities. Examples: `Person`, `Movie`, `Company`. A node can have multiple labels. Labels enable efficient filtering in queries.
</Term>
<AnkiCard type="term" front={"Label"} back={"A tag applied to a node that groups it with similar entities. Examples: `Person`, `Movie`, `Company`. A node can have multiple labels. Labels enable efficient filtering in queries."} los="KGR-1.1" />





<Term name="Property" los="KGR-1.1">
  A key-value pair stored on a node or relationship. Keys are strings; values can be strings, numbers, booleans, or lists. Example: `{name: "Andreas", born: 1975}`.
</Term>
<AnkiCard type="term" front={"Property"} back={"A key-value pair stored on a node or relationship. Keys are strings; values can be strings, numbers, booleans, or lists. Example: `{name: \"Andreas\", born: 1975}`."} los="KGR-1.1" />



For example:

- A **Person** node stores `name`, `email`, and
  other personal details.

- A **Company** node stores `numberOfEmployees` and
  `annualRevenue`.

- A **Movie** node stores `title`, `tagline`,
  and `released` year.

## Relationships as Data Records

**Relationships** connect two nodes and are themselves rich data records.
Each relationship contains:

- The **pair of nodes** it connects (start and end node).

- A **type** that describes the nature of the connection
  (e.g., `ACTED_IN`, `KNOWS`, `TEACHES`).

- Optional **properties** (key-value pairs) about the
  relationship itself.



<Term name="Relationship" los="KGR-1.1">
  A directed connection between two nodes with a type and optional properties. Contains the pair of connected nodes plus metadata. Preferred over the graph theory term "edge" because it conveys richness beyond a simple connection.
</Term>
<AnkiCard type="term" front={"Relationship"} back={"A directed connection between two nodes with a type and optional properties. Contains the pair of connected nodes plus metadata. Preferred over the graph theory term \"edge\" because it conveys richness beyond a simple connection."} los="KGR-1.1" />



Text notation uses **square brackets** and arrows:



```cypher
# Cypher text notation (not executable Python)
# Person named Andreas KNOWS Person named Andrew since 2024
(Person {name: "Andreas"})-[:KNOWS {since: 2024}]->(Person {name: "Andrew"})
```





<Sidenote category="warning">The term "relationship" is preferred over "edge" because it conveys that the connection is a rich data record, not just a simple link.</Sidenote>



## Directionality and Rich Patterns

Relationships have **direction**, and patterns can chain together to
express complex scenarios:



```cypher
# Multi-relationship pattern in Cypher notation
(Person {name: "Andreas"})-[:TEACHES]->(Course {title: "KG for RAG"})
    <-[:INTRODUCES]-(Person {name: "Andrew"})
```





<Sidenote category="formula">Graph traversal cost: $O(k^d)$ where $k$ = avg connections/node, $d$ = hops. SQL equivalent: $O(n^d)$ self-JOINs.</Sidenote>



An important modelling insight: rather than labelling a person as a “teacher”
or “introducer,” the **relationship itself** defines their role.
Andreas is a teacher because he `TEACHES`; Andrew is an introducer
because he `INTRODUCES`. This pattern—*identity through
relationships rather than explicit type labels*—is central to Knowledge
Graph design.

&lt;!–MDXB-13-OPEN–&gt;

In a Knowledge Graph, a node’s role is determined by its relationships,
not by explicit labels or type fields. A `Person` node is an
actor because it has an `ACTED_IN` relationship, a director
because it has a `DIRECTED` relationship, and a writer because
it has a `WROTE` relationship—all without separate
`Actor`, `Director`, or `Writer` labels.

**When It Breaks:** When a node’s role requires properties specific to
that role (e.g., an actor’s `salary` per film vs. a director’s
`budget`), relationship-only identity forces these onto the
relationship itself, which can become unwieldy at scale.

# Introduction to Cypher

Knowledge Graphs in Neo4j are queried using **Cypher**<Citation src="francis2018cypher" />, a pattern-matching
query language. Cypher uses the same visual notation as the text representations
introduced above, making it intuitive to read and write.



<Term name="Cypher" los="KGR-1.6">
  Neo4j's declarative, pattern-matching query language. Uses ASCII art notation: parentheses `()` for nodes, square brackets `[]` for relationships, and arrows `->` for direction. Designed to be visually similar to whiteboard diagrams of graph patterns.
</Term>
<AnkiCard type="term" front={"Cypher"} back={"Neo4j's declarative, pattern-matching query language. Uses ASCII art notation: parentheses `()` for nodes, square brackets `[]` for relationships, and arrows `->` for direction. Designed to be visually similar to whiteboard diagrams of graph patterns."} los="KGR-1.6" />



The core idea: you **draw** the pattern you want to find, and Cypher
finds all matching subgraphs. A simple example:



```cypher
# Find all people who acted in a movie
MATCH (p:Person)-[:ACTED_IN]->(m:Movie)
RETURN p.name, m.title
```



This reads as: “find a `Person` node connected to a `Movie`
node via an `ACTED_IN` relationship, and return their names and
titles.” The pattern syntax mirrors the graph structure, making Cypher
queries self-documenting.

# Chapter Summary

Knowledge Graphs store data as nodes and relationships, both carrying
properties. Nodes have labels for grouping; relationships have types and
direction that encode semantic meaning. The graph structure enables
traversal-based retrieval that complements vector similarity search,
revealing connections that embedding distance alone cannot surface.
Cypher provides an intuitive, pattern-matching query language that
mirrors the visual structure of the graph. The combination of Knowledge
Graphs with embedding models opens new RAG strategies: retrieve a relevant
chunk via vector search, then traverse the graph to expand context with
connected entities and documents.

# Practice Problems

&lt;!–MDXB-14-OPEN–&gt;

**Core Insight:** Knowledge Graphs are schema-optional: you can add new
node labels and relationship types without schema migrations. This flexibility
makes KGs ideal for domains where entity types evolve over time (new data
sources, changing business requirements).

**Why It Matters:** In design interviews, explaining when schema
flexibility outweighs the data integrity guarantees of relational databases
demonstrates architectural judgment.

**When It Breaks:** Schema-optional is not schema-free. Without
conventions (naming standards, uniqueness constraints), the graph becomes a
tangled mess. Production KGs need governance even without DDL enforcement.

&lt;!–MDXB-16-OPEN–&gt;

You are designing a Knowledge Graph for a university course catalogue.
The domain has the following entities and relationships:

- Professors teach Courses

- Students enrol in Courses

- Courses belong to Departments

- Some professors advise students

**Tasks:**

1.  Identify the node labels and their key properties.

2.  Identify the relationship types and their directions.

3.  Write the Cypher text notation for: Professor “Dr. Smith” who
    teaches “Machine Learning 101” in the “CS” department.

4.  Can a student’s role (TA vs. regular student) be modelled through
    relationships alone? Explain.

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-18-OPEN–&gt;

**Approach:** Apply the “identity through relationships” pattern from
this chapter.

**Step 1: Node Labels and Properties**

- `Professor`: `name`, `email`, `hireYear`

- `Student`: `name`, `studentId`, `year`

- `Course`: `title`, `courseCode`, `credits`

- `Department`: `name`, `building`

**Step 2: Relationship Types**

- `Professor -[:TEACHES]-> Course`

- `Student -[:ENROLLED_IN]-> Course`

- `Course -[:BELONGS_TO]-> Department`

- `Professor -[:ADVISES]-> Student`

**Step 3: Cypher Text Notation**


```cypher
(smith:Professor {name: "Dr. Smith"})
  -[:TEACHES]->
(ml101:Course {title: "Machine Learning 101"})
  -[:BELONGS_TO]->
(cs:Department {name: "CS"})
```



**Step 4:** Yes. A TA is a student who has both an `ENROLLED_IN`
relationship and a `ASSISTS` relationship to the same course. No
separate `TA` label is needed—their role is defined by the
relationship pattern, exactly like actors/directors in the movie dataset.

**Key Insight:** The “identity through relationships” pattern extends
naturally to new domains. When you can model a role through relationship
presence, prefer that over adding labels—it keeps the schema cleaner
and avoids the “label explosion” anti-pattern.

**Answer:** Apply the “identity through relationships” pattern from
this chapter.

&lt;!–MDXB-17-OPEN–&gt;

Your team is building a customer support system. The data includes:

- 10 million support tickets with text descriptions

- Each ticket is assigned to exactly one agent and one customer

- Tickets have a status (open, in-progress, resolved, closed)

- You need to find similar past tickets for a new incoming ticket

Should you use a Knowledge Graph or a relational database? Justify your answer
along three dimensions: schema flexibility, relationship complexity, and
query patterns.

&lt;!–MDXB-17-CLOSE–&gt;

&lt;!–MDXB-19-OPEN–&gt;

**Approach:** Apply the KG vs. relational decision framework from
this chapter.

**Analysis by Dimension:**

**Schema flexibility:** The ticket schema is stable (ticket, agent,
customer, status). New fields can be added with `ALTER TABLE`. No
advantage to KG here.

**Relationship complexity:** Each ticket has exactly one agent and one
customer—simple foreign keys. No many-to-many or multi-hop relationships
needed for core operations. Relational DB is sufficient.

**Query patterns:** “Find similar past tickets” is a semantic similarity
task best served by vector search, not graph traversal. The relationships
(ticket→agent, ticket→customer) are simple lookups.

**Answer:** Use a relational database (e.g., PostgreSQL with pgvector).
The data is tabular with simple relationships. Add a vector index on ticket
embeddings for similarity search. A Knowledge Graph would add complexity
without benefit for this use case.

**Key Insight:** Not every system needs a Knowledge Graph. KGs shine when
data has complex, multi-hop relationships and flexible schemas. For tabular
data with simple foreign keys, relational databases are simpler and more
battle-tested. The decision should be driven by relationship complexity,
not technology novelty.
