# The Movie Dataset

The dataset models **persons** and **movies** with multiple
relationship types that demonstrate the “identity through relationships”
pattern from Module 1:

| **Relationship** | **Direction**   | **Description**                     |
|:-----------------|:----------------|:------------------------------------|
| `ACTED_IN`       | Person → Movie  | A person acted in a movie           |
| `DIRECTED`       | Person → Movie  | A person directed a movie           |
| `WROTE`          | Person → Movie  | A person wrote a movie              |
| `REVIEWED`       | Person → Movie  | A person reviewed a movie           |
| `FOLLOWS`        | Person → Person | A reviewer follows another reviewer |

**Node properties:**

- **Person**: `name` (string), `born` (integer)

- **Movie**: `title` (string), `tagline` (string),
  `released` (integer)

The dataset contains **171 total nodes** and **38 movies**. A
person’s role (actor, director, writer) is determined entirely by their
relationships, not by explicit labels on the person node.



<Sidenote category="crossref">This is the same "identity through relationships" pattern from M1 (§). The movie dataset makes it concrete.</Sidenote>



# Basic Cypher Queries

## Counting All Nodes

The simplest Cypher query matches all nodes and counts them:



```cypher
# Count all nodes in the graph
result = kg.query("""
    MATCH (n)
    RETURN count(n) AS totalNodes
""")
# Returns: [{'totalNodes': 171}]
```



The `MATCH` clause specifies a pattern; `(n)` matches any node
regardless of label. The variable `n` binds to each matched node,
and `count(n)` aggregates them.

## Filtering by Label

Add a label inside the parentheses to filter by node type:



```cypher
# Count only Movie nodes
result = kg.query("""
    MATCH (m:Movie)
    RETURN count(m) AS numberOfMovies
""")
# Returns: [{'numberOfMovies': 38}]
```





<Sidenote category="pattern">Use meaningful variable names: `m` for Movie, `p` for Person, `tom` for a specific person named Tom. This makes queries self-documenting.</Sidenote>



## Value-Based Matching

Use **curly braces** with object notation to match specific property
values directly in the pattern:



```cypher
# Find a specific person by name
result = kg.query("""
    MATCH (tom:Person {name: "Tom Hanks"})
    RETURN tom
""")
```



## Returning Specific Properties

Instead of returning the entire node, access individual properties with
dot notation:



```cypher
# Get the release year of a specific movie
result = kg.query("""
    MATCH (cloudAtlas:Movie {title: "Cloud Atlas"})
    RETURN cloudAtlas.released
""")
```



## Conditional Filtering with WHERE

For more complex conditions, use the `WHERE` clause:



```cypher
# Find movies released in the 1990s
result = kg.query("""
    MATCH (m:Movie)
    WHERE m.released > 1990 AND m.released < 2000
    RETURN m.title
""")
```

<ConceptBox>

**Property Match vs. WHERE.**
These two queries are equivalent:

- `MATCH (tom:Person {name: "Tom Hanks"}) RETURN tom`

- `MATCH (tom:Person) WHERE tom.name = "Tom Hanks" RETURN tom`

Use property matching for simple equality checks and `WHERE`
for ranges, boolean logic, or complex conditions.

</ConceptBox>

# Relationship Queries



<Sidenote category="interview">Pattern matching with relationships is the core Cypher skill. Practice writing these queries from memory until they feel natural.</Sidenote>



## Finding Connected Nodes

Extend the `MATCH` pattern with relationship syntax to find
connected nodes:



```cypher
# Find actors and their movies (limit to 10)
result = kg.query("""
    MATCH (actor:Person)-[:ACTED_IN]->(movie:Movie)
    RETURN actor.name, movie.title
    LIMIT 10
""")
```



The arrow `->` indicates relationship direction: the person
`ACTED_IN` the movie, not the reverse.



<Sidenote category="pattern">Cypher pattern: node–relationship–node mirrors whiteboard diagrams. Draw the pattern first, then translate to Cypher.</Sidenote>



## Filtering by Relationship and Node

Combine property matching with relationship patterns:



```cypher
# Find all movies Tom Hanks acted in
result = kg.query("""
    MATCH (tom:Person {name: "Tom Hanks"})
          -[:ACTED_IN]->(tomHanksMovies:Movie)
    RETURN tom.name, tomHanksMovies.title
""")
```



## Multi-Hop Traversal: Co-Actors

<KeyConcept title="Multi-Hop Traversal" los="KGR-2.2">

The power of graph queries lies in following chains of relationships.
To find all co-actors of Tom Hanks, traverse two `ACTED_IN`
relationships through a shared movie node:

`Tom` $\xrightarrow{\text{ACTED\\IN}}$ `Movie`
$\xleftarrow{\text{ACTED\\IN}}$ `CoActor`

This two-hop pattern discovers people who acted in the same movies as
Tom Hanks—a query that would require complex self-JOINs in SQL but
is a natural pattern match in Cypher.

**When It Breaks:** Multi-hop traversals explode combinatorially on
high-degree nodes. A movie with 50 actors produces 50<sup>2</sup> co-actor pairs;
three hops through such nodes can return millions of rows. Always add
`LIMIT` or filter by label/property to bound result sets.

</KeyConcept>



```cypher
# Find all co-actors of Tom Hanks
result = kg.query("""
    MATCH (tom:Person {name: "Tom Hanks"})
          -[:ACTED_IN]->(m)<-[:ACTED_IN]-(coActors:Person)
    RETURN coActors.name, m.title
""")
```



The reverse arrow `<-` matches the incoming `ACTED_IN`
relationship from the co-actor to the shared movie node.



<Term name="Multi-Hop Traversal" los="KGR-2.2">
  Following a chain of two or more relationships to discover indirect connections. Each "hop" follows one relationship from one node to the next. The number of hops determines query depth and result scope.
</Term>
<AnkiCard type="term" front={"Multi-Hop Traversal"} back={"Following a chain of two or more relationships to discover indirect connections. Each \"hop\" follows one relationship from one node to the next. The number of hops determines query depth and result scope."} los="KGR-2.2" />



# Modifying the Graph

<ConceptBox>

**Read vs. Write Operations.**
`MATCH` + `RETURN` reads data. `CREATE`, `MERGE`,
and `DELETE` modify data. In production, read operations vastly
outnumber writes, but understanding mutations is essential for graph
construction pipelines (Modules 4–6).

</ConceptBox>

## Deleting Relationships

Remove a specific relationship by matching it and calling `DELETE`:



```cypher
# Delete Emil Eifrem's ACTED_IN relationship
result = kg.query("""
    MATCH (emil:Person {name: "Emil Eifrem"})
          -[actedIn:ACTED_IN]->(movie:Movie)
    DELETE actedIn
""")
# Returns empty -- DELETE produces no output
```





<Sidenote category="warning">You cannot delete a node that still has relationships. Delete all relationships first, or use `DETACH DELETE` to remove the node and all its relationships simultaneously.</Sidenote>



## Creating Nodes

The `CREATE` clause adds new nodes unconditionally:



```cypher
# Create a new Person node
result = kg.query("""
    CREATE (andreas:Person {name: "Andreas"})
    RETURN andreas
""")
```



## Creating Relationships with MERGE

<RedFlag title="Duplicate Creation with CREATE">

Using `CREATE` for relationships produces duplicates if the
query runs multiple times. Always use `MERGE` for relationships
to ensure idempotency: if the relationship already exists, it will
not be created again. This is critical for bulk-loading pipelines
where retries are common.

</RedFlag>



<Sidenote category="interview">"When would you use MERGE instead of CREATE?" tests production-readiness. Answer: always for relationships in pipelines where retries are possible.</Sidenote>





```cypher
# MERGE prevents duplicate relationships
result = kg.query("""
    MATCH (andreas:Person {name: "Andreas"}),
          (emil:Person {name: "Emil Eifrem"})
    MERGE (andreas)-[r:KNOWS]->(emil)
    RETURN andreas, r, emil
""")
```





<Term name="CREATE" los="KGR-2.3">
  Cypher clause that unconditionally creates new nodes or relationships. Always creates, even if an identical element already exists. Use for guaranteed-unique insertions only.
</Term>

<NarrativeBox title="When to Use CREATE vs. MERGE">

1.  **Use CREATE** when you are certain the element does not
    exist and want the fastest insertion (no existence check).

2.  **Use MERGE** when the operation might run multiple times
    (bulk loading, retries, idempotent pipelines). MERGE is the
    safe default for all production code.

3.  **Combine MERGE with ON CREATE SET** to set properties
    only on first creation, preserving existing values on
    subsequent runs.

</NarrativeBox>

# Query Execution Model

Understanding how Cypher executes helps you write efficient queries:

<PipelineBox title="Pipeline: Cypher Query Execution">

1.  **Parse** *(syntax validation)*  
    The query string is parsed into an abstract syntax tree.
    Label filters and property matches are identified.

2.  **Plan** *(query optimiser)*  
    The optimiser chooses indexes, join strategies, and scan
    orders. Labels and indexes narrow the search space dramatically.

3.  **Execute** *(pattern matching)*  
    The engine traverses the graph, following relationships
    hop by hop, binding variables to matched elements.

4.  **Project** *(RETURN clause)*  
    Only the requested properties and aggregations are
    extracted and returned to the client.

</PipelineBox>



<Sidenote category="practice">Use `EXPLAIN` before a query to see the execution plan without running it. Use `PROFILE` to run the query and see actual row counts at each step.</Sidenote>



# Query Patterns Summary

| **Pattern**         | **Cypher Template**                                |
|:--------------------|:---------------------------------------------------|
| Count all nodes     | `MATCH (n) RETURN count(n)`                        |
| Filter by label     | `MATCH (m:Movie) RETURN m`                         |
| Property match      | `MATCH (p:Person {name: "Tom"}) RETURN p`          |
| Conditional         | `MATCH (m:Movie) WHERE m.released > 2000 RETURN m` |
| One-hop             | `MATCH (p)-[:ACTED_IN]->(m) RETURN p, m`           |
| Two-hop (co-actors) | `MATCH (a)-[:R]->(b)<-[:R]-(c) RETURN a, c`        |
| Create node         | `CREATE (n:Label {key: "val"}) RETURN n`           |
| Merge relation      | `MATCH (a), (b) MERGE (a)-[:R]->(b)`               |
| Delete relation     | `MATCH ()-[r:R]->() DELETE r`                      |



<Sidenote category="interview">Memorise these nine Cypher patterns. They cover 90% of Knowledge Graph query needs and form the foundation for more complex queries in later modules.</Sidenote>



# Chapter Summary

Cypher uses pattern matching with parentheses for nodes and brackets for
relationships, making queries visually mirror the graph structure. Labels
filter nodes by type; WHERE clauses add conditional logic; meaningful
variable names improve readability. Multi-hop traversals follow chains
of relationships to discover indirect connections—a capability that
would require complex self-JOINs in SQL but is natural in Cypher<Citation src="angles2017foundations" />. MERGE
prevents duplicate creation and is the safe default for production graph
construction. DELETE removes matched elements, with DETACH DELETE handling
referential integrity. These Cypher fundamentals form the foundation for
all subsequent modules, where you will build, query, and extend a
Knowledge Graph from SEC filings.

# Practice Problems

<KeyConcept title="MERGE as the Production Default" los="KGR-2.3">

**Core Insight:** MERGE combines existence checking with creation in a
single atomic operation. In production graph construction pipelines, data
arrives from unreliable sources (API retries, duplicate messages, replay
recovery). MERGE ensures that re-processing the same data produces exactly
the same graph—the pipeline is **idempotent**.

**Why It Matters:** Every production KG pipeline uses MERGE, not CREATE,
for relationships. Interviewers expect you to know this distinction and
explain *why* CREATE is dangerous in bulk-loading scenarios.

**When It Breaks:** MERGE checks all properties in the pattern for
existence. If you MERGE a relationship with a `timestamp` property that
changes each run, MERGE creates a *new* relationship every time.
Solution: MERGE on the stable identifier, then use `ON MATCH SET`
to update volatile properties.

</KeyConcept>

<Problem title="Three-Hop Co-Director Discovery" los="KGR-2.2">

Using the movie dataset, write a Cypher query to find all people who directed
a movie that Tom Hanks acted in. Return the director names and movie titles.

**Hint:** This requires a two-relationship pattern: one `ACTED_IN`
and one `DIRECTED`, both connecting to the same movie node.

</Problem>

<Solution>

**Approach:** Chain two relationship patterns through a shared movie node.

**Query:**


```cypher
MATCH (tom:Person {name: "Tom Hanks"})
      -[:ACTED_IN]->(m:Movie)
      <-[:DIRECTED]-(director:Person)
RETURN director.name, m.title
```



**Step 1:** Match Tom Hanks by name property.  
**Step 2:** Follow `ACTED_IN` forward to find his movies.  
**Step 3:** Follow `DIRECTED` backward from the same movie to
find directors.

**Key Insight:** The bidirectional pattern (`->` for ACTED\_IN,
`<-` for DIRECTED) through a shared node is the canonical way to
discover indirect connections. The movie node acts as a **join point**—
the graph equivalent of a SQL JOIN, but expressed as a visual pattern.

**Answer:** Returns all directors of Tom Hanks movies (e.g., Robert
Zemeckis for *Forrest Gump*, Steven Spielberg for *The Terminal*).

</Solution>

<Problem title="Idempotent Graph Construction" los="KGR-2.3">

You are building a pipeline that ingests social media posts into a Knowledge
Graph. Each post has an `id`, `author`, `text`, and
`timestamp`. The pipeline may re-process the same batch due to
failures.

1.  Write the Cypher to create a uniqueness constraint on
    `Post.postId`.

2.  Write a MERGE query that creates a Post node if it does not exist
    and updates the timestamp if it does.

3.  Explain why using CREATE instead of MERGE would cause problems
    during batch retries.

</Problem>

<Solution>

**Approach:** **Step 1: Uniqueness Constraint**


```cypher
CREATE CONSTRAINT unique_post IF NOT EXISTS
FOR (p:Post) REQUIRE p.postId IS UNIQUE
```



**Step 2: MERGE with Conditional SET**


```cypher
MERGE (p:Post {postId: $postParam.postId})
ON CREATE SET
  p.author = $postParam.author,
  p.text = $postParam.text,
  p.timestamp = $postParam.timestamp,
  p.createdAt = datetime()
ON MATCH SET
  p.timestamp = $postParam.timestamp,
  p.updatedAt = datetime()
```



**Step 3:** CREATE would insert duplicate Post nodes on each retry
because it does not check for existing nodes. After 3 retries, you would
have 3 identical posts. The uniqueness constraint would cause CREATE to
*fail* on the second attempt, but MERGE handles it gracefully by
updating the existing node instead.

**Key Insight:** The combination of uniqueness constraints + MERGE +
ON CREATE/ON MATCH SET is the **idempotent pipeline pattern**. It
ensures exactly-once semantics regardless of how many times the pipeline
runs. This is the production standard for all graph construction.

**Answer:** MERGE on stable identifier (`postId`), use ON
CREATE SET for initial properties, ON MATCH SET for updates. Constraint
provides both correctness and performance (implicit index).

</Solution>
