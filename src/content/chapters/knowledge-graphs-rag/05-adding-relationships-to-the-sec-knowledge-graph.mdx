<NarrativeBox title="Where We Are">

Module 4 built a working RAG system, but Neo4j was used only as a
vector store—chunk nodes floated disconnected in the graph. This
module is the turning point: by adding relationships, you transform
the flat collection into a navigable Knowledge Graph<Citation src="robinson2015graph" />. Chunks form
linked lists that preserve document order. Forms connect to their
chunks via PART\_OF and SECTION. The payoff is immediate: chunk
window queries expand retrieval context by pulling in adjacent
chunks, improving answer quality without changing the embedding model.

</NarrativeBox>

# Creating the Form Node

A new **Form** node represents the 10-K filing itself, with properties
extracted from the chunk metadata:



```cypher
# Create a Form node representing the 10-K filing
kg.query("""
    CREATE (f:Form)
    SET f.formId = $formInfoParam.formId,
        f.source = $formInfoParam.source,
        f.cik = $formInfoParam.cik,
        f.cusip6 = $formInfoParam.cusip6
""", params={"formInfoParam": form_info})
```

# Building the Chunk Linked List



<Sidenote category="interview">"How do you preserve document order in a graph?" is a knowledge graph design question. The answer: linked lists with NEXT relationships, ordered by sequence ID.</Sidenote>



## Ordering Chunks by Section

Chunks must be ordered within their section. Two filter parameters are
needed for correct ordering:

- `$formIdParam` — filters chunks from the same form

- `$f10kItemParam` — filters chunks from the same section

<RedFlag title="Missing Section Filter">

Without the section filter, chunks from different sections (e.g., Item 7
and Item 7A) both start at sequence 0, causing incorrect ordering and
cross-section NEXT relationships. Always filter by both `formId`
and `item` when creating NEXT relationships.

</RedFlag>



```cypher
# Verify chunk ordering within a section
result = kg.query("""
    MATCH (c:Chunk)
    WHERE c.formId = $formIdParam AND c.item = $f10kItemParam
    RETURN c.chunkId, c.chunkSeqId
    ORDER BY c.chunkSeqId
""", params={
    "formIdParam": form_id,
    "f10kItemParam": "item1"
})
```



## Creating NEXT Relationships

Connect sequential chunks with **NEXT** relationships to form a
linked list:



```cypher
# Create NEXT relationships between sequential chunks
kg.query("""
    MATCH (c1:Chunk), (c2:Chunk)
    WHERE c1.formId = $formIdParam
      AND c1.item = $f10kItemParam
      AND c2.formId = $formIdParam
      AND c2.item = $f10kItemParam
      AND c2.chunkSeqId = c1.chunkSeqId + 1
    MERGE (c1)-[:NEXT]->(c2)
""", params={
    "formIdParam": form_id,
    "f10kItemParam": "item1"
})
```





<Term name="NEXT Relationship" los="KGR-5.2">
  A directed relationship connecting sequential chunks within the same form section. Forms a singly-linked list that preserves document order. Enables sequential traversal and chunk window queries for expanded retrieval context.
</Term>
<AnkiCard type="term" front={"NEXT Relationship"} back={"A directed relationship connecting sequential chunks within the same form section. Forms a singly-linked list that preserves document order. Enables sequential traversal and chunk window queries for expanded retrieval context."} los="KGR-5.2" />



The `MERGE` clause ensures idempotency—running the same section
again will not create duplicate NEXT relationships.



<Sidenote category="pattern">Linked lists in graphs are a general-purpose pattern: chat message threads, audit trails, and event streams all use NEXT chains.</Sidenote>





<Sidenote category="formula">Chunk window context: $w = 2k + 1$ chunks where $k$ = hops in each direction. Default $k=1$ gives 3-chunk window.</Sidenote>



# Connecting Chunks to the Form

## PART\_OF Relationship

Link every chunk to its parent form:



```cypher
# Connect all chunks to their parent form
kg.query("""
    MATCH (c:Chunk), (f:Form)
    WHERE c.formId = f.formId
    MERGE (c)-[:PART_OF]->(f)
""")
# Creates 23 relationships (one per chunk)
```





<Term name="PART\_OF Relationship" los="KGR-5.1">
  A directed relationship from a Chunk node to its parent Form node. Establishes document membership, enabling traversal from any chunk back to its source filing and onward to connected entities.
</Term>
<AnkiCard type="term" front={"PART\\_OF Relationship"} back={"A directed relationship from a Chunk node to its parent Form node. Establishes document membership, enabling traversal from any chunk back to its source filing and onward to connected entities."} los="KGR-5.1" />



## SECTION Relationship

Connect the form to the **first chunk** of each section (the chunk
with sequence ID 0):



```cypher
# Connect form to first chunk of each section
kg.query("""
    MATCH (c:Chunk), (f:Form)
    WHERE c.formId = f.formId AND c.chunkSeqId = 0
    MERGE (f)-[s:SECTION {f10kItem: c.item}]->(c)
""")
# Creates 4 relationships (one per form section)
```



The `f10kItem` property on the SECTION relationship stores the
section name (e.g., “item1”, “item7”), enabling direct navigation
to the start of any section.



<Term name="SECTION Relationship" los="KGR-5.1">
  A directed relationship from a Form node to the first Chunk of each section. Carries an `f10kItem` property that identifies the section name. Provides indexed entry points into the document structure.
</Term>
<AnkiCard type="term" front={"SECTION Relationship"} back={"A directed relationship from a Form node to the first Chunk of each section. Carries an `f10kItem` property that identifies the section name. Provides indexed entry points into the document structure."} los="KGR-5.1" />



<ConceptBox>

**The Graph Schema After Module 5.**
The graph now has three relationship types connecting chunks and forms:

- `Chunk -[:NEXT]-> Chunk` — linked list (document order)

- `Chunk -[:PART_OF]-> Form` — document membership

- `Form -[:SECTION]-> Chunk` — section entry points

This structure enables both sequential traversal (follow NEXT) and
hierarchical navigation (jump to a section via SECTION, then follow
NEXT through the section content).

</ConceptBox>

# Graph Traversal Queries

## Finding the First Chunk of a Section



```cypher
# Navigate to the first chunk of Item 1
result = kg.query("""
    MATCH (f:Form)-[s:SECTION]->(c:Chunk)
    WHERE f.formId = $formIdParam AND s.f10kItem = $itemParam
    RETURN c.chunkId, c.text
""", params={
    "formIdParam": form_id,
    "itemParam": "item1"
})
```



## Following NEXT to Get Sequential Chunks



```cypher
# Get the next chunk in the linked list
result = kg.query("""
    MATCH (c1:Chunk)-[:NEXT]->(c2:Chunk)
    WHERE c1.chunkId = $chunkIdParam
    RETURN c1.chunkId, c2.chunkId
""", params={"chunkIdParam": chunk_id})
```



## Chunk Window Pattern (3-Node Path)

<KeyConcept title="Chunk Window Query" los="KGR-5.4">

A chunk window retrieves the target chunk plus its immediate
neighbours in the linked list, providing expanded context for the
LLM without requiring additional embedding searches:

`before` $\xrightarrow{\text{NEXT}}$ `middle`
$\xrightarrow{\text{NEXT}}$ `after`

**When It Breaks:** Fixed-length window patterns fail at linked list
boundaries (first and last chunks). The first chunk has no predecessor and
the last has no successor, returning zero results. Use variable-length paths
(`*0..1`) to degrade gracefully at boundaries.

</KeyConcept>



```cypher
# Fixed 3-node chunk window
result = kg.query("""
    MATCH (before:Chunk)-[:NEXT]->(middle:Chunk)
          -[:NEXT]->(after:Chunk)
    WHERE middle.chunkId = $chunkIdParam
    RETURN before, middle, after
""", params={"chunkIdParam": chunk_id})
```





<Sidenote category="warning">The fixed 3-node window fails at linked list boundaries: the first chunk has no predecessor, and the last chunk has no successor. Variable-length paths solve this problem.</Sidenote>



# Variable-Length Paths for Boundary Handling



```cypher
# Variable-length chunk window (handles boundaries)
result = kg.query("""
    MATCH window = (before:Chunk)-[:NEXT*0..1]->(middle:Chunk)
                   -[:NEXT*0..1]->(after:Chunk)
    WHERE middle.chunkId = $chunkIdParam
    WITH window, length(window) AS windowLength
    ORDER BY windowLength DESC
    LIMIT 1
    RETURN window
""", params={"chunkIdParam": chunk_id})
```





<Term name="Variable-Length Path" los="KGR-5.3">
  A Cypher pattern that matches a range of relationship hops. The notation `*0..1` matches zero or one relationships, while `*1..3` matches one to three hops. Used to handle boundary conditions where a fixed-length pattern would fail.
</Term>
<AnkiCard type="term" front={"Variable-Length Path"} back={"A Cypher pattern that matches a range of relationship hops. The notation `*0..1` matches zero or one relationships, while `*1..3` matches one to three hops. Used to handle boundary conditions where a fixed-length pattern would fail."} los="KGR-5.3" />



The `*0..1` notation matches 0 or 1 NEXT relationships:

- At the **first chunk**: `before = middle` (0 hops
  backward), `after` is the next chunk (1 hop forward).

- At the **last chunk**: `before` is the previous chunk
  (1 hop backward), `after = middle` (0 hops forward).

- In the **middle**: both before and after are distinct chunks
  (1 hop each direction).

Ordering by path length descending and limiting to 1 gives the
**longest available window**—the maximum context around the
target chunk.



<Sidenote category="practice">Always test chunk window queries at both ends of the linked list. Edge cases at boundaries are the most common source of bugs.</Sidenote>



<NarrativeBox title="Debugging Variable-Length Path Queries">

1.  **No results?** Check that the `chunkId` exists
    and the NEXT relationships were created correctly.

2.  **Duplicate results?** The `ORDER BY ... LIMIT 1`
    pattern should select the longest window. Verify the ordering.

3.  **Wrong chunks?** Verify that NEXT relationships were
    created with section filtering (same `formId` and
    `item`).

</NarrativeBox>

# Enhanced RAG with Chunk Windows

## Custom Retrieval Query

Extend the default vector search with a Cypher query that retrieves
adjacent chunks:



```cypher
# Custom retrieval query with chunk windows
retrieval_query = """
    WITH node, score
    MATCH window = (:Chunk)-[:NEXT*0..1]->(node)
                   -[:NEXT*0..1]->(:Chunk)
    WITH node, score, window
    ORDER BY length(window) DESC LIMIT 1
    WITH nodes(window) AS chunks, score
    UNWIND chunks AS chunk
    WITH chunk, score
    RETURN chunk.text AS text, score,
           {source: chunk.source} AS metadata
"""

neo4j_vector = Neo4jVector.from_existing_graph(
    OpenAIEmbeddings(),
    url=NEO4J_URI,
    username=NEO4J_USERNAME,
    password=NEO4J_PASSWORD,
    index_name="form10kChunks",
    node_label="Chunk",
    text_node_properties=["text"],
    embedding_node_property="textEmbedding",
    retrieval_query=retrieval_query,
)
```

| “What is NetApp’s primary business?” | Enterprise storage and data management | Enterprise storage and data management,

<KeyConcept title="Vector Search + Graph Traversal" los="KGR-5.6">

The combination of vector search (finding the starting point) and
graph traversal (expanding context)<Citation src="hogan2021knowledge" /> is more powerful than either
technique alone. Vector search identifies the most relevant chunk;
graph traversal adds surrounding context that the LLM needs to
produce a comprehensive answer. The chunk window pattern demonstrates
this synergy: the expanded context includes specific product details
(NetApp Keystone) that a single chunk missed.

**When It Breaks:** If NEXT relationships cross section boundaries
(missing section filter), the window pulls in irrelevant context from an
adjacent section, degrading answer quality. Also, very large windows
(*k* &gt; 3) may exceed the LLM’s useful context length, diluting the signal.

</KeyConcept>



<Sidenote category="interview">"How do you combine vector search with graph traversal in RAG?" is a senior system design question. The chunk window pattern is the canonical answer.</Sidenote>



# Chapter Summary

Adding NEXT, PART\_OF, and SECTION relationships transforms a flat vector
store into a navigable Knowledge Graph. Linked lists of chunks preserve
document order and enable sequential traversal. SECTION relationships
provide entry points to the beginning of each form section. Variable-length
paths (`*0..1`) handle boundary conditions at the start and end
of linked lists gracefully. Chunk window queries expand retrieval context
by including adjacent chunks, improving answer quality. The combination
of vector search and graph traversal is the core innovation of
Knowledge Graph–powered RAG<Citation src="gao2024retrieval" />.

# Practice Problems

<Problem title="Chunk Linked List Construction" los="KGR-5.2">

You have 10 text chunks from a research paper, numbered 0–9. Chunks 0–4
belong to the “Introduction” section and chunks 5–9 belong to the
“Methods” section.

1.  Write the Cypher to create NEXT relationships within each section.

2.  What happens if you omit the section filter and create NEXT
    relationships across all chunks ordered by `chunkSeqId`?

3.  How many NEXT relationships should exist after correct creation?

</Problem>

<Solution>

**Approach:** **Step 1: Section-Filtered NEXT Creation**


```sql
MATCH (c1:Chunk), (c2:Chunk)
WHERE c1.paperId = $paperId
  AND c1.section = $section
  AND c2.paperId = $paperId
  AND c2.section = $section
  AND c2.chunkSeqId = c1.chunkSeqId + 1
MERGE (c1)-[:NEXT]->(c2)
```


Run once for `section = "introduction"` and once for
`section = "methods"`.

**Step 2: Omitting Section Filter**  
Without section filtering, chunk 4 (last of Introduction) would get a NEXT
relationship to chunk 5 (first of Methods), because both have sequential
`chunkSeqId` values. This creates a false continuity across section
boundaries—the linked list would not respect the paper’s structure.

**Step 3: Relationship Count**  
Introduction: 4 NEXT relationships (0→1, 1→2, 2→3, 3→4).  
Methods: 4 NEXT relationships (5→6, 6→7, 7→8, 8→9).  
Total: **8 NEXT relationships**.

**Key Insight:** Section filtering is not optional—it is a correctness
requirement. Without it, chunk windows at section boundaries pull in
irrelevant context from adjacent sections, degrading RAG answer quality.

**Answer:** 8 NEXT relationships across 2 sections. Section filter
prevents cross-section linking.

</Solution>

<Problem title="Variable-Length Path for Context Windows" los="KGR-5.3">

Write a Cypher query that retrieves a 5-chunk window (2 chunks before + target
+ 2 chunks after) using variable-length paths. Handle boundary cases where
fewer than 2 preceding or following chunks exist.

</Problem>

<Solution>

**Approach:** Extend the `*0..1` pattern to `*0..2` for
2-hop windows in each direction.



```sql
MATCH window = (before:Chunk)-[:NEXT*0..2]->(target:Chunk)
               -[:NEXT*0..2]->(after:Chunk)
WHERE target.chunkId = $targetChunkId
WITH window, length(window) AS windowLength
ORDER BY windowLength DESC
LIMIT 1
WITH nodes(window) AS chunks
UNWIND chunks AS chunk
RETURN chunk.chunkId, chunk.text
ORDER BY chunk.chunkSeqId
```



**Boundary Handling:**

- At chunk 0 (start): `*0..2` backward matches 0 hops,
  giving 3 chunks total (target + 2 after).

- At chunk 1: `*0..2` backward matches 1 hop, giving 4 chunks.

- In the middle: full 5-chunk window.

**Key Insight:** The `ORDER BY windowLength DESC LIMIT 1` pattern
selects the longest available window at any position. This generalises to
any window size *k*: use `*0..`*k* in both directions.

**Answer:** Use `*0..2` in each direction with ORDER BY length
DESC LIMIT 1. Maximum 5 chunks, gracefully degrades at boundaries.

</Solution>

<Problem title="Graph Schema for Document Hierarchy" los="KGR-5.1">

Design a graph schema for a technical documentation system with:

- Books containing chapters containing sections

- Each section has text chunks with embeddings

- Chunks within a section form a linked list

- Users can jump to any chapter or section by name

Define the node types, relationship types, and explain which relationships
enable each of the four navigation patterns: sequential reading, section
jump, chapter jump, and similarity search.

</Problem>

<Solution>

**Approach:** **Node Types:**

- `Book` (bookId, title)

- `Chapter` (chapterId, title, chapterNumber)

- `Section` (sectionId, title, sectionNumber)

- `Chunk` (chunkId, text, chunkSeqId, textEmbedding)

**Relationship Types:**

- `Chapter -[:PART_OF]-> Book`

- `Section -[:PART_OF]-> Chapter`

- `Chunk -[:PART_OF]-> Section`

- `Chunk -[:NEXT]-> Chunk` (within same section)

- `Chapter -[:HAS_SECTION]-> Section` (entry point)

- `Book -[:HAS_CHAPTER]-> Chapter` (entry point)

**Navigation Patterns:**

1.  **Sequential reading**: Follow NEXT within a section.

2.  **Section jump**: Book → HAS\_CHAPTER → Chapter →
    HAS\_SECTION → Section → first Chunk.

3.  **Chapter jump**: Book → HAS\_CHAPTER → Chapter.

4.  **Similarity search**: Vector index on Chunk.textEmbedding,
    then traverse PART\_OF to get section/chapter context.

**Key Insight:** The PART\_OF and NEXT relationship pattern from the SEC
filing graph generalises to any hierarchical document structure. The key
design decision is which *entry point* relationships to create
(HAS\_CHAPTER, HAS\_SECTION)—these enable direct navigation without
traversing the entire hierarchy.

**Answer:** 4 node types, 6 relationship types. NEXT enables sequential
reading; HAS\_SECTION/HAS\_CHAPTER enable direct jumps; PART\_OF enables
upward traversal; vector index enables semantic search.

</Solution>

<Vignette title="Graph-Augmented RAG vs. Pure Vector Retrieval">

\[KGR-5.6\]
DataInc is evaluating two architectures for their customer support RAG system:

**Option A:** Pure vector retrieval using Pinecone. Support articles are
chunked, embedded, and searched by similarity. Top-5 chunks are passed to
the LLM.

**Option B:** Knowledge Graph–augmented retrieval using Neo4j. Same
chunking and embedding, but chunks are connected via NEXT relationships
(document order), PART\_OF relationships (article membership), and
RELATED\_TO relationships (cross-article topic links).

| **Metric**              | **Option A** | **Option B** |
|:------------------------|:------------:|:------------:|
| Avg answer accuracy     |     78%      |     89%      |
| Avg answer completeness |     62%      |     84%      |
| Avg latency (p50)       |    120ms     |    180ms     |
| Infrastructure cost     |   $200/mo    |   $450/mo    |

**Question 1:** What explains the 22-point improvement in answer
completeness for Option B?

**Question 2:** Is the additional latency and cost justified? Under
what conditions would you recommend each option?

**Question 3:** Design a hybrid approach that captures most of Option
B’s accuracy at closer to Option A’s cost.

</Vignette>

<Solution>

**Approach:** **Question 1: Completeness Improvement**  
The 22-point improvement comes from chunk window retrieval. When Option A
retrieves a single chunk, it may miss context that spans chunk boundaries.
Option B follows NEXT relationships to include adjacent chunks, providing
the LLM with complete context. The RELATED\_TO relationships also surface
relevant information from *other* articles that Option A cannot discover.

**Question 2: Cost-Benefit Analysis**  
The additional 60ms latency and $250/mo cost is justified when:

- Answer quality directly impacts revenue (customer retention,
  support ticket resolution)

- Questions frequently require multi-document context

- The support article corpus has strong inter-article relationships

Option A is sufficient when:

- Questions are simple lookups (FAQ-style)

- Budget is constrained and accuracy is “good enough”

- Articles are self-contained (no cross-references)

**Question 3: Hybrid Approach**  
Use a tiered architecture: vector search first (Option A), then
**conditionally** expand via graph traversal only when the top result’s
similarity score is below a threshold (e.g., 0.85) or when the question
contains multi-entity references. This captures 80%+ of Option B’s accuracy
improvement at ≈$300/mo (graph queries only triggered 30–40% of the time).

**Answer:** **Question 1: Completeness Improvement**  
The 22-point improvement comes from chunk window retrieval.

</Solution>
