&lt;!–MDXB-10-OPEN–&gt;

You can now query a Knowledge Graph with Cypher. But RAG systems need
*semantic* search—finding text chunks that are conceptually
similar to a user’s question, even when the exact words differ. This
module adds vector search to the graph by creating embeddings, indexing
them, and querying by similarity. At this stage, Neo4j is used as a
vector store; the real power of combining vector search with graph
traversal comes in Modules 5–7.

&lt;!–MDXB-10-CLOSE–&gt;

# Creating a Vector Index



<Sidenote category="interview">"How do vector indexes work in a graph database?" tests whether you understand the intersection of graph and vector paradigms.</Sidenote>



The first step is to create a **vector index** that tells Neo4j which
node property holds embeddings, how many dimensions they have, and which
similarity function to use for comparisons.



```cypher
# Create a vector index on Movie tagline embeddings
kg.query("""
    CREATE VECTOR INDEX movie_tagline_embeddings IF NOT EXISTS
    FOR (m:Movie) ON (m.taglineEmbedding)
    OPTIONS {
      indexConfig: {
        `vector.dimensions`: 1536,
        `vector.similarity_function`: 'cosine'
      }
    }
""")
```



| **Parameter** | **Value** | **Reason** |
|:---|:---|:---|
| Dimensions | 1536 | Default size for OpenAI’s embedding model |
| Similarity | Cosine | Recommended by OpenAI; normalises for vector magnitude |
| IF NOT EXISTS | — | Idempotent creation; safe to re-run |

# Generating and Storing Embeddings

&lt;!–MDXB-11-OPEN–&gt;

**The Key Architectural Decision.**
Embeddings are stored as **node properties**, co-locating vector
data with graph data. This means a single query can combine vector
similarity search with graph traversal—you do not need a separate
vector database.

&lt;!–MDXB-11-CLOSE–&gt;

Use Neo4j’s built-in `genai.vector.encode` function to calculate
embeddings via OpenAI and store them directly on nodes:



```cypher
# Generate and store embeddings for all Movie taglines
kg.query("""
    MATCH (m:Movie)
    WHERE m.tagline IS NOT NULL
    WITH m, genai.vector.encode(
      m.tagline, "OpenAI",
      { token: $openAiApiKey }
    ) AS vector
    CALL db.create.setNodeVectorProperty(
        m, "taglineEmbedding", vector
    )
""", params={"openAiApiKey": OPENAI_API_KEY})
```

  Neo4j's built-in function that calls external embedding APIs (e.g., OpenAI) directly from Cypher. Takes text, a provider name, and configuration (including API key) as arguments. Returns a float array representing the embedding vector.
</Term>

<Sidenote category="pattern">Embedding generation pattern: MATCH nodes → encode text → store as property → verify dimensions. Same pattern for any node type.</Sidenote>



The `$openAiApiKey` is passed as a **query parameter**—never
hardcoded in the query string. This call goes out to the OpenAI API for each
movie node, so execution time depends on dataset size and network conditions.

# Performing Vector Similarity Search

With embeddings stored and indexed, you can query for semantically similar
content by encoding the question and finding nearest neighbours:



```cypher
# Vector similarity search for movies
result = kg.query("""
    WITH genai.vector.encode(
      $question, "OpenAI",
      { token: $openAiApiKey }
    ) AS questionEmbedding
    CALL db.index.vector.queryNodes(
      'movie_tagline_embeddings',
      $topK,
      questionEmbedding
    ) YIELD node AS movie, score
    RETURN movie.title, movie.tagline, score
""", params={
    "question": "movies about love",
    "openAiApiKey": OPENAI_API_KEY,
    "topK": 5
})
```





<Term name="db.index.vector.queryNodes" los="KGR-3.3">
  Neo4j procedure that performs approximate nearest-neighbour search on a vector index. Takes the index name, number of results (top-K), and query vector as arguments. Yields matched nodes with similarity scores.
</Term>
<AnkiCard type="term" front={"db.index.vector.queryNodes"} back={"Neo4j procedure that performs approximate nearest-neighbour search on a vector index. Takes the index name, number of results (top-K), and query vector as arguments. Yields matched nodes with similarity scores."} los="KGR-3.3" />



&lt;!–MDXB-12-OPEN–&gt;

1.  **Encode** *(question → vector)*  
    The user’s natural language question is converted to an
    embedding vector using the same model (OpenAI) that generated
    the stored embeddings.

2.  **Search** *(nearest neighbours)*  
    `db.index.vector.queryNodes` finds the top-K nodes
    whose embedding vectors are closest to the query vector.

3.  **Score** *(similarity ranking)*  
    Each result includes a similarity score (0 to 1 for cosine).
    Higher scores indicate more semantically similar content.

4.  **Return** *(text + metadata)*  
    The matched nodes’ text properties and metadata are returned
    for use as LLM context.

&lt;!–MDXB-12-CLOSE–&gt;

  A variable passed to a Cypher query via the `params` argument of `kg.query()`. Referenced in Cypher with `$` prefix. Prevents injection attacks, keeps API keys out of query strings, and enables query plan caching.
</Term>
<AnkiCard type="term" front={"Query Parameter"} back={"A variable passed to a Cypher query via the `params` argument of `kg.query()`. Referenced in Cypher with `$` prefix. Prevents injection attacks, keeps API keys out of query strings, and enables query plan caching."} los="KGR-3.5" />



&lt;!–MDXB-15-OPEN–&gt;

Query parameters serve two purposes: **security** (API keys and
user inputs never appear in query strings, preventing injection and
leakage in logs) and **performance** (Neo4j caches execution plans
for parameterised queries, reusing them across calls with different
values). Always use `$variable` syntax with the `params`
argument—never f-strings or string concatenation.

**When It Breaks:** DDL statements (CREATE INDEX, CREATE
CONSTRAINT) cannot use query parameters in Neo4j. For these, sanitise
inputs manually.

# Neo4j as a Vector Store



<Sidenote category="crossref">vol6 Ch 4: RAG — co-locating vector indexes with graph structure eliminates the separate vector DB in KG-augmented retrieval.</Sidenote>



&lt;!–MDXB-16-OPEN–&gt;

Most RAG architectures use a *separate* vector database alongside
their primary data store. Neo4j’s vector indexes<Citation src="neo4j2024vector" /> eliminate this
separation: embeddings live as node properties in the same database
as the graph structure. This means a single Cypher query can:

1.  Find the most similar chunk via vector search.

2.  Traverse relationships to find connected chunks.

3.  Return both the matched text and its graph context.

At this stage (Module 3), only step 1 is used. Modules 5–7 add
steps 2 and 3, unlocking the full power of graph-augmented RAG.

**When It Breaks:** Co-location ties you to Neo4j’s embedding support.
If you need to swap embedding models frequently or require advanced ANN
algorithms (e.g., ScaNN, IVF-PQ) not yet available in Neo4j, a dedicated
vector database alongside the graph may outperform the single-engine approach.

&lt;!–MDXB-16-CLOSE–&gt;

| **Capability**           | **Dedicated Vector DB** | **Neo4j**  |
|:-------------------------|:-----------------------:|:----------:|
| Vector similarity search |           Yes           |    Yes     |
| Graph traversal          |           No            |    Yes     |
| Full-text search         |        Sometimes        |    Yes     |
| Geospatial queries       |         Rarely          |    Yes     |
| Combined queries         |           No            |    Yes     |
| Operational simplicity   |       One system        | One system |



<Sidenote category="interview">"Why not use a separate vector database?" is a design-level interview question. The answer: co-location enables combined graph+vector queries in a single round trip.</Sidenote>

# Interpreting Similarity Scores

&lt;!–MDXB-13-OPEN–&gt;

**What Scores Mean.**
Cosine similarity scores range from 0 to 1 for normalised vectors.
A score of 0.89 indicates strong semantic similarity; 0.75 is moderate;
below 0.5 is weak. There is no universal “good” threshold—it
depends on the embedding model, the data distribution, and the
application requirements.

&lt;!–MDXB-13-CLOSE–&gt;

When evaluating vector search results, consider these factors:

- **Score distribution**: If all results have similar scores
  (e.g., 0.78–0.82), the query may be ambiguous or the data may
  lack a strong match. A clear winner (0.92 vs. 0.75 for the rest)
  indicates high confidence.

- **Score threshold**: Setting a minimum score (e.g., 0.7)
  filters out irrelevant results. This prevents the LLM from
  receiving low-quality context that could lead to hallucination.

- **Domain sensitivity**: Scores are relative to the embedding
  model and training data. An 0.85 score on movie taglines may
  represent a different quality level than 0.85 on SEC filings.



<Term name="Similarity Score" los="KGR-3.7">
  A numerical value returned by vector search indicating how closely an embedding matches the query vector. For cosine similarity, ranges from 0 (unrelated) to 1 (identical direction). Used to rank results and filter low-quality matches.
</Term>
<AnkiCard type="term" front={"Similarity Score"} back={"A numerical value returned by vector search indicating how closely an embedding matches the query vector. For cosine similarity, ranges from 0 (unrelated) to 1 (identical direction). Used to rank results and filter low-quality matches."} los="KGR-3.7" />

# Security: Parameterised Queries

&lt;!–MDXB-22-OPEN–&gt;

Never embed API keys directly in Cypher query strings. String
interpolation (f-strings, format) risks leaking keys in logs,
error messages, and query caches. Always use Cypher query parameters
(`$variable`) passed through the `params` argument.

&lt;!–MDXB-22-CLOSE–&gt;



```cypher
# WRONG: API key in query string (security risk)
kg.query(f"""
    ... {{ token: "{api_key}" }} ...
""")

# RIGHT: API key as query parameter
kg.query("""
    ... {{ token: $openAiApiKey }} ...
""", params={"openAiApiKey": api_key})
```



Query parameters also enable **query plan caching**: Neo4j can
reuse the execution plan for parameterised queries, improving performance
for repeated queries with different parameter values.



<Sidenote category="formula">Cosine similarity: $() = A  B\{\|A\|\|B\|\}$. Range: $[-1, 1]$. For normalised embeddings: $[0, 1]$.</Sidenote>



# Chapter Summary

Vector indexes in Neo4j<Citation src="neo4j2024vector" /> define which node property holds embeddings, the
dimensionality, and the similarity function. Neo4j’s
`genai.vector.encode` function calls external embedding APIs like
OpenAI directly from Cypher, and embeddings are stored as node properties,
keeping vector data co-located with graph data.
`db.index.vector.queryNodes` performs top-K nearest-neighbour search
to find semantically similar content. Query parameters keep API keys and
dynamic values out of the query string, preventing security risks and
enabling plan caching. At this stage, Neo4j functions as a vector store;
the transformative power of combining vector search with graph traversal
is introduced in Module 5 and fully realised in Modules 6–7.

# Practice Problems

&lt;!–MDXB-17-OPEN–&gt;

**Core Insight:** The embedding model is the bottleneck of vector search.
If the model encodes “cloud computing” and “data storage” as distant vectors,
no amount of index tuning will make them match. Conversely, a high-quality
embedding model compensates for simple retrieval strategies.

**Why It Matters:** Interview candidates often focus on retrieval
algorithm details (HNSW parameters, re-ranking) while ignoring the
fundamental constraint: the embedding model defines the ceiling of
search quality.

**When It Breaks:** Domain-specific corpora (legal documents, medical
records) may not be well-represented by general-purpose embedding models
like OpenAI’s. Fine-tuning or domain-specific models may be necessary.

&lt;!–MDXB-18-OPEN–&gt;

You are setting up a Neo4j vector index for a product catalogue with 50,000
items. Each product has a description embedded using a model that outputs
768-dimensional vectors.

1.  Write the Cypher to create the vector index.

2.  Your colleague suggests using Euclidean distance instead of cosine
    similarity. Under what conditions would this be appropriate?

3.  After creating the index, you run a similarity search and get zero
    results. List three possible causes.

&lt;!–MDXB-18-CLOSE–&gt;

&lt;!–MDXB-20-OPEN–&gt;

**Approach:** **Step 1: Vector Index Creation**


```cypher
CREATE VECTOR INDEX product_embeddings IF NOT EXISTS
FOR (p:Product) ON (p.descriptionEmbedding)
OPTIONS {
  indexConfig: {
    `vector.dimensions`: 768,
    `vector.similarity_function`: 'cosine'
  }
}
```



**Step 2: Euclidean vs. Cosine**  
Euclidean distance is appropriate when vector magnitudes carry meaning (e.g.,
TF-IDF vectors where magnitude reflects term frequency). For normalised
embeddings (most modern models including OpenAI), cosine and Euclidean produce
the same ranking. Use cosine as the default unless you have specific reasons
to prefer Euclidean.

**Step 3: Zero Results — Three Causes**

1.  Index is still in `POPULATING` status (not `ONLINE`).

2.  Dimension mismatch: index expects 768 but embeddings are 1536.

3.  No embeddings stored: the `descriptionEmbedding` property is
    null on all Product nodes.

**Key Insight:** Vector index debugging follows a checklist: (1) index
status, (2) dimension match, (3) embedding population, (4) query vector
format. Always verify each step before concluding the search is broken.

**Answer:** Create with 768 dimensions and cosine similarity. Prefer
cosine for normalised embeddings. Debug zero results by checking index
status, dimensions, and embedding population.

You run a similarity search for “renewable energy initiatives” against a
corporate filing knowledge graph. The top-5 results are:

| **Rank** | **Chunk Topic**                    | **Score** |
|:--------:|:-----------------------------------|:---------:|
|    1     | Solar panel manufacturing capacity |   0.91    |
|    2     | Wind farm investment portfolio     |   0.88    |
|    3     | Carbon credit trading programme    |   0.84    |
|    4     | Employee volunteer programmes      |   0.82    |
|    5     | Office recycling policy            |   0.79    |

1.  Which results are likely relevant? Which are false positives?

2.  What similarity score threshold would you set for this use case?

3.  How would you improve retrieval precision without changing the
    embedding model?

&lt;!–MDXB-19-CLOSE–&gt;

&lt;!–MDXB-21-OPEN–&gt;

**Approach:** **Step 1: Relevance Assessment**  
Results 1–3 are likely relevant (directly about energy/environmental
initiatives). Results 4–5 are borderline—they relate to corporate
responsibility but not specifically to *energy* initiatives. They
are semantic neighbours but not precise matches.

**Step 2: Threshold Selection**  
A threshold of **0.85** would retain the top-3 results (genuine
energy-related content) and filter out results 4–5. However, the
optimal threshold depends on the application:

- High recall needed (research): 0.75–0.80

- Balanced: 0.82–0.85

- High precision needed (customer-facing): 0.88+

**Step 3: Improving Precision**

- Add a re-ranking step using a cross-encoder model.

- Chunk more granularly (smaller chunks = more specific embeddings).

- Use metadata filtering (section type, keywords) before vector search.

- Combine vector search with keyword filtering (hybrid search).

**Key Insight:** Similarity scores are *relative*, not absolute.
A score of 0.82 might be excellent for one corpus and mediocre for another.
Always calibrate thresholds against your specific data distribution.

**Answer:** Top 3 relevant, 4–5 are false positives. Threshold
≈0.85. Improve precision with re-ranking, smaller chunks, or
hybrid search.
