# Why State Graphs for Agents



<Sidenote category="interview">"What is an agent?" Answer: a system that uses an LLM to decide actions in a loop—not just a single call. The loop is the key distinction.</Sidenote>



An LLM call is a function: input in, output out. A *chain* composes
multiple calls sequentially—prompt → LLM → parser → output.
But neither an LLM call nor a chain is an *agent*. The distinction
is the loop<Citation src="dlai-langgraph-course" />.



<Term name="Agent" los="LG-1.1">
  A system that uses an LLM as a reasoning engine to decide which actions to take, executes those actions, observes the results, and repeats until the task is complete. The defining feature is the *cycle*: the LLM's output feeds back as input to the next iteration<Citation src="yao2022react" />.
</Term>
<AnkiCard type="term" front={"Agent"} back={"A system that uses an LLM as a reasoning engine to decide which actions to take, executes those actions, observes the results, and repeats until the task is complete. The defining feature is the *cycle*: the LLM's output feeds back as input to the next iteration[yao2022react]."} los="LG-1.1" />



**Why chains fail.** A linear chain executes a fixed sequence of steps.
It cannot:

- **Branch:** Call tool A or tool B depending on the input

- **Loop:** Re-invoke the LLM after observing a tool result

- **Accumulate:** Build up context across multiple reasoning steps



<Sidenote category="warning">A chain with tools is not an agent. Without a cycle back to the LLM after tool results, the system cannot reason about what it observed.</Sidenote>



An agent needs a runtime that supports *cycles*—the output of one step
becomes the input of a previous step. This is a graph, not a pipeline. LangGraph
provides exactly this: a state graph where nodes are functions, edges define
control flow (including cycles), and a typed state dictionary is the shared
memory that persists across the loop<Citation src="langgraph-docs" />.

**LangGraph vs vanilla LangChain.** LangChain’s core abstraction is the
*Runnable*—a composable unit that forms linear chains via the pipe
operator (`|`). LangGraph extends this with `StateGraph`: a
directed graph where edges can loop back to earlier nodes. LangChain provides
the building blocks (chat models, tools, messages); LangGraph provides the
agent runtime<Citation src="langchain-docs" />.



<Sidenote category="pattern">LangChain = building blocks (models, tools, messages). LangGraph = agent runtime (state graphs, cycles, persistence). Use both together.</Sidenote>



&lt;!–MDXB-13-OPEN–&gt;

**Core Insight:** The fundamental difference between a chain and an agent
is the cycle. A chain executes a fixed path once. An agent loops: reason
→ act → observe → reason, continuing until the task is
complete or a termination condition is met.

**Why It Matters:** Without cycles, the system cannot adapt to tool
results, handle multi-step reasoning, or recover from errors. The cycle is
what makes the LLM a *decision maker* rather than a *text generator*.

**When It Breaks:** When the task is truly single-step (summarize this
text, translate this sentence), an agent adds unnecessary overhead. Use a
chain for deterministic, single-pass tasks; use an agent when the number
of steps is not known in advance.

# LangGraph Primitives



<Sidenote category="interview">Know the five primitives cold: `StateGraph`, `add_node`, `add_edge`, `add_conditional_edges`, `START`/`END`.</Sidenote>



LangGraph provides a small set of primitives that compose into arbitrarily
complex agent architectures<Citation src="langgraph-docs" />:

## State as Shared Memory



<Term name="StateGraph" los="LG-1.2">
  A directed graph where each node is a Python function that reads and writes to a shared typed state. The state is a `TypedDict` with optional reducer annotations that control how concurrent writes merge. Edges define execution order, including conditional branches and cycles<Citation src="langgraph-docs" />.
</Term>
<AnkiCard type="term" front={"StateGraph"} back={"A directed graph where each node is a Python function that reads and writes to a shared typed state. The state is a `TypedDict` with optional reducer annotations that control how concurrent writes merge. Edges define execution order, including conditional branches and cycles[langgraph-docs]."} los="LG-1.2" />



The state is defined as a `TypedDict` with an `Annotated` reducer:

~~~ python
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]
~~~



<Sidenote category="formula">`Annotated[list, operator.add]` means: new messages are *appended*, not replaced. Without this, each node would overwrite the entire list.</Sidenote>



The `operator.add` annotation is a *reducer*: when a node returns
`{"messages": [new_msg]}`, LangGraph appends the new message instead
of replacing the old list. That is why conversation history accumulates across
the agent loop.

## Nodes, Edges, and Conditional Routing

~~~ python
from langgraph.graph import StateGraph, END

# 1. Create the graph with the state schema
graph = StateGraph(AgentState)

# 2. Add nodes (name -> function)
graph.add_node("llm", call_llm)
graph.add_node("action", take_action)

# 3. Add edges (fixed routing)
graph.add_edge("action", "llm")

# 4. Add conditional edges (dynamic routing)
graph.add_conditional_edges(
    "llm",                    # source node
    should_continue,          # routing function
    {True: "action", False: END}  # map output -> target
)

# 5. Set entry point and compile
graph.set_entry_point("llm")
abot = graph.compile()
~~~



<Sidenote category="practice">Build the minimal 2-node graph (llm + action) from scratch. Target: 10 min from empty file to working agent.</Sidenote>



**Key primitives:**

- `add_node(name, fn)`: Registers a function. The function
  receives the current state and returns a partial state update.

- `add_edge(src, dst)`: Fixed routing—after `src`
  finishes, always go to `dst`.

- `add_conditional_edges(src, fn, mapping)`: Dynamic
  routing—`fn` inspects the state and returns a key;
  `mapping` converts that key to the next node name.

- `set_entry_point(name)`: Equivalent to
  `add_edge(START, name)`.

- `END`: A special sentinel indicating graph termination.



<Sidenote category="crossref">Ch 3 adds `compile(checkpointer=...)` for persistence. Ch 3 also covers `interrupt_before` for HITL.</Sidenote>



# Building a Tool-Calling Agent



<Sidenote category="interview">ReAct loop: LLM reasons $$ emits `tool_calls` $$ action node executes tools $$ results appended to messages $$ LLM reasons again. Loop until no `tool_calls`.</Sidenote>



## The ReAct Pattern

The course builds a tool-calling agent using the ReAct
pattern<Citation src="yao2022react" />: the LLM interleaves **reasoning** (deciding
what to do) with **acting** (invoking tools). In LangGraph, this becomes
a two-node cycle:

1.  **LLM node:** Receives the message history, reasons about it,
    and either (a) returns a final answer or (b) emits one or more
    `tool_calls`.

2.  **Action node:** Executes each tool call, wraps results in
    `ToolMessage` objects, and appends them to state.

3.  The conditional edge checks: if the LLM’s response contains
    `tool_calls`, route to the action node (loop). Otherwise,
    route to `END` (terminate).



<Sidenote category="pattern">ReAct = Reason + Act. Two-node cycle: LLM decides, action executes. Conditional edge on `tool_calls` controls the loop.</Sidenote>



## Defining and Binding Tools

Tools are Python functions decorated with metadata that the LLM uses to decide
when to call them<Citation src="openai-function-calling" /><Citation src="schick2023toolformer" />:

~~~ python
from langchain_core.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers and return the product."""
    return a * b

@tool
def add(a: int, b: int) -> int:
    """Add two integers and return the sum."""
    return a + b
~~~

The tools are bound to the model so the LLM knows what is available:

~~~ python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o")
model = model.bind_tools([multiply, add])
~~~



<Sidenote category="warning">`bind_tools()` does not execute tools—it tells the model they exist. Execution happens in the action node. Confusing these causes "tool not found" bugs.</Sidenote>



`bind_tools()` serializes each tool’s name, description, and parameter
schema into the model’s function-calling format. When the LLM decides to use a
tool, it returns a structured `tool_calls` list with the tool name and
arguments<Citation src="openai-function-calling" />.

## The Agent Class

The course wraps the full agent in a class<Citation src="dlai-langgraph-course" />:

~~~ python
class Agent:
    def __init__(self, model, tools, system=""):
        self.system = system
        graph = StateGraph(AgentState)
        graph.add_node("llm", self.call_llm)
        graph.add_node("action", self.take_action)
        graph.add_conditional_edges(
            "llm", self.exists_action,
            {True: "action", False: END}
        )
        graph.add_edge("action", "llm")
        graph.set_entry_point("llm")
        self.graph = graph.compile()
        self.tools = {t.name: t for t in tools}
        self.model = model.bind_tools(tools)
~~~



<Sidenote category="formula">`self.tools = {t.name: t for t in tools}` creates a name $$ tool lookup dict. The action node dispatches by name from `tool_calls`.</Sidenote>



## Conditional Routing: The Decision Point

The routing function inspects the last message for tool calls:

~~~ python
def exists_action(self, state: AgentState):
    result = state["messages"][-1]
    return len(result.tool_calls) > 0
~~~

If `tool_calls` is non-empty, route to `"action"` (the agent
needs to execute tools). If empty, the LLM has produced a final answer—route
to `END`.

## The Action Node

The action node iterates over all pending tool calls, executes each, and
appends the results as `ToolMessage` objects:

~~~ python
def take_action(self, state: AgentState):
    results = []
    for t in state["messages"][-1].tool_calls:
        result = self.tools[t["name"]].invoke(t["args"])
        results.append(ToolMessage(
            tool_call_id=t["id"],
            name=t["name"],
            content=str(result)
        ))
    return {"messages": results}
~~~



<Sidenote category="warning">Each `ToolMessage` must include the `tool_call_id` from the original request. Without it, the LLM cannot match results to calls.</Sidenote>



The `ToolMessage` wrapper is critical: it carries the
`tool_call_id` that links the result back to the original request.
The LLM uses this linkage to interpret which result corresponds to which
tool call—essential when multiple tools are invoked in parallel.

&lt;!–MDXB-14-OPEN–&gt;

**Core Insight:** A LangGraph tool-calling agent is a two-node cycle
with a conditional exit. The LLM node decides; the action node executes; the
conditional edge checks `tool_calls` to determine whether to loop or
terminate. The entire pattern is fewer than 40 lines of code.

**Why It Matters:** This minimal loop is the foundation for every agent
pattern in the course. Chapter 2 adds tools; Chapter 3 adds persistence and
HITL; Chapter 4 adds multi-node orchestration. All build on this cycle.

**When It Breaks:** When the LLM hallucinates tool calls (calling tools
that do not exist) or enters infinite loops (always generating tool calls).
Production agents need a max-iteration guard and tool-name validation in the
action node.

Interview question (agent fundamentals): “Explain the difference between
a chain and an agent. When would you use each?”

**Strong answer:** “A chain is a fixed, linear pipeline: prompt →
LLM → parser. An agent adds a cycle: the LLM can call tools, observe
results, and decide what to do next. The key difference is that an agent’s
number of steps is *not known in advance*—it depends on the task and
tool results. I’d use a chain for deterministic tasks like summarization or
translation, and an agent when the task requires dynamic tool use, multi-step
reasoning, or adapting to intermediate results.”

**Meta-signal:** This tests whether you understand that the loop is the
defining feature. Weak answers describe agents as “LLMs with tools”—but
a chain can have tools too. The cycle is what makes it an agent.

&lt;!–MDXB-20-OPEN–&gt;

**Key Insight:** Returning an error as a `ToolMessage` (rather than
raising an exception) keeps the agent loop running. The LLM sees the error in
its next reasoning step and can self-correct—choosing a valid tool or
producing a final answer. This is the Reflexion principle applied at the tool
level<Citation src="shinn2023reflexion" />: verbal error feedback enables self-correction
without breaking the loop.

**Answer:** (1) Check `t["name"] not in self.tools` before invoking.
(2) Return a `ToolMessage` with the error string and available tool names.
(3) The loop continues because the graph receives a valid state update (a message),
not an exception.
