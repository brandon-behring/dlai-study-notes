&lt;!–MDXB-4-OPEN–&gt;

Chapter 1 built a tool-calling agent with LangGraph’s state graph primitives.
The agent can invoke tools—but *which* tools, and why do agents need
specialized search rather than standard web search? This chapter examines
agentic search: what it does internally, why standard search fails for agents,
and how to integrate it.

&lt;!–MDXB-4-CLOSE–&gt;

Before reading, consider:

1.  Why can’t an agent just use a standard search engine API that returns links?

2.  What does “source attribution” mean in the context of agent-generated answers?

3.  How does agentic search differ from retrieval-augmented generation (RAG)?

# The Problem with Standard Search



<Sidenote category="interview">"Why not just give the agent Google search?" Answer: agents need structured data, not HTML. Standard search returns links; agents need answers.</Sidenote>





<Term name="Agentic Search" los="LG-2.1">
  A search tool designed for LLM agents that returns structured, source-attributed answers rather than link lists. Internally decomposes complex queries, selects optimal data sources, extracts relevant content, and scores results for relevance<Citation src="tavily-docs" />.
</Term>
<AnkiCard type="term" front={"Agentic Search"} back={"A search tool designed for LLM agents that returns structured, source-attributed answers rather than link lists. Internally decomposes complex queries, selects optimal data sources, extracts relevant content, and scores results for relevance[tavily-docs]."} los="LG-2.1" />



In a zero-shot scenario, an LLM produces answers from static weights—it cannot access
dynamic data (last night’s game scores) or provide source attribution (reducing
hallucinations). Search solves both problems, but *how* the search returns results
matters enormously<Citation src="dlai-langgraph-course" />.

**Standard search** (e.g., DuckDuckGo API) returns a list of URLs. To use these
results, the agent must:

1.  Fetch each URL’s HTML content

2.  Parse and clean the HTML (e.g., with BeautifulSoup)

3.  Extract relevant text from potentially thousands of tokens of noise

4.  Hope the content answers the original question



<Sidenote category="warning">Standard search adds 3–4 extra steps (fetch, parse, extract, filter). Each step can fail. Agentic search collapses this into one API call.</Sidenote>



The course demonstrates this directly: a DuckDuckGo search for “weather in San Francisco”
returns URLs that, when scraped and parsed, produce verbose, unstructured text. The agent
receives far more noise than signal.

**Agentic search** collapses this pipeline into a single API call. The tool handles
query decomposition, source selection, content extraction, and relevance scoring internally.
The agent receives a structured JSON response with exactly the information it needs.

&lt;!–MDXB-6-OPEN–&gt;

**Core Insight:** A human searching for weather wants a visual dashboard with
temperature, humidity, and wind icons. An agent wants structured JSON with numeric
values it can reason over. Standard search engines are optimized for human consumption;
agentic search is optimized for LLM consumption.

**Why It Matters:** Giving an agent a human-oriented search tool forces it to
parse visual layouts and extract structured data from prose—error-prone and token-wasteful.
Agentic search eliminates this impedance mismatch.

**When It Breaks:** When the agent needs to interact with a specific website’s
UI (filling forms, clicking buttons), agentic search is insufficient. You need a
browser-automation tool instead.

&lt;!–MDXB-6-CLOSE–&gt;

# Inside an Agentic Search Tool



<Sidenote category="pattern">Agentic search pipeline: (1) decompose query into sub-queries, (2) select best source per sub-query, (3) extract + chunk, (4) score + filter. All internal.</Sidenote>



The course walks through the internal architecture of a basic agentic search
implementation<Citation src="tavily-docs" />:

1.  **Query decomposition:** Complex queries are split into sub-questions.
    For example, “What is the weather in SF? Should I travel there today?” decomposes
    into (1) “Current weather San Francisco” and (2) “Events and activities in San
    Francisco today”—each routed to the optimal data source independently.

2.  **Source selection:** For each sub-query, the tool selects the best
    data source—a weather API for weather, a news API for events, a knowledge
    base for facts.

3.  **Content extraction:** The tool scrapes or queries the selected source,
    chunks the content, and runs a vector similarity search to retrieve the top-K
    most relevant chunks.

4.  **Scoring and filtering:** Results are scored for relevance and low-quality
    chunks are filtered out. The final output is a structured JSON with answers
    and source URLs.



<Sidenote category="formula">`TavilySearchResults(max_results=2)` limits to 2 results per query. Adjust based on context window budget.</Sidenote>



## Standard vs Agentic vs RAG Search

| **Aspect**  | **Standard** | **Agentic**     | **RAG**          |
|:------------|:-------------|:----------------|:-----------------|
| Returns     | URL links    | Structured JSON | Retrieved chunks |
| Source      | Public web   | Web + APIs      | Private corpus   |
| Attribution | Links only   | Inline sources  | Chunk metadata   |
| Agent-ready | No (HTML)    | Yes             | Yes              |
| Dynamic     | Yes          | Yes             | Index freshness  |
| Queries     | Keyword      | Decompose       | Embedding        |

# Integrating Search into a LangGraph Agent



<Sidenote category="interview">Know the integration pattern: create tool $$ `bind_tools()` $$ action node invokes by name from `tool_calls`. Same pattern for any tool.</Sidenote>



The Tavily tool integrates with the Chapter 1 agent through three connection points:

~~~ python
from langchain_community.tools.tavily_search import (
    TavilySearchResults,
)

# 1. Create the tool
tool = TavilySearchResults(max_results=2)

# 2. Bind to the model (in Agent.__init__)
self.model = model.bind_tools([tool])

# 3. Action node invokes by name
result = self.tools[t["name"]].invoke(t["args"])
~~~

**Step 1:** `TavilySearchResults` creates a LangChain tool object with a
`name` attribute (`tavily_search_results_json`) and an `invoke`
method that calls the Tavily API.

**Step 2:** `model.bind_tools([tool])` tells the LLM about available tools.
The model uses the tool’s name, description, and parameter schema to decide when and how
to call it<Citation src="openai-function-calling" />.

**Step 3:** When the LLM returns a `tool_calls` list, the action node looks
up each tool by name and invokes it with the provided arguments. Results are wrapped in
`ToolMessage` objects and appended to state.



<Sidenote category="pattern">Any LangChain tool follows this pattern: create $$ bind $$ invoke. Swap Tavily for a custom tool and the graph structure stays identical.</Sidenote>



&lt;!–MDXB-7-OPEN–&gt;

**Core Insight:** Adding a new tool to a LangGraph agent requires zero graph
restructuring. You add the tool to the tools list, and the existing action node handles
it automatically—the node loops over `tool_calls` and dispatches by name.

**Why It Matters:** This decoupling means you can add, remove, or swap tools without
touching the graph topology. The graph is the *control flow*; the tools are the
*capabilities*.

**When It Breaks:** When different tools require different error handling, timeouts,
or retry logic. A production agent may need a custom action node per tool category rather
than a single generic dispatcher.

&lt;!–MDXB-7-CLOSE–&gt;

Interview question (tool integration): “How would you add search capabilities to an
LLM agent? Walk through the architecture.”

**Strong answer:** “I’d use an agentic search tool like Tavily rather than standard
web search. Standard search returns links that need scraping and parsing—three extra
failure points. Agentic search decomposes the query into sub-questions, routes each to
the optimal data source, extracts and scores relevant content, and returns structured JSON
with source attribution. Integration is three lines: create the tool, bind it to the model,
and the existing action node dispatches by tool name.”

**Meta-signal:** This tests whether you understand the impedance mismatch between
search-for-humans and search-for-agents, and whether you can articulate the architecture
beyond ‘I’d use an API.’

**Agentic vs Standard Search Cost-Benefit**

Your team is building an agent that answers customer questions about product availability.
You are evaluating two options: (A) standard search (DuckDuckGo API at $0/query) with
an HTML parsing pipeline, or (B) agentic search (Tavily at $0.01/query). The agent
handles 50,000 queries/month. The HTML parsing pipeline requires a developer to maintain
(estimated 4 hours/month at $75/hour).

1.  Calculate the monthly cost of each approach.

2.  Beyond cost, list three reliability risks of the standard search pipeline.

3.  Under what conditions would you choose standard search despite the maintenance burden?

&lt;!–MDXB-9-CLOSE–&gt;

&lt;!–MDXB-13-OPEN–&gt;

**Step 1: Cost Calculation.**
Option A (standard): API cost $0 + maintenance 4 hrs × $75 = **$300/month**.
Option B (agentic): 50,000 × $0.01 = **$500/month**, zero maintenance.

**Step 2: Reliability Risks of Standard Search.**

1.  **HTML structure changes:** Websites redesign without notice, breaking the parser.
    A single CSS class rename can silently return empty results.

2.  **Rate limiting and blocking:** Scraping 50K pages/month triggers bot detection.
    IP bans cause silent failures.

3.  **Content extraction noise:** Even with BeautifulSoup, ads, navigation, and
    cookie banners contaminate the extracted text. The agent receives irrelevant tokens.

**Step 3: When Standard Search Wins.**
Choose standard search when: (a) the target is a single known website with a stable structure
(e.g., your own product catalog), (b) you already have a mature scraping infrastructure, or
(c) query volume is low enough that maintenance cost dominates API cost (under ∼30,000
queries/month at these rates).

**Key Insight:** The real cost of standard search is not the API price—it is the
maintenance burden and silent failure modes. Agentic search trades a per-query fee for
reliability and zero maintenance.

**Answer:** Standard = $300/month (maintenance-dominated); Agentic = $500/month
(usage-dominated). Choose agentic unless scraping a stable, owned data source at low volume.

**Source Attribution Verification Pipeline**

Your agent uses Tavily to answer medical questions. A user asks: “What are the side effects
of metformin?” The agent returns an answer citing three sources. Your compliance team
requires that every claim in the agent’s response be traceable to a specific source URL.

1.  Design a verification pipeline that checks whether each claim in the response
    is supported by the cited sources.

2.  What LangGraph nodes would this pipeline require?

3.  How would you handle the case where a claim has no supporting source?

&lt;!–MDXB-10-CLOSE–&gt;

&lt;!–MDXB-14-OPEN–&gt;

**Step 1: Verification Pipeline Design.**
The pipeline has three stages:

1.  **Claim extraction:** Use structured output to decompose the agent’s response
    into individual factual claims (e.g., “Metformin can cause nausea”).

2.  **Source matching:** For each claim, compute semantic similarity against each
    source’s content. A claim is “supported” if similarity exceeds a threshold (e.g., 0.8).

3.  **Report generation:** Produce a verification report: each claim paired with
    its supporting source URL, or flagged as “unsupported.”

**Step 2: LangGraph Nodes.**
Four nodes in a linear pipeline:

- `search_node`: Calls Tavily, stores raw results with URLs in state

- `generate_node`: Produces the answer from search results

- `extract_claims_node`: Decomposes answer into atomic claims via structured output

- `verify_node`: Matches each claim to source content, flags unsupported claims

**Step 3: Handling Unsupported Claims.**
Two options: (a) **conservative**—strip unsupported claims from the response and
add a disclaimer, or (b) **iterative**—route unsupported claims back to the search
node for additional research (a generate-verify-research loop).

**Key Insight:** Source attribution is not just about returning URLs—it requires
verifying that the content at those URLs actually supports the claims made. This is
especially critical in high-stakes domains (medical, legal, financial).

**Answer:** Extract claims → match to sources → flag unsupported. Use a
4-node LangGraph pipeline. Strip or re-research unsupported claims based on risk tolerance.

\[advanced\]\[full\]
**Query Decomposition for Multi-Hop Questions**

A user asks your agent: “Is the CEO of the company that acquired Instagram older than the
CEO of the company that acquired YouTube?” This requires three pieces of information that
must be retrieved in a specific order.

1.  Identify the sub-queries needed and their dependency order.

2.  Show how an agentic search tool would handle this differently than a single query.

3.  What happens if the agent sends the original question as one search query?

&lt;!–MDXB-11-CLOSE–&gt;

&lt;!–MDXB-15-OPEN–&gt;

**Step 1: Sub-Query Decomposition.**
Three sub-queries with dependencies:

1.  “Which company acquired Instagram?” → Meta (Facebook)

2.  “Which company acquired YouTube?” → Google (Alphabet)

3.  “How old is Mark Zuckerberg?” and “How old is Sundar Pichai?” → compare ages

Queries 1 and 2 are independent (parallel). Query 3 depends on results of 1 and 2 (sequential).

**Step 2: Agentic Search Handling.**
An agentic search tool internally decomposes the complex query into sub-queries, routes
each to the optimal source (company acquisition data, biographical data), and assembles
the results. The agent receives a structured response with all three facts and source URLs.
With standard search, the agent would need to make 3–4 separate API calls, parse each
result, and manage the dependency ordering itself.

**Step 3: Single-Query Failure Mode.**
Sending the full question as one search query returns results about Instagram’s acquisition
history OR YouTube’s acquisition history—rarely both, and almost never the CEO age
comparison. The search engine optimizes for keyword matching, not multi-hop reasoning.
The agent gets partial, irrelevant results and either hallucinates the missing pieces or
produces an incomplete answer.

**Key Insight:** Multi-hop questions expose the fundamental limitation of keyword
search. Agentic search’s query decomposition step is what makes complex reasoning possible—it
converts a single hard question into multiple easy questions with clear dependency ordering.

**Answer:** Decompose into 3 sub-queries (2 parallel, 1 dependent). Agentic search
handles decomposition internally. A single-query approach fails because search engines
cannot reason across multiple hops.
