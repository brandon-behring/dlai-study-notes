# Designing Multi-Node Agent State



<Sidenote category="interview">Essay writer state has 7 fields: task, plan, draft, critique, content (list), revision_number, max_revisions. Each field serves one node.</Sidenote>



The essay writer is substantially more complex than the single-loop agent from Chapter 1.
Instead of one state field (`messages`), it uses seven fields—each serving a
different node in the graph<Citation src="dlai-langgraph-course" />:

~~~ python
class AgentState(TypedDict):
    task: str             # original user input
    plan: str             # generated outline
    draft: str            # current essay draft
    critique: str         # reflection feedback
    content: list[str]    # accumulated research docs
    revision_number: int  # current revision count
    max_revisions: int    # termination threshold
~~~



<Term name="Multi-Node Agent State" los="LG-4.1">
  A structured `TypedDict` where each field maps to a specific node's output. Unlike the simple `messages`-only state, multi-node state has semantically distinct fields (plan, draft, critique) that each node reads and writes independently.
</Term>
<AnkiCard type="term" front={"Multi-Node Agent State"} back={"A structured `TypedDict` where each field maps to a specific node's output. Unlike the simple `messages`-only state, multi-node state has semantically distinct fields (plan, draft, critique) that each node reads and writes independently."} los="LG-4.1" />





<Sidenote category="pattern">State design rule: one field per node output. If two nodes write the same field, make the merge strategy explicit (overwrite vs accumulate).</Sidenote>



Note the design decisions:

- `content` is a *list* that grows over cycles (research accumulates)

- `draft` is overwritten each cycle (only the latest draft matters)

- `revision_number` and `max_revisions` control termination

- No `operator.add` annotations—all fields use simple overwrite
  semantics except `content`, which is managed manually via list concatenation



<Sidenote category="warning">Without `max_revisions`, the reflect-generate loop runs forever. Always include a termination counter in iterative agent designs.</Sidenote>



# The Essay Writer: Plan, Research, Generate, Reflect



<Sidenote category="interview">Be ready to whiteboard the essay writer graph: plan $$ research_plan $$ generate $$ reflect $$ research_critique $$ generate. Conditional edge on generate.</Sidenote>



The essay writer has five nodes and one conditional edge:

## Plan Node

Takes the user’s task and generates an essay outline:

~~~ python
def plan_node(state: AgentState):
    messages = [
        SystemMessage(content=PLAN_PROMPT),
        HumanMessage(content=state["task"])
    ]
    response = model.invoke(messages)
    return {"plan": response.content}
~~~

## Research Plan Node

Given the plan, generates search queries using structured output, then
searches Tavily for each query:

~~~ python
def research_plan_node(state: AgentState):
    queries = model.with_structured_output(Queries).invoke(
        [SystemMessage(content=RESEARCH_PLAN_PROMPT),
         HumanMessage(content=state["task"])]
    )
    content = state.get("content", [])
    for q in queries.queries:
        response = tavily.search(query=q, max_results=2)
        for r in response["results"]:
            content.append(r["content"])
    return {"content": content}
~~~



<Sidenote category="formula">`model.with_structured_output(Queries)` uses function calling to guarantee a Pydantic-typed response—no parsing needed.</Sidenote>



The Pydantic model for structured output:

~~~ python
from pydantic import BaseModel

class Queries(BaseModel):
    queries: list[str]
~~~



<Sidenote category="crossref">Structured output via `with_structured_output()` builds on function calling from Ch 1.</Sidenote>



## Generation Node

Combines the task, plan, and accumulated research content to write (or rewrite) the essay:

~~~ python
def generation_node(state: AgentState):
    content = "\n\n".join(state.get("content", []))
    user_message = HumanMessage(content=
        f"{state['task']}\n\nPlan:\n{state['plan']}")
    messages = [
        SystemMessage(content=WRITER_PROMPT.format(
            content=content)),
        user_message
    ]
    response = model.invoke(messages)
    return {
        "draft": response.content,
        "revision_number": state.get("revision_number", 1) + 1
    }
~~~

## Reflect Node

Critiques the current draft, identifying strengths and areas for improvement:

~~~ python
def reflection_node(state: AgentState):
    messages = [
        SystemMessage(content=REFLECTION_PROMPT),
        HumanMessage(content=state["draft"])
    ]
    response = model.invoke(messages)
    return {"critique": response.content}
~~~

## Research Critique Node

Similar to `research_plan_node`, but generates queries based on the
critique rather than the original plan. Results are appended to the existing
content list, giving the next generation cycle more material.

&lt;!–MDXB-9-OPEN–&gt;

**Core Insight:** The essay writer’s power comes from its *cycle*: generate
a draft, critique it, research the gaps, then rewrite with new material. This is not
a single LLM call but a controlled loop where each iteration provably improves the
output by adding targeted research.

**Why It Matters:** Single-pass generation (“write an essay in one shot”) is
limited by the model’s current knowledge. Iterative refinement lets the agent
*discover what it doesn’t know* (via reflection) and *fill those gaps*
(via targeted research). This matches how humans write.

**When It Breaks:** When the critique is vague (“make it better”) or the
research queries are too broad, iterations add noise rather than signal. The quality
of the reflection prompt is the bottleneck.

# Graph Construction and Termination



<Sidenote category="pattern">Graph construction sequence: add nodes $$ set entry point $$ add conditional edge $$ add fixed edges $$ compile with checkpointer.</Sidenote>



The complete graph construction:

~~~ python
builder = StateGraph(AgentState)
builder.add_node("planner", plan_node)
builder.add_node("research_plan", research_plan_node)
builder.add_node("generate", generation_node)
builder.add_node("reflect", reflection_node)
builder.add_node("research_critique", research_critique_node)

builder.set_entry_point("planner")
builder.add_conditional_edges(
    "generate", should_continue,
    {END: END, "reflect": "reflect"}
)
builder.add_edge("planner", "research_plan")
builder.add_edge("research_plan", "generate")
builder.add_edge("reflect", "research_critique")
builder.add_edge("research_critique", "generate")

graph = builder.compile(checkpointer=memory)
~~~

The termination condition is straightforward:

~~~ python
def should_continue(state):
    if state["revision_number"] > state["max_revisions"]:
        return END
    return "reflect"
~~~



<Sidenote category="warning">The conditional edge fires after `generate`, not after `reflect`. Placing it wrong creates an infinite loop without the revision check.</Sidenote>

| **Architecture** | **State**         | **Best For**       | **Trade-off**  |
|:-----------------|:------------------|:-------------------|:---------------|
| Shared-State     | Single shared     | Tight coordination | Agent coupling |
| Supervisor       | Per-agent         | Heterogeneous      | Bottleneck     |
| Flow Eng.        | Pipeline + loops  | Domain-specific    | Less reusable  |
| Plan-Execute     | Plan + sub-agents | Multi-step         | Re-plan cost   |

## Shared-State Multi-Agent

Multiple agents (each with their own prompt, model, and tools) work on the same
shared state, passing it sequentially. The essay writer uses this pattern: plan,
research, generate, and reflect nodes all read and write the same
`AgentState`<Citation src="dlai-langgraph-course" />.

## Supervisor Agent

One powerful LLM acts as a supervisor, routing tasks to specialized sub-agents.
Each sub-agent can have its own internal state and tool set. The supervisor
determines what input each sub-agent receives and how to integrate their outputs.



<Sidenote category="practice">Use a supervisor when sub-agents need different models or tools. Use shared-state when all agents need the same context.</Sidenote>



## Flow Engineering

From the AlphaCodium paper<Citation src="alphacodium2024" />: a bespoke directed pipeline
with loops only at critical bottleneck nodes. Unlike a generic agent loop,
the flow is hand-designed for the specific problem—directed steps with
targeted iteration points. This achieves state-of-the-art performance by
trading generality for controllability.

## Plan-and-Execute

Explicit planning upfront, followed by sequential execution of each plan step
by a sub-agent. After execution, optionally re-plan based on results. Variants
include Language Agent Tree Search (LATS), which does a tree search over action
states with reflection-based backpropagation—persistence is essential for
backtracking to previous states.

&lt;!–MDXB-10-OPEN–&gt;

**Core Insight:** The choice of agent architecture is not “which is best” but
“which matches the problem structure.” Tight coordination with shared context
→ shared-state. Heterogeneous specialists → supervisor. Known domain
pipeline → flow engineering. Complex multi-step reasoning → plan-and-execute.

**Why It Matters:** Picking the wrong architecture creates unnecessary complexity.
A simple tool-calling agent (Chapter 1) is often sufficient; the essay writer
pattern (shared-state multi-agent) is needed only when the task has a clear
decomposition into specialized subtasks.

**When It Breaks:** When the problem doesn’t decompose cleanly. If every node
needs access to every other node’s output, shared-state becomes a tangled mess.
If the supervisor can’t accurately route, the whole system degrades.

**Human-in-the-Loop Interrupt Design for a Multi-Node Pipeline**

You are building the essay writer from this chapter for a legal document drafting application.
The pipeline has five nodes: planner, research, generate, reflect, and research\_critique.
Legal review is expensive ($200/hour for a lawyer), so you cannot interrupt at every node.

1.  Which nodes should have human interrupts? Justify each decision.

2.  Design the state fields needed to track approval status across cycles.

3.  How do you handle the case where the lawyer rejects the draft at revision 3
    but wants to keep the research from revisions 1–2?

&lt;!–MDXB-12-CLOSE–&gt;

&lt;!–MDXB-16-OPEN–&gt;

**Step 1: Interrupt Placement.**

- **planner** — `interrupt_after`: The outline determines everything
  downstream. A wrong outline wastes all subsequent cycles. **Interrupt: yes.**

- **research\_plan** — No interrupt: research queries are low-risk and
  correctable in later cycles. **Interrupt: no.**

- **generate** — `interrupt_after`: The draft is the primary deliverable.
  The lawyer must review before reflection begins. **Interrupt: yes.**

- **reflect** — No interrupt: reflection is internal feedback, not a
  deliverable. **Interrupt: no.**

- **research\_critique** — No interrupt: same rationale as research\_plan.
  **Interrupt: no.**

Result: 2 interrupts per cycle (planner on first cycle, generate on every cycle).

**Step 2: Approval State Fields.**
Add three fields to `AgentState`:

- `plan_approved: bool` — gates progression past the planner

- `draft_approved: bool` — gates whether to finalize or continue revising

- `lawyer_notes: str` — free-text feedback injected into the reflect node’s prompt

**Step 3: Reject Draft, Keep Research.**
Find the checkpoint after revision 2’s research phase. Keep
`content`, clear `draft`, add the rejection reason to
`lawyer_notes`, and resume from there. The research persists; only the
draft is discarded.

**Key Insight:** Interrupt placement is a cost optimization problem: interrupt at
nodes whose output is expensive to redo (plan, final draft), skip nodes whose output
is cheap to correct (research, reflection). The accumulative `content` field makes
research durable across rejections.

**Answer:** Interrupt after planner and generate (2 per cycle). Track approval with
`plan_approved`, `draft_approved`, `lawyer_notes`. On rejection,
time-travel to post-research checkpoint, reset draft, keep accumulated research.

\[advanced\]\[full\]
**Multi-Agent Routing — When to Split into Specialist Agents**

Your team has a monolithic customer service agent with 12 tools: FAQ search, order lookup,
refund processing, shipping tracker, product recommender, complaint logger, escalation
trigger, appointment scheduler, warranty checker, return label generator, survey sender,
and loyalty points calculator. The agent’s tool selection accuracy has dropped to 73%.

1.  Diagnose why tool selection accuracy degrades with more tools.

2.  Design a multi-agent architecture that groups these 12 tools into specialist agents.

3.  What routing mechanism should the supervisor use, and what happens when the
    customer’s intent spans two specialists?

&lt;!–MDXB-13-CLOSE–&gt;

&lt;!–MDXB-17-OPEN–&gt;

**Step 1: Diagnosis.**
Tool selection accuracy degrades because:

- **Schema confusion:** With 12 tool schemas in the system prompt, the LLM
  struggles to distinguish similar tools (e.g., “order lookup” vs “shipping tracker”
  vs “warranty checker” all involve order IDs).

- **Context dilution:** Each tool’s description consumes tokens, leaving less
  context budget for the conversation and reasoning.

- **Ambiguous routing:** “Where’s my order?” could trigger order lookup,
  shipping tracker, or both. With 12 options, the LLM makes more boundary errors.

**Step 2: Specialist Agent Design.**
Group by customer intent into 4 specialists:

- **Order Agent** (4 tools): order lookup, shipping tracker, return label, warranty

- **Support Agent** (3 tools): FAQ search, complaint logger, escalation trigger

- **Commerce Agent** (3 tools): product recommender, loyalty points, survey sender

- **Operations Agent** (2 tools): refund processing, appointment scheduler

Each specialist sees only 2–4 tools, restoring selection accuracy.

**Step 3: Routing Mechanism.**
The supervisor agent uses an intent classifier (structured output with a `Route`
Pydantic model listing the target agent and confidence score). For cross-specialist
intents (e.g., “I want to return this and get a recommendation for a replacement”):

1.  Supervisor decomposes into two sub-intents

2.  Routes “return” to Order Agent and “recommendation” to Commerce Agent

3.  Collects both results and synthesizes a unified response

If confidence is below a threshold (e.g., 0.7), the supervisor asks the user a
clarifying question before routing.

**Key Insight:** The optimal number of tools per agent is 3–5. Beyond that, selection
accuracy drops nonlinearly. Splitting into specialists is not premature optimization—it
is a reliability requirement. The supervisor pattern from Section <a href="#sec:ch4-architectures" data-reference-type="ref" data-reference="sec:ch4-architectures">[sec:ch4-architectures]</a>
is the right architecture because sub-agents need different tool sets.

**Answer:** 12 tools → schema confusion + context dilution. Split into 4 specialists
(2–4 tools each). Supervisor routes by intent classification; cross-specialist queries get
decomposed and routed to multiple agents.

\[advanced\]\[full\]
**Essay Writer State Machine Design**

You are adapting the essay writer pattern for a code review agent. The agent should:
(a) read a pull request diff, (b) identify issues by category (bugs, style, performance),
(c) generate review comments, (d) self-critique the comments for false positives, and
(e) iterate until the false positive rate is below 10%.

1.  Define the `AgentState` fields for this application.

2.  Draw the graph topology: nodes, edges, and the conditional termination edge.

3.  How does the termination condition differ from the essay writer’s revision counter?

&lt;!–MDXB-14-CLOSE–&gt;

&lt;!–MDXB-18-OPEN–&gt;

**Step 1: State Definition.**

- `diff: str` — the raw pull request diff (input, never modified)

- `issues: list[dict]` — identified issues with category, line, and description

- `comments: list[dict]` — generated review comments (one per issue)

- `critique: dict` — self-critique result: `false_positives` (list of
  comment IDs), `false_positive_rate` (float)

- `iteration: int` — current iteration count

- `max_iterations: int` — safety limit (e.g., 5)

**Step 2: Graph Topology.**
Five nodes, one conditional edge:

1.  `parse_diff` → `identify_issues` (fixed edge)

2.  `identify_issues` → `generate_comments` (fixed edge)

3.  `generate_comments` → `self_critique` (fixed edge)

4.  `self_critique` → conditional edge:
    if `false_positive_rate < 0.1` OR `iteration >= max_iterations`
    → END; else → `filter_and_regenerate`

5.  `filter_and_regenerate` → `self_critique` (loop back)

The `filter_and_regenerate` node removes flagged false positives from `comments`
and regenerates replacements.

**Step 3: Termination Difference.**
The essay writer terminates on a fixed revision count. The code review agent
terminates on a quality metric such as
`false_positive_rate < 0.1`, plus a safety cap like
`max_iterations`. That is convergence-based termination: the loop exits
when quality is good enough, not just when a counter runs out.

**Key Insight:** The essay writer uses count-based termination (simple, predictable).
The code review agent uses metric-based termination (adaptive, quality-driven). Metric-based
termination is more powerful but requires a measurable quality signal—false positive rate
is measurable; “essay quality” is not.

**Answer:** 6 state fields; 5-node graph with a critique-filter loop; terminate on
quality metric (FP rate  &lt; 10%) with iteration safety cap, unlike essay writer’s fixed
revision count.
