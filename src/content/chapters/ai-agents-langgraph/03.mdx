&lt;!–MDXB-3-OPEN–&gt;

Chapter 1 built the agent graph; Chapter 2 gave it a search tool. But the agent has no
memory between runs, no way to show progress during execution, and no mechanism for
human oversight. This chapter adds all three: persistence for memory, streaming for
observability, and interrupt points for human control.

&lt;!–MDXB-3-CLOSE–&gt;

Before reading, consider:

1.  Why would you want to checkpoint agent state after every node execution?

2.  How does streaming help users interact with long-running agents?

3.  At which point in the execution cycle should a human be able to intervene?

# Persistence with Checkpointers



<Sidenote category="interview">"How do you handle agent memory?" Answer: LangGraph checkpointers snapshot state after every node. Thread IDs separate conversations. Replay from any snapshot.</Sidenote>





<Term name="Checkpointer" los="LG-3.1">
  A persistence backend that snapshots the agent state after every node execution. LangGraph provides built-in checkpointers for SQLite (`SqliteSaver`), Redis, and Postgres. Each snapshot is keyed by a thread ID and a unique timestamp<Citation src="langgraph-docs" />.
</Term>
<AnkiCard type="term" front={"Checkpointer"} back={"A persistence backend that snapshots the agent state after every node execution. LangGraph provides built-in checkpointers for SQLite (`SqliteSaver`), Redis, and Postgres. Each snapshot is keyed by a thread ID and a unique timestamp[langgraph-docs]."} los="LG-3.1" />



When agents work on longer-running tasks, two capabilities become essential:
*persistence* (save and resume state) and *streaming* (show progress).
LangGraph provides both through its checkpointer system<Citation src="dlai-langgraph-course" />.

**Adding persistence** requires minimal code changes:

~~~ python
from langgraph.checkpoint.sqlite import SqliteSaver

memory = SqliteSaver.from_conn_string(":memory:")
# Pass checkpointer to graph.compile()
self.graph = graph.compile(checkpointer=memory)
~~~



<Sidenote category="warning">The `":memory:"` database vanishes when the process exits. For production, use a persistent backend (Postgres, Redis).</Sidenote>



The checkpointer snapshots state after *every* node execution—not just at the end.
This means you can inspect or resume from any intermediate step.

## Thread-Based Conversations



<Term name="Thread ID" los="LG-3.1">
  A string identifier that separates conversations within a checkpointer. Passing the same thread ID across calls resumes the conversation; changing it starts fresh. Essential for multi-user production applications.
</Term>
<AnkiCard type="term" front={"Thread ID"} back={"A string identifier that separates conversations within a checkpointer. Passing the same thread ID across calls resumes the conversation; changing it starts fresh. Essential for multi-user production applications."} los="LG-3.1" />



Each conversation is identified by a `thread_id` in the configuration:

~~~ python
thread = {"configurable": {"thread_id": "1"}}
result = abot.graph.stream(
    {"messages": [HumanMessage(content="Weather in SF?")]},
    thread
)
~~~



<Sidenote category="pattern">Same thread ID = continued conversation (agent remembers context). New thread ID = fresh start (no history). This is how you support multiple users.</Sidenote>



The course demonstrates this with three successive calls on thread “1”:

1.  “What is the weather in SF?” — full agent cycle with tool call

2.  “What about in LA?” — the agent infers “weather” from conversation history

3.  “Which is warmer?” — requires both previous results from state

Switching to thread “2” and asking “Which is warmer?” produces confusion—the
agent has no prior context, proving that thread IDs correctly isolate conversations.

&lt;!–MDXB-5-OPEN–&gt;

**Core Insight:** Because the checkpointer stores every intermediate state, you can
“time travel” to any previous point. Call `graph.get_state_history(thread)`
to retrieve all snapshots, pick one, and invoke `graph.stream(None, snapshot.config)`
to resume from that exact point.

**Why It Matters:** Time travel is essential for debugging (“what did the agent
decide at step 3?”), auditing (“show me the tool calls made”), and branching
(“what if the agent had searched for X instead of Y?”).

**When It Breaks:** State history grows linearly with execution length. For
agents that run thousands of iterations, you need a retention policy or external
storage with TTL.

&lt;!–MDXB-5-CLOSE–&gt;

## Code Pattern: Time Travel with State History

The `get_state_history()` method returns an iterator over all checkpointed
snapshots for a thread, from newest to oldest:

~~~ python
# Retrieve all state snapshots for a thread
states = list(abot.graph.get_state_history(thread))

# The last element is the earliest snapshot
earliest = states[-1]

# Resume from any historical snapshot
for event in abot.graph.stream(
    None, earliest.config
):
    print(event)
~~~

Each snapshot contains: the agent state (`.values`), the next node to execute
(`.next`), and a config with a unique `thread_ts` timestamp. You can
also branch from a historical state by calling `update_state()` on it—this
creates a new timeline without affecting the original.

# Streaming Agent Execution



<Sidenote category="interview">Two streaming levels: `graph.stream()` gives node-level events (AI message, tool result). `astream_events()` gives token-level streaming.</Sidenote>



LangGraph supports two levels of streaming<Citation src="langgraph-docs" />:

## Node-Level Streaming

The `graph.stream()` method yields state updates after each node completes:

~~~ python
for event in abot.graph.stream(
    {"messages": messages}, thread
):
    for v in event.values():
        print(v)
~~~

This produces a sequence of events: the AI message (with tool call request), the
tool message (search result), and the final AI message (answer). You see each
*step* as it completes.



<Sidenote category="formula">Node streaming: one event per node completion. Token streaming: one event per output token. Choose based on UX requirements.</Sidenote>



## Token-Level Streaming

For real-time UX, the `astream_events()` method streams individual tokens
as the LLM generates them:

~~~ python
async for event in abot.graph.astream_events(
    {"messages": messages}, thread, version="v1"
):
    kind = event["event"]
    if kind == "on_chat_model_stream":
        content = event["data"]["chunk"].content
        if content:
            print(content, end="|")
~~~



<Sidenote category="warning">Token streaming requires an async checkpointer (`AsyncSqliteSaver`). The synchronous `SqliteSaver` does not support `astream_events()`.</Sidenote>



Token streaming fires `on_chat_model_stream` events. During tool-call
generation there is no content to stream (just the function call structure);
tokens appear only during the final natural-language response.

# Human-in-the-Loop Patterns



<Sidenote category="interview">HITL pattern: `interrupt_before=["action"]` pauses before tool execution. Resume with `stream(None, thread)`. Human approves, modifies, or mocks.</Sidenote>





<Term name="Human-in-the-Loop (HITL)" los="LG-3.3">
  An agent design pattern where execution pauses at designated points for human review. In LangGraph, implemented via `interrupt_before` (or `interrupt_after`) parameters on `graph.compile()`. The human can approve, modify, or replace the pending action.
</Term>
<AnkiCard type="term" front={"Human-in-the-Loop (HITL)"} back={"An agent design pattern where execution pauses at designated points for human review. In LangGraph, implemented via `interrupt_before` (or `interrupt_after`) parameters on `graph.compile()`. The human can approve, modify, or replace the pending action."} los="LG-3.3" />



## Adding Breakpoints

The simplest HITL pattern: pause before tool execution for human approval.

~~~ python
self.graph = graph.compile(
    checkpointer=memory,
    interrupt_before=["action"]
)
~~~



<Sidenote category="practice">Try different interrupt points: `interrupt_before=["llm"]` pauses before each LLM call. Useful for cost-sensitive workflows.</Sidenote>



When the agent reaches the action node, execution pauses. The human inspects the
proposed tool calls via `graph.get_state(thread)`:

~~~ python
state = abot.graph.get_state(thread)
print(state.values["messages"][-1].tool_calls)
# => [{'name': 'tavily_search_results_json',
#      'args': {'query': 'current weather LA'}}]
print(state.next)  # => ('action',)
~~~

To continue: `abot.graph.stream(None, thread)`. Passing `None` means
“resume with the current state—don’t add new input.”

## Interactive Approval Loop

The course wraps the interrupt pattern in a loop that prompts the user for approval
at each breakpoint:

~~~ python
thread = {"configurable": {"thread_id": "3"}}
while True:
    for event in abot.graph.stream(
        {"messages": [HumanMessage(content=query)]}, thread
    ):
        for v in event.values():
            print(v)
    state = abot.graph.get_state(thread)
    if not state.next:
        break  # graph finished, no pending node
    response = input("Continue? (yes/no): ")
    if response.lower() != "yes":
        print("Aborted by human.")
        break
    # Resume with None input (no new messages)
    query = None
~~~

This pattern gives the human a chance to inspect and approve at every interrupt point
before the agent proceeds. In production, the `input()` call would be replaced
by a webhook or UI callback.

## Custom State Reducers for Message Replacement

The default `operator.add` reducer only *appends* messages. For HITL,
we often need to *replace* a message (e.g., correct a tool call query). The
course introduces a custom reducer:

~~~ python
def reduce_messages(left, right):
    """Match by ID: same ID replaces, new ID appends."""
    by_id = {m.id: m for m in left}
    for m in right:
        by_id[m.id] = m
    return list(by_id.values())

class AgentState(TypedDict):
    messages: Annotated[list, reduce_messages]
~~~



<Sidenote category="pattern">Custom reducer pattern: same message ID = replace (edit). New message ID = append (add). This enables both correction and extension.</Sidenote>



## Modifying State: Three Patterns

The course demonstrates three increasingly powerful HITL interactions:

**Pattern 1: Modify the current state.**
Change the search query from “Los Angeles” to “Louisiana” before the tool
executes. Update the existing AI message (same ID triggers replacement via
the custom reducer), then resume:

~~~ python
# Modify tool call args on the last message
_id = state.values["messages"][-1].tool_calls[0]["id"]
state.values["messages"][-1].tool_calls = [
    {"name": "tavily_search_results_json",
     "args": {"query": "current weather Louisiana"},
     "id": _id}
]
abot.graph.update_state(thread, state.values)
~~~

**Pattern 2: Time travel and edit.**
Go back to a previous checkpoint, modify the state there, and resume from
the branched state. This creates a new execution branch without affecting
the original timeline.



<Sidenote category="crossref">Time travel uses `get_state_history()` from the persistence section above.</Sidenote>



**Pattern 3: Mock a tool response.**
Instead of calling the actual tool, inject a fake `ToolMessage` into
state. The key: pass `as_node="action"` to `update_state()`
so the framework treats this as if the action node produced it:

~~~ python
tool_call_id = state.values["messages"][-1].tool_calls[0]["id"]
state_update = {"messages": [
    ToolMessage(
        tool_call_id=tool_call_id,
        name="tavily_search_results_json",
        content="54 degrees"
    )
]}
abot.graph.update_state(thread, state_update, as_node="action")
~~~



<Sidenote category="warning">Forgetting `as_node="action"` when mocking a tool response means the graph still thinks the action node hasn't run—it will try to execute the real tool.</Sidenote>



&lt;!–MDXB-6-OPEN–&gt;

**Core Insight:** Human-in-the-loop is not just for debugging—it is a
production safety pattern. High-stakes tool calls (database writes, API mutations,
financial transactions) should always pass through human approval before execution.
LangGraph’s interrupt mechanism makes this a compile-time configuration, not an
afterthought.

**Why It Matters:** The three patterns—approve, modify, mock—cover the
full spectrum of human intervention. Approve is the common case; modify handles
corrections; mock enables testing and cost control (skip expensive API calls
during development).

**When It Breaks:** HITL adds latency. For real-time applications where
sub-second response matters, you need selective interrupts (only for dangerous
tools) rather than blanket interrupts on every action.

&lt;!–MDXB-6-CLOSE–&gt;

Interview question (agent safety): “How would you add human oversight to an autonomous
agent in production?”

**Strong answer:** “I’d use LangGraph’s interrupt mechanism. At compile time, you
specify which nodes require human approval via `interrupt_before`. When the agent
reaches that point, execution pauses and the pending action is surfaced to the human via
`get_state()`. The human can approve (resume with `None`), modify (edit the
tool call arguments and resume), or mock (inject a fake result to skip the real call).
All of this is enabled by the checkpointer, which stores every intermediate state. For
different risk levels, I’d use selective interrupts: always interrupt before database
writes, never before read-only searches.”

**Meta-signal:** This tests whether you think about agent safety beyond “it works
in the notebook.” Interviewers want to hear about approval flows, state inspection,
and risk-based interrupt strategies.

**Checkpoint Storage Sizing for Production**

Your production agent uses a Postgres-backed checkpointer. Each checkpoint stores the full
agent state (serialized JSON). The average state size is 12 KB per checkpoint. The agent
executes 5 nodes per conversation turn, and the average conversation has 8 turns. You
expect 10,000 conversations/day with a 30-day retention policy.

1.  Calculate the total storage required for the 30-day retention window.

2.  What is the checkpoint write throughput (writes/second) during peak hours
    (assume 60% of traffic in 8 hours)?

3.  Propose a storage optimization strategy that reduces costs by at least 50%.

&lt;!–MDXB-8-CLOSE–&gt;

&lt;!–MDXB-12-OPEN–&gt;

**Step 1: Storage Calculation.**
Checkpoints per conversation: 5 nodes × 8 turns = 40 checkpoints.
Daily checkpoints: 40 × 10,000 = 400,000.
Daily storage: 400,000 × 12 KB = 4.8 GB/day.
30-day retention: 4.8 × 30 = **144 GB**.

**Step 2: Peak Write Throughput.**
Peak daily conversations: 10,000 × 0.6 = 6,000 in 8 hours.
Peak checkpoints: 6,000 × 40 = 240,000 in 8 hours.
Writes/second: 240,000 / (8 × 3,600) = **8.3 writes/second**.

**Step 3: Storage Optimization.**
Three strategies:

- **Delta checkpointing:** Store only the diff from the previous state
  instead of the full state. Adjacent checkpoints typically differ by one field
  (the node’s output), reducing size by ∼70%.

- **Tiered retention:** Keep all checkpoints for 24 hours (debugging),
  then compact to first/last checkpoint per conversation for 30 days.

- **Selective checkpointing:** Only checkpoint after nodes that modify
  critical state fields (draft, plan), skip read-only nodes.

Delta checkpointing alone reduces 144 GB to ∼43 GB (70% reduction).

**Key Insight:** Full-state checkpointing after every node is expensive at scale.
The “checkpoint everything” default is correct for development; production needs a
retention policy and storage optimization strategy designed before launch, not after
the database fills up.

**Answer:** 144 GB for 30-day retention; 8.3 writes/sec peak; delta checkpointing
reduces storage by 70% to ∼43 GB.

\[intermediate\]\[full\]
**Streaming UX Design — Token vs Event Streaming**

You are building a chat UI for an agent that searches the web, then generates a response.
The product manager wants users to see “something happening” within 500ms of sending a
message. The search tool takes 2–4 seconds. The LLM generation takes 3–6 seconds.

1.  Compare what the user sees with node-level streaming vs token-level streaming.

2.  Design a hybrid streaming strategy that satisfies the 500ms requirement.

3.  What async infrastructure does token-level streaming require that node-level
    does not?

&lt;!–MDXB-9-CLOSE–&gt;

&lt;!–MDXB-13-OPEN–&gt;

**Step 1: Streaming Comparison.**

- **Node-level** (`graph.stream()`): User sees nothing for 2–4 seconds
  (search), then the full search result appears, then nothing for 3–6 seconds
  (generation), then the full answer appears. Total perceived latency: 5–10 seconds
  with two “dead” periods.

- **Token-level** (`astream_events()`): User sees nothing during search
  (no tokens to stream from a tool call), then sees the answer appear word-by-word
  during generation. Perceived latency: 2–4 seconds of silence, then incremental output.

Neither alone satisfies the 500ms requirement.

**Step 2: Hybrid Strategy.**
Combine both streaming levels with UI status indicators:

1.  On message send: immediately show a “Searching…” indicator (UI-side, no agent event needed)—satisfies 500ms.

2.  Subscribe to `astream_events()`: filter for `on_tool_start` to update
    indicator to “Found 3 sources, generating answer…”

3.  Filter for `on_chat_model_stream` to stream tokens into the response area.

4.  On graph completion: remove the indicator, finalize the response.

**Step 3: Async Infrastructure.**
Token-level streaming requires:

- **`AsyncSqliteSaver`** (or async Postgres)—the synchronous
  `SqliteSaver` does not support `astream_events()`.

- An **async event loop** (`asyncio`)—the `async for` pattern
  requires awaitable iteration.

- **WebSocket or SSE** on the frontend—HTTP request/response cannot stream
  individual tokens.

Node-level streaming works with synchronous checkpointers and standard HTTP chunked transfer.

**Key Insight:** Token streaming solves the “generation feels slow” problem but not the
“search feels slow” problem. A production UX needs UI-side status indicators for tool
execution and token streaming for generation—two separate mechanisms combined.

**Answer:** Neither streaming level alone hits 500ms. Use a hybrid: UI-side status
indicators for tool execution + token streaming for generation. Token streaming requires
async checkpointer + async event loop + WebSocket/SSE.

\[advanced\]\[full\]
**Memory Management — When to Prune Conversation History**

Your agent uses a checkpointer with thread-based conversations. After 50 turns, the
`messages` list contains 200+ messages (human, AI, tool calls, tool results).
The LLM’s context window is 128K tokens, and the messages consume 95K tokens—leaving
only 33K for the system prompt, tools, and new generation.

1.  At what point does conversation history become a liability rather than an asset?

2.  Design three pruning strategies with different tradeoffs.

3.  How does LangGraph’s custom reducer pattern enable message pruning without
    losing checkpoint integrity?

&lt;!–MDXB-10-CLOSE–&gt;

&lt;!–MDXB-14-OPEN–&gt;

**Step 1: The Tipping Point.**
History becomes a liability when: (a) it crowds out the generation budget (as here—95K
of 128K consumed), (b) older messages contain outdated information that contradicts recent
context, or (c) the LLM “forgets” recent instructions because they are buried under
hundreds of earlier messages (lost-in-the-middle effect).

**Step 2: Three Pruning Strategies.**

1.  **Sliding window:** Keep only the last *N* message pairs (e.g., last 10 turns).
    Simple, predictable token budget. Risk: loses important early context (the original task).

2.  **Summarize-and-truncate:** Periodically summarize older messages into a single
    summary message, then drop the originals. Preserves key context in compressed form.
    Risk: summary may lose critical details.

3.  **Importance-based:** Score messages by relevance (tool results with data &gt;
    pleasantries). Keep high-importance messages regardless of age, prune low-importance
    ones. Risk: scoring heuristic may misjudge importance.

**Step 3: Custom Reducer for Pruning.**
LangGraph’s custom `reduce_messages` function (from HITL) can be extended for pruning.
Instead of only matching by ID to replace, add a pruning step:

1.  Match by ID (same ID = replace, as before)

2.  After merging, check total message count or token estimate

3.  If over threshold, apply the chosen pruning strategy

4.  Return the pruned list

Because the reducer runs on every state update, pruning happens automatically at each node
execution. The checkpointer stores the pruned state—old messages are gone from future
checkpoints but preserved in historical ones (time travel still works for debugging).

**Key Insight:** The checkpointer stores *every* state snapshot, including
pre-pruning ones. This means pruning is safe—you can always time-travel back to a
checkpoint before pruning occurred. The reducer is the right place for pruning because
it runs automatically and keeps the state consistent.

**Answer:** Prune when history exceeds ∼70% of context window. Use sliding window
(simple), summarize-and-truncate (preserves context), or importance-based (fine-grained).
Implement via custom reducer for automatic, checkpoint-safe pruning.
