&lt;!–MDXB-4-OPEN–&gt;

Chapter 1 established the evaluation problem and decomposed agents into
testable components. But you cannot evaluate what you cannot see. This
chapter adds *observability*: structured traces that record every
router decision, skill invocation, and LLM call. These traces become
the foundation for all evaluation workflows in Chapters 3–5.

&lt;!–MDXB-4-CLOSE–&gt;

# Why Observability Matters



<Sidenote category="interview">"How do you debug a non-deterministic system?" Tracing is the standard answer for LLM-based systems. Show layered thinking.</Sidenote>



Traditional software is deterministic: a stack trace tells you exactly where
something went wrong. Agents break both assumptions—the same query may
trigger different tool sequences on different runs, and failures may be
semantic (wrong answer, not a crash). Print statements cannot scale to this
complexity.

**Observability** means complete visibility into every layer of your
application. For agents, this includes prompts, model responses, token
usage, latency, and the function calls orchestrating behaviour.

&lt;!–MDXB-5-OPEN–&gt;

**Beyond Debugging.**
Traces are not just for fixing bugs. They are the raw material for
evaluation at scale—you can run automated checks over thousands of
traces to detect regressions, measure quality, and monitor cost.

&lt;!–MDXB-5-CLOSE–&gt;



<Sidenote category="pattern">Observability stack: (1) instrument with OTEL, (2) collect with Phoenix, (3) evaluate over traces.</Sidenote>



# Traces and Spans



<Term name="Trace" los="EAA-2.1">
  A complete end-to-end record of a single agent run. Contains one or more spans in a hierarchical tree, linked by a unique trace ID.
</Term>
<AnkiCard type="term" front={"Trace"} back={"A complete end-to-end record of a single agent run. Contains one or more spans in a hierarchical tree, linked by a unique trace ID."} los="EAA-2.1" />





<Term name="Span" los="EAA-2.1">
  An individual step within a trace—an LLM call, tool invocation, or routing decision. Records start time, end time, attributes, and status. Spans nest hierarchically.
</Term>
<AnkiCard type="term" front={"Span"} back={"An individual step within a trace—an LLM call, tool invocation, or routing decision. Records start time, end time, attributes, and status. Spans nest hierarchically."} los="EAA-2.1" />



A trace for the sales agent might contain: an Agent span wrapping the
entire run, Chain spans for each router iteration, Tool spans for skill
invocations, and LLM spans for model calls. Each span records timing,
attributes, and status.



<Sidenote category="formula">Trace depth = nesting levels. Typical agent: 3–4 levels (Agent $$ Chain $$ Tool $$ LLM).</Sidenote>



&lt;!–MDXB-7-OPEN–&gt;

**Core Insight:** The nesting of spans directly reflects the
agent’s architecture. An Agent span wraps the run. Chain spans
represent router iterations. Tool spans represent skill invocations.
LLM spans represent model calls. Reading a trace is like reading the
architecture diagram with real data.

**Why It Matters:** When a trace shows the wrong tool being
called, you examine the Chain span’s LLM call to see what the model
received.

**When It Breaks:** Poorly instrumented agents produce flat
traces that are harder to navigate than print statements.

# OpenTelemetry and Open Inference



<Term name="OpenTelemetry (OTEL)" los="EAA-2.3">
  An open-source observability framework defining standards for traces, spans, metrics, and logs. Vendor-neutral—instrument once, send to any compatible backend.
</Term>
<AnkiCard type="term" front={"OpenTelemetry (OTEL)"} back={"An open-source observability framework defining standards for traces, spans, metrics, and logs. Vendor-neutral—instrument once, send to any compatible backend."} los="EAA-2.3" />



OpenTelemetry<Citation src="opentelemetry2024spec" /> provides the data model,
instrumentation APIs, and collector architecture. For LLM applications, the
**Open Inference** standard (from Arize) adds LLM-specific span kinds
and attribute names for prompts, completions, and token counts.



<Sidenote category="warning">OTEL spans track timing and metadata. Open Inference adds LLM-specific semantics. You need both for meaningful agent traces.</Sidenote>



The four span kinds defined by Open Inference: **Agent** (full run),
**Chain** (router iteration), **Tool** (skill invocation), and
**LLM** (single model call).

# Automatic Instrumentation

The fastest path to tracing is **automatic instrumentation**: a
library hooks into your API client and creates spans for every call
without code changes. For OpenAI, the `OpenAIInstrumentor` does
this in two lines:



```cypher
import phoenix as px
from openinference.instrumentation.openai import OpenAIInstrumentor

px.register(project_name="sales-agent",
            endpoint="http://localhost:6006/v1/traces")
OpenAIInstrumentor().instrument()
# Every client.chat.completions.create() is now traced
```





<Sidenote category="practice">Start with automatic instrumentation for immediate visibility. Add manual spans only where auto-instrumentation leaves gaps.</Sidenote>



Automatic instrumentation captures LLM-level detail (prompts, completions,
tokens) but cannot see your router logic, tool dispatch, or business code.

# Manual Instrumentation

Manual instrumentation gives you control over exactly what gets traced.
The key principle is **outside-in**: start from the outermost layer
(agent run) and work inward. Nesting `with` blocks automatically
produces the correct span hierarchy.



```cypher
from opentelemetry import trace
tracer = trace.get_tracer(__name__)

def run_agent(user_message: str) -> str:
    with tracer.start_as_current_span(
        "Agent Run", openinference_span_kind="agent"
    ) as agent_span:
        while True:
            with tracer.start_as_current_span(
                "Router Iteration", openinference_span_kind="chain"
            ):
                response = client.chat.completions.create(...)
                if not msg.tool_calls:
                    return msg.content
                for tool_call in msg.tool_calls:
                    with tracer.start_as_current_span(
                        tool_call.function.name,
                        openinference_span_kind="tool"
                    ):
                        result = dispatch_tool(tool_call)
```





<Sidenote category="interview">"Show me how you'd add observability to an agent." Demonstrate outside-in: agent span first, then chain, then tool. Shows layered thinking.</Sidenote>



&lt;!–MDXB-8-OPEN–&gt;

**Core Insight:** Automatic instrumentation covers all LLM API
calls with zero code changes. Manual instrumentation adds business-logic
spans. Together, they give full visibility.

**Decision Rule:** Start with automatic for immediate visibility.
Add manual spans where the trace has gaps—typically agent, router,
and tool dispatch layers.

**When It Breaks:** Automatic can produce noise in batch processing.
Manual requires discipline—miss a span and you have a hole.

&lt;!–MDXB-8-CLOSE–&gt;

# Phoenix: Collecting and Visualising Traces

**Phoenix**<Citation src="arize2024phoenix" /> is an open-source observability tool
from Arize that receives OTEL traces, stores them, and provides a visual
interface. It organises traces by **project** and provides trace tree
views, timeline views, span detail inspection, and evaluation integration.



<Sidenote category="crossref">Phoenix evaluation features are covered in Ch 3 (component evals), Ch 4 (trajectory/structured), and Ch 5 (LLM-as-Judge).</Sidenote>



# From Traces to Evaluation

Traces are the **bedrock for evaluation at scale**. Every collected
trace contains full inputs, outputs, and intermediate steps. You can:
(1) build evaluation datasets from real runs, (2) run automated evaluators
over traces, (3) detect regressions by comparing scores across versions,
(4) monitor production quality by sampling live traces.

&lt;!–MDXB-9-OPEN–&gt;

**Core Insight:** Traces are the raw material for every evaluation
workflow. Router evaluations check trace spans. Trajectory evaluations
score step sequences. LLM-as-Judge evaluates span outputs. Without
traces, evaluation requires manual data collection that does not scale.

**Why It Matters:** The investment in tracing pays off
multiplicatively—every trace can be evaluated, compared, monitored.

**When It Breaks:** Traces with missing spans produce incomplete
evaluations. Instrument thoroughly before building eval workflows.

&lt;!–MDXB-9-CLOSE–&gt;



<Sidenote category="formula">Trace storage: $$1–5 KB per span. 10-span agent trace $$ 50 KB. 100K traces/day $$ 5 GB/day.</Sidenote>

&lt;!–MDXB-11-OPEN–&gt;

A customer support agent has: a router selecting from `search_kb`,
`check_order`, and `draft_response`. The `search_kb`
tool makes one LLM call then an API call. The `draft_response` tool
makes two LLM calls (draft + policy check). Draw the span hierarchy for a
trace where the agent calls `search_kb` then `draft_response`.
Which span would you check first if the response violated policy?

&lt;!–MDXB-11-CLOSE–&gt;

&lt;!–MDXB-14-OPEN–&gt;

**Approach:** **Span Hierarchy:**

    Agent Run                          [Agent]
      Router Iteration #1              [Chain]
        LLM: Route Decision            [LLM]
        search_kb                      [Tool]
          LLM: Generate Search Query   [LLM]
          API: Knowledge Base Search   [Tool]
      Router Iteration #2              [Chain]
        LLM: Route Decision            [LLM]
        draft_response                 [Tool]
          LLM: Generate Response       [LLM]
          LLM: Policy Compliance Check [LLM]
      Router Iteration #3              [Chain]
        LLM: Final Answer              [LLM]

**Debugging:** Start at `LLM: Policy Compliance Check`. If
it approved a violating response, the compliance prompt needs revision.
If it flagged the issue but the response was sent anyway, the tool logic
has a bug.

**Key Insight:** Span hierarchy determines your debugging workflow.
Start at the symptom and trace backward through parent spans.

**Answer:** Check `LLM: Policy Compliance Check` first
(child of `draft_response`). If it approved a violating
response, fix the compliance prompt; if it flagged the violation but
the response was sent anyway, the tool’s post-check gating logic is
broken. Trace symptom → parent span back to the agent root.

&lt;!–MDXB-13-OPEN–&gt;

Your sales agent processes 5,000 queries per day. Each trace is stored in
Phoenix. The finance team asks you to attribute LLM costs per skill. From
a sample of 200 traces, you extract the following averages:

| **Skill**          | **Avg LLM Calls** | **Avg Tokens/Call** | **Frequency (%)** |
|:-------------------|:-----------------:|:-------------------:|:-----------------:|
| Data Lookup        |        1.2        |         800         |        45%        |
| Data Analysis      |        1.0        |        1,500        |        35%        |
| Data Visualisation |        2.1        |        2,200        |        20%        |

Assume the router itself uses 1 LLM call of 300 tokens per query, and
the cost is $0.01 per 1,000 tokens.

1.  Calculate the daily LLM cost broken down by: router, each skill,
    and total.

2.  Which skill is the most cost-efficient per query? Which is most
    expensive? By what factor?

3.  Propose a trace-based optimisation that could reduce the most
    expensive skill’s cost by at least 30%.

&lt;!–MDXB-13-CLOSE–&gt;

&lt;!–MDXB-16-OPEN–&gt;

**Approach:** Use trace data to compute per-skill token usage, then
multiply by cost rate and daily volume.

**Step 1: Daily cost breakdown.**

Router: 5, 000 × 1 × 300 = 1, 500, 000 tokens  = $15.00.

Data Lookup: 5, 000 × 0.45 × 1.2 × 800 = 2, 160, 000 tokens  = $21.60.

Data Analysis: 5, 000 × 0.35 × 1.0 × 1, 500 = 2, 625, 000 tokens  = $26.25.

Data Visualisation: 5, 000 × 0.20 × 2.1 × 2, 200 = 4, 620, 000 tokens  = $46.20.

**Total: $109.05/day** ($15.00 router + $21.60 lookup + $26.25 analysis + $46.20 viz).

**Step 2: Cost per query by skill.**

- Lookup: $21.60/2, 250 = $0.0096/query

- Analysis: $26.25/1, 750 = $0.0150/query

- Visualisation: $46.20/1, 000 = $0.0462/query

Visualisation is **4.8x** more expensive per query than Lookup.

**Step 3: Optimisation.**
The visualisation skill makes 2.1 LLM calls per invocation (chart config
extraction + code generation). Inspect traces to determine if the config
extraction step can use a smaller, cheaper model (e.g., GPT-4o-mini for
structured extraction). If the config call uses ∼1,000 of the 2,200
tokens per call, switching it to a 10x cheaper model reduces viz cost by
∼45%.

**Key Insight:** Trace data transforms cost optimisation from
guesswork into data-driven decisions. The per-skill breakdown reveals that
20% of queries (visualisation) account for 42% of skill cost.

**Answer:** $109.05/day total. Visualisation is 4.8x more expensive
per query than lookup. Optimise by using a cheaper model for the config
extraction sub-step.
