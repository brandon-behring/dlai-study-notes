&lt;!–MDXB-4-OPEN–&gt;

You have built LLM applications—prompt chains, RAG pipelines, perhaps
a simple agent. They work in demos, but when you change a prompt, swap a
model, or add a tool, something else breaks. This chapter establishes the
core problem: LLM systems are non-deterministic, so traditional testing
is insufficient. We introduce evaluation-driven development and decompose
agents into independently testable components.

&lt;!–MDXB-4-CLOSE–&gt;

# The Evaluation Problem



<Sidenote category="interview">"How do you test an LLM application?" is a common system design question at ML platform roles. Start with the two-layer distinction.</Sidenote>



John Gilhuly and Aman Khan open the course with an observation that
experienced ML engineers recognise immediately: building an LLM application
is relatively easy, but knowing whether it *works well* is surprisingly
hard. Traditional software testing relies on deterministic inputs and
outputs. LLM systems violate this assumption at their core.

Consider a research agent that searches the web, identifies relevant sources,
collects content, summarises findings, and iterates. Each step involves an
LLM call, and each call can produce different output on every run. A small
change to the summarisation prompt might improve summary quality but cause
the search step to receive poorly formatted queries. Without systematic
evaluation, these regressions hide until they surface in production.



<Sidenote category="warning">Even small prompt changes can cause regressions in unrelated components. Without eval coverage, you won't know until users complain.</Sidenote>



# Model Evaluation vs. System Evaluation

The course distinguishes two fundamentally different layers of evaluation.
**LLM model evaluation** measures an isolated model’s capabilities
using standardised benchmarks—MMLU for general knowledge, HumanEval for
code, GSM8K for math. These are run by model providers and answer: “How
capable is this model in general?”

**LLM system evaluation** measures how well your entire application
performs using real-world, domain-specific data. It answers: “Does my
system solve the user’s actual problem?”



<Term name="LLM Model Evaluation" los="EAA-1.2">
  Evaluation of an isolated LLM using standardised benchmarks. Measures general capability but does not predict performance in a specific application context.
</Term>
<AnkiCard type="term" front={"LLM Model Evaluation"} back={"Evaluation of an isolated LLM using standardised benchmarks. Measures general capability but does not predict performance in a specific application context."} los="EAA-1.2" />





<Term name="LLM System Evaluation" los="EAA-1.2">
  Evaluation of an entire LLM-based application's end-to-end performance using real-world, domain-specific data.
</Term>
<AnkiCard type="term" front={"LLM System Evaluation"} back={"Evaluation of an entire LLM-based application's end-to-end performance using real-world, domain-specific data."} los="EAA-1.2" />





<Sidenote category="formula">Common benchmarks: MMLU (knowledge), HumanEval (code), GSM8K (math). Higher scores $$ better for your specific app.</Sidenote>



| **Dimension** |      **Model Eval**       |       **System Eval**       |
|:--------------|:-------------------------:|:---------------------------:|
| Data source   |  Standardised benchmarks  |       Domain-specific       |
| What’s tested | Isolated model capability |   End-to-end application    |
| Frequency     |  Before model selection   | On every code/prompt change |

&lt;!–MDXB-8-OPEN–&gt;

**Core Insight:** Model evaluation tells you what a model
*can* do. System evaluation tells you what your application
*actually does*. A top-ranked model on MMLU can still produce
a failing application if prompts, retrieval, or tools are poor.

**Why It Matters:** Teams that only do model evaluation ship
applications that “should work” but don’t.

**When It Breaks:** System evaluation requires representative
test data, which is expensive to curate early on. Start with synthetic
test sets and evolve as real data arrives.

&lt;!–MDXB-8-CLOSE–&gt;

# Non-Determinism and the Testing Gap



<Sidenote category="pattern">Traditional testing = "train on a track" (deterministic). LLM testing = "driving through a busy city" (non-deterministic, variable paths).</Sidenote>



The course draws a vivid analogy. Testing traditional software is like a
**train on a track**—given the same input, the system follows a
fixed path to a deterministic output. Testing an LLM system is like
**driving through a busy city**. The same starting point can produce
different routes depending on traffic. Traditional pass/fail assertions
cannot capture this reality.



<Term name="Non-Deterministic Behaviour" los="EAA-1.3">
  The property of LLM systems where identical inputs can produce different outputs across runs. Caused by sampling temperature, floating-point variance, and API-side changes.
</Term>
<AnkiCard type="term" front={"Non-Deterministic Behaviour"} back={"The property of LLM systems where identical inputs can produce different outputs across runs. Caused by sampling temperature, floating-point variance, and API-side changes."} los="EAA-1.3" />



This has concrete consequences: a prompt change that improves average
quality might introduce occasional failures that a single test run misses.
You need **statistical evaluation** over representative datasets,
run on every change.



<Sidenote category="warning">Setting temperature to 0 reduces but does not eliminate variation across API calls. Evaluation must be statistical, not binary.</Sidenote>



# What Is an AI Agent?

&lt;!–MDXB-5-OPEN–&gt;

**Definition.**
An AI agent is a software-based system that can **take actions on
behalf of a user utilising reasoning**. Unlike a simple LLM application,
an agent decides *what* to do next, *which* tool to use, and
*when* to stop—all through LLM-powered reasoning.

&lt;!–MDXB-5-CLOSE–&gt;



<Term name="AI Agent" los="EAA-1.1">
  A software system that takes actions on behalf of a user using reasoning. Composed of three components: reasoning (LLM), routing (tool selection), and action (tool execution).
</Term>
<AnkiCard type="term" front={"AI Agent"} back={"A software system that takes actions on behalf of a user using reasoning. Composed of three components: reasoning (LLM), routing (tool selection), and action (tool execution)."} los="EAA-1.1" />



Agents add a third evaluation layer beyond model and application<Citation src="yao2022react" />. The three
layers of evaluation complexity are:

| **Layer** | **What**    | **Evaluation Challenge**                    |
|:---------:|:------------|:--------------------------------------------|
|     1     | Model       | Fixed benchmarks; handled by provider       |
|     2     | Application | Domain-specific; your prompts + retrieval   |
|     3     | Agent       | Multi-step, dynamic routing, variable paths |



<Sidenote category="interview">When asked "how would you evaluate an agent?" start by naming the three layers. Shows you understand the problem structure before jumping to solutions.</Sidenote>



# Decomposing Agents

The course decomposes every agent into three components. This is not just
architectural convenience—it is an **evaluation strategy**. Each
component has different failure modes and different evaluation criteria.

**The Router** is the agent’s brain—it decides which skill or
function to call. Routers range from rules-based code (deterministic,
limited) to LLM function calling (flexible, non-deterministic)<Citation src="openai2023function" />. The
course uses GPT-4o-mini with function calling.

**Skills** are the agent’s hands—individual capabilities like
querying a database, generating analysis, or creating visualisations.
Each skill may have multiple sub-steps, and each sub-step is an
independent evaluation target.

**Memory and State** is the agent’s notebook—retrieved context,
configuration, and the log of previous execution steps.



<Term name="Router" los="EAA-1.4">
  The agent component that decides which skill to invoke at each step. Can be rules-based, an NLP classifier, or LLM function calling.
</Term>
<AnkiCard type="term" front={"Router"} back={"The agent component that decides which skill to invoke at each step. Can be rules-based, an NLP classifier, or LLM function calling."} los="EAA-1.4" />





<Term name="Skill" los="EAA-1.4">
  An individual capability within an agent. May consist of multiple sub-steps (LLM calls, API calls, code). An entire LLM application can be a single skill in a larger agent.
</Term>
<AnkiCard type="term" front={"Skill"} back={"An individual capability within an agent. May consist of multiple sub-steps (LLM calls, API calls, code). An entire LLM application can be a single skill in a larger agent."} los="EAA-1.4" />





<Sidenote category="pattern">Agent cycle: Router $$ Skill $$ Memory update $$ Router. Each transition is an evaluation boundary.</Sidenote>



## Centralised vs. Distributed Routing

In **centralised routing**, a single router makes all decisions. In
**distributed routing** (LangGraph, OpenAI Swarm), routing logic is
spread across the agent graph. Distributed routing is more flexible but
harder to evaluate because routing decisions occur at multiple points.



<Term name="Distributed Routing" los="EAA-1.6">
  An architecture where routing decisions are distributed across multiple components. More flexible but harder to evaluate because routing logic is spread across the system.
</Term>
<AnkiCard type="term" front={"Distributed Routing"} back={"An architecture where routing decisions are distributed across multiple components. More flexible but harder to evaluate because routing logic is spread across the system."} los="EAA-1.6" />



## The Example Agent

The course builds a **data analysis assistant** over a sales database
with three skills:

- **Data Lookup**: Generates SQL via LLM, executes on DuckDB.

- **Data Analysis**: Single LLM call returning markdown analysis.

- **Data Visualisation**: Two sequential LLM calls—chart
  config extraction via Pydantic<Citation src="pydantic2024docs" />, then Python code generation.



<Sidenote category="formula">End-to-end success $$ P(correct route) $$ P(correct skill output). If each is 90%, end-to-end is 81%.</Sidenote>



&lt;!–MDXB-9-OPEN–&gt;

**Core Insight:** Each component in the agent decomposition
becomes an independent evaluation target. The router is evaluated on
skill selection accuracy. Each skill on output quality. Each sub-step
on its specific correctness criteria.

**Why It Matters:** End-to-end evaluation tells you *that*
the agent failed. Component-wise evaluation tells you *where*
and *why*.

**When It Breaks:** Component-wise evaluation misses interaction
effects. Both component and end-to-end evaluation are needed.

&lt;!–MDXB-9-CLOSE–&gt;

&lt;!–MDXB-11-OPEN–&gt;

**Why interviewers ask this:** Anthropic, Google DeepMind, and Meta
GenAI ask this at L4/L5 AI Engineer screens (70%+ of agent-focused
loops). It gates whether you can move from “built a demo” to “shipped
a production system.”

**What they’re really testing:** Whether you decompose the problem
before proposing metrics. Candidates who jump straight to “accuracy”
reveal they have never debugged a multi-step agent. The interviewer wants
to hear router → skill → end-to-end as independent evaluation
targets, each with distinct failure modes (EAA-1.4).

**Expected depth by level:**

- **IC3/IC4:** Name the three-layer decomposition
  (model/application/agent). Explain why component-wise eval
  localises failures that end-to-end eval misses.

- **IC5+/Staff:** Quantify the multiplicative accuracy
  problem (90% router × 90% skill = 81% e2e), propose
  an evaluation-driven development loop with dataset curation,
  and discuss the cost of false confidence from end-to-end-only
  evaluation.

**Red flag:** “I’d write unit tests for each prompt” — treats
LLM outputs as deterministic, ignores non-determinism (EAA-1.3) and
the need for statistical evaluation over representative datasets.

# Evaluation-Driven Development

&lt;!–MDXB-6-OPEN–&gt;

**The Core Workflow.**
Evaluation-driven development follows three steps on every change:
(1) **Trace** agent execution to capture each step’s inputs and
outputs, (2) **Evaluate** each component against defined criteria,
(3) **Iterate** on the component that scored worst.

&lt;!–MDXB-6-CLOSE–&gt;



<Term name="Evaluation-Driven Development" los="EAA-1.5">
  A methodology where every code or prompt change triggers a systematic evaluation cycle: trace execution, evaluate components, iterate on failures. The LLM analogue of test-driven development.
</Term>
<AnkiCard type="term" front={"Evaluation-Driven Development"} back={"A methodology where every code or prompt change triggers a systematic evaluation cycle: trace execution, evaluate components, iterate on failures. The LLM analogue of test-driven development."} los="EAA-1.5" />



The course introduces five supporting tools<Citation src="arize2024phoenix" />: trace
instrumentation, an eval runner (including LLM-as-a-judge), datasets for
repeatable experiments, human feedback and annotations, and a prompt playground
for rapid iteration.



<Sidenote category="crossref">vol6 Ch 8: Agents—evaluation methodology follows the same trace-evaluate-iterate loop.</Sidenote>



&lt;!–MDXB-10-OPEN–&gt;

**Core Insight:** Evaluation-driven development treats eval runs
as the primary feedback loop during development, not as a gate before
deployment. Every change triggers: trace → evaluate → iterate.

**Why It Matters:** Teams that evaluate only before deployment
catch regressions too late.

**When It Breaks:** Requires representative test data and
well-calibrated evaluators. Poorly calibrated evaluators give false
confidence.

&lt;!–MDXB-10-CLOSE–&gt;



<Sidenote category="practice">Build the habit: every prompt change triggers a full eval run. No exceptions. Regressions hide in the runs you skip.</Sidenote>

&lt;!–MDXB-13-OPEN–&gt;

A customer support agent can: (1) look up order status, (2) check return
eligibility, (3) escalate to a human, (4) generate responses. It uses
GPT-4o function calling for routing. Identify the router, skills, and
memory/state. Which component would you evaluate first?

&lt;!–MDXB-13-CLOSE–&gt;

&lt;!–MDXB-16-OPEN–&gt;

**Approach:** **Router:** GPT-4o with function calling, deciding among 4 skills.

**Skills:** Order lookup, return eligibility, escalation, response
generation.

**Memory/State:** Full conversation history (message-passing).

**Priority:** Evaluate the **router first**. If it selects the
wrong skill, everything downstream is wasted. Create a labelled dataset
of customer messages with expected skill selections and measure per-category
routing accuracy.

**Key Insight:** 40–60% of agent failures originate in routing.
Catching routing errors early is cheaper than debugging downstream effects.

**Answer:**

- **Router:** GPT-4o function calling, choosing among the 4 skills.

- **Skills:** order lookup, return eligibility, escalation, response generation.

- **Memory/State:** full conversation history (message-passing).

- **Evaluate first:** the router. Routing errors cascade and cost the most to debug downstream.

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-14-OPEN–&gt;

Your team has deployed a customer-support agent that retrieves knowledge-base
articles, drafts a response, and optionally escalates to a human. The PM asks
you to “evaluate the agent.” Outline a three-layer evaluation plan that
covers the model, application, and agent levels, naming one concrete metric
and one test case at each layer.

&lt;!–MDXB-14-CLOSE–&gt;

&lt;!–MDXB-17-OPEN–&gt;

**Approach:** Map each evaluation layer to the agent’s architecture.

**Model layer:** Measure the LLM’s factual accuracy on a curated set of
50 knowledge-base questions (metric: exact-match accuracy). Test case: verify
the model returns the correct refund policy paragraph for “How do I get a
refund?”

**Application layer:** Evaluate the RAG retrieval pipeline’s relevance
(metric: NDCG@5 over 100 query–document pairs). Test case: for the query
“shipping delay,” the top-3 retrieved articles should all be from the
Shipping FAQ category.

**Agent layer:** Measure end-to-end task completion across multi-turn
trajectories (metric: resolution rate within 3 turns). Test case: a simulated
user asks about a lost package, provides an order number, and the agent
correctly escalates after confirming the package is genuinely missing.

**Key Insight:** Each layer catches different failure modes—a perfect
model can still fail at the agent level if tool selection or escalation logic
is broken.

**Answer:** Three layers: model (exact-match accuracy on QA),
application (NDCG@5 on retrieval), agent (resolution rate on trajectories).
