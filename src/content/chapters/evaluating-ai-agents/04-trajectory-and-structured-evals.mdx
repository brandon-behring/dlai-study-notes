&lt;!–MDXB-3-OPEN–&gt;

Chapter 3 evaluated components in isolation. But a correct final answer
can mask wasteful trajectories—calling 5 tools when 2 suffice. This
chapter shifts from “what did the agent produce?” to “how did it get
there?” We then introduce the structured experimentation framework that
turns isolated evaluations into a repeatable development process.

&lt;!–MDXB-3-CLOSE–&gt;

# What Is a Trajectory?



<Term name="Trajectory" los="EAA-4.1">
  The ordered sequence of all steps (router decisions, tool calls, LLM completions) from input to final response. Captures not just what the agent produced but how it arrived there.
</Term>
<AnkiCard type="term" front={"Trajectory"} back={"The ordered sequence of all steps (router decisions, tool calls, LLM completions) from input to final response. Captures not just what the agent produced but how it arrived there."} los="EAA-4.1" />





<Sidenote category="interview">"Why evaluate trajectories?" Correct answers taking 10 steps instead of 3 cost 3$$ more in LLM calls and introduce 3$$ more variance.</Sidenote>



Two agents can produce the same correct answer through radically different
paths<Citation src="yao2022react" />. The longer path means more LLM calls, more latency,
more cost, and more opportunities for stochastic failure. At scale, this
difference determines viability.



<Sidenote category="warning">Correct answer $$ efficient trajectory. An agent producing correct outputs can still be unusable at $0.03/step $$ 10 steps per query.</Sidenote>



# Convergence Scoring



<Term name="Convergence Score" los="EAA-4.2">
  A metric in $[0, 1]$ measuring the fraction of agent runs that follow the optimal (minimum-step) path. Computed by running similar queries, finding the minimum step count, and calculating the proportion of runs matching that minimum.
</Term>
<AnkiCard type="term" front={"Convergence Score"} back={"A metric in $[0, 1]$ measuring the fraction of agent runs that follow the optimal (minimum-step) path. Computed by running similar queries, finding the minimum step count, and calculating the proportion of runs matching that minimum."} los="EAA-4.2" />



$$\text{Convergence} = \frac{\|\\r \in R : \text{steps}(r) = \min\_{r'} \text{steps}(r')\\\|}{\|R\|}$$



<Sidenote category="formula">Convergence $= \{runs at min steps\} \{total completed runs\}$; 1.0 = perfectly consistent.</Sidenote>





<Sidenote category="pattern">Interpretation: $ 0.8$ = stable; $0.5$–$0.8$ = investigate; $< 0.5$ = unreliable, needs fix.</Sidenote>



## Limitations

Convergence has three structural blind spots:

1.  **Universal unnecessary steps**: If every run includes the
    same waste, the minimum includes it and convergence reports 1.0.

2.  **Errored runs**: Partial runs that crash after 2 steps
    would falsely lower the minimum. Always filter to completed runs.

3.  **Parallel tool calls**: If the agent calls 3 tools in one
    step, is that 1 step or 3? Define a counting convention and apply
    uniformly.

&lt;!–MDXB-5-OPEN–&gt;

**Core Insight:** A convergence score of 1.0 means the agent
always takes the *same* path—not necessarily the *correct*
path. Pair with per-step correctness evals from Ch 3.

**Why It Matters:** High convergence on the wrong path is worse
than low convergence with some correct runs.

**When It Breaks:** Convergence cannot detect waste present in
every run. Cross-check with domain experts.

&lt;!–MDXB-5-CLOSE–&gt;

&lt;!–MDXB-8-OPEN–&gt;

**Why interviewers ask this:** Anthropic (Research Engineer),
Google DeepMind (L5+ SWE-ML), and Stripe (Staff ML) use trajectory
and dataset design questions to test whether candidates can build

in system design rounds for agent-focused roles (40%+ of loops).

**What they’re really testing:** Whether you distinguish
consistency from correctness. Candidates who cite high convergence as
proof of reliability miss that convergence 1.0 on the wrong path is
the worst outcome (EAA-4.2). The interviewer wants to hear: trajectory
eval for efficiency, component eval for correctness, and a structured
experiments framework (dataset → task → evaluators, EAA-4.3)
that enables repeatable comparison across agent variants (EAA-4.5).

**Expected depth by level:**

- **IC3/IC4:** Define trajectory evaluation and explain
  why step count matters for cost. Describe the “comprehensive,
  not exhaustive” dataset principle (EAA-4.4) with input keys
  and output keys.

- **IC5+/Staff:** Design a multi-evaluator experiment
  comparing agent variants on a dashboard, explain the
  production feedback flywheel (EAA-4.6), and discuss how to
  prevent convergence from masking correctness regressions by
  composing trajectory and per-step evaluators.

**Red flag:** “High convergence score means the agent is
reliable” — confuses path consistency with path correctness, and
misses that universal waste inflates convergence to 1.0.

# Phoenix Experiments Framework



<Term name="Experiment" los="EAA-4.3">
  A structured evaluation run in Phoenix: execute a task function against every row in a dataset, record outputs, apply evaluator functions. Named and versioned for comparison.
</Term>
<AnkiCard type="term" front={"Experiment"} back={"A structured evaluation run in Phoenix: execute a task function against every row in a dataset, record outputs, apply evaluator functions. Named and versioned for comparison."} los="EAA-4.3" />



The Experiments workflow<Citation src="arize2024phoenix" /> has four stages:

1.  **Create Dataset**: Upload test cases with input keys and
    (optionally) output keys via `upload_dataset()`.

2.  **Define Task**: A function taking one dataset row, running
    the agent, returning output + metadata.

3.  **Run Experiment**: `run_experiment()` iterates over
    the dataset, manages parallelism and errors.

4.  **Apply Evaluators**: Functions decorated with
    `@create_evaluator` score each result.



<Sidenote category="formula">Pipeline: `upload_dataset()` $$ `run_experiment()` $$ `evaluate_experiment()`.</Sidenote>





<Sidenote category="interview">Phoenix Experiments $$ pytest fixtures + parametrize. Dataset = test cases, task = test function, evaluator = assertion.</Sidenote>



# Evaluation-Driven Development

The EDD cycle has four phases: (1) **Curate** a dataset, (2) **Run**
test cases through agent variants, (3) **Evaluate** with composed
evaluators, (4) **Compare** scores on a dashboard.



<Term name="Evaluation Dataset" los="EAA-4.4">
  A structured collection of test cases with input keys (forwarded to the agent) and output keys (forwarded to evaluators for comparison). "Comprehensive, not exhaustive"—1–2 examples per input type.
</Term>
<AnkiCard type="term" front={"Evaluation Dataset"} back={"A structured collection of test cases with input keys (forwarded to the agent) and output keys (forwarded to evaluators for comparison). \"Comprehensive, not exhaustive\"—1–2 examples per input type."} los="EAA-4.4" />





<Sidenote category="warning">"Comprehensive, not exhaustive." Resist adding 100 cases per category. 1–2 per type is the sweet spot for iteration speed.</Sidenote>



Three sources feed the dataset: manually constructed (for edge cases),
model-generated (for coverage), and production-sampled (highest ecological
validity). Including expected outputs wherever possible unlocks code-based
evaluators.

## Agent Variant Experimentation

Five primary levers for improving an agent: prompts, tool definitions,
router logic, skill structure, and model selection. Change one lever at a
time to isolate effects.



<Sidenote category="pattern">Change one lever at a time. If you modify prompt *and* model simultaneously, you cannot attribute improvements.</Sidenote>



# Composing Evaluators

No single evaluator captures the full picture. The course composes five
evaluators: function calling correctness, SQL result accuracy, clarity
(LLM-as-judge), entity correctness, and code runnability.



```cypher
results = run_experiment(
    dataset=dataset,
    task=run_agent,
    evaluators=[
        eval_function_calling,
        eval_sql_result,
        eval_clarity,
    ],
)
```

The experiment dashboard is the core decision artifact:

| **Variant**     | **Routing** | **SQL** | **Clarity** | **Runnable** |     |
|:----------------|:-----------:|:-------:|:-----------:|:------------:|:---:|
| V1 (baseline)   |    0.82     |  0.75   |    0.88     |     0.95     |     |
| V2 (new prompt) |    0.85     |  0.78   |    0.91     |     0.95     |     |
| V3 (new model)  |    0.90     |  0.82   |    0.86     |     0.90     |     |

&lt;!–MDXB-6-OPEN–&gt;

**Core Insight:** Comparing across multiple dimensions
simultaneously reveals tradeoffs that a single metric masks. V3
improves correctness but regresses on clarity and runnability.

**Why It Matters:** Shipping decisions require holistic assessment.

**When It Breaks:** If evaluators are too coarse (binary pass/fail),
the dashboard cannot capture nuanced differences.

# The Production Feedback Flywheel



<Term name="Evaluation Flywheel" los="EAA-4.6">
  A self-reinforcing cycle: production traces $$ new test cases $$ updated evaluators $$ agent improvements $$ better production data.
</Term>
<AnkiCard type="term" front={"Evaluation Flywheel"} back={"A self-reinforcing cycle: production traces $$ new test cases $$ updated evaluators $$ agent improvements $$ better production data."} los="EAA-4.6" />



The flywheel connects production data, new test cases, updated evaluators,
and agent improvements in a continuous cycle. The key engineering challenge
is speed: if promoting a production trace into the dataset takes a week of
manual review, the flywheel stalls.

&lt;!–MDXB-7-OPEN–&gt;

**Core Insight:** The flywheel is only as fast as its slowest
stage. Automate trace-to-dataset promotion, annotation, and evaluator
updates.

**Why It Matters:** Teams that automate iterate 10× faster.

**When It Breaks:** Noisy production data (bots, adversarial
inputs) entering unfiltered degrades evaluation quality.

# Practice Problems

&lt;!–MDXB-9-OPEN–&gt;

An agent handles “return item” requests. 12 runs yield step counts:
4, 6, 4, 4, 8, 4, 4, 4, 6, 4, 4, 6.

1.  Calculate convergence.

2.  Exclude run 5 (errored) and recalculate.

3.  What percentage of LLM cost is wasted on non-optimal runs?

&lt;!–MDXB-9-CLOSE–&gt;

&lt;!–MDXB-12-OPEN–&gt;

**Approach:**

1.  Min = 4. Runs at min: 8 of 12. Convergence = 8/12 = 0.667.

2.  11 runs, min still 4, 8 at min. 8/11 = 0.727.

3.  Total steps = 58. Optimal = 12 × 4 = 48. Waste = 10 of 58, about 17 percent.

**Key Insight:** A convergence of 0.667 implies roughly 17 percent
cost waste on non-optimal runs. At 10K queries/day and $0.03 per step,
that is about $180/day wasted.

**Answer:**

1.  Convergence = 8/12 = 0.667 (8 runs at the 4-step minimum).

2.  Excluding errored run 5: 8/11 = 0.727.

3.  About 17% of LLM cost wasted on non-optimal runs (10 wasted steps out of 58 total); ≈$180/day at 10K queries/day, $0.03/step.

&lt;!–MDXB-11-OPEN–&gt;

Your sales agent is adding a fourth skill: `forecast_revenue`,
which takes a date range and product category, generates a SQL query for
historical data, then produces a markdown forecast with confidence
intervals. The team needs to create an evaluation dataset before shipping.

1.  Design the dataset schema (input keys and output keys) for this
    skill. Include at least 5 fields and explain why each is needed.

2.  Following the “comprehensive, not exhaustive” principle,
    specify the minimum number of test cases and their distribution
    across input categories.

3.  Define three evaluators for this skill. For each, state whether
    it is code-based or LLM-as-a-judge and what it measures.

&lt;!–MDXB-11-CLOSE–&gt;

&lt;!–MDXB-14-OPEN–&gt;

**Approach:** Apply the Phoenix Experiments dataset design pattern
from the course, covering input diversity and multi-evaluator composition.

**Step 1: Schema.**

- `query` (input key): The natural language forecast request
  (e.g., “Forecast Q4 revenue for electronics”). Needed: forwards
  to the agent.

- `date_range` (input key): Expected date range the agent
  should extract (e.g., “2025-10-01 to 2025-12-31”). Needed:
  parameter extraction eval.

- `category` (input key): Product category for grouping
  error analysis (e.g., “electronics,” “apparel”).

- `expected_sql_tables` (output key): Tables the SQL
  should query (e.g., `["sales", "products"]`). Needed:
  code-based SQL eval.

- `expected_trend_direction` (output key): Whether the
  forecast should show growth, decline, or flat (e.g., “growth”).
  Needed: LLM judge correctness eval.

- `historical_data_snapshot` (output key): Ground-truth
  data for the date range. Needed: verify the agent queried the
  correct data.

**Step 2: Dataset distribution.**

| **Category**  | **Cases** |            **Purpose**            |
|:--------------|:---------:|:---------------------------------:|
| Electronics   |     2     |   Normal category, growth trend   |
| Apparel       |     2     | Normal category, seasonal pattern |
| New category  |     2     |     Category with sparse data     |
| Invalid range |     1     |  Future-only range (no history)   |
| Ambiguous     |     1     |    “Next quarter” without year    |
| **Total**     |   **8**   |   Comprehensive, not exhaustive   |

**Step 3: Three evaluators.**

1.  **SQL Table Check** (code-based): Assert that the generated
    SQL references the expected tables. Measures: correct data sourcing.

2.  **Forecast Direction** (LLM-as-a-judge): Judge reads the
    markdown forecast and classifies trend as “growth,” “decline,”
    or “flat.” Compare against `expected_trend_direction`.
    Measures: analytical correctness.

3.  **Confidence Interval Presence** (code-based): Regex check
    that the output contains confidence interval notation (e.g.,
    “±” or “95% CI”). Measures: output completeness.

**Key Insight:** The dataset schema must include output keys that
enable code-based evaluation wherever possible. Including
`expected_sql_tables` converts what would be an expensive LLM
judge call into a free string comparison.

**Answer:** 6-field schema with 3 input + 3 output keys. 8 test
cases across 5 categories. 3 evaluators: 2 code-based (SQL tables,
CI presence) + 1 LLM judge (trend direction).

&lt;!–MDXB-15-OPEN–&gt;

\[EAA-4.1, EAA-4.5\]
Your team ships a V2 agent with a new prompt that achieves a convergence
score of 0.95 (up from 0.72 in V1). V2 consistently completes queries in
3 steps vs. V1’s variable 3–7 steps. The dashboard shows improvement on
every trajectory metric. Two weeks after deployment, users report that the
agent’s SQL queries return stale data. Investigation reveals that V2 skips
the `data_lookup` skill entirely and generates analysis from cached
context—producing fast, consistent, but outdated answers.

**Question 1:** V2’s convergence score is near-perfect. Explain why
high convergence masked a correctness regression. What additional evaluator
would have caught this?

**Question 2:** Using the experiment dashboard below, determine which
variant you would ship and why.

| **Variant** | **Convergence** | **SQL Accuracy** | **Freshness** | **Latency (s)** |
|:---|:--:|:--:|:--:|:--:|
| V1 (baseline) | 0.72 | 0.85 | 100% | 3.1 |
| V2 (new prompt) | 0.95 | 0.40 | 12% | 1.4 |
| V3 (hybrid) | 0.83 | 0.82 | 95% | 2.6 |

**Question 3:** Design a “freshness” evaluator that could be added
to the Phoenix Experiments framework to prevent this class of regression.

**Answer Rubric:**

- **Q1:** High convergence measures whether the agent reaches a *stable* answer in few steps, not whether the answer is *correct*. V2 converges fast because it skips the data lookup entirely and generates from cached context—a consistently wrong shortcut that convergence rewards. A *factual accuracy* evaluator comparing outputs against ground-truth query results would have caught the regression.

- **Q2:** Ship V3 (hybrid): it recovers 95% freshness and 0.82 SQL accuracy (close to V1 baseline) while still improving convergence to 0.83 and reducing latency by 16%. V2 is disqualified by its 12% freshness and 0.40 SQL accuracy—no latency gain justifies serving stale data.

- **Q3:** Add a freshness evaluator that checks each agent response’s trajectory for a `data_lookup` tool call; when present, compare the query timestamp against the data source’s last-updated timestamp and flag any response where the data is older than a configurable threshold (e.g., 1 hour). Responses that skip `data_lookup` entirely when the query requires live data should auto-fail.
