&lt;!–MDXB-3-OPEN–&gt;

Chapter 4 introduced structured experimentation and the evaluation
dashboard. But one question remains: *how accurate are the
evaluators themselves?* This chapter tackles meta-evaluation, then
extends the framework into production with golden datasets, monitoring,
and the self-improving pipeline.

&lt;!–MDXB-3-CLOSE–&gt;

# Meta-Evaluation: Evaluating the Evaluator



<Sidenote category="interview">"How do you know your LLM evaluator is accurate?" Meta-evaluation: run both code-based and LLM judge on the same data, measure agreement.</Sidenote>





<Term name="Meta-Evaluation" los="EAA-5.1">
  Evaluating an evaluator's accuracy by comparing its judgments against known ground truth. Quantified by agreement rate between the LLM judge and a deterministic reference evaluator.
</Term>
<AnkiCard type="term" front={"Meta-Evaluation"} back={"Evaluating an evaluator's accuracy by comparing its judgments against known ground truth. Quantified by agreement rate between the LLM judge and a deterministic reference evaluator."} los="EAA-5.1" />





<Term name="Agreement Rate" los="EAA-5.1">
  The fraction of cases where the LLM judge produces the same label as the ground-truth evaluator. Target: $ 0.90$.
</Term>
<AnkiCard type="term" front={"Agreement Rate"} back={"The fraction of cases where the LLM judge produces the same label as the ground-truth evaluator. Target: $ 0.90$."} los="EAA-5.1" />



The protocol<Citation src="zheng2023judging" />: (1) select cases with deterministic
expected outputs, (2) run a code-based evaluator (100% accurate by
construction), (3) run the LLM judge on the same cases, (4) compute agreement.



<Sidenote category="formula">Agreement rate = $\{judge matches code eval\} \{total cases\}$. Below 85% = do not ship the judge.</Sidenote>



&lt;!–MDXB-5-OPEN–&gt;

**Core Insight:** You cannot measure LLM judge accuracy without
a deterministic reference. The code-based evaluator on ground-truth
data provides that reference.

**Why It Matters:** A dashboard showing “92% accuracy” means
nothing if the judge itself is only 75% accurate.

**When It Breaks:** For purely subjective dimensions (tone,
creativity), inter-annotator agreement with humans replaces code-based
meta-evaluation.

&lt;!–MDXB-5-CLOSE–&gt;

&lt;!–MDXB-9-OPEN–&gt;

**Why interviewers ask this:** Anthropic (Applied Research, all
levels), Google (L5+ Trust & Safety ML), and OpenAI (Research
Engineer) ask about evaluator reliability to test whether candidates
understand that the evaluation layer itself can fail. Asked in 55%+
of safety-aware ML loops as a follow-up to “how would you evaluate
an agent?”

**What they’re really testing:** Whether you recognise that an
LLM judge can conflate helpfulness (polite, well-structured) with
faithfulness (factually correct). The meta-signal: candidates who
propose meta-evaluation—comparing judge labels against code-based
ground truth (EAA-5.1)—and track false positive rate separately
from agreement rate demonstrate they have shipped evaluators that
actually work. Those who also describe the golden dataset as a CI
shipping gate (EAA-5.3) show production maturity.

**Expected depth by level:**

- **IC3/IC4:** Explain meta-evaluation protocol (ground
  truth → code eval → LLM judge → agreement rate).
  State the 85%+ agreement threshold and why numeric judge
  scores fail (EAA-5.2).

- **IC5+/Staff:** Design the full self-improving pipeline
  (EAA-5.5): production traces → feedback filter →
  dataset augmentation → CI experiments → golden dataset
  gate. Discuss feedback poisoning risks and asymmetric error
  analysis (FPR vs. FNR).

**Red flag:** “Our LLM judge reports 94% accuracy so the agent
is production-ready” — uses the judge’s own score as validation,
with no independent ground truth or meta-evaluation.

&lt;!–MDXB-9-CLOSE–&gt;



<Sidenote category="warning">A 70% agreement rate means 30% of evaluations are wrong. Enough to mask real regressions or flag false improvements.</Sidenote>



# Improving LLM Judge Accuracy

Four techniques, each targeting a different failure mode:

**1. Prompt Engineering**: Reword the judge prompt—make criteria
explicit, specify output format strictly, add chain-of-thought. Simplest
and often most effective.

**2. Few-Shot Examples**: Add 3–5 examples of correct judgments
covering boundary cases (e.g., case-insensitive match, floating-point
tolerance).

**3. Model Selection**: Swap the judge model. GPT-4o at $0.01/eval
may agree 95%; GPT-3.5 at $0.001 may agree 82%.

**4. Semantic Similarity**: For non-binary outputs, use embedding
cosine distance instead of exact string comparison<Citation src="schick2023toolformer" />.

&lt;!–MDXB-6-OPEN–&gt;

**Core Insight:** Prompt engineering, few-shot, model selection,
and semantic similarity target different failure modes. The agreement
rate is the single metric that tells you if any worked.

**Why It Matters:** Each lever targets a specific failure. Prompt
fixes misunderstood criteria. Few-shot fixes calibration. Model
selection fixes capability gaps. Semantic similarity fixes false
negatives on paraphrases.

**When It Breaks:** Stacking all four simultaneously makes
attribution hard. Apply one at a time.

&lt;!–MDXB-6-CLOSE–&gt;



<Sidenote category="pattern">Meta-eval protocol: ground-truth subset $$ code eval as oracle $$ LLM judge $$ agreement rate. Repeat after every judge change.</Sidenote>





<Sidenote category="interview">"How would you debug a low-accuracy LLM judge?" Start with the prompt. 80% of judge failures are prompt failures.</Sidenote>



# Golden Datasets



<Term name="Golden Dataset" los="EAA-5.3">
  A curated evaluation dataset capturing critical use cases and known failure modes. Used as a shipping gate: every agent change must pass before deployment.
</Term>
<AnkiCard type="term" front={"Golden Dataset"} back={"A curated evaluation dataset capturing critical use cases and known failure modes. Used as a shipping gate: every agent change must pass before deployment."} los="EAA-5.3" />



The golden dataset differs from general evaluation datasets:
(1) curated for criticality—every row is a must-pass scenario,
(2) includes known failure modes codified from past production bugs,
(3) grows continuously as new failures are discovered.



<Sidenote category="pattern">Golden dataset as CI gate: every PR modifying agent code triggers a run. Any regression blocks the merge.</Sidenote>



Because agent tests are probabilistic, teams run golden dataset evaluations
multiple times and use the median or worst score with tolerance bands.

&lt;!–MDXB-7-OPEN–&gt;

**Core Insight:** A golden dataset grows with every production
failure and new use case. Its value compounds over time.

**Why It Matters:** Encodes institutional knowledge. New team
members inherit it through the CI gate.

**When It Breaks:** If too large (&gt;100 rows), run times become
prohibitive. Periodically prune rows that never triggered regressions.

&lt;!–MDXB-7-CLOSE–&gt;

# Production Monitoring

Production reveals failure modes no dataset anticipated: unseen queries,
new entities, API degradations, distribution shifts. The development tools
(tracing, annotations) carry directly into production, enriched by real
user data.



<Sidenote category="warning">Most dangerous production failure: *silent regression*. Plausible-looking but wrong answers. Only monitoring with evaluators catches this.</Sidenote>



Key production metrics:

- **Evaluator scores**: Running averages per dimension.

- **Convergence scores**: Steps to terminal state.

- **LLM call counts**: Unexpected increases signal loops.

- **Latency**: End-to-end, broken by component.

- **Cost**: Dollar cost per query, per model, per skill.



<Sidenote category="formula">Alert thresholds: eval scores, convergence, LLM calls/query, p50/p99 latency, cost/query. Alert on $>$10% deviation.</Sidenote>





<Sidenote category="crossref">Tracing from Ch 2 carries directly into production. Phoenix works identically in dev and prod.</Sidenote>



# The Self-Improving Agent Pipeline



<Term name="Self-Improving Agent" los="EAA-5.5">
  An automated pipeline where production feedback continuously updates evaluation datasets, triggers CI/CD experiments, and refines the agent with minimal human intervention.
</Term>
<AnkiCard type="term" front={"Self-Improving Agent"} back={"An automated pipeline where production feedback continuously updates evaluation datasets, triggers CI/CD experiments, and refines the agent with minimal human intervention."} los="EAA-5.5" />



Five stages<Citation src="arize2024phoenix" />: (1) collect user feedback, (2) augment
evaluation dataset with successful and failed interactions, (3) run CI/CD
experiments on every dataset update, (4) incorporate few-shot examples from
collected data, (5) gate deployment via golden dataset.

&lt;!–MDXB-8-OPEN–&gt;

**Core Insight:** The pipeline transforms evaluation from periodic
manual effort into continuous automated process. Each interaction makes
the system incrementally better.

**Why It Matters:** Teams with automated pipelines iterate orders
of magnitude faster.

**When It Breaks:** Automation without quality gates is dangerous.
Noisy or adversarial feedback can poison the dataset. Human review is
a necessary safety valve.

&lt;!–MDXB-8-CLOSE–&gt;



<Sidenote category="interview">"Describe a self-improving agent system." Walk through all five stages. Emphasize the automated feedback loop and golden dataset gate.</Sidenote>



# Practice Problems

&lt;!–MDXB-10-OPEN–&gt;

Your LLM judge scores code correctness by prompting a model to assess
generated code. You suspect it is too lenient. Design a meta-evaluation:

1.  ground-truth evaluator,

2.  dataset requirements,

3.  agreement metric,

4.  acceptance threshold.

&lt;!–MDXB-10-CLOSE–&gt;

&lt;!–MDXB-12-OPEN–&gt;

**Approach:**

1.  Execute code in sandbox, compare actual vs. expected output. 100% accurate by construction.

2.  40–50 rows: correct code, syntax errors, subtle logic bugs (30%+ of dataset—where leniency manifests), edge case failures.

3.  Binary agreement rate, plus false positive rate (judge says correct, code fails). FPR is the leniency metric.

4.  Overall agreement ≥ 85% *and* FPR ≤ 10%.

**Key Insight:** A single agreement rate can mask asymmetric errors.
Breaking into FP and FN reveals whether the judge is too lenient or strict.

**Answer:**

1.  Ground truth: sandboxed code execution comparing actual to expected output (100% accurate by construction).

2.  Dataset: 40–50 rows mixing correct code, syntax errors, subtle logic bugs (≥30% to surface leniency), and edge-case failures.

3.  Metrics: binary agreement rate plus false-positive rate (judge accepts code that fails)—FPR is the leniency signal.

4.  Acceptance: overall agreement ≥85% *and* FPR ≤10%.

&lt;!–MDXB-12-CLOSE–&gt;

&lt;!–MDXB-11-OPEN–&gt;

Your agent handles payment processing, account security, and data export.
Define:

1.  minimum golden dataset composition,

2.  pass/fail criteria,

3.  evolution over 3 months.

&lt;!–MDXB-11-CLOSE–&gt;

&lt;!–MDXB-13-OPEN–&gt;

**Approach:**

1.  5 rows × 3 workflows = 15 core. 2 rows × 3 known failures = 6. 3 cross-workflow rows. Total: 24 minimum.

2.  100% pass on payment/security (zero tolerance). ≥90% on data export. ≥0.85 LLM clarity. Run 3×, take worst score.

3.  Month 1: add every production bug (5–10 rows). Month 2: prune never-triggered rows, add new features. Month 3: stabilize at 40–60 rows with quarterly review.

**Key Insight:** Asymmetric thresholds—zero tolerance on
safety-critical, softer on lower stakes.

**Answer:**

1.  24 rows minimum: 5 happy-path × 3 workflows = 15, plus 2 known-failure × 3 = 6, plus 3 cross-workflow rows.

2.  Pass thresholds: 100% on payment/security (zero tolerance), ≥90% on data export, ≥0.85 LLM clarity. Run 3× and take the worst score.

3.  Month 1: capture every production bug (5–10 rows). Month 2: prune never-triggered rows, add new features. Month 3: stabilise at 40–60 rows with quarterly review.

**Case Study: The Lenient Judge Disaster**

Your team ships an LLM judge for a customer support agent that classifies
responses as “helpful” or “not helpful.” After two weeks in production,
CSAT scores drop 15% despite the judge reporting 94% helpfulness. A manual
audit of 50 production traces reveals the judge marks 40% of incorrect
answers as “helpful” because they are polite and well-structured.

| **Metric**                   | **Judge Reports** | **Manual Audit** |
|:-----------------------------|:------------------|:-----------------|
| Helpfulness                  | 94%               | 67%              |
| False positive rate          | unknown           | 40%              |
| False negative rate          | unknown           | 3%               |
| Agreement (judge vs. manual) | —                 | 72%              |

1.  What meta-evaluation failure allowed this to ship? Design the
    meta-evaluation that would have caught it.

2.  The judge has a 40% FPR but only 3% FNR. What does this
    asymmetry reveal about the judge prompt?

3.  Propose two changes (one prompt-level, one architectural) to fix
    the judge without replacing the model.

&lt;!–MDXB-14-OPEN–&gt;

**Approach:** **1.** No meta-evaluation was run before shipping. The 94% metric was
the judge’s self-reported score, not validated against ground truth. Fix:
build a 50-row ground-truth dataset with code-verifiable outcomes (e.g.,
did the agent return the correct order status?). Run the judge against this
dataset and require ≥85% agreement and ≤10% FPR before
shipping.

**2.** The judge conflates politeness/structure with correctness. It
is biased toward surface-level quality signals and ignores factual
accuracy. The prompt likely says “evaluate helpfulness” without defining
that helpfulness requires factual correctness.

**3.** Prompt fix: Add explicit criterion: “A response is helpful
ONLY if the factual content is correct. A polite but incorrect answer
scores 0.” Add 3 few-shot examples of polite-but-wrong responses scored
as “not helpful.” Architectural fix: Add a code-based evaluator that
checks factual claims against the knowledge base, run in parallel with the
LLM judge. Flag disagreements for human review.

**Key Insight:** Agreement rate alone can mask asymmetric errors.
Always compute FPR and FNR separately. A judge with 40% FPR is
operationally useless for quality gating.

**Answer:**

1.  No meta-evaluation was run before shipping; 94% was the judge’s self-reported score, not validated against ground truth. Build a 50-row code-verifiable dataset and require ≥85% agreement / ≤10% FPR.

2.  The judge conflated politeness/structure with correctness. The prompt asked for “helpfulness” without anchoring it to factual accuracy.

3.  Prompt fix: “A response is helpful ONLY if its factual content is correct. A polite but incorrect answer scores 0.” Plus 3 few-shot examples of polite-but-wrong → “not helpful”. Architectural fix: parallel code-based evaluator that checks factual claims against the knowledge base; flag any LLM/code disagreement for human review.

&lt;!–MDXB-14-CLOSE–&gt;

**Case Study: Golden Dataset Rot**

A payment processing agent has a golden dataset of 45 rows that was
curated 6 months ago. The team runs it as a CI gate on every PR. Last
quarter, 3 production incidents occurred—all involving features added
after the golden dataset was frozen. The golden dataset passed 100% on
every PR during this period.

| **Metric**                 | **Q1 (fresh)** | **Q2 (stale)** |
|:---------------------------|:---------------|:---------------|
| Golden dataset rows        | 45             | 45             |
| Production incidents       | 0              | 3              |
| Golden dataset pass rate   | 98%            | 100%           |
| New features since freeze  | 0              | 4              |
| Rows covering new features | —              | 0              |

1.  Why did a 100% pass rate coexist with 3 production incidents?

2.  Design a process that prevents golden dataset staleness.

3.  Should the team add all 3 incident cases to the golden dataset?
    What criteria should govern additions?

&lt;!–MDXB-15-OPEN–&gt;

**Approach:** **1.** The golden dataset tested only pre-existing features. New
features (4 added in Q2) had zero coverage. 100% pass rate on stale rows
creates false confidence—the dataset tests what used to break, not what
might break now.

**2.** Process: (a) Every PR that adds a new feature or workflow MUST
add ≥2 golden dataset rows covering that feature. Code review
enforces this. (b) Monthly review: compare golden dataset coverage against
the current feature list. Flag uncovered features. (c) After every
production incident, add a regression row within 48 hours.

**3.** Add all 3 incidents as regression rows. Criteria for additions:
(a) any production incident, (b) any new feature or workflow, (c) any
edge case discovered during testing. Criteria for removal: rows that have
not triggered a failure in 6+ months AND cover a feature that has been
stable. Never remove rows for safety-critical workflows.

**Key Insight:** A golden dataset that never fails is a red flag, not
a success signal. It means the dataset is not keeping pace with the system.

**Answer:**

1.  The dataset only tested pre-existing features. The 4 new features added in Q2 had zero coverage; 100% pass rate on stale rows is false confidence.

2.  Process: every feature-adding PR must include ≥2 golden rows for the new feature (enforced in code review); monthly coverage review against current feature list flags uncovered features; every production incident gets a regression row within 48 hours.

3.  Add all 3 incidents as regression rows. Inclusion criteria: production incidents, new features/workflows, testing-discovered edge cases. Removal criteria: rows untriggered for 6+ months covering a stable feature; never remove rows for safety-critical workflows.

&lt;!–MDXB-15-CLOSE–&gt;

**Case Study: Self-Improving Pipeline Feedback Poisoning**

A travel booking agent implements the self-improving pipeline. After 2
months, the agent starts recommending luxury hotels for budget-conscious
users. Investigation reveals that 30% of the “positive” feedback came
from users who clicked “helpful” on any response without reading it.
This noise was incorporated into the few-shot examples and evaluation
dataset.

| **Metric**                 | **Month 1** | **Month 2** |
|:---------------------------|:------------|:------------|
| User satisfaction (survey) | 82%         | 64%         |
| Automated eval score       | 88%         | 91%         |
| Feedback volume            | 200         | 500         |
| Noisy feedback (%)         | 10%         | 30%         |
| Few-shot examples added    | 15          | 40          |

1.  Why did the automated eval score increase while user satisfaction
    decreased?

2.  Design a feedback quality filter that prevents noisy signals from
    entering the pipeline.

3.  What role should the golden dataset play in catching this type of
    drift?

&lt;!–MDXB-16-OPEN–&gt;

**Approach:** **1.** The automated eval dataset was contaminated by the same noisy
feedback. As noisy “positive” examples entered the dataset, the
evaluator learned to score luxury recommendations highly. The eval score
tracked the noise, not actual quality. User surveys, being independent,
captured the true degradation.

**2.** Feedback quality filter: (a) Require minimum engagement
time—feedback submitted within 2 seconds of response is discarded.
(b) Cross-validate against explicit signals: if a user rates “helpful”
but immediately re-queries the same topic, treat as noisy.
(c) Confidence weighting: feedback from users with &gt;10 interactions
weighted 3x vs. new users. (d) Human review sample: randomly audit 10%
of feedback weekly.

**3.** The golden dataset should include “budget user requests
budget hotel” scenarios. If these pass before and after pipeline updates,
the drift would be detected. The golden dataset acts as an anchor:
automated eval can drift, but golden dataset rows are human-curated and
fixed.

**Key Insight:** The self-improving pipeline’s strength (automated
feedback incorporation) is also its vulnerability. The golden dataset is
the firewall between noisy automation and production quality.

**Answer:**

1.  The eval dataset was contaminated by the same noisy feedback. The evaluator learned to score luxury recommendations highly because the few-shot examples ingested noise. Independent user surveys captured the true degradation.

2.  Feedback filters: minimum engagement time (discard &lt;2s clicks), cross-validation against explicit signals (re-query within 30s = noise), confidence weighting (users with &gt;10 interactions count 3× vs. first-touch), and a 10% weekly human-review audit.

3.  The golden dataset must include “budget user requests budget hotel”-style scenarios; human-curated fixed rows act as a firewall against drift in automated eval. Pipeline updates that fail golden rows fail to ship even when automated eval is unchanged.

\[EAA-5.4, EAA-5.5\]
Your production agent uses an external knowledge base API for the
`search_kb` skill. On Saturday at 2 AM, the API provider deploys a
breaking change that returns empty results for 40% of queries. The agent
gracefully handles the empty results by generating responses from its
training data instead. Monday morning, the team discovers that weekend users
received plausible but fabricated answers. The golden dataset CI gate passed
on Friday’s last PR, and no alerts fired over the weekend.

**Question 1:** Why did the golden dataset gate and the existing
monitoring fail to catch this production failure? Identify at least two
gaps in the monitoring strategy.

**Question 2:** Design a production monitoring rule that would have
detected the knowledge base degradation within 1 hour. Specify the metric,
the data source (traces), and the alerting threshold.

**Question 3:** After fixing the immediate issue, the team wants to
add this failure mode to the self-improving pipeline. Describe the specific
steps: what gets added to the golden dataset, what new evaluator is created,
and how the feedback loop prevents recurrence.

**Answer Rubric:**

- **Q1:** The golden dataset gate runs only on PR merges (not continuously in production), and existing monitoring tracked surface metrics (latency, error rate) rather than *output provenance*—since the agent gracefully fell back to training data instead of erroring, no alert fired. The two gaps are: (1) no production-time content quality monitoring, and (2) no trace-level check on whether the `search_kb` skill returned substantive results.

- **Q2:** Monitor the `search_kb` skill’s empty-result rate from production traces; alert when the 1-hour rolling percentage of empty results exceeds a baseline threshold (e.g., &gt;15% when the historical norm is &lt;5%). This uses trace data already collected by the observability layer and would have fired within the first hour of the API degradation.

- **Q3:** Add the Saturday failure cases (queries that returned empty KB results + the fabricated responses) to the golden dataset as negative examples with ground-truth labels. Create a “source attribution” evaluator that checks whether the agent’s response cites KB documents when the query requires factual lookup. The feedback loop prevents recurrence because each new failure mode becomes a permanent regression test.
