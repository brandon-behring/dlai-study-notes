does not answer “is this agent behaving correctly?” This chapter

# The Three Evaluation Techniques



<Sidenote category="interview">"How would you evaluate an agent skill?" Start with the three-technique taxonomy before diving into implementation.</Sidenote>



Every agent evaluation reduces to one of three techniques, differing on
accuracy vs. scalability:



<Term name="Code-Based Evaluation" los="EAA-3.1">
  Programmatic checks—regex, JSON validation, exact match, cosine similarity—that classify output as correct or incorrect. 100% reproducible but requires codifiable criteria.
</Term>
<AnkiCard type="term" front={"Code-Based Evaluation"} back={"Programmatic checks—regex, JSON validation, exact match, cosine similarity—that classify output as correct or incorrect. 100% reproducible but requires codifiable criteria."} los="EAA-3.1" />





<Term name="LLM-as-a-Judge" los="EAA-3.1">
  A separate LLM prompt classifies the agent's output using discrete labels. Scalable but never 100% accurate.
</Term>
<AnkiCard type="term" front={"LLM-as-a-Judge"} back={"A separate LLM prompt classifies the agent's output using discrete labels. Scalable but never 100% accurate."} los="EAA-3.1" />





<Term name="Human Annotation" los="EAA-3.1">
  Evaluation by human labelers or end-user feedback. Most accurate but slowest to scale and subject to selection bias.
</Term>
<AnkiCard type="term" front={"Human Annotation"} back={"Evaluation by human labelers or end-user feedback. Most accurate but slowest to scale and subject to selection bias."} los="EAA-3.1" />





<Sidenote category="formula">Cosine similarity: $() = \{a  b\}\{\|a\| \|b\|\}$; threshold $ 0.85$ typical for "semantically equivalent."</Sidenote>



&lt;!–MDXB-5-OPEN–&gt;

| **Output Type**           | **Technique**    | **Rationale**             |
|:--------------------------|:-----------------|:--------------------------|
| Quantitative / codifiable | Code-based       | Deterministic, free, fast |
| Qualitative / subjective  | LLM-as-a-judge   | Scalable, handles nuance  |
| Safety-critical           | Human annotation | 100% accuracy required    |

&lt;!–MDXB-5-CLOSE–&gt;



<Sidenote category="warning">NEVER use "rate from 1–10" with LLM judges. LLMs cannot calibrate numeric scales. Always use 2–4 discrete labels (rails).</Sidenote>



&lt;!–MDXB-7-OPEN–&gt;

**Core Insight:** LLM judges must output discrete classification
labels (“correct”/“incorrect”), never numeric scores<Citation src="zheng2023judging" />. An LLM cannot
reliably distinguish 83 from 79.

**Why It Matters:** Numeric scores create false precision. Teams
averaging LLM-assigned scores aggregate noise.

**When It Breaks:** Even discrete labels are imperfect. For
safety-critical decisions, human labels remain necessary.

&lt;!–MDXB-7-CLOSE–&gt;

# Router Evaluation



<Sidenote category="pattern">Router eval has two independent dimensions: (1) tool selection, (2) parameter extraction. Both must be tested separately.</Sidenote>



The router is evaluated on two independent dimensions:

**Function Calling Choice**: Did the agent select the correct tool<Citation src="patil2023gorilla" />?
A simple string comparison—`predicted_tool == expected_tool`.

**Parameter Extraction**: Even with the correct tool, did the agent
extract the right parameter values? A customer asks about order \#12345
and the agent passes it as a `tracking_id` instead of an
`order_id`—right tool, wrong parameter.

&lt;!–MDXB-8-OPEN–&gt;

**Core Insight:** Router evaluation requires two separate checks
that fail independently. 95% tool selection × 85% parameter
accuracy = 80.8% end-to-end router correctness.

**Why It Matters:** Tracking separately reveals where to invest.

**When It Breaks:** For ambiguous queries, ground-truth labels
require careful annotation guidelines.

&lt;!–MDXB-8-CLOSE–&gt;



<Sidenote category="formula">Router accuracy = $P(tool correct)  P(params correct  tool correct)$.</Sidenote>



# Skill Evaluation by Output Type

Different skills produce different output types:

**Database Lookup (SQL)**: Code-based—compare generated SQL result
sets against ground truth. Or LLM-judged for query logic assessment.

**Data Analysis**: LLM-as-a-judge—output is qualitative; no single
correct string. Use rails like `["correct", "incorrect"]`.


<Sidenote category="pattern">Eval selection shortcut: if you can write an assert, use code-based. If output is prose or judgment, use LLM judge with discrete rails.</Sidenote>



**Data Visualisation**: Code-based—execute generated code in a
sandbox. If it runs without error, mark as “runnable.” Runnability is
necessary but not sufficient for correctness.



<Sidenote category="warning">Runnability $$ correctness. Code that runs but plots the wrong data passes. Layer an LLM judge for semantic correctness.</Sidenote>



# Implementation with Phoenix

The Phoenix workflow<Citation src="arize2024phoenix" />: (1) export spans via
`SpanQuery`, (2) run evaluations with `llm_classify()` using
rails, (3) wrap judge calls in `suppress_tracing()` to avoid polluting
traces, (4) upload results with `log_evaluations()`.



```cypher
from phoenix.evals import llm_classify, suppress_tracing

with suppress_tracing():
    results = llm_classify(
        dataframe=spans_df,
        template=eval_template,
        model=judge_model,
        rails=["correct", "incorrect"],
    )
px_client.log_evaluations(results)
```



&lt;!–MDXB-9-OPEN–&gt;

**Core Insight:** Wrap LLM-as-a-judge calls in
`suppress_tracing()` to prevent evaluation LLM calls from
appearing in agent traces. Without suppression, judge spans intermingle
with agent spans and corrupt trace analysis.

**Why It Matters:** A 500-span evaluation run doubles trace store
size with evaluation artifacts.

**When It Breaks:** If debugging the judge itself, temporarily
remove suppression.

&lt;!–MDXB-9-CLOSE–&gt;



<Sidenote category="interview">When asked "how would you evaluate a summarization agent?"—say "LLM-as-a-judge with discrete labels" and explain why numeric scores fail. Immediate credibility signal.</Sidenote>

judges for problems with deterministic answers.

2.  Complaint summary → LLM-as-a-judge. 1, 000 × $0.01 = $10/day.

3.  Refund calculator → code-based (dollar-amount diff ±$0.01). $0/day.

**Total cost:** $10/day; two of three skills are code-evaluable, cutting cost by 67% vs LLM-judge across the board.

\[EAA-3.2, EAA-3.6\]
Your data analysis agent has three skills: `data_lookup` (SQL),
`data_analysis` (markdown), and `data_visualisation`
(chart code). After a prompt update to improve routing accuracy, the
router’s tool selection score jumped from 82% to 96%. The team
celebrates—until a manual audit reveals that the router now defaults to
`data_analysis` for 70% of queries, including ones that clearly
need SQL lookups. The “improvement” occurred because
`data_analysis` happens to produce plausible-looking output for
any query, and the end-to-end eval scored it as acceptable.

**Question 1:** Why did the end-to-end evaluation miss this
regression? What is the difference between “plausible output” and
“correct routing”?

**Question 2:** Design a router evaluation that would detect the
over-routing to `data_analysis`. Specify the dataset, the metric,
and the acceptance threshold.

**Question 3:** The team proposes adding a “routing distribution”
metric that alerts when any single skill receives more than 50% of
queries. What are the strengths and limitations of this approach?

**Answer Rubric:**

- **Q1:** The end-to-end eval measured *output quality* (plausibility) rather than *process correctness* (whether the right skill handled the query). Because `data_analysis` can hallucinate a plausible-looking answer for any query, the eval rewarded the router for choosing the skill with the highest surface-level pass rate rather than the semantically correct one.

- **Q2:** Create a labelled dataset of 100+ queries with ground-truth skill assignments; measure *exact-match accuracy* of the router’s tool selection against these labels, with an acceptance threshold of ≥85%. This isolates routing correctness from downstream output quality.

- **Q3:** Strength: the distribution metric is cheap, model-agnostic, and catches dramatic routing collapse. Limitation: the 50% threshold is arbitrary—a legitimate workload might be 60% analysis queries, and the metric cannot distinguish correct skew from over-routing without ground-truth labels.

<Sidenote category="practice">5 min  Code-based eval design  Onsite</Sidenote>



Your agent’s `data_lookup` skill generates SQL queries. You have a
dataset of 200 test cases, each with a user question, the expected SQL
result set (rows), and the expected column names. Design a code-based
evaluation function that:

1.  Executes the generated SQL against a test database.

2.  Compares the result set to the expected output.

3.  Returns a score and a failure reason when the query is incorrect.

What edge cases must the evaluation handle, and why is row ordering a
particular concern?

&lt;!–MDXB-13-CLOSE–&gt;

&lt;!–MDXB-16-OPEN–&gt;

**Approach:** Build a deterministic evaluation pipeline that executes
SQL, compares result sets as unordered collections, and captures three
failure modes: execution errors, wrong columns, and wrong rows.

~~~ python
import sqlite3
from typing import Literal

def eval_sql(
    generated_sql: str,
    expected_rows: list[tuple],
    expected_cols: list[str],
    db_path: str,
) -> dict:
    try:
        conn = sqlite3.connect(db_path)
        cur = conn.execute(generated_sql)
        actual_cols = [d[0] for d in cur.description]
        actual_rows = cur.fetchall()
        conn.close()
    except Exception as e:
        return {"score": 0, "reason": f"Execution error: {e}"}

    if set(actual_cols) != set(expected_cols):
        return {"score": 0, "reason":
            f"Wrong columns: {actual_cols} vs {expected_cols}"}

    if set(actual_rows) != set(expected_rows):
        return {"score": 0, "reason":
            f"Wrong rows: {len(actual_rows)} vs {len(expected_rows)}"}

    return {"score": 1, "reason": "correct"}
~~~

**Edge cases:**

- **Row ordering**: SQL result order is non-deterministic
  without `ORDER BY`. Compare as sets (or sorted tuples) to
  avoid false negatives when the query is logically correct but
  returns rows in a different order.

- **Floating-point columns**: Use approximate comparison
  (±*ϵ*) for numeric columns.

- **Timeout**: Wrap execution in a timeout to catch infinite
  loops or full table scans.

- **Destructive queries**: Execute in a read-only connection
  or rollback transaction to prevent `DROP TABLE` side effects.

**Key Insight:** Code-based SQL evaluation is deterministic and free,
but the comparison logic must account for non-deterministic row ordering
and floating-point imprecision—otherwise correct queries fail the eval.

**Answer:** Execute SQL, compare column names as sets, compare row
sets (not lists), and handle execution errors, timeouts, and destructive
queries as distinct failure modes.
