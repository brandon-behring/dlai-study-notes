# Creating a Remote MCP Server



<Sidenote category="interview">Production MCP = remote servers over HTTP. Know the one-line change from stdio to SSE and why it matters for multi-user access.</Sidenote>



The transition from local to remote is minimal at the code level. The server keeps all
tools, resources, and prompts unchanged. Only the transport and port configuration change:



```cypher
from mcp.server.fastmcp import FastMCP

# Configure port for remote access
mcp = FastMCP("research", port=8000)

@mcp.tool()
def search_papers(topic: str, max_results: int = 5) -> str:
    """Search arxiv for papers on a given topic."""
    # ... same implementation as before ...

@mcp.resource("docs://paper-list")
def get_paper_list() -> str:
    """List of indexed papers."""
    # ... same implementation ...

@mcp.prompt()
def research_summary(topic: str) -> str:
    """Generate a research summary."""
    # ... same implementation ...

if __name__ == "__main__":
    mcp.run(transport="sse")  # Changed from "stdio" to "sse"
```





<Sidenote category="warning">At recording, Python SDK lacks Streamable HTTP; course uses SSE. When SDK support arrives, only the transport string changes.</Sidenote>



&lt;!–MDXB-10-OPEN–&gt;

**Core Insight:** The only code change to go from local to remote is the transport parameter.
All tools, resources, and prompts remain identical. This is MCP’s design goal: tool logic
is transport-independent.

**Decision Matrix:**

- Development / Claude Desktop → stdio (no networking)

- Team-shared server / multi-user → SSE<Citation src="sse2024spec" /> (HTTP endpoint)

- Stateless deployments at scale → Streamable HTTP<Citation src="mcp2025spec" /> (when SDK supports it)

**When It Breaks:** SSE requires a persistent connection. Long-running tool calls
can timeout if the connection drops. For tools that take &gt;30 seconds, implement heartbeat
pings or consider chunked responses.

&lt;!–MDXB-10-CLOSE–&gt;



<Sidenote category="formula">SSE endpoint: server runs at `http://host:port/sse`. The `/sse` path returns a session ID on GET. POST to `/messages` for tool calls.</Sidenote>



# Testing Remote Servers with Inspector



<Sidenote category="practice">Always test remote servers with Inspector before deployment. Switch transport type to SSE and enter the server URL.</Sidenote>



The MCP Inspector works with remote servers too. Switch the transport type to SSE
and provide the server URL:



```cypher
# Start Inspector (no server command needed for remote)
npx @modelcontextprotocol/inspector

# In the Inspector UI:
# Transport: SSE
# URL: http://localhost:8000/sse
# Click "Connect"
```



The Inspector shows the same initialization handshake, tool listing, and interactive testing
as with stdio—confirming that the protocol is transport-independent. After verifying
locally, the server is ready for deployment.

# Deploying to Render



<Sidenote category="pattern">Deployment pipeline: local dev (uv + stdio) $$ test remote (SSE + Inspector) $$ push to GitHub $$ deploy on Render $$ verify /sse endpoint.</Sidenote>



The course walks through deploying the research server to Render, a cloud hosting platform:

**Step 1: Prepare dependencies for pip** (Render uses pip, not uv):


```cypher
# Convert uv dependencies to requirements.txt
uv pip compile pyproject.toml > requirements.txt

# Specify Python version for Render
echo "python-3.11.11" > runtime.txt
```



**Step 2: Push to GitHub:**


```cypher
git init
echo ".venv" > .gitignore
git add -A && git commit -m "ready for deployment"
git remote add origin https://github.com/user/remote-research.git
git push origin main
```



**Step 3: Deploy on Render:**

- Create a new Web Service connected to the GitHub repository

- Set start command: `python research_server.py`

- Render installs from `requirements.txt` using the Python version in `runtime.txt`

- After deployment, `/sse` returns a session ID confirming the server is running



<Sidenote category="warning">The root URL returns 404—this is expected. The MCP endpoint is at `/sse`. A session ID in the response confirms successful deployment.</Sidenote>



&lt;!–MDXB-11-OPEN–&gt;

**Core Insight:** MCP is deployment-agnostic<Citation src="mcp2024spec" />. The same server code runs on Render,
AWS, GCP, Azure, a local Docker container, or bare metal. The protocol is the same;
only the hosting infrastructure changes. Start with the simplest deployment (Render free tier)
and scale later.

**Why It Matters:** You can prototype on Render’s free tier and move to Kubernetes
when traffic demands it—without changing any MCP server code.

**When It Breaks:** Platform-specific features (Render’s auto-sleep, cold starts on
serverless) can cause latency spikes that violate MCP client timeout expectations.
SSE connections also behave differently behind different reverse proxies and CDNs.

&lt;!–MDXB-11-CLOSE–&gt;

# Authentication and Security



<Sidenote category="interview">MCP has NO built-in auth. This is the \#1 security question. Know that auth must be implemented at the HTTP layer (bearer tokens, OAuth2).</Sidenote>



MCP itself does not define authentication or authorization<Citation src="mcp2026roadmap" />. For remote servers,
you must implement auth at the transport layer:



```cypher
from starlette.middleware import Middleware
from starlette.middleware.authentication import AuthenticationMiddleware

class BearerTokenBackend:
    async def authenticate(self, conn):
        token = conn.headers.get("Authorization", "").replace("Bearer ", "")
        if not token or not await verify_token(token):
            return None
        return AuthCredentials(["authenticated"]), get_user(token)

app = Starlette(
    routes=[...],
    middleware=[Middleware(AuthenticationMiddleware, backend=BearerTokenBackend())]
)
```



&lt;!–MDXB-12-OPEN–&gt;

**Core Insight:** MCP deliberately excludes built-in authentication. Security is implemented
at the HTTP transport layer using bearer tokens, OAuth2, or API keys. This design choice keeps
the protocol simple but means every remote deployment must add auth explicitly.

**Why It Matters:** A remote MCP server without auth is an open API—anyone with the URL
can invoke your tools. This is the \#1 production security question in MCP interviews.

**When It Breaks:** For local stdio servers, auth is unnecessary since the process runs
on the user’s machine. Auth only matters for remote (SSE/HTTP) deployments.

&lt;!–MDXB-12-CLOSE–&gt;

**Production security checklist:**

- Bearer token or OAuth2 on all endpoints

- HTTPS only—no plaintext HTTP

- Rate limiting per user/API key

- Input validation on all tool parameters

- Path traversal prevention for file-access tools

- Audit logging of all tool invocations

- Principle of least privilege: expose only needed tools



<Sidenote category="warning">A remote MCP server without auth is an open API. Anyone with the URL can call your tools. Always deploy auth before exposing to the network.</Sidenote>



# Production Architecture Patterns



<Sidenote category="pattern">Three patterns: sidecar (per-app isolation), shared service (efficient multi-user), gateway (enterprise routing). Most production = shared service.</Sidenote>



## Sidecar Pattern

One MCP server per application instance. Simple and isolated, but duplicates resources
and doesn’t allow sharing between applications.



<Sidenote category="formula">Gateway pattern: clients see 1 endpoint; gateway fans out to N backends. Central auth + unified monitoring + simplified config.</Sidenote>



## Shared Service Pattern

One MCP server shared by multiple clients. All users connect to the same endpoint.
Efficient and consistent, but requires auth and rate limiting. Best for most teams.

## Gateway Pattern

An MCP proxy that routes to multiple backend servers based on tool name.
Clients see one server; the gateway fans out to many. This is the enterprise pattern—central
auth, unified monitoring, simplified client configuration.

&lt;!–MDXB-13-OPEN–&gt;

**Design an MCP Architecture for a Growing Startup**

Your startup has 10 engineers using Claude Desktop, 2 AI agents (customer support bot,
code review bot), and 4 tools (GitHub, PostgreSQL, Slack, internal docs search).

Design the architecture: deployment pattern, transport, auth strategy, and scaling plan.
Justify each choice.

&lt;!–MDXB-13-CLOSE–&gt;

&lt;!–MDXB-21-OPEN–&gt;

**Approach:**
**Architecture:**

- **Pattern:** Shared service (one server per tool, shared by all clients)

- **Transport:** SSE/HTTP (12 clients need shared access)

- **Deployment:** Docker Compose on a single server (startup scale—no K8s yet)

- **Auth:** API keys per client. Engineers get personal keys; bots get service accounts.

- **Config:** Shared `claude_desktop_config.json` template in the company
  dotfiles repo. Each engineer adds their personal API key.

**Why not stdio?** 10 engineers need shared access to the same PostgreSQL and docs server.
Running 10 copies wastes resources and creates consistency issues.

**Scaling plan:** When the team grows to 50+ or traffic spikes, migrate from Docker Compose
to Kubernetes with auto-scaling per server. The MCP protocol is identical regardless of
deployment infrastructure.

**Key Insight:** Start with the simplest deployment that works (Docker Compose &gt; Render
&gt; bare Python). MCP’s transport independence means you never rewrite server code when
upgrading infrastructure.

**Answer:** Start with the simplest deployment that works (Docker Compose &gt; Render
&gt; bare Python). MCP’s transport independence means you never rewrite server code when
upgrading infrastructure.

**Case Study: Enterprise MCP at Scale**

**Scenario:** A company with 50 engineers, 3 custom AI applications, and 5 MCP servers
(GitHub, Jira, Confluence, Slack, internal DB).

**Architecture:**

- **Gateway:** nginx reverse proxy routing requests to backend servers

- **Auth:** Company SSO via OAuth2 at the gateway layer

- **Monitoring:** Prometheus metrics on tool call volume, latency, error rates

- **Deployment:** Kubernetes with per-server auto-scaling

**Questions:**

1.  Why use a gateway instead of direct client-to-server connections?
    (Central auth, unified monitoring, simplified client config)

2.  How do you add a new server without updating 50+ client configs?
    (Add to gateway; clients auto-discover via updated `list_tools`)

3.  A tool call takes 90 seconds. What problem does this cause with SSE?
    (Connection timeout. Fix: heartbeat pings, chunked responses, or async completion notification.)

&lt;!–MDXB-14-OPEN–&gt;

**Case Study: MCP Migration at a Fintech Startup**

A fintech startup runs 8 MCP servers (Stripe, PostgreSQL, Redis, Slack,
internal-docs, compliance-checker, risk-scorer, notification-hub) on stdio
with Claude Desktop for 5 engineers. They just hired 20 more engineers and
need shared access. The compliance-checker tool queries PII and must be
auditable. Two servers (risk-scorer, compliance-checker) have 45-second
average response times.

| **Metric**         | **Current (stdio)** | **Target (remote)**          |
|:-------------------|:--------------------|:-----------------------------|
| Engineers          | 5                   | 25                           |
| Servers            | 8                   | 8                            |
| Avg. response      | 200ms               | 200ms (non-PII)              |
| PII tools          | 2                   | 2 (audit required)           |
| Long-running tools | 2                   | 2 (&gt;30s) |

1.  Which deployment pattern (sidecar, shared service, gateway) should
    they choose? Justify considering the PII audit requirement.

2.  How should they handle the 45-second response times for
    risk-scorer and compliance-checker over SSE?

3.  Design the auth strategy: should all 25 engineers have the same
    access to PII tools?

&lt;!–MDXB-14-CLOSE–&gt;

&lt;!–MDXB-22-OPEN–&gt;

**Approach:**
**1.** Gateway pattern. Central auth enables per-tool access control
(PII tools restricted to compliance team). Unified audit logging at the
gateway captures every tool invocation with user identity. Shared service
alone lacks the routing granularity for per-tool authorization.

**2.** Two mitigations: (a) Implement SSE heartbeat pings every 10
seconds to keep connections alive during long computations. (b) Return a
job ID immediately and poll for completion—convert synchronous SSE to
async completion notification.

**3.** Role-based API keys: “standard” keys access 6 non-PII
servers; “compliance” keys access all 8. Gateway enforces the mapping.
Every compliance-checker call is logged with user ID, timestamp, and
parameters for audit trail. Rotate keys quarterly.

**Key Insight:** The PII audit requirement is the deciding factor for
gateway over shared service. Without it, shared service would suffice for
25 engineers.

**Answer:** The PII audit requirement is the deciding factor for
gateway over shared service. Without it, shared service would suffice for
25 engineers.

&lt;!–MDXB-22-CLOSE–&gt;

&lt;!–MDXB-15-OPEN–&gt;

**Case Study: Multi-Cloud MCP Gateway Failure**

An enterprise deploys an MCP gateway on AWS routing to 12 backend servers.
During a regional AWS outage, 4 backend servers become unreachable. The
gateway returns 502 errors for tools hosted on those servers, but clients
have no visibility into which tools are affected. Engineers waste 20
minutes discovering which tools work.

| **Metric**          | **Before Outage** | **During Outage** |
|:--------------------|:------------------|:------------------|
| Available tools     | 30                | 18                |
| Error rate          | 0.1%              | 33%               |
| Mean discovery time | —                 | 20 min            |
| Affected backends   | 0/12              | 4/12              |

1.  How should the gateway communicate partial availability to
    clients via the MCP protocol?

2.  Design a health-check system that proactively detects backend
    failures before clients hit them.

3.  What architectural change prevents a single-region outage from
    degrading the entire gateway?

&lt;!–MDXB-15-CLOSE–&gt;

&lt;!–MDXB-23-OPEN–&gt;

**Approach:**
**1.** The gateway should filter its `list_tools` response to
exclude tools from unhealthy backends. Clients see only working tools.
Additionally, return structured error messages with a
`server_status` field when a tool call fails, naming the affected
backend and estimated recovery time.

**2.** Health-check system: each backend exposes a `/health`
endpoint. Gateway polls every 15 seconds. After 3 consecutive failures,
mark backend as unhealthy and remove its tools from `list_tools`.
After 2 consecutive successes, re-add. Alert on-call via PagerDuty on
first failure.

**3.** Multi-region deployment: deploy critical backends in 2+ AWS
regions. Gateway routes to the healthy region. For the 4 affected servers,
failover to us-west-2 replicas. This adds cost but eliminates single-region
dependency.

**Key Insight:** MCP’s `list_tools` is the natural mechanism
for communicating availability. A gateway that dynamically filters tools
based on backend health turns a confusing outage into a graceful
degradation.

**Answer:** MCP’s `list_tools` is the natural mechanism
for communicating availability. A gateway that dynamically filters tools
based on backend health turns a confusing outage into a graceful
degradation.

&lt;!–MDXB-23-CLOSE–&gt;

&lt;!–MDXB-16-OPEN–&gt;

Your MCP server processes document analysis requests that take 15–60
seconds. Users report intermittent “connection reset” errors during long
tool calls. Diagnose the cause and design a solution that works with
standard SSE transport.

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-24-OPEN–&gt;

**Approach:**
**Diagnosis:** SSE connections are long-lived HTTP connections. Many
reverse proxies (nginx default: 60s), load balancers (AWS ALB: 60s), and
CDNs have idle connection timeouts. A 60-second tool call with no data sent
triggers the timeout.

**Solution:** Implement SSE heartbeat events. Send a comment line
(`:heartbeat`) every 15 seconds during tool execution. This keeps
the connection alive without sending actual data. The MCP client ignores
comment lines per the SSE specification.

**Infrastructure fix:** Increase proxy timeouts to 120s as a safety
margin. Configure ALB idle timeout to 120s. These are defense-in-depth;
heartbeats are the primary fix.

**Key Insight:** The SSE spec defines comment lines (starting with
`:`) that are ignored by clients. Using these as keepalive pings is
the standard pattern—no protocol extension needed.

**Answer:** The SSE spec defines comment lines (starting with
`:`) that are ignored by clients. Using these as keepalive pings is
the standard pattern—no protocol extension needed.

&lt;!–MDXB-24-CLOSE–&gt;

&lt;!–MDXB-17-OPEN–&gt;

Your team has 15 MCP servers running on stdio for Claude Desktop. You need
to migrate to SSE for a new multi-user application while keeping Claude
Desktop working. Design a migration plan that avoids downtime.

&lt;!–MDXB-17-CLOSE–&gt;

&lt;!–MDXB-25-OPEN–&gt;

**Approach:**
**Phase 1—Dual transport:** Modify each server’s entry point to
accept a `--transport` flag. Default to stdio; pass
`--transport sse` for remote deployment. Same server code, two run
modes.

**Phase 2—Deploy remote:** Deploy each server to Render/Docker with
`--transport sse`. Test with Inspector against remote URLs. Claude
Desktop configs remain unchanged (still stdio).

**Phase 3—Migrate clients:** Update Claude Desktop configs from
stdio to SSE, pointing to remote URLs. Roll out one server at a time. If a
server fails, revert that config entry to stdio.

**Phase 4—Decommission:** After all clients use SSE, remove stdio
entry points if desired (or keep for local development).

**Key Insight:** MCP’s transport independence makes migration a
configuration change, not a code rewrite. The dual-transport phase ensures
zero downtime.

**Answer:** MCP’s transport independence makes migration a
configuration change, not a code rewrite. The dual-transport phase ensures
zero downtime.

&lt;!–MDXB-18-OPEN–&gt;

An MCP server exposes a `search_database` tool that costs $0.02
per query to the underlying API. 25 engineers and 3 AI agents use it. Last
month the bill was $4,000—4x budget. Design a rate limiting strategy.

&lt;!–MDXB-18-CLOSE–&gt;

&lt;!–MDXB-26-OPEN–&gt;

**Approach:**
**Analysis:** $4,000 / $0.02 = 200,000 queries/month. Budget
of $1,000 = 50,000 queries/month ≈ 1,667/day.

**Strategy:**

- Per-user daily limit: engineers get 50 queries/day (25 ×
  50 = 1,250/day). AI agents get 100 queries/day (3 × 100
  = 300/day). Total: 1,550/day, within budget.

- Implement at the auth middleware layer using a Redis counter per
  API key. Return a structured MCP error with remaining quota when
  limit is hit.

- Add a `search_quota` resource that clients can check
  before querying.

**Key Insight:** Rate limiting belongs at the auth/middleware layer,
not inside the tool function. MCP resources (not just tools) can expose
quota information, enabling clients to self-regulate.

**Answer:** Rate limiting belongs at the auth/middleware layer,
not inside the tool function. MCP resources (not just tools) can expose
quota information, enabling clients to self-regulate.

&lt;!–MDXB-19-OPEN–&gt;

Design the monitoring dashboard for a production MCP gateway serving 50
users across 8 backend servers. Specify metrics, alert thresholds, and the
dashboard layout.

&lt;!–MDXB-19-CLOSE–&gt;

&lt;!–MDXB-27-OPEN–&gt;

**Approach:**
**Metrics (per server + aggregate):**

- Tool call volume (calls/min), latency (p50, p95, p99), error rate

- SSE connection count (active), connection duration distribution

- Auth failures/min (potential attack indicator)

- Per-user call volume (abuse detection)

**Alert thresholds:**

- Error rate &gt; 5% sustained 5 min → page on-call

- p99 latency &gt; 30s → warning

- Auth failures &gt; 50/min → page security

- Backend health check failure → immediate alert

**Dashboard layout:** Row 1: aggregate call volume + error rate (time
series). Row 2: per-server health grid (green/yellow/red). Row 3: latency
heatmap by tool. Row 4: top users by volume + cost.

**Key Insight:** MCP-specific monitoring adds SSE connection health
and per-tool latency breakdown. Standard API monitoring misses these
because MCP tools have heterogeneous latency profiles.

**Answer:** MCP-specific monitoring adds SSE connection health
and per-tool latency breakdown. Standard API monitoring misses these
because MCP tools have heterogeneous latency profiles.

&lt;!–MDXB-27-CLOSE–&gt;

&lt;!–MDXB-20-OPEN–&gt;

Your MCP server wraps a PostgreSQL database, a Stripe API, and an internal
microservice. Each requires different credentials. The server runs on
Render. Design the secrets management approach.

&lt;!–MDXB-20-CLOSE–&gt;

&lt;!–MDXB-28-OPEN–&gt;

**Approach:**
**Never in code or config files.** Use Render’s environment variable
secrets:

- `POSTGRES_URI`: Connection string with credentials

- `STRIPE_SECRET_KEY`: API key for payment operations

- `INTERNAL_SERVICE_TOKEN`: Bearer token for microservice

**Access pattern:** Each tool function reads its credential from
`os.environ` at call time, not at import time. This enables
credential rotation without server restart.

**Rotation strategy:** Render supports secret updates without
redeployment. Schedule quarterly rotation. Use short-lived tokens where
possible (Stripe supports this natively).

**Key Insight:** MCP tools are thin wrappers around external services.
Each tool needs exactly one credential set. Map credentials 1:1 with tools,
not with servers.

**Answer:** MCP tools are thin wrappers around external services. Each tool needs exactly one credential set.
