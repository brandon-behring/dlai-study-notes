# Configuring MCP for Claude Desktop



<Sidenote category="interview">Claude Desktop is the most common MCP deployment. Know the config file location and JSON format. This comes up in onboarding questions.</Sidenote>



Claude Desktop acts as an MCP host<Citation src="claudedesktop2024" /> that manages multiple clients, each connecting to a
configured server. The configuration JSON specifies how to launch each server:

// macOS:  /Library/Application Support/Claude/claude\_desktop\_config.json
// Windows:
"mcpServers":
"research":
"command": "uv",
"args": \["–directory", "/path/to/mcp-project",
"run", "research\_server.py"\]
,
"fetch":
"command": "npx",
"args": \["-y", "@modelcontextprotocol/server-fetch"\]
,
"filesystem":
"command": "npx",
"args": \["-y", "@modelcontextprotocol/server-filesystem",
"/path/to/allowed/directory"\]



<Sidenote category="warning">After editing the config file, fully quit and reopen Claude Desktop. Changes are NOT hot-reloaded.</Sidenote>



The course demonstrates connecting the research server (from Ch 2) alongside the `fetch`
and `filesystem` reference servers. Once configured, Claude Desktop shows available
tools, resources, and prompts from all connected servers in its UI.

&lt;!–MDXB-5-OPEN–&gt;

**Core Insight:** Every MCP server is effectively a plugin for Claude Desktop. Adding
a database, API integration, or custom tool capability requires only one JSON entry—no code
changes to Claude Desktop. The same servers you build and test with the Inspector work
immediately in Claude Desktop.

**Why It Matters:** This turns Claude from a chatbot into a tool-using agent with access
to your local environment, databases, and APIs. All the lower-level client code from Ch 3
is abstracted away.

**When It Breaks:** Claude Desktop uses stdio transport only. Remote SSE servers
require a different host or a local proxy.

&lt;!–MDXB-5-CLOSE–&gt;



<Sidenote category="pattern">Config pattern: `command` + `args` = how to start the server as a subprocess. `env` = optional environment variables (API keys).</Sidenote>



# The MCP Application Ecosystem



<Sidenote category="crossref">Full list of MCP-compatible apps: modelcontextprotocol.io/clients. Includes IDEs, web apps, CLI tools, and agent frameworks.</Sidenote>



The MCP documentation<Citation src="mcp2025anniversary" /> lists a growing ecosystem of compatible applications:

- **Desktop:** Claude Desktop, Cursor, Windsurf

- **IDEs:** VS Code (via extensions), JetBrains (via plugins)

- **Web:** Claude.ai, custom web applications

- **CLI:** Claude Code, command-line agent tools

- **Agentic:** LangChain, CrewAI, custom agent frameworks

Each application supports different subsets of MCP primitives (tools, resources, prompts,
sampling). The key takeaway: the MCP servers you build work across this entire ecosystem
without modification.

# Prompt Templates



<Sidenote category="interview">Prompts are the most underused MCP primitive. Know the rationale: move prompt engineering from the user to the server developer.</Sidenote>



Prompt templates remove the burden of prompt engineering from end users. Instead of
requiring users to craft optimal prompts, the server provides battle-tested templates
with placeholders for dynamic data:



```cypher
@mcp.prompt()
def research_summary(topic: str) -> str:
    """Generate a research summary for a given topic.
    Searches papers, extracts key findings, and creates
    a structured summary."""
    return f"""Search for recent papers on {topic}.
For each paper found:
1. Extract the title, authors, and abstract
2. Identify the key contribution
3. Note any methodological innovations

Then synthesize across all papers:
- What are the main themes?
- Where is the field heading?
- What gaps remain?

Present as a structured research briefing."""
```





<Sidenote category="interview">Prompt templates shift prompt engineering from end users to server developers. Battle-tested prompts shipped as code, not documentation.</Sidenote>



In the Claude Desktop UI, prompts appear as selectable options. The user chooses a prompt
template, provides the dynamic data (e.g., a topic), and the server returns a fully formed
prompt that the LLM executes using the available tools.



<Sidenote category="formula">Prompt primitives: user-controlled (user selects which to use). Tools: model-controlled (LLM decides when to call). Resources: app-controlled (application decides what context to inject).</Sidenote>



# Dynamic and Templated Resources



<Sidenote category="pattern">Two resource types: direct (`docs://api-reference`) returns fixed data. Templated (`docs://{doc_id}`) accepts parameters like an f-string.</Sidenote>



Resources provide read-only data to the LLM’s context. The course demonstrates both
static resources (fixed data) and templated resources (parameterized access):



```cypher
# Direct resource: always returns the same URI
@mcp.resource("docs://paper-list")
def get_paper_list() -> str:
    """List of all indexed research papers."""
    return json.dumps(get_all_papers())

# Templated resource: URI contains a parameter
@mcp.resource("docs://{paper_id}")
def get_paper_details(paper_id: str) -> str:
    """Detailed information for a specific paper."""
    paper = lookup_paper(paper_id)
    return json.dumps(paper)
```



In Claude Desktop and similar hosts, resources appear in the UI (often with an `@` symbol).
The user can reference a resource to inject data into the conversation without requiring
a tool call. The course’s SQLite demo showed a “business insight memo” resource that
updated dynamically as the database changed.

&lt;!–MDXB-6-OPEN–&gt;

**Core Insight:** The three primitives serve distinct purposes:

- **Resources:** Inject context into the LLM (like RAG retrieval)

- **Tools:** Let the LLM take actions (like function calling)

- **Prompts:** Guide the LLM’s workflow (like a recipe card)

The combination is powerful: the LLM reads a resource (schema), calls a tool (query),
and follows a prompt (analysis workflow). Each primitive alone is limited; together they
build sophisticated applications.

**When It Breaks:** Don’t make everything a tool. If data is read-only and doesn’t
require dynamic parameters, it should be a resource. If the goal is guiding behavior,
it should be a prompt.

&lt;!–MDXB-6-CLOSE–&gt;



<Sidenote category="warning">Classification test: Does it change state? $$ Tool. Does it provide read-only context? $$ Resource. Does it guide the LLM's approach? $$ Prompt.</Sidenote>



# Combining Primitives in Practice



<Sidenote category="practice">The course demo: Claude Desktop uses fetch (tool) to visit DeepLearning.AI, research server (tool) to find papers, and artifacts (Claude feature) to build a quiz app.</Sidenote>



The course demonstrates combining tools from multiple MCP servers in Claude Desktop:

1.  **Fetch tool** visits DeepLearning.AI to find interesting ML topics

2.  **Research server tools** search arXiv for papers on those topics

3.  **Claude’s artifacts** generate a web-based flashcard quiz from the findings

This pattern—composing tools from different servers with LLM orchestration—is the
fundamental value proposition of MCP.

&lt;!–MDXB-7-OPEN–&gt;

**Design a Context-Aware Project Management MCP Server**

Classify each capability as a tool, resource, or prompt and justify your choice:

- `create_task`: Creates a new task in the project board

- `sprint_board`: Current sprint status and task assignments

- `standup_summary`: Multi-step workflow for generating daily standup reports

- `search_tasks`: Searches tasks by keyword and status filters

- `team_members`: List of team members with roles and availability

- `retro_facilitator`: Guides the LLM through running a retrospective

&lt;!–MDXB-7-CLOSE–&gt;

&lt;!–MDXB-9-OPEN–&gt;

**Approach:**
**Tools** (have side effects or require dynamic queries):

- `create_task` — mutation (creates new entity)

- `search_tasks` — read-only but requires dynamic query parameters (tool pattern)

**Resources** (read-only context):

- `sprint_board` — snapshot of current state, useful as LLM background context

- `team_members` — relatively static data the LLM needs for assignment decisions

**Prompts** (workflow templates):

- `standup_summary` — prescribes a multi-step workflow (read board → summarize per person)

- `retro_facilitator` — structures a facilitation workflow with specific steps

**Key Insight:** When in doubt, it’s probably a tool. Promote to resource when data
is read-only and useful as ambient context. Promote to prompt when you’re defining a
multi-step workflow the LLM should follow.

**Answer:** When in doubt, it’s probably a tool. Promote to resource when data
is read-only and useful as ambient context.

&lt;!–MDXB-9-CLOSE–&gt;

&lt;!–MDXB-8-OPEN–&gt;

Your company’s MCP server for HR operations currently exposes only tools.
The team wants to add prompt templates that standardize common HR
workflows for the AI assistant. Design prompt templates for the following
two workflows, specifying: (a) the template name, (b) arguments the
template accepts, (c) the multi-step workflow it prescribes, and
(d) which existing tools each step invokes.

**Workflow 1:** New employee onboarding: provision accounts, assign
a buddy, send a welcome email, and schedule the first-week check-in.

**Workflow 2:** Quarterly access review: for each team member, pull
current permissions, compare against role baseline, flag deviations, and
generate an approval request for the manager.

&lt;!–MDXB-8-CLOSE–&gt;

&lt;!–MDXB-10-OPEN–&gt;

**Approach:**
**Workflow 1: `onboard_new_hire`**

- **Arguments:** `employee_name`, `team`,
  `start_date`, `manager_email`

- **Steps:**

  1.  Call `provision_accounts(employee_name, team)`
      to create email, Slack, GitHub, and SSO accounts

  2.  Call `assign_buddy(team)` to select an available
      onboarding buddy from the team roster (resource:
      `team_roster`)

  3.  Call `send_email(manager_email, template= ‘‘welcome’’)` with a customized welcome message

  4.  Schedule the first-week check-in five days after the start
      date by calling `create_calendar_event(...)` with
      the employee, manager, and buddy as attendees

**Workflow 2: `quarterly_access_review`**

- **Arguments:** `team_name`, `review_quarter`

- **Steps:**

  1.  Call `list_team_members(team_name)` to get
      the current roster

  2.  For each member, call
      `get_permissions(member_id)` to pull current
      access

  3.  Load resource `role_baselines` to get expected
      permissions per role

  4.  Compare actual vs. baseline; flag any excess permissions

  5.  Call `create_approval_request(manager, deviations)` for each member with excess access

**Key Insight:** Prompt templates turn ad-hoc tool usage into
repeatable workflows. Without them, the LLM might skip steps (forgetting
the buddy assignment) or execute them in the wrong order (sending the
welcome email before accounts are provisioned). The template encodes
organizational process knowledge.

**Answer:** Prompt templates turn ad-hoc tool usage into
repeatable workflows. Without them, the LLM might skip steps (forgetting
the buddy assignment) or execute them in the wrong order (sending the
welcome email before accounts are provisioned).
