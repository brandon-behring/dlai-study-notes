# Creating an MCP Client



<Sidenote category="interview">The client-side code is lower level than server code. Know the lifecycle: `StdioServerParameters` $$ `stdio_client` $$ `ClientSession` $$ initialize $$ list_tools.</Sidenote>





<Term name="MCP Client" los="MCP-3.1">
  The protocol handler inside a host application. Each client maintains a 1:1 connection with exactly one MCP server, discovers capabilities via `list_tools()`, and routes tool calls through the session.
</Term>
<AnkiCard type="term" front={"MCP Client"} back={"The protocol handler inside a host application. Each client maintains a 1:1 connection with exactly one MCP server, discovers capabilities via `list_tools()`, and routes tool calls through the session."} los="MCP-3.1" />



The course builds a client from scratch using the Python SDK<Citation src="mcp2024pythonsdk" /> to understand what hosts like Claude Desktop
do under the hood. The client connects to the research server built in Chapter 2,
discovers its tools, and makes them available to an LLM.



```cypher
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

# Define which server to connect to
server_params = StdioServerParameters(
    command="uv",
    args=["run", "research_server.py"],
    env=None  # optional environment variables
)

# Establish connection
async with stdio_client(server_params) as (read, write):
    async with ClientSession(read, write) as session:
        # Phase 1: Initialize (handshake)
        await session.initialize()

        # Phase 2: Discover tools
        tools = await session.list_tools()
        for tool in tools.tools:
            print(f"  {tool.name}: {tool.description}")

        # Phase 3: Call a tool
        result = await session.call_tool(
            "search_papers", {"topic": "physics", "max_results": 2}
        )
```





<Sidenote category="pattern">Client lifecycle: `StdioServerParameters` $$ `stdio_client` context $$ `ClientSession` context $$ `initialize()` $$ `list_tools()` $$ `call_tool()`.</Sidenote>



&lt;!–MDXB-8-OPEN–&gt;

**Core Insight:** The `stdio_client` context manager launches the server as
a subprocess and returns read/write streams. These streams are passed to `ClientSession`,
which provides higher-level methods (`initialize`, `list_tools`, `call_tool`).
This two-layer design separates transport (how bytes flow) from protocol (what messages mean).

**Why It Matters:** When you switch from stdio to SSE, only the transport layer changes.
The `ClientSession` API stays identical. This is the value of protocol abstraction.

**When It Breaks:** If the server subprocess crashes, the read stream closes and
`ClientSession` operations will raise exceptions. Always handle connection errors.

&lt;!–MDXB-8-CLOSE–&gt;



<Sidenote category="warning">The client uses `async/await` extensively. Use `nest_asyncio` if running inside Jupyter or environments with existing event loops.</Sidenote>



# Chatbot with MCP Tools



<Sidenote category="practice">Target: build a chatbot with MCP tool routing in under 30 min. This is the end-to-end MCP integration pattern.</Sidenote>



The course builds `mcp_chatbot.py`—a host containing one client that connects
to the research server and exposes its tools to Claude<Citation src="claude2024docs" />. The key pattern: convert MCP tool
schemas to the Anthropic API format, send them with the prompt, and route tool calls
back through MCP.



```cypher
class MCPChatbot:
    def __init__(self):
        self.session = None  # set during connection
        self.tools = []      # populated after discovery

    async def process_query(self, query: str):
        messages = [{"role": "user", "content": query}]
        response = self.client.messages.create(
            model="claude-sonnet-4-20250514",
            messages=messages,
            tools=self.tools,
            max_tokens=4096,
        )

        # Tool call loop
        while response.stop_reason == "tool_use":
            tool_use = next(
                b for b in response.content if b.type == "tool_use"
            )
            # Route to MCP server
            result = await self.session.call_tool(
                tool_use.name, tool_use.input
            )
            # Continue with tool result
            messages.append({"role": "assistant",
                             "content": response.content})
            messages.append({"role": "user", "content": [{
                "type": "tool_result",
                "tool_use_id": tool_use.id,
                "content": result.content[0].text,
            }]})
            response = self.client.messages.create(
                model="claude-sonnet-4-20250514",
                messages=messages,
                tools=self.tools,
                max_tokens=4096,
            )
        return response.content[0].text
```





<Sidenote category="formula">Tool call flow: User $$ LLM $$ tool_use block $$ client routes to MCP server $$ server executes $$ result appended to messages $$ LLM responds.</Sidenote>



**Running the chatbot:**


```cypher
# Terminal
uv run mcp_chatbot.py

# Output:
# Processing list_tools request...
# Connected to server with tools: ['search_papers', 'extract_info']
# MCP Chatbot > search for physics papers
```



The `list_tools` request in the output confirms the MCP protocol discovery mechanism
is working—the client queried the server for available tools before starting the chat loop.

&lt;!–MDXB-9-OPEN–&gt;

**Core Insight:** The chatbot host implements a while loop: send messages + tools to the LLM;
if the response contains a `tool_use` block, route the call to the MCP server via
`session.call_tool()`, append the result to messages, and call the LLM again. The loop
terminates when the LLM responds with text instead of a tool call.

**Why It Matters:** This is the universal pattern for any MCP-powered application. Every
host—Claude Desktop, Cursor, custom agents—implements this same loop internally.

**When It Breaks:** If the LLM enters an infinite tool-calling loop (calling the same tool
repeatedly), you need a `max_turns` guard or deduplication logic.

&lt;!–MDXB-9-CLOSE–&gt;

# Multi-Server Clients



<Sidenote category="interview">Production MCP hosts aggregate tools and guard collisions.</Sidenote>





<Term name="Tool Aggregation" los="MCP-3.4">
  The pattern where a multi-server host collects tools from all connected MCP servers into a single unified list. A `tool_map` dictionary routes each tool call to the correct server session.
</Term>
<AnkiCard type="term" front={"Tool Aggregation"} back={"The pattern where a multi-server host collects tools from all connected MCP servers into a single unified list. A `tool_map` dictionary routes each tool call to the correct server session."} los="MCP-3.4" />



A single host can connect to multiple MCP servers simultaneously, presenting their combined
tool sets to the LLM as one unified list:



```cypher
class MultiServerHost:
    def __init__(self):
        self.sessions = {}     # server_name -> ClientSession
        self.tool_map = {}     # tool_name -> session

    async def connect(self, servers: dict[str, StdioServerParameters]):
        for name, params in servers.items():
            # Each server gets its own client session
            read, write = await stdio_client(params).__aenter__()
            session = await ClientSession(read, write).__aenter__()
            await session.initialize()
            self.sessions[name] = session

            # Aggregate tools with routing map
            tools = await session.list_tools()
            for tool in tools.tools:
                self.tool_map[tool.name] = session
```



&lt;!–MDXB-10-OPEN–&gt;

**Core Insight:** The LLM doesn’t know which server provides which tool. The host
aggregates all tools into one list and transparently routes calls to the correct server
via a `tool_map` dictionary. This enables composability: a weather server + a GitHub
server + a database server appear as one unified tool set.

**Why It Matters:** This is how Claude Desktop works. When you configure 5 MCP servers,
Claude sees all their tools as one combined set and routes calls automatically.

**When It Breaks:** Tool name collisions. If two servers expose `search`,
the `tool_map` will overwrite one. Fix: prefix with server name or reject collisions at startup.

&lt;!–MDXB-10-CLOSE–&gt;



<Sidenote category="warning">Tool name collisions across servers are silent bugs. The last server registered wins. Add collision detection at startup.</Sidenote>

**Build a Multi-Server Research Assistant**

Design an MCP client that connects to three servers simultaneously:

- **Brave Search:** Web search for current information

- **Filesystem:** Read local notes and documents

- **Memory:** Persist findings across conversation sessions

Describe: (1) the connection architecture, (2) tool routing strategy,
(3) the conversation flow for a research query, and (4) how to handle a server going down.

&lt;!–MDXB-11-CLOSE–&gt;

&lt;!–MDXB-12-OPEN–&gt;

**Approach:**
**Architecture:** Three `ClientSession` instances, one per server.
Tool map aggregates all tools. Connection errors for one server don’t block others.

**Conversation flow:**

1.  User asks a research question

2.  LLM calls `brave_search` (Brave server) to find current information

3.  LLM calls `read_file` (Filesystem server) to check local notes for prior work

4.  LLM synthesizes web results with local context

5.  LLM calls `store_memory` (Memory server) to persist key insights

6.  LLM responds with the final answer

**Server failure handling:** If the Memory server is down, the host catches the connection
error, removes its tools from the aggregated list, and proceeds with the remaining servers.
The LLM can still search and read files—it just can’t persist findings this session.

**Key Insight:** The Memory server is what makes the agent persistent. Without it,
each session starts from scratch. With it, the agent accumulates knowledge—the foundation
of long-term agent memory.

**Answer:** The Memory server is what makes the agent persistent. Without it,
each session starts from scratch.

\[MCP-3.2, MCP-3.4, MCP-5.4\]
StreamCo builds a content recommendation agent that connects to three MCP
servers: `catalog` (movie/show metadata), `analytics`
(viewing history and engagement data), and `social` (trending
topics from social media APIs). The agent works in development, but after
deploying to production with SSE transport, users report two problems:
(1) the agent intermittently returns “I don’t have access to viewing
data” even though the analytics server is running, and (2) when a user
asks “What’s trending that I haven’t watched?”, the agent calls
`catalog.search_titles` but never calls the analytics or social
servers, producing generic recommendations.

The team’s client code aggregates tools from all three servers into a
single tool map using `tool_name: server_session` pairs. The
analytics server exposes a tool called `search_content` and the
catalog server also exposes `search_content`.

**Question 1:** Diagnose problem (1). Trace the tool call lifecycle
for a viewing history request. At which stage does the failure occur, and
why is it intermittent?

**Question 2:** Diagnose problem (2). Why does the agent only call
one server for a query that requires all three? Identify the root cause
in the tool aggregation architecture.

**Question 3:** Design a fix for the tool name collision. Propose
two approaches (namespacing and aliasing), compare their tradeoffs, and
recommend one. How does your fix affect the LLM’s tool selection
accuracy?

&lt;!–MDXB-14-CLOSE–&gt;

&lt;!–MDXB-13-OPEN–&gt;

**Approach:**
**Question 1:** The intermittent failure is a SSE connection
timeout. The analytics server’s `search_content` tool queries a
data warehouse that sometimes takes 30+ seconds. SSE connections through
the production load balancer timeout at 60 seconds (idle). When the
analytics query runs long without sending data, the connection drops.
The client catches a connection error and the LLM, unable to call the
tool, responds with “I don’t have access.” The lifecycle: discover
→ present → route → *timeout during return* → error.
Fix: implement SSE heartbeat pings during long queries.

**Question 2:** Tool name collision. Both servers expose
`search_content`. The tool map uses `tool_name` as the
key, so one server’s tool overwrites the other during aggregation.
Depending on connection order (which varies—hence intermittent), the
LLM sees either the catalog or analytics version. When catalog wins,
the LLM has no tool for viewing history or social data, so it falls
back to catalog-only recommendations. The LLM is not ignoring the other
servers—it literally cannot see their tools.

**Question 3:**

- **Namespacing:** Prefix each tool with its server name:
  `catalog_search_content`,
  `analytics_search_content`. Pro: zero server-side
  changes, applied at client aggregation. Con: tool names become
  longer, potentially confusing the LLM.

- **Aliasing:** Keep original names but maintain a map from
  `(server, tool)` to a unique alias. Pro: server code
  unchanged, aliases can be human-readable
  (`search_catalog`, `search_viewing_history`).
  Con: requires a mapping layer in the client.

Recommendation: aliasing. Descriptive aliases improve LLM tool selection
because the tool name itself signals intent (“search\_viewing\_history”
is more informative than “analytics\_search\_content”). The mapping
layer is 10 lines of code and prevents all future collisions.

**Key Insight:** Tool name collision in multi-server clients is the
MCP equivalent of a namespace conflict. Unlike code imports, there is no
compiler to catch it—the second tool silently overwrites the first.
Multi-server clients must assume collisions will occur and handle them
architecturally.

**Answer:** Tool name collision in multi-server clients is the
MCP equivalent of a namespace conflict. Unlike code imports, there is no
compiler to catch it—the second tool silently overwrites the first.
