# Pre-Training Mechanics



<Sidenote category="interview">Pre-training = self-supervised next-token prediction on web-scale data. No human labels required.</Sidenote>



Every large language model begins as a blank slate. At initialization, the model’s
weights are completely random—it cannot form English words, let alone reason about
the world<Citation src="dlai-ft-course" />. The training objective that transforms these random
weights into a capable language model is remarkably simple: **next-token prediction**.
Given a sequence of tokens, the model learns to predict the token that comes next.



<Sidenote category="pattern">Pre-training pipeline: random init $$ next-token loss on web corpus $$ base model with knowledge but no task behavior.</Sidenote>



This process is called **self-supervised learning** because the training signal
comes from the data itself rather than from human annotators. The model reads a token
sequence like “Once upon a” and must predict “time.” No one labels these pairs; the
structure of language provides the supervision for free. As Sharon Zhou demonstrates
in the course, a model that starts by producing gibberish like “sd!!!@” for the next
word eventually learns to predict “upon” after “wants”—simply by processing enough
text<Citation src="dlai-ft-course" />.



<Term name="Pre-Training" los="FT-1.1">
  The initial phase of LLM training in which a model with random weights learns language structure and world knowledge through next-token prediction on a massive, unlabeled corpus<Citation src="brown2020gpt3" />.
</Term>

<Sidenote category="warning">Pre-training data quality matters: "scraped from the web" still requires extensive cleaning pipelines.</Sidenote>



The scale of pre-training data is staggering. While closed-source models keep their
datasets private, the open-source community has produced well-documented alternatives.
EleutherAI’s **The Pile** is a curated collection of 22 diverse datasets totaling
approximately 800 GB of text<Citation src="gao2020pile" />. It includes:

- Historical and literary texts (e.g., the Gettysburg Address)

- Scientific literature from PubMed

- Source code from GitHub

- Web-scraped general knowledge

- Recipes, news, and encyclopedic content



<Sidenote category="formula">The Pile: 22 datasets, $$800 GB. Model learns code, medicine, history, and recipes—all via next-token loss.</Sidenote>



This diversity is deliberate: a model pre-trained on The Pile learns not just English
grammar but also how to write code, discuss medical topics, and reason about history.
The breadth of knowledge comes from the breadth of data.

&lt;!–MDXB-16-OPEN–&gt;

**Core Insight:** Pre-training via next-token prediction on web-scale data
produces a model that has absorbed broad knowledge and language fluency, but has
no particular task behavior—it will continue text in whatever pattern it has
seen most, not answer questions or follow instructions.

**Why It Matters:** This is the foundation every fine-tuned model builds on.
The base model’s knowledge ceiling is set during pre-training; fine-tuning steers
behavior but rarely adds fundamentally new knowledge domains.

**When It Breaks:** When the pre-training corpus lacks coverage of a specific
domain (e.g., proprietary internal documentation), fine-tuning alone may not
compensate—you may also need retrieval augmentation.

&lt;!–MDXB-16-CLOSE–&gt;

Pre-training is computationally expensive precisely because it is so data-intensive.
Training a model to go from randomness to understanding the Gettysburg Address,
carrot cake recipes, and Python code simultaneously requires processing hundreds
of billions of tokens across thousands of GPUs<Citation src="biderman2023pythia" />.

# Base Model Limitations



<Sidenote category="interview">"Why can't you just use a base model?" Because it autocompletes—it does not answer. Interviewers test this distinction.</Sidenote>



Pre-trained base models are powerful but not useful as assistants out of the box.
The course illustrates this with a vivid example: imagine the model has seen
geography homework in its training data—lists of questions like “What is the
capital of Kenya? What is the capital of France?”<Citation src="dlai-ft-course" />

When you then input “What is the capital of Mexico?”, the base model does not
answer “Mexico City.” Instead, it continues the pattern it learned: it outputs
“What is the capital of Hungary?”—because in its training data, geography
questions were followed by more geography questions, not by answers.



<Sidenote category="warning">Base models mimic training data patterns. If training data has Q-then-Q format, the model produces more questions, not answers.</Sidenote>



This is not a bug; it is the direct consequence of the training objective. The model
learned to predict what comes next in text, and in the text it saw, the next thing
after a geography question was another geography question. As Zhou puts it: “It’s not
really useful from the sense of a chatbot interface”<Citation src="dlai-ft-course" />.

The gap between a base model and something like ChatGPT is precisely the gap that
fine-tuning bridges. ChatGPT was created by taking a base GPT model and fine-tuning
it with instruction-following data so that it learns a new pattern: questions should
be followed by answers, not more questions<Citation src="ouyang2022instructgpt" />.



<Sidenote category="practice">Try The Pile in HuggingFace: `datasets.load_dataset("EleutherAI/pile", streaming=True)`</Sidenote>



~~~ python
from datasets import load_dataset

# Pre-training data: massive, unstructured, scraped
pretrain_data = load_dataset(
    "EleutherAI/pile", split="train", streaming=True
)
# Each sample is just raw text -- no structure
for sample in itertools.islice(pretrain_data, 5):
    print(sample["text"][:200])

# Fine-tuning data: small, structured Q&A pairs
finetune_data = [
    {"question": "What is Lamini?",
     "answer": "Lamini is a platform for fine-tuning LLMs."}
]
~~~

The contrast between pre-training data and fine-tuning data is stark. Pre-training
data is a “hodgepodge” of web scrapes—app reviews, XML code, news articles about
AWS, and family fishing businesses all mixed together. Fine-tuning data is structured:
question-answer pairs, instruction-response pairs, or input-output pairs curated for
a specific task<Citation src="dlai-ft-course" />.

# Fine-Tuning vs Prompt Engineering



<Sidenote category="interview">"When would you fine-tune vs prompt?" Top interview Q. Answer with the four axes: consistency, tone, data privacy, cost.</Sidenote>



Fine-tuning and prompt engineering are complementary tools, not competitors. Prompt
engineering writes instructions in the input context; fine-tuning changes the model’s
weights so those instructions become the default behavior<Citation src="dlai-ft-course" />.



<Term name="Fine-Tuning" los="FT-1.3">
  The process of further training a pre-trained LLM on a smaller, task-specific dataset, updating the model's weights to specialize its behavior for a particular domain or task<Citation src="dlai-ft-course" />.
</Term>
<AnkiCard type="term" front={"Fine-Tuning"} back={"The process of further training a pre-trained LLM on a smaller, task-specific dataset, updating the model's weights to specialize its behavior for a particular domain or task[dlai-ft-course]."} los="FT-1.3" />





<Sidenote category="pattern">Fine-tuning advantage axes: (1) consistency, (2) tone, (3) private data, (4) reduced prompting cost at inference.</Sidenote>



Zhou identifies two major categories of what fine-tuning achieves:

1.  **Behavior change:** The model learns to respond in a specific format
    (chat vs. survey), maintain consistent tone, focus on particular tasks
    (e.g., moderation), and generally “tease out its capabilities” without
    extensive prompt engineering at inference time.

2.  **Knowledge gain:** The model absorbs information about specific topics
    not present in pre-training data, corrects outdated information, or
    incorporates proprietary company data.

In practice, most fine-tuning applications involve both—you want the model to know
about your domain *and* behave in a particular way when discussing it.

&lt;!–MDXB-17-OPEN–&gt;

**Core Insight:** All LLM tasks are text-in, text-out. **Extraction** tasks
produce less text than the input (reading: keywords, topics, routing, classification).
**Expansion** tasks produce more text than the input (writing: chat, email, code
generation). Knowing which category your task falls into is “the clearest indicator
of success” for fine-tuning<Citation src="dlai-ft-course" />.

**Why It Matters:** Extraction and expansion tasks need different evaluation
strategies and different data formats. Extraction can often be evaluated with exact
match or F1; expansion requires human judgment or model-based evaluation.

**When It Breaks:** Some tasks straddle both categories (e.g., summarization
extracts key points but generates new prose). Classify by the dominant behavior.

&lt;!–MDXB-17-CLOSE–&gt;



<Sidenote category="crossref">For instruction fine-tuning details (InstructGPT/RLHF), see Ch 2.</Sidenote>



The recommended first-time fine-tuning workflow is deliberately conservative:

1.  **Prompt-engineer first:** Use ChatGPT or another large LLM to explore
    your task. Find something it does “okay at—not great, but not horrible.”

2.  **Pick one task.** Do not try to fine-tune for multiple tasks
    simultaneously on your first attempt.

3.  **Collect 1,000 input-output pairs.** This is Zhou’s “golden number”—a
    practical starting point that balances data collection effort against
    fine-tuning performance gains.

4.  **Ensure quality exceeds the baseline.** Your training pairs must be
    better than what the prompted LLM produces. You cannot simply generate
    fine-tuning data from the model you intend to improve.

5.  **Fine-tune a small LLM** to validate the performance bump before
    scaling up.



<Sidenote category="formula">Golden rule: 1,000 high-quality pairs as starting dataset. Quality must beat prompted baseline.</Sidenote>



Fine-Tuning vs Prompt Engineering
This is one of the most common questions in ML engineer interviews, especially
at companies building LLM-powered products. Interviewers are testing whether you
understand the trade-off space, not just the definitions.

**What they want to hear:**

- Prompt engineering is cheaper to start, faster to iterate, requires no
  training infrastructure, but adds latency and token cost at every inference call.

- Fine-tuning requires upfront data collection and compute, but yields consistent
  behavior without long prompts, can encode private data into weights, and
  reduces per-request cost once deployed.

- The two are not mutually exclusive: you can fine-tune *and* use prompts,
  and you can combine either with retrieval augmented generation (RAG).

**Meta-signal:** The interviewer is testing whether you can reason about
engineering trade-offs (cost, latency, consistency, data privacy) rather than
defaulting to a single tool.



<Sidenote category="warning">Do not generate fine-tuning data from the model you want to improve—the ceiling stays the same.</Sidenote>



The fine-tuning data format matters. The simplest approach is to concatenate question
and answer as plain text. A more structured approach uses prompt templates with
delimiters (e.g., `### Question:` / `### Answer:`) that help the
model learn expected structure and simplify post-processing of outputs. Data is
typically stored in JSONL format (one JSON object per line) and can be uploaded to
HuggingFace Hub for reproducibility<Citation src="dlai-ft-course" />.

~~~ python
# Prompt template for fine-tuning data
prompt_template = """### Question:
{question}

### Answer:
{answer}"""

# Apply template to all examples
formatted = [
    prompt_template.format(**pair)
    for pair in qa_pairs
]
~~~

\[foundation\]
A junior engineer prompts a base GPT model with “What is the capital of
France?” and receives a list of ten more geography trivia questions instead
of “Paris.” They conclude the model “doesn’t know geography.” Explain why
this diagnosis is wrong and what is actually happening.

&lt;!–MDXB-22-CLOSE–&gt;

&lt;!–MDXB-27-OPEN–&gt;

**Approach:** Trace the base model’s training objective back to its
behavior.

Base models are trained with a next-token prediction (language modeling)
objective on internet text. A passage that begins “What is the capital of
France?” in the training corpus is most often followed by more quiz questions
(e.g., a geography quiz page), not by the answer “Paris.” The model is
faithfully completing the most likely continuation of the text distribution it
learned—it is *completing*, not *answering*. The knowledge of
“Paris” is encoded in the weights; the model simply has no behavioral
incentive to surface it as a direct answer without instruction fine-tuning.

**Key Insight:** Base models optimize for completion probability, not
helpfulness—the knowledge is present, but the response format is wrong.

**Answer:** The model knows “Paris” but its pre-training objective
produces the most likely text continuation (more quiz questions), not a direct
answer. Instruction fine-tuning is needed to reshape the output format.
