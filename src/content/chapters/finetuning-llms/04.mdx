# Getting Started — The Practical Workflow



<Sidenote category="interview">Iterate small: start 400M–1B params, vary data volume, evaluate, then scale. Most candidates jump to 7B+ and waste weeks.</Sidenote>



The course emphasizes a pragmatic workflow: resist the temptation to start
large<Citation src="dlai-ft-course" />. Following these steps in order prevents the most
common failure—over-investing in compute before understanding the data.

1.  **Define your task.** Be specific: “classify tickets into 12 categories,”
    not “customer support.”

2.  **Collect and structure data.** Gather input–output pairs. If data
    is insufficient, generate synthetic examples or use prompt templates.

3.  **Fine-tune a small model first.** Start 400M–1B parameters. The goal
    is understanding data influence, not production quality.

4.  **Vary data volume.** Train with 100, 500, 1K, 5K examples. Plot loss
    curves to find where more data stops helping.

5.  **Evaluate.** Task-specific accuracy, human evaluation, benchmarks.
    Identify failure modes.

6.  **Fix data based on failures.** Targeted data collection is the
    iterative loop that matters most.

7.  **Scale up only when justified.** Increase model size only after you
    understand the data–performance curve at smaller scale.



<Sidenote category="pattern">Fine-tuning loop: define task $$ collect data $$ train small $$ evaluate $$ fix data $$ scale. Never skip to "scale."</Sidenote>



# Task Complexity and Model Sizing



<Sidenote category="interview">Reading tasks (extraction, classification) $$ small models. Writing tasks (chat, code gen) $$ larger models. Know the boundary.</Sidenote>



Not all tasks require the same model capacity. The course draws a fundamental
distinction between *reading* tasks and *writing* tasks that maps
directly to model sizing decisions<Citation src="dlai-ft-course" />.

**Reading tasks** (classification, NER, intent detection) produce few tokens
with a constrained output space. Models in the 70M–300M range often suffice, and
fine-tuning converges quickly<Citation src="biderman2023pythia" />.



<Sidenote category="warning">"Writing" = more output tokens = harder. A chatbot producing 200-token replies needs far more capacity than a classifier producing one label.</Sidenote>



**Writing tasks** (email, code generation, chat) produce many tokens and
require maintaining coherence. Models below 1B rarely produce fluent extended
text; 7B–13B is the practical starting point for production writing.

**Combination tasks** (agents, multi-step reasoning) layer reading and writing.
These typically require 7B+ parameters, with substantial gains from scaling to
13B or 70B<Citation src="brown2020gpt3" />.

| **Task Type**        | **Examples**                 | **Recommended Size** |
|:---------------------|:-----------------------------|:---------------------|
| Simple extraction    | NER, classification, routing | 70M–300M             |
| Constrained writing  | Short-form QA, slot filling  | 300M–1B              |
| Open-ended writing   | Chat, email, summarization   | 1B–7B                |
| Multi-step reasoning | Code gen, agents, complex QA | 7B–70B               |

Task complexity to model size mapping. These are starting points for
fine-tuning; pre-trained model quality and data volume shift the boundaries.



<Sidenote category="formula">GPU memory rule: inference $$ 2$$ params (fp16), training $$ 4–8$$ params (optimizer states + gradients).</Sidenote>



## Compute Requirements

Concrete hardware mapping: a V100 (16 GB) runs a 7B model for inference but can
only *train* up to ∼1B parameters<Citation src="dlai-ft-course" />. Training needs
4–8× more memory (gradients, Adam momentum buffers, activations). This
inference-training memory gap motivates parameter-efficient methods: reduce
trainable parameters by 10,000× and fine-tune models that otherwise need
a GPU cluster.

# Parameter-Efficient Fine-Tuning (PEFT/LoRA)



<Sidenote category="interview">LoRA is the single most common PEFT interview topic. Know: freeze base, add low-rank matrices, merge at inference. 30-second explanation.</Sidenote>





<Term name="LoRA (Low-Rank Adaptation)" los="FT-4.3">
  A parameter-efficient fine-tuning method that freezes pre-trained model weights and injects trainable low-rank decomposition matrices into each transformer layer. For a weight matrix $W  R^{d  k}$, LoRA adds $ W = BA$ where $B  R^{d  r}$ and $A  R^{r  k}$ with rank $r  (d, k)$. At inference, the adapter merges into the base weights with zero latency overhead<Citation src="hu2022lora" />.

Full fine-tuning updates every parameter. For GPT-3 (175B parameters), this
requires hundreds of gigabytes of GPU memory for gradients and optimizer states
alone<Citation src="brown2020gpt3" />. LoRA solves this elegantly.

## The LoRA Mechanism



<Sidenote category="pattern">LoRA in one sentence: instead of updating $W$ directly, learn $ W = BA$ where $B$ and $A$ are thin matrices. Train $r  (d + k)$ params instead of $d  k$.</Sidenote>



The key insight behind LoRA is that the weight updates during fine-tuning have
low intrinsic rank—they can be well-approximated by the product of two much
smaller matrices<Citation src="hu2022lora" />. For a pre-trained weight matrix
*W*<sub>0</sub> ∈ ℝ<sup>*d* × *k*</sup>, the update is:

*W* = *W*<sub>0</sub> + *Δ**W* = *W*<sub>0</sub> + *B**A*

where *B* ∈ ℝ<sup>*d* × *r*</sup> and *A* ∈ ℝ<sup>*r* × *k*</sup>,
with rank *r* typically between 4 and 64.

**During training:** *W*<sub>0</sub> is frozen (no gradients, no optimizer states).
Only *B* and *A* receive gradients: *r* × (*d* + *k*) trainable parameters per
layer instead of *d* × *k*. Initialization sets *B* = 0, so *Δ**W* = 0 at
the start—the model begins identical to the pre-trained version.

**During inference:** Merge *W* = *W*<sub>0</sub> + *B**A* via a one-time matrix addition.
The merged model has identical architecture and latency to the original. To revert,
subtract *B**A*. To switch tasks, swap adapters.



<Sidenote category="formula">Parameter reduction: $r(d+k)$ vs. $dk$. For $d=k=4096$, $r=8$: 65K vs. 16.7M params per layer. That is 256$$ fewer.</Sidenote>



&lt;!–MDXB-17-OPEN–&gt;

**Core Insight:** Fine-tuning weight updates are low-rank. LoRA exploits
this by decomposing *Δ**W* into two thin matrices *B* and *A*, reducing
trainable parameters by orders of magnitude while preserving the pre-trained
model’s knowledge in the frozen weights.

**Why It Matters:** For GPT-3, LoRA reduces trainable parameters by
10,000× and GPU memory by 3×, making fine-tuning of large models
feasible on commodity hardware. At inference, merged weights add zero latency.
This is the method that made fine-tuning accessible to teams without GPU
clusters<Citation src="hu2022lora" />.

**When It Breaks:** LoRA assumes the fine-tuning task’s weight updates are
low-rank. Tasks requiring fundamentally different representations from pre-training
(e.g., adapting an English model to Chinese from scratch) may exceed what low-rank
updates can capture. In such cases, higher rank *r* or full fine-tuning may be
needed.

&lt;!–MDXB-17-CLOSE–&gt;

## Rank Selection



<Sidenote category="warning">Rank too low = underfitting (can't capture task). Rank too high = overfitting + losing efficiency gains. Start $r=8$, adjust.</Sidenote>



The rank *r* is the primary hyperparameter in LoRA, controlling adapter
expressiveness: *r* = 1–4 for minimal adaptation (binary classification);
*r* = 8–16 as the sweet spot for most tasks (the LoRA paper found *r* = 4–8
sufficient for GPT-3<Citation src="hu2022lora" />); *r* = 32–64 for complex domain shifts;
*r* = 128+ yields diminishing returns with growing overfitting risk.



<Sidenote category="practice">Start $r=8$, double if validation loss plateaus. If $r=64$ still underperforms, the bottleneck is data, not rank.</Sidenote>



The practical approach: start with *r* = 8, evaluate. Overfitting (training loss
drops, validation plateaus) means reduce *r*. Both losses plateau means increase
*r*. If *r* = 64 still underperforms, the problem is data, not adapter capacity.

LoRA mitigates catastrophic forgetting by keeping pre-trained weights frozen and confining adaptation to low-rank subspaces<Citation src="hu2022lora" />.

## Multi-Customer LoRA Deployment



<Sidenote category="interview">Multi-adapter LoRA: one base model, N customer adapters swapped at inference. Storage = base + N $$ tiny adapter files. This is a system design question.</Sidenote>



One of LoRA’s most powerful production applications<Citation src="dlai-ft-course" />: serve
multiple customers from a single base model. Train Customer A’s adapter (*B*<sub>*A*</sub>, *A*<sub>*A*</sub>),
Customer B’s adapter (*B*<sub>*B*</sub>, *A*<sub>*B*</sub>). At inference, load the base model once; merge
*W*<sub>0</sub> + *B*<sub>*i*</sub>*A*<sub>*i*</sub> for whichever customer is active. Adapters are tens of MB vs. tens of GB for the full model—swapping is a matrix addition, not a model reload.



<Sidenote category="pattern">LoRA adapters decouple *capability* (base model) from *customization* (adapter). This is the plugin architecture of ML.</Sidenote>



Instead of hosting *N* separate fine-tuned models, host one base model and *N*
lightweight adapters. Cost scales linearly in *storage* but remains constant
in *GPU memory*.

# Fine-Tuning vs RAG — Decision Framework



<Sidenote category="interview">"When would you fine-tune vs. use RAG?" is the most common LLM systems design question. Have a crisp 2-minute framework ready.</Sidenote>



Fine-tuning and RAG solve different problems, and confusing them is among the most
expensive mistakes in LLM application design<Citation src="dlai-ft-course" />.

**Fine-tuning changes how the model behaves**—output style, format,
reasoning patterns. After fine-tuning, the model *intrinsically* produces
different outputs with no external data at inference.

**RAG changes what the model knows**—retrieves documents at inference and
injects them into the prompt. Weights unchanged; the model simply has more context.

| **Dimension** | **Fine-Tuning**              | **RAG**                     |
|:--------------|:-----------------------------|:----------------------------|
| Modifies      | Model weights (behavior)     | Prompt context (knowledge)  |
| Best for      | Tone, format, reasoning      | Factual recall, freshness   |
| Data needs    | 100–10,000+ labeled pairs    | Document corpus             |
| Latency       | No overhead at inference     | Retrieval adds 100–500ms    |
| Freshness     | Static after training        | Real-time document updates  |
| Hallucination | Reduced for trained patterns | Reduced for retrieved facts |
| Cost          | GPU hours for training       | Vector DB + retrieval infra |

Fine-tuning vs. RAG across key decision dimensions.

## When to Fine-Tune

Fine-tune when the problem is *behavioral*: consistent output format (JSON,
templates, brand voice), domain-specific reasoning patterns (medical, legal),
instruction following that the base model lacks<Citation src="ouyang2022instructgpt" />,
latency-critical paths (zero inference overhead), or constrained output tasks
(classification, extraction, routing).

## When to Use RAG

Use RAG when the problem is *knowledge*: frequently changing information
(catalogs, news), factual grounding with citations, large knowledge bases
exceeding what any model can memorize, or rapid deployment without training.

## When to Combine Both



<Sidenote category="warning">Hybrid = fine-tune for behavior + RAG for knowledge. Most production LLM systems end up here. Build RAG first, add FT when behavior gaps appear.</Sidenote>



Most production systems combine both: fine-tune for behavioral consistency (voice,
schema, reasoning) and RAG for knowledge injection (product info, policies,
customer history). Example: a support system fine-tuned on 5,000 transcripts
for tone with RAG over the product knowledge base for accuracy.

&lt;!–MDXB-18-OPEN–&gt;

**Core Insight:** Fine-tuning changes behavior (how the model responds);
RAG changes knowledge (what the model knows). They solve orthogonal problems.
The question is never “fine-tune *or* RAG” but rather “what is the model
getting wrong—its behavior or its knowledge?”

**Decision Rule:**
If the model says the right things in the wrong way → fine-tune.
If the model says the wrong things in the right way → RAG.
If both → hybrid (fine-tune first for behavior, add RAG for knowledge).

**When It Breaks:** Extremely domain-specific tasks (e.g., radiology report
generation) may require fine-tuning for both behavior *and* domain knowledge,
because RAG alone cannot teach the model the reasoning patterns of a specialist.
Conversely, if your “behavior problem” is really a prompt engineering problem,
fine-tuning is overkill.

&lt;!–MDXB-18-CLOSE–&gt;

Interview question for ML/AI Engineering roles at L5+: “You have a base LLM and
a customer wants it to respond in their specific brand voice, always output valid
JSON, and answer questions about their 10,000-page product catalog. How would
you architect this?”

**Strong answer:** “Hybrid problem. Brand voice + JSON format = behavioral
→ fine-tune with LoRA (*r* = 8–16) on 500–1K examples. Product catalog =
knowledge → RAG over vector DB, retrieve top-*k* chunks. The fine-tuned model
formats retrieved information correctly because it learned the output pattern. Build
RAG first to validate retrieval, then add fine-tuning for behavior.”

**Meta-signal:** Tests decomposing ambiguous requirements into behavior vs. knowledge components. Weak: “fine-tune everything” or “just use RAG.” Strong:
identify the orthogonal axes and architect each component with the right tool.

**Choose the Right LoRA Rank**

You are fine-tuning a 7B parameter model for two tasks:

1.  Binary sentiment classification on product reviews (positive/negative).

2.  Open-ended customer email generation matching a specific brand voice.

Your GPU has 24 GB of memory. For each task, recommend a LoRA rank *r*, estimate
the number of trainable parameters (assume LoRA is applied to query and value
projection matrices with *d* = 4096), and justify your choice.

&lt;!–MDXB-19-CLOSE–&gt;

&lt;!–MDXB-22-OPEN–&gt;

**Step 1: Task (a) — Sentiment Classification.**
Simple reading task, two-element output. Recommend *r* = 4.
Params per layer: 4 × (4096 + 4096) = 32, 768. Across *Q*, *V* in 32 layers:
32, 768 × 2 × 32 = 2.1M trainable params (0.03% of 7B).

**Step 2: Task (b) — Email Generation.**
Complex writing with style constraints. Recommend *r* = 16.
Params per layer: 16 × 8192 = 131, 072. Total:
131, 072 × 64 = 8.4M trainable params (0.12% of 7B).

**Step 3: Memory.**
7B in fp16 ≈ 14 GB. LoRA optimizer states add ∼50 MB even at
*r* = 16. Both tasks fit comfortably in 24 GB.

**Key Insight:** Rank should match task complexity, not model size. A simple
task on a large model still needs low rank. The rank controls expressiveness of the
*adaptation*, not the base capability.

**Answer:** (a) *r* = 4, ∼2.1M trainable params. (b) *r* = 16,
∼8.4M trainable params. Both fit in 24 GB.

**Design an Adapter Strategy for 10 Clients**

You manage an ML platform serving 10 enterprise clients. Each client wants the
same base 13B model fine-tuned on their proprietary support transcripts (2,000–5,000
examples each). Your infrastructure has 4 A100 GPUs (80 GB each).

1.  Design the adapter strategy: training, storage, and serving architecture.

2.  Calculate total storage for base model + 10 adapters at *r* = 8.

3.  A new client arrives. How long before they are live?

&lt;!–MDXB-20-CLOSE–&gt;

&lt;!–MDXB-23-OPEN–&gt;

**Step 1: Architecture Design.**

**Training:** One LoRA adapter per client. Each run uses 1 A100 (13B + LoRA
fits in ∼30 GB). Four clients train in parallel; 3 rounds for all 10.
**Storage:** Base model once (∼26 GB fp16) + 10 adapter files.
**Serving:** Load base model once. Swap client adapters via LRU cache at
request time.

**Step 2: Storage Calculation.**

For 13B model with *d* = 5120 (typical for 13B), LoRA at *r* = 8 applied to
*Q* and *V* across 40 layers:
Params per adapter = 8 × (5120 + 5120) × 2 × 40 = 6, 553, 600 ≈ 6.6M
At fp16: 6.6M × 2 bytes = 13.2 MB per adapter.

Total: 26 GB (base) + 10 × 13.2 MB (adapters) = 26.13 GB.

The 10 adapters add 0.5% to total storage.

**Step 3: Time to Live for New Client.**
Receive data (hours) → preprocess (hours) → train adapter (1–4 hrs on A100)
→ evaluate (hours) → deploy adapter file (seconds). Total: 1–2 business
days, dominated by data prep—not training.

**Key Insight:** Multi-customer LoRA turns model fine-tuning from a per-client
GPU cost into a per-client *storage* cost. The base model is a shared fixed
cost; each additional client adds only megabytes of adapter weights.

**Answer:** (a) One base model + per-client LoRA adapters with LRU adapter cache.
(b) 26.13 GB total (adapters add 0.5%). (c) 1–2 days, bottlenecked by data prep.
