<NarrativeBox title="Where We Are">

You have an LLM that can answer questions—but only from its pre-training
knowledge. Users need answers grounded in *their* documents: internal
wikis, legal contracts, research papers. Retrieval Augmented Generation (RAG)
bridges this gap by fetching relevant context at query time and injecting it
into the LLM prompt. This chapter builds the baseline pipeline and establishes
the evaluation framework that will guide every improvement in Modules 2–4.

</NarrativeBox>

# Why RAG Matters

<Sidenote category="interview">"Walk me through a RAG pipeline" is a top-3 question for MLE and applied scientist roles at every major tech company.</Sidenote>



Anupam Datta opens the course with a critical observation: getting LLMs to
answer questions over a user’s own data requires both effective
**retrieval techniques** that give the LLM highly relevant context
and an effective **evaluation framework** to help you iterate
efficiently. Raw LLMs hallucinate when they lack context; naive RAG
retrieves irrelevant chunks<Citation src="lewis2020retrieval" />. The goal of this course
is to close both gaps simultaneously.

The two advanced retrieval methods covered in this course are:

- **Sentence-window retrieval**: retrieves individual sentences
  for precision, then expands each with its surrounding context window
  before synthesis.

- **Auto-merging retrieval**: organises documents into a
  hierarchy of parent-child chunks, merging children into parents
  when enough children are retrieved.

# The Three-Stage RAG Pipeline

<PipelineBox title="Pipeline: Basic RAG">

1.  **Ingestion** *(offline, one-time)*  
    Load documents → split into text chunks → generate
    embeddings → store in a vector index.

2.  **Retrieval** *(online, per-query)*  
    Accept user query → fetch top-K most similar chunks from
    the vector index via embedding similarity search.

3.  **Synthesis** *(online, per-query)*  
    Combine retrieved chunks with the user query into the LLM
    prompt window → generate the final response.

</PipelineBox>



<Sidenote category="pattern">The pipeline pattern: every RAG system—basic or advanced—follows ingestion $$ retrieval $$ synthesis. Advanced techniques modify *how* each stage works, not *whether* it exists.</Sidenote>



# Ingestion: From Documents to Vectors



<Sidenote category="crossref">For document parsing, normalization, and chunking with Unstructured, see Preprocessing Ch 1–5</Sidenote>



<ConceptBox>

**The Chunking Dilemma.**
Embedding models work best on short, focused passages (128–512 tokens).
LLMs work best with longer, contextually rich passages (512–2048 tokens).
The basic pipeline uses the *same chunk* for both embedding and
synthesis. This tension is the fundamental problem that advanced retrieval
techniques solve.

</ConceptBox>

The ingestion stage has four sequential steps:

1.  **Load documents**: Read the source PDF, HTML, or text files
    into memory. The course uses Andrew Ng’s *How to Build a
    Career in AI* PDF (41 pages).

2.  **Merge into a single document**: For advanced retrieval
    methods, merging all pages into one document improves text blending
    accuracy across page boundaries.

3.  **Split into chunks**: A text splitter divides the document
    into overlapping or non-overlapping segments of a target size.

4.  **Embed and index**: Each chunk is passed through an
    embedding model (e.g., `BAAI/bge-small-en-v1.5`), and the
    resulting vector is stored in the index alongside the source text.



<Sidenote category="warning">Always merge multi-page documents into a single string before chunking. Page boundaries create artificial breaks that degrade retrieval quality for advanced methods.</Sidenote>





<Sidenote category="formula">Chunk overlap rule of thumb: 10–15% overlap between adjacent chunks to prevent hard boundary information loss. E.g., 256-token chunks with 32-token overlap.</Sidenote>



# Setting Up the Baseline with LlamaIndex

Jerry Liu demonstrates the baseline pipeline using LlamaIndex’s high-level
API, which abstracts the ingestion steps into a single call.



```cypher
from llama_index import VectorStoreIndex, ServiceContext
from llama_index.llms import OpenAI
from llama_index.embeddings import HuggingFaceEmbedding

# LLM and embedding model
llm = OpenAI(model="gpt-3.5-turbo", temperature=0.1)  % freshness-ok
\warningmargin{Course uses gpt-3.5-turbo; modern equivalent: gpt-4o-mini}
embed_model = HuggingFaceEmbedding(model_name="BAAI/bge-small-en-v1.5")

# Service context bundles LLM + embedding model
service_context = ServiceContext.from_defaults(
    llm=llm, embed_model=embed_model
)

# One-line ingestion: chunking, embedding, and indexing
index = VectorStoreIndex.from_documents(
    documents, service_context=service_context
)

# Query engine for retrieval + synthesis
query_engine = index.as_query_engine()
response = query_engine.query(
    "What are steps to take when finding projects to build your experience?"
)
```

# The RAG Triad of Metrics

<KeyConcept title="The RAG Triad" los="BEA-1.3">

Three evaluation metrics that together assess every critical step of a
RAG pipeline’s execution. Each metric isolates a different failure mode:

- **Answer Relevance**: Is the final response relevant to
  the user’s query? Compares *Response vs. Query*.

- **Context Relevance**: Is the retrieved context relevant
  to the query? Compares *Retrieved Context vs. Query*.

- **Groundedness**: Is the response supported by the
  retrieved context? Compares *Response vs. Retrieved Context*.

These three metrics form a triangle of trust: if any one fails, the
RAG system is unreliable.

**When It Breaks:** The triad assumes the evaluation provider is
reliable. A weak evaluator (e.g., GPT-3.5 scoring groundedness) can
produce false positives, masking real failures. Always calibrate
automated scores against manual review on 10–20 records.

</KeyConcept>

<InterviewContext title="RAG Evaluation: The Triad Framework" los="BEA-1.3">

**Why interviewers ask this:** Google, Amazon, and Notion all run
production RAG systems and ask candidates to design evaluation pipelines
in system design rounds. Perplexity uses the triad as a core quality
signal. This question gates ML engineer and applied scientist roles
at L5+ because RAG evaluation is where most production systems fail.

**What they’re really testing:** Whether you can decompose
end-to-end RAG quality into independently measurable failure modes.
The meta-signal is *structured debugging*—can you pinpoint
*where* in the pipeline a bad answer originated (retrieval vs. generation vs. grounding) rather than just saying “the output is wrong.”

**Expected depth by level:**

- **IC3/IC4:** Name the three metrics, explain what each
  compares (response vs. query, context vs. query, response vs. context), and describe one failure mode per metric.

- **IC5+/Staff:** Discuss automated evaluation calibration
  (LLM-as-judge agreement rates), cost-accuracy tradeoffs of
  evaluation providers, and how triad scores feed into retrieval
  iteration loops. Reference record-level debugging.

**Red flag:** Evaluating RAG only on final answer quality without
decomposing into retrieval and grounding metrics. This signals a
candidate who cannot debug production failures systematically.

</InterviewContext>

| **Metric** | **What It Measures** | **Failure Mode** |
|:---|:---|:---|
| Answer Relevance | Response vs. Query | Off-topic or tangential answers |
| Context Relevance | Retrieved Context vs. Query | Irrelevant chunks retrieved |
| Groundedness | Response vs. Context | LLM uses pre-training knowledge |

The evaluation workflow for the baseline pipeline:

1.  Create a set of **evaluation questions** (the course provides
    10 pre-written questions, extensible with domain-specific queries).

2.  Initialize a **TruLens recorder** with the three RAG triad
    feedback functions.

3.  Run each query through the query engine while TruLens records
    inputs, outputs, intermediate context, and metric scores.

4.  Inspect results via notebook output or the
    **Streamlit dashboard**.

5.  Track different pipeline versions by changing the **app ID**.



```cypher
from trulens_eval import Feedback, TruLlama
from trulens_eval.feedback import OpenAI as TruLensOpenAI
import numpy as np

# Provider for evaluation
provider = TruLensOpenAI(model="gpt-3.5-turbo")  % freshness-ok
\warningmargin{gpt-3.5-turbo deprecated; use gpt-4o-mini for eval providers}

# Three feedback functions for the RAG triad
f_answer_relevance = Feedback(
    provider.relevance_with_cot_reasons, name="Answer Relevance"
).on_input().on_output()

f_context_relevance = Feedback(
    provider.qs_relevance_with_cot_reasons, name="Context Relevance"
).on_input().on(context_selection).aggregate(np.mean)

f_groundedness = Feedback(
    provider.groundedness_measure_with_cot_reasons, name="Groundedness"
).on(context_selection).on_output().aggregate(np.mean)

# Record and evaluate
tru_recorder = TruLlama(
    query_engine, app_id="baseline_rag",
    feedbacks=[f_answer_relevance, f_context_relevance, f_groundedness]
)

eval_questions = [
    "What are steps to take when finding projects?",
    "How can altruism be beneficial in building a career?",
    # ... 10 total evaluation questions
]

for question in eval_questions:
    with tru_recorder as recording:
        response = query_engine.query(question)
```





<Sidenote category="warning">Always use chain-of-thought reasoning variants (`relevance_with_cot_reasons`) for feedback functions. They provide interpretable justifications, not just scores.</Sidenote>



# Baseline Results and the Context Relevance Bottleneck

<ConceptBox>

**The Central Insight.**
The baseline RAG pipeline shows decently high answer relevance and
groundedness, but **notably low context relevance**. This tells us
the retrieval step is the primary bottleneck—the LLM is capable of
generating good answers *if* it receives relevant context.

</ConceptBox>

When context relevance is low, the LLM compensates by drawing on its
pre-training knowledge. This produces plausible-sounding responses that
are **not grounded** in the retrieved context—a subtle failure
that only systematic evaluation can detect.



<Sidenote category="crossref">Module 2 explains *why* context relevance drives the other metrics and how to diagnose failures at the record level.</Sidenote>



The two advanced techniques covered in Modules 3 and 4 both target
this context relevance bottleneck:

| **Dimension**     | **Sentence Window**           | **Auto-Merging**        |
|:------------------|:------------------------------|:------------------------|
| Retrieval unit    | Individual sentences          | Leaf nodes (128 tokens) |
| Context expansion | Surrounding window (metadata) | Parent node merging     |
| Strength          | Contiguous context            | Non-contiguous context  |
| Key parameter     | Window size                   | Hierarchy depth         |

# Chapter Summary

A production-ready RAG system requires both effective retrieval and
systematic evaluation. The three-stage pipeline (ingestion, retrieval,
synthesis) provides the structural foundation, while the RAG triad
(answer relevance, context relevance, groundedness) provides the
evaluation framework. Baseline evaluation reveals context relevance
as the primary bottleneck—the LLM generates plausible but ungrounded
responses when retrieval quality is poor. Sentence-window and auto-merging
retrieval address this bottleneck through different mechanisms: expanded
context windows and hierarchical merging, respectively. Experiment tracking
with versioned app IDs enables systematic comparison across techniques,
ensuring that every change is evaluated before promotion.

<KeyConcept title="Context Relevance as the Primary Bottleneck" los="BEA-1.5">

**Core Insight:** When retrieval fails to find relevant context, the LLM
compensates using pre-training knowledge, producing plausible but *ungrounded*
answers. Low context relevance is the root cause; low groundedness is the symptom.

**Why It Matters:** Fixing retrieval quality cascades into groundedness
improvement without changing the synthesis step. This diagnostic pattern—fix
retrieval first, then evaluate synthesis—is the standard RAG debugging workflow.

**When It Breaks:** The cascade reverses when context is *too* relevant
(oversized chunks): the LLM gets overwhelmed and falls back on pre-training
knowledge despite having the right context. There is an optimal retrieval
granularity, not a monotonic more-is-better relationship.

</KeyConcept>

<Problem title="RAG Triad Diagnosis" los="BEA-1.5">

You evaluate a baseline RAG system on 10 questions. Results: Answer
Relevance  = 0.82, Context Relevance  = 0.51, Groundedness  = 0.64.
Rank the three metrics by priority for improvement and explain why.

</Problem>

<Solution>

**Approach:**
**Priority:** Context Relevance (0.51) → Groundedness (0.64) →
Answer Relevance (0.82).

**Reasoning:** Context relevance is the bottleneck—the retrieval system
returns mostly irrelevant chunks. The LLM compensates by drawing on pre-training
knowledge, which explains why groundedness is mediocre (0.64): answers contain
claims not supported by retrieved context. Answer relevance is already acceptable
(0.82) because the LLM produces on-topic responses regardless of context quality.

**Key Insight:** Improving context relevance will cascade into groundedness
improvement without changing the synthesis step. Fixing answer relevance first
would mask the underlying retrieval problem.

**Answer:** Improving context relevance will cascade into groundedness
improvement without changing the synthesis step. Fixing answer relevance first
would mask the underlying retrieval problem.

</Solution>

<Problem title="Document Merging for Advanced Retrieval" los="BEA-1.2">

A 41-page PDF is ingested for a RAG system. Each page is loaded as a separate
object. Explain why merging all pages into a single document
before chunking is critical for sentence-window retrieval. What specific failure
occurs without merging?

</Problem>

<Solution>

**Approach:** Sentence-window retrieval expands each retrieved sentence with
its surrounding context (the “window”). If pages are stored as separate documents,
sentences at page boundaries cannot access context from the adjacent page.

**Failure mode:** A sentence at the end of page 12 has window context only
from page 12. The related continuation on page 13 is inaccessible. This creates
artificial context boundaries that degrade retrieval quality for cross-page topics.

**Key Insight:** Merging pages into a single document ensures that the
sentence-window parser treats the entire PDF as continuous text, enabling windows
to span page boundaries seamlessly.

**Answer:** Merging pages into a single document ensures that the
sentence-window parser treats the entire PDF as continuous text, enabling windows
to span page boundaries seamlessly.

</Solution>

<Problem title="Chunking Strategy Impact on RAG Triad" los="BEA-1.2">

You ingest a 200-page technical manual using three chunking strategies:
(A) 128-token chunks, (B) 512-token chunks, (C) 2048-token chunks. For
each, predict the relative RAG triad scores (high/medium/low) for the query
“What is the maximum operating temperature?” where the answer is a single
sentence on page 47. Explain your reasoning.

</Problem>

<Solution>

**Approach:**
**Strategy A (128-token chunks):**

- Context Relevance: **High**—the small chunk containing the temperature
  sentence produces a precise embedding that matches the query closely.

- Groundedness: **Medium**—the retrieved chunk has the exact answer but
  lacks surrounding context (e.g., conditions, caveats), so the LLM may supplement
  with pre-training knowledge.

- Answer Relevance: **High**—the answer is directly about operating
  temperature.

**Strategy B (512-token chunks):**

- Context Relevance: **Medium-High**—the chunk embedding averages over
  ∼4 paragraphs, diluting precision but still matching if the surrounding
  text is related.

- Groundedness: **High**—the chunk provides enough surrounding context
  for the LLM to ground its answer fully.

- Answer Relevance: **High**.

**Strategy C (2048-token chunks):**

- Context Relevance: **Low-Medium**—the embedding averages over
  ∼2 pages, making it less discriminative. The chunk may not rank in top-K.

- Groundedness: **High if retrieved**—but retrieval is the bottleneck.

- Answer Relevance: **Medium**—the LLM may extract the answer but could
  also get distracted by unrelated content in the oversized chunk.

**Key Insight:** This is the embedding–synthesis tension. Strategy B is the
typical sweet spot for baseline RAG. Advanced techniques (sentence-window,
auto-merging) exist precisely to get Strategy A’s precision with Strategy C’s context.

**Answer:** This is the embedding–synthesis tension. Strategy B is the
typical sweet spot for baseline RAG.

</Solution>
