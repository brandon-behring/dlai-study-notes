# Feedback Functions: The Core Abstraction



<Sidenote category="interview">"How do you evaluate a RAG system?" is the question that separates practitioners from tutorial-followers. Lead with the feedback function abstraction.</Sidenote>



Anupam Datta introduces feedback functions as the fundamental building
block of RAG evaluation. A **feedback function** provides a score
on a scale of **0 to 1** after reviewing an LLM app’s inputs,
outputs, and intermediate results.



<Term name="Feedback Function" los="BEA-2.1">
  A programmatic evaluation that produces a 0–1 score for an LLM application. Every feedback function has two components: a **provider** (the evaluation model) and a **function definition** (the evaluation logic, input selectors, and aggregation method).
</Term>
<AnkiCard type="term" front={"Feedback Function"} back={"A programmatic evaluation that produces a 0–1 score for an LLM application. Every feedback function has two components: a **provider** (the evaluation model) and a **function definition** (the evaluation logic, input selectors, and aggregation method)."} los="BEA-2.1" />



Every feedback function has two key components:

## 1. Provider

The underlying model used to implement the evaluation. The course uses
**OpenAI GPT-3.5 Turbo**, but feedback functions can be implemented
with any evaluation backend:

- **LLM providers**: GPT-4, Claude, open-source models

- **BERT-class models**: Smaller, faster, deterministic

- **Traditional NLP metrics**: ROUGE<Citation src="lin2004rouge" />, BLEU<Citation src="papineni2002bleu" /> scores

- **Human evaluations**: Gold-standard but expensive

- **Ground truth comparisons**: Exact or fuzzy matching



<Term name="Provider" los="BEA-2.1">
  The underlying evaluation model in a feedback function. Determines the quality and cost of the evaluation. LLM providers are most common for semantic evaluation; traditional NLP metrics are used for syntactic comparisons.
</Term>
<AnkiCard type="term" front={"Provider"} back={"The underlying evaluation model in a feedback function. Determines the quality and cost of the evaluation. LLM providers are most common for semantic evaluation; traditional NLP metrics are used for syntactic comparisons."} los="BEA-2.1" />



## 2. Function Definition

The specific evaluation logic, including:

- A **human-readable name** displayed in dashboards and logs

- **Input selectors** pointing to the relevant parts of the
  app’s execution (prompt, response, intermediate context)

- Optional **chain-of-thought reasoning** for score justification

- An **aggregation method** (e.g., mean) when multiple
  sub-scores exist



<Sidenote category="pattern">The feedback function pattern generalises beyond the RAG triad. You can define custom feedback functions for any property: toxicity, factual accuracy, formatting compliance, tone, etc.</Sidenote>



# Answer Relevance

<KeyConcept title="Answer Relevance" los="BEA-2.2">

Answer relevance checks whether the **final response** is relevant
to the **user’s query**. It uses only two inputs—the query and
the response—making it the simplest of the three RAG triad metrics.

**Example:**

- **Query**: “How can altruism be beneficial in building a career?”

- **Response**: \[detailed response about altruism and career benefits\]

- **Score**: 0.9 (highly relevant)

- **CoT**: “The response directly addresses career benefits of
  altruism with specific examples…”

**When It Breaks:** A high answer relevance score does not guarantee
correctness—only topicality. The response can be on-topic but entirely
fabricated. Groundedness is needed to verify factual support.

</KeyConcept>



```cypher
from trulens_eval import Feedback
from trulens_eval.feedback import OpenAI as TruLensOpenAI

provider = TruLensOpenAI(model="gpt-3.5-turbo")  % freshness-ok
\warningmargin{gpt-3.5-turbo deprecated; use gpt-4o-mini}

# Answer relevance: compares query (input) to response (output)
f_qa_relevance = Feedback(
    provider.relevance_with_cot_reasons,
    name="Answer Relevance"
).on_input().on_output()
# on_input()  -> selects the user prompt
# on_output() -> selects the final response
```





<Sidenote category="warning">A high answer relevance score does *not* mean the answer is correct—only that it is *on topic*. Groundedness is needed to verify factual support.</Sidenote>



# Context Relevance

<KeyConcept title="Context Relevance" los="BEA-2.2">

Context relevance evaluates the **retrieval step**: given a query,
how relevant is each piece of retrieved context? Unlike answer relevance,
context relevance accesses **intermediate results**—the retrieved
chunks that the user never sees directly.

**Example:**

- **Query**: “How can altruism be beneficial in building a career?”

- **Context 1**: Score 0.5 (partially relevant)

- **Context 2**: Score 0.7 (more relevant)

- **Mean context relevance**: 0.6

**When It Breaks:** Mean aggregation hides bimodal distributions—five
perfect chunks and five irrelevant ones still average to 0.5. Inspect
per-chunk scores, not just the aggregate, to detect retrieval failures.

</KeyConcept>



<Term name="Context Selection" los="BEA-2.2">
  A TruLens input selector that extracts the intermediate context chunks from a RAG pipeline's execution trace. Enables feedback functions to evaluate retrieval quality by accessing data that is not part of the final output.
</Term>
<AnkiCard type="term" front={"Context Selection"} back={"A TruLens input selector that extracts the intermediate context chunks from a RAG pipeline's execution trace. Enables feedback functions to evaluate retrieval quality by accessing data that is not part of the final output."} los="BEA-2.2" />



Each retrieved chunk is scored individually, then scores are
**averaged** to produce the final aggregate score:



```cypher
import numpy as np

# Context relevance: compares query (input) to each retrieved chunk
f_context_relevance = Feedback(
    provider.qs_relevance_with_cot_reasons,
    name="Context Relevance"
).on_input().on(
    context_selection  # selects each retrieved context chunk
).aggregate(np.mean)   # average across all chunks
```



<ConceptBox>

**Key Difference from Answer Relevance.**
Context relevance uses **intermediate results** (the retrieved
chunks), not just the final output. This demonstrates the full power
of feedback functions—they can access inputs, outputs, *and*
intermediate results at any point in the execution pipeline.

</ConceptBox>



<Sidenote category="interview">Context relevance is the most actionable metric in the RAG triad. If it is low, you know exactly what to fix: the retrieval strategy. The other two metrics are consequences.</Sidenote>



# Groundedness

<KeyConcept title="Groundedness" los="BEA-2.2">

Groundedness checks whether each **statement in the final response**
is supported by the **retrieved context**. It is the metric that
directly measures hallucination risk.

**When It Breaks:** Groundedness can score high by coincidence when
the LLM’s pre-training knowledge happens to overlap with irrelevant
retrieved context. Cross-check against context relevance—high
groundedness with low context relevance is a red flag for a weak evaluator.

</KeyConcept>



<Term name="Groundedness" los="BEA-2.3">
  The degree to which an LLM's response is supported by the retrieved context. Measured by decomposing the response into individual statements and checking each against the context for supporting evidence. Low groundedness indicates the LLM is relying on pre-training knowledge.
</Term>
<AnkiCard type="term" front={"Groundedness"} back={"The degree to which an LLM's response is supported by the retrieved context. Measured by decomposing the response into individual statements and checking each against the context for supporting evidence. Low groundedness indicates the LLM is relying on pre-training knowledge."} los="BEA-2.3" />



The groundedness evaluation follows a four-step process:

1.  The final response is broken into individual **statements**

2.  Each statement is checked against the retrieved context for
    **supporting evidence**

3.  Statements with supporting evidence get high scores; those
    relying on the LLM’s pre-training knowledge get low scores

4.  Scores are **aggregated** (averaged) across all statements

## Example of a Failure Mode

<NarrativeBox title="Diagnosing Ungrounded Statements">

**Query**: “How can altruism be beneficial in building a career?”

**Statement**: “Additionally, practicing altruism can contribute to
personal fulfillment and a sense of purpose…”

**Score**: Low—while plausible, no supporting evidence was found in
the retrieved context. The LLM drew on its **pre-training knowledge**
rather than the supplied context.

**Diagnosis**: This is not a “wrong” answer—it is an
*ungrounded* answer. The LLM is making up reasonable-sounding
claims that happen not to be supported by the evidence.

</NarrativeBox>



```cypher
# Groundedness: compares retrieved context to final response
f_groundedness = Feedback(
    provider.groundedness_measure_with_cot_reasons,
    name="Groundedness"
).on(
    context_selection  # retrieved context as evidence
).on_output().aggregate(np.mean)
```



# Why Context Relevance Drives Everything

<ConceptBox>

**The Cascade Effect.**
Context relevance is typically the first metric to optimise. When it
improves, groundedness often follows. But the relationship is not
monotonic—there is an optimal range.

</ConceptBox>

| **Context Relevance** | **Effect on Groundedness** | **Explanation** |
|:---|:---|:---|
| Low | Tends to be low | LLM fills gaps with pre-training knowledge |
| Increasing | Tends to increase | LLM has sufficient context to stay grounded |
| Too high (oversized) | May decrease | LLM gets overwhelmed, falls back on pre-training |

This cascade effect explains why the two advanced retrieval techniques
(sentence window, auto-merging) focus on improving context relevance.
They do not directly modify the LLM’s synthesis behaviour—they give
the LLM better raw material to work with.



<Sidenote category="crossref">Module 3 demonstrates this cascade quantitatively: window size 3 improves context relevance from 0.57 to 0.9, and groundedness follows from low to 1.0.</Sidenote>

# Types of Evaluation Approaches

| **Approach** | **Strengths** | **Weaknesses** |
|:---|:---|:---|
| Ground truth evals | High confidence; good starting point | Expensive to collect; hard to scale |
| Human evals | Meaningful, real-world signal | Hard to scale; ∼80% inter-rater agreement |
| LLM evals | Scalable; programmatic; ∼80–85% agreement with humans | Dependent on evaluation model quality |
| Traditional NLP (ROUGE, BLEU) | Fast; deterministic | Syntactic only; “river bank” vs. “financial bank” |

<NarrativeBox title="Evaluation Provider Too Weak">

If feedback function scores seem inconsistent or the CoT reasoning
contains obvious errors, the evaluation provider may be too weak
for your domain. **Symptoms:**

- Groundedness scores of 1.0 for clearly ungrounded statements

- CoT reasoning that contradicts the assigned score

- Context relevance scores that do not change when retrieval
  strategy changes

**Fix:** Upgrade the evaluation provider (e.g., GPT-3.5 →
GPT-4) or use a domain-specific evaluation model. Verify by manually
scoring 10 records and comparing with the automated scores.

</NarrativeBox>

# Chain-of-Thought Reasoning in Evaluations

<ConceptBox>

**Why CoT Matters for Evaluation.**
Chain-of-thought reasoning in feedback functions does not just improve
accuracy—it provides **interpretable justifications** for every
score. When a context relevance score is 0.3, the CoT explains
*why*: “The retrieved passage discusses project management but
the query asks about career-building through altruism.”

</ConceptBox>



<Term name="Chain-of-Thought Evaluation" los="BEA-2.8">
  A feedback function variant that produces step-by-step reasoning before assigning a score. The reasoning is logged alongside the score, enabling human reviewers to understand and verify the evaluation. Indicated by the `_with_cot_reasons` suffix in TruLens.
</Term>
<AnkiCard type="term" front={"Chain-of-Thought Evaluation"} back={"A feedback function variant that produces step-by-step reasoning before assigning a score. The reasoning is logged alongside the score, enabling human reviewers to understand and verify the evaluation. Indicated by the `_with_cot_reasons` suffix in TruLens."} los="BEA-2.8" />



The CoT reasoning is logged with every record in TruLens, making it
accessible through both the notebook API and the Streamlit dashboard.
This transforms evaluation from “a number happened” into
“here is why this number happened.”

# The Iterative Evaluation Workflow

<PipelineBox title="Workflow: Evaluate and Iterate">

1.  **Start with basic RAG** — Evaluate with the RAG triad.
    Establish baseline metrics.

2.  **Identify failure modes** — Focus on context relevance
    (the most common bottleneck). Drill down to individual records.

3.  **Apply advanced retrieval** — Switch to sentence-window
    or auto-merging retrieval. Re-evaluate with a new app ID.

4.  **Check for improvements** — Compare metrics in the
    leaderboard. Focus on context relevance and groundedness.

5.  **Tune hyperparameters** — Experiment with window size,
    chunk sizes, top-K, re-ranker top-N. Track every variant.

6.  **Repeat** — Evaluation is never “done.” Each
    improvement may reveal new failure modes at the record level.

</PipelineBox>

- **Yes**  

- **No—context relevance is high**

- **Yes**  

- **No—groundedness is also high**

- **Yes**  

- **No—all three metrics are high**  

</DecisionTree>

# Chapter Summary

The RAG triad (answer relevance, context relevance, groundedness) provides
a systematic framework for evaluating every critical step of a RAG
pipeline’s execution. Feedback functions are the core abstraction: they
score LLM app quality on a 0–1 scale using inputs, outputs, and
intermediate results. Context relevance is the primary lever—when
retrieval quality improves, groundedness typically follows, because the
LLM no longer needs to compensate with pre-training knowledge.
Chain-of-thought reasoning in evaluations provides interpretable
justifications, not just numbers. LLM-based evaluations achieve 80–85%
agreement with human evaluators, making them a practical and scalable
alternative. The evaluation workflow is iterative: evaluate, identify
failure modes at the record level, improve retrieval, re-evaluate.

<KeyConcept title="Feedback Functions: The Universal Evaluation Pattern" los="BEA-2.1">

**Core Insight:** Every TruLens feedback function follows the same pattern:
provider (the LLM doing evaluation), function definition (what to score), input
selectors (, ) that route pipeline data to the
scorer, and aggregation (how to combine per-chunk scores). This pattern scales
from the RAG triad to any custom evaluation.

**Why It Matters:** Once you understand the four-component pattern, you can
create feedback functions for toxicity, domain compliance, factual accuracy, or
any other property—not just the three standard RAG metrics. The abstraction is
the reusable skill.

**When It Breaks:** Feedback functions are only as good as their provider.
GPT-3.5 may over-score groundedness (false positives). Chain-of-thought variants
improve accuracy but increase latency and cost by 2–3×. Always calibrate
against human judgments on a small sample.

</KeyConcept>

reducing the need for pre-training compensation.

(same LLM, same prompt). This confirms that low groundedness was a *symptom*
of poor retrieval, not a synthesis problem. Fix retrieval first, always.

<Problem title="Evaluation Provider Selection" los="BEA-2.5">

Compare LLM-based evaluation (GPT-4) vs. human evaluation for a RAG
system serving medical information. LLM evaluators achieve 80–85%
agreement with humans. Should you use LLM evaluation, human evaluation,
or both? Justify your answer.

</Problem>

<Solution>

**Approach:**
**Answer:** Both, in a calibrated pipeline.

**Reasoning:** 80–85% agreement is comparable to inter-annotator agreement
among humans, making LLM evaluation reliable for *most* queries. However,
medical RAG has high stakes—incorrect information can cause harm.

**Recommended approach:**

1.  Use LLM evaluation for all queries (scalable, fast, cheap)

2.  Flag responses where any metric scores  &lt; 0.7 for human review

3.  Use human evaluation on a 5% random sample for calibration

4.  Compare LLM vs. human scores monthly to detect evaluation drift

**Key Insight:** LLM evaluation scales; human evaluation validates. Neither
alone is sufficient for high-stakes domains.

</Solution>

<Vignette title="RAG Evaluation Pipeline for Production">

\[BEA-2.1, BEA-2.4\]
A fintech startup deploys a RAG system over SEC filings for investor queries.
After launch, support tickets report “plausible but wrong” answers about company
financials. The engineering team runs TruLens evaluation on 50 production queries:

| **Metric**        | **Mean Score** | **% Below 0.5** |
|:------------------|:--------------:|:---------------:|
| Answer Relevance  |      0.91      |       2%        |
| Context Relevance |      0.43      |       58%       |
| Groundedness      |      0.52      |       44%       |

**Question 1:** What is the root cause of the “plausible but wrong” answers?
Which metric confirms this?

**Question 2:** The team proposes adding a disclaimer: “This answer may not
be accurate.” Evaluate this approach from a product and engineering perspective.

**Question 3:** Propose a two-phase improvement plan. What metrics would you
track to know each phase succeeded?

</Vignette>

<Solution>

**Approach:**
**Q1:** Context relevance (0.43, 58% below threshold) is the root cause.
The retrieval system fails to find relevant SEC filing passages, so the LLM
draws on pre-training knowledge about companies—producing plausible but
ungrounded answers. Groundedness (0.52) confirms: nearly half of response
claims lack support in retrieved context.

**Q2:** The disclaimer is a band-aid, not a fix. From a product perspective,
users will lose trust quickly—“plausible but wrong” with a disclaimer is worse
than no answer. From engineering, the retrieval system is fundamentally broken
(58% of queries return irrelevant context). Fix the retrieval, don’t disclaim it.

**Q3:**

1.  **Phase 1 — Retrieval improvement:** Implement sentence-window
    retrieval (window=3) with re-ranking. Target: Context Relevance  &gt; 0.80,
    Groundedness  &gt; 0.85 (cascade effect).

2.  **Phase 2 — Synthesis guardrails:** Add a “refuse to answer” policy
    when context relevance  &lt; 0.5 for a query. Target: % below-threshold
    responses  &lt; 5%.

**Key Insight:** Low context relevance is the root cause of poor RAG performance—fix retrieval first. Disclaimers are bandaids that signal retrieval failure, not solutions.

**Answer:** Context relevance (0.43) is the root cause. Fix retrieval: add financial-domain embeddings, hybrid search, and SEC-specific chunking. The disclaimer signals retrieval failure and should be replaced by a citation mechanism.

</Solution>

<Problem title="Anomalous Metric Pattern Diagnosis" los="BEA-2.3">

A RAG system produces the following scores on a single record: Answer
Relevance  = 0.92, Context Relevance  = 0.35, Groundedness  = 0.88. This
pattern is anomalous—explain why high groundedness with low context relevance
is suspicious. What is the most likely explanation?

</Problem>

<Solution>

**Approach:**
**Why it is anomalous:** The expected cascade is: low context relevance
→ LLM compensates with pre-training → low groundedness. High groundedness
