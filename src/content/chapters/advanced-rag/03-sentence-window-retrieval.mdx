# The Embedding–Synthesis Tension



<Sidenote category="interview">"What is the fundamental tradeoff in RAG chunk sizing?" is a common screen question. The answer is: embedding precision vs. synthesis context.</Sidenote>



&lt;!–MDXB-9-OPEN–&gt;

**The Core Problem.**
Standard RAG uses the *same text chunk* for both embedding and
synthesis. But the optimal sizes are different:

- **Embedding-based retrieval** works best with
  **smaller chunks**—more precise semantic matching,
  less noise.

- **LLM synthesis** needs **larger chunks**—more
  surrounding context to generate coherent, comprehensive answers.

Sentence-window retrieval **decouples** these two concerns,
using small units for retrieval and large units for synthesis.

&lt;!–MDXB-9-CLOSE–&gt;

Resolved by decoupling the retrieval unit from the synthesis unit through techniques like sentence-window and auto-merging retrieval.

# How Sentence-Window Retrieval Works

&lt;!–MDXB-10-OPEN–&gt;

1.  **Parse** — Split the document into individual
    **sentences**. Each sentence becomes a node.

2.  **Augment** — Store surrounding sentences (the
    “window”) as **metadata** on each node.

3.  **Embed & Index** — Embed and index the
    **sentence-level nodes** (small, precise).

4.  **Retrieve** — Fetch the top-K most similar
    sentence nodes via similarity search.

5.  **Replace & Synthesise** — **Replace** each
    retrieved sentence with its full surrounding window from
    the metadata, then feed the expanded context to the LLM.

&lt;!–MDXB-10-CLOSE–&gt;



<Sidenote category="pattern">The pattern: retrieve on fine-grained units for precision, expand to coarse-grained units for synthesis. This pattern appears in many IR systems beyond RAG.</Sidenote>



The intuition is straightforward: individual sentences are precise enough
to match semantically with the query, but the LLM needs the surrounding
context to generate a coherent, comprehensive answer. By storing the
window as metadata, we get both precision and context without any
compromise.

</Term>

Jerry Liu demonstrates the parser with a concrete example:



```cypher
from llama_index.node_parser import SentenceWindowNodeParser

# Window size 3: include 3 sentences before and after each sentence
node_parser = SentenceWindowNodeParser.from_defaults(window_size=3)
nodes = node_parser.get_nodes_from_documents([document])

# Each node contains:
# - text: a single sentence
# - metadata["window"]: the surrounding sentences
print(nodes[1].text)              # "Second sentence."
print(nodes[1].metadata["window"])
# "First sentence. Second sentence. Third sentence. Fourth sentence."
```



For a document with three sentences and window size 3, the parser
produces three nodes. Each node’s text is a single sentence, while the
metadata window contains the original sentence **plus** the
sentences before and after it (up to the window size limit).



<Sidenote category="warning">For edge nodes (first and last sentences), the window is asymmetric. The first node with window size 3 includes only the sentences *after* it, not before.</Sidenote>

The node parser transforms the source document into sentence-level nodes
with surrounding context metadata, embeds the sentence text (not the
window), and loads the embeddings into the vector store. The metadata is
preserved but not embedded—it is used only during the post-processing
step.

# Query Engine: Post-Processing and Re-Ranking

The sentence-window query engine uses two post-processors in sequence:

## 1. MetadataReplacementPostProcessor



<Term name="MetadataReplacementPostProcessor" los="BEA-3.4">
  A LlamaIndex post-processor that replaces each retrieved node's text with a value from its metadata. For sentence-window retrieval, it replaces the single-sentence text with the full surrounding context window, expanding the synthesis input.
</Term>
<AnkiCard type="term" front={"MetadataReplacementPostProcessor"} back={"A LlamaIndex post-processor that replaces each retrieved node's text with a value from its metadata. For sentence-window retrieval, it replaces the single-sentence text with the full surrounding context window, expanding the synthesis input."} los="BEA-3.4" />



After retrieval, this post-processor replaces each node’s text with the
expanded window context from its metadata. This is the core mechanism
that transforms fine-grained retrieval results into contextually rich
synthesis inputs.

## 2. SentenceTransformerRerank



<Term name="Re-Ranker" los="BEA-3.4">
  A model that takes the query and a set of retrieved nodes and re-orders them by relevance. Unlike embedding similarity (which compares vectors), a re-ranker performs cross-attention between query and document, producing more accurate relevance scores at higher computational cost.
</Term>
<AnkiCard type="term" front={"Re-Ranker"} back={"A model that takes the query and a set of retrieved nodes and re-orders them by relevance. Unlike embedding similarity (which compares vectors), a re-ranker performs cross-attention between query and document, producing more accurate relevance scores at higher computational cost."} los="BEA-3.4" />



A **re-ranker** takes the query and retrieved nodes and re-orders
them by relevance using a specialised cross-encoder model<Citation src="nogueira2019passage" />.
The workflow:

1.  Retrieve **top-K** nodes (larger set, e.g., K=6)

2.  Re-rank and filter to **top-N** (smaller set, e.g., N=2)

&lt;!–MDXB-11-OPEN–&gt;

**Why Re-Ranking Matters.**
Embedding similarity is fast but approximate—it compares query and
document *independently*. A re-ranker performs *cross-attention*
between query and document, producing more accurate relevance scores.

**Example:**

- Query: “I want a dog”

- Before re-ranking: “This is a cat” → score 0.6;
  “This is a dog” → score 0.4

- After re-ranking: “This is a dog” surfaced to top
  with a high relevance score

&lt;!–MDXB-11-CLOSE–&gt;

## Complete Query Engine



```cypher
from llama_index.postprocessor import (
    MetadataReplacementPostProcessor,
    SentenceTransformerRerank,
)

query_engine = sentence_index.as_query_engine(
    similarity_top_k=6,  # retrieve 6 candidates
    node_postprocessors=[
        MetadataReplacementPostProcessor(
            target_metadata_key="window"
        ),
        SentenceTransformerRerank(
            top_n=2,  # keep top 2 after re-ranking
            model="BAAI/bge-reranker-base"
        ),
    ],
)

response = query_engine.query(
    "What are steps to take when finding projects?"
)
```





<Sidenote category="practice">The top-K $$ top-N pattern (retrieve many, re-rank to few) is a general IR technique. Experiment with K=6–12 and N=2–4 to find the sweet spot for your documents.</Sidenote>



# Experimenting with Window Size



<Sidenote category="interview">"How would you tune a sentence-window RAG system?" **Answer:** systematically vary window size, evaluate with the RAG triad, and track the context-relevance–groundedness–cost tradeoff.</Sidenote>



Anupam Datta demonstrates the window-size tuning workflow:

1.  Start with **window size 1**

2.  Evaluate with the RAG triad

3.  Gradually increase the window size

4.  Track the tradeoffs between quality metrics and cost

| **Window Size** | **Context Relevance** | **Groundedness** | **Cost/Tokens** | **Verdict** |
|:---|:--:|:--:|:--:|:---|
| 1 (too small) | Low (0.57) | Low | Lower | Insufficient context |
| 3 (optimal) | High (0.90) | 1.0 | Moderate | Best balance |
| 5 (too large) | Flat | Drops | Higher | LLM overwhelmed |

# Window Size 1: Why Small Windows Fail

&lt;!–MDXB-12-OPEN–&gt;

With window size 1, only one extra sentence is added before and after
each retrieved sentence. On a representative question:

- **Context relevance**: 0.57—retrieved chunks are too
  small, missing critical information

- **Groundedness**: Low—the LLM leverages pre-training
  knowledge to fill the gaps

**Root cause**: The context window is too narrow to contain the
information needed for a complete, grounded answer.

&lt;!–MDXB-12-CLOSE–&gt;



<Term name="Pre-Training Compensation" los="BEA-3.6">
  The phenomenon where an LLM, given insufficient context, draws on its pre-training knowledge to generate plausible-sounding statements. These statements may be factually correct but are not grounded in the retrieved context, leading to low groundedness scores.
</Term>
<AnkiCard type="term" front={"Pre-Training Compensation"} back={"The phenomenon where an LLM, given insufficient context, draws on its pre-training knowledge to generate plausible-sounding statements. These statements may be factually correct but are not grounded in the retrieved context, leading to low groundedness scores."} los="BEA-3.6" />



When context relevance is low, the LLM compensates by drawing on its
**pre-training knowledge** rather than relying on the retrieved
context. This produces plausible responses that are not grounded—a
subtle failure that the RAG triad reveals clearly.

# Window Size 3: The Sweet Spot

&lt;!–MDXB-15-OPEN–&gt;

Switching to window size 3 for the same problematic question produces
dramatic improvements:

- **Context relevance**: jumped from 0.57 to **0.9**

- **Groundedness**: increased to **1.0**—the LLM
  can now find all supporting evidence in the retrieved context

- **Answer relevance**: remained high

The expanded window captures enough surrounding context for the
retrieved sentences to be fully relevant, and the LLM stays grounded
because it no longer needs to compensate with pre-training knowledge.

**When It Breaks:** The optimal window size is document-dependent.
Dense technical documents (patents, APIs) may peak at *w* = 1–2;
verbose narrative (court opinions, essays) may need *w* = 5–7.
Always tune empirically—there is no universal “best” window size.

&lt;!–MDXB-15-CLOSE–&gt;

# Window Size 5: When Bigger Is Not Better

&lt;!–MDXB-13-OPEN–&gt;

Increasing to window size 5:

- **Context relevance** and **answer relevance**:
  remained flat—no improvement

- **Groundedness**: **dropped**—the LLM gets
  overwhelmed by oversized context and starts introducing
  pre-training knowledge

- **Total tokens**: increased (higher cost, higher latency)

**Root cause**: Excessive context dilutes the relevant information,
and the LLM falls back on familiar patterns from pre-training.

&lt;!–MDXB-13-CLOSE–&gt;



<Sidenote category="warning">Larger windows are not always better. There is an optimal range for every document type and query pattern. Always evaluate systematically rather than assuming "more context = better."</Sidenote>





<Sidenote category="interview">"What happens if you set window size too large?" **Answer:** context dilution overwhelms the LLM, groundedness drops, and token cost increases—a non-monotonic quality curve.</Sidenote>



This demonstrates the non-monotonic relationship between context size
and quality that Anupam Datta highlighted in Module 2: context relevance
and groundedness improve with more context *up to a point*, then
degrade when the LLM is overwhelmed.

# Putting It All Together

Jerry Liu encapsulates the complete pipeline in two high-level functions:



```cypher
def build_sentence_window_index(
    document, llm, embed_model, save_dir, window_size=3
):
    """Build a sentence-window vector index.

    1. SentenceWindowNodeParser with specified window size
    2. ServiceContext with LLM, embedding model, node parser
    3. VectorStoreIndex from documents with persistence
    """
    node_parser = SentenceWindowNodeParser.from_defaults(
        window_size=window_size
    )
    service_context = ServiceContext.from_defaults(
        llm=llm, embed_model=embed_model, node_parser=node_parser
    )
    index = VectorStoreIndex.from_documents(
        [document], service_context=service_context
    )
    index.storage_context.persist(persist_dir=save_dir)
    return index


def get_sentence_window_query_engine(
    index, similarity_top_k=6, rerank_top_n=2
):
    """Create a query engine with metadata replacement and re-ranking.

    1. MetadataReplacementPostProcessor for window expansion
    2. SentenceTransformerRerank for relevance filtering
    3. Query engine combining both post-processors
    """
    postproc = MetadataReplacementPostProcessor(
        target_metadata_key="window"
    )
    rerank = SentenceTransformerRerank(
        top_n=rerank_top_n, model="BAAI/bge-reranker-base"
    )
    return index.as_query_engine(
        similarity_top_k=similarity_top_k,
        node_postprocessors=[postproc, rerank],
    )
```

# Chapter Summary

Sentence-window retrieval solves the fundamental embedding–synthesis
tension in RAG by decoupling the two concerns: embed individual sentences
for precision, then expand to surrounding context windows for synthesis.
The SentenceWindowNodeParser splits text into sentence nodes with window
metadata; the MetadataReplacementPostProcessor expands them at query time;
and a re-ranker filters the initial candidates to the most relevant.
Window size is the critical hyperparameter: too small causes low context
relevance and groundedness (LLM compensates with pre-training knowledge);
too large overwhelms the LLM. For the course evaluation setup, window
size 3 was optimal across all RAG triad metrics, producing a 33-percentage-point
improvement in context relevance over window size 1.

&lt;!–MDXB-16-OPEN–&gt;

**Core Insight:** Sentence-window retrieval resolves the fundamental RAG
tradeoff by embedding individual sentences (small, precise for matching) but
synthesising with expanded windows (large, rich for LLM context). Retrieval
granularity and synthesis granularity are independent design choices.

**Why It Matters:** Standard RAG uses the same chunk for both embedding and
synthesis—a forced compromise. Sentence windows break this coupling: embed at
sentence level for precision, expand to ±*k* sentences for context. This
pattern generalises beyond RAG to any retrieve-then-process pipeline.

**When It Breaks:** The expansion is *contiguous only*—it cannot
capture relevant information scattered across distant sections. For documents with
non-adjacent relevant passages (e.g., contracts with clauses referencing
appendices), auto-merging retrieval is more appropriate.

&lt;!–MDXB-16-CLOSE–&gt;

&lt;!–MDXB-17-OPEN–&gt;

**Why interviewers ask this:** Notion, Perplexity, and Google
Search teams ask “How would you improve retrieval quality in a RAG
system?” in nearly every ML engineer loop. The sentence-window
pattern is the most common first optimization applied to production
RAG pipelines and signals practical experience vs. textbook knowledge.

**What they’re really testing:** Whether you recognize that
embedding granularity and synthesis granularity are *independent
design choices*. The meta-signal: can you articulate the fundamental
tradeoff (small chunks = precise matching but thin context; large
chunks = rich context but noisy matching) and then explain how
sentence windows break this coupling?

**Expected depth by level:**

**Red flag:** Proposing to “just use bigger chunks” without
