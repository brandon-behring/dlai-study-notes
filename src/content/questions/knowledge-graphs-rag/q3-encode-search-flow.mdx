answer: >
  Four stages: encode — turn the user's question into a vector with the same embedding model
  that produced the stored vectors; search — `db.index.vector.queryNodes` finds the top-K nodes
  whose vectors are nearest the query vector; score — each result carries a cosine similarity
  (0–1), higher = closer; return — the matched nodes' text and metadata become the LLM's context.
  The one consistency rule that makes it work: query and corpus must be embedded by the *same*
  model into the *same* space. Parameterise the question, key, and topK so the plan caches and
  secrets stay out of the string. Common wrong answer: embedding the query with a different model
  than the stored text — the vectors then live in different spaces and the scores are noise.
